AWS 开源 Pizza Bot，给后台 AI 发了个收件箱

这是什么：AWS 在官方开源博客上发布了 Pizza Bot，一个自托管的开源收件箱，专门接收在后台替用户干活的 AI Agent 交回来的活。干完的成果进 Unread 栏等用户过目，需要审批或者需要回答的任务进 Action 栏暂停等待，All 栏保留全部线程历史。代码以 Apache 2.0 许可开源，提供 macOS、Windows、Linux 桌面安装包和浏览器、终端客户端，后端可本地跑也可独立部署。早期版本在 Amazon 内部服务过 2000 多人。
🔥 为什么今天值得看：后台 Agent 能干多少活，取决于人不在场时任务能推进多远，卡点集中在交接和审批上。Pizza Bot 把线程历史、待查看成果、待审批请求装进一个邮箱式的界面，任务由服务端持有，客户端断开也不中断，审批动作还能按工具配置。加上 Apache 2.0 许可和自托管部署，开发者可以把它改造成自己团队的后台任务基础设施，不必绑定某家云服务。
展开正文

让 AI Agent 在后台替你干活，最难的一步往往在交接。任务可能要跑几个小时，活干完了你人不在，需要批准的时候找不到人，等你想起来去看，结果散落在各个窗口和对话里。AWS 本周在官方开源博客上发布了 Pizza Bot，The New Stack、Techstrong、MarkTechPost 等媒体相继报道。这个项目长得像邮箱，把后台任务的结果和待决策统一收进来，代码以 Apache 2.0 许可开源，提供 macOS、Windows 和 Linux 的桌面安装包，另有浏览器和终端客户端，后端既可以跑在本地，也可以独立部署。

这个设计有内部来历。早期版本在 Amazon 内部服务过 2000 多人，用过的场景包括会议准备、邮件起草、Slack 消息摘要、往 CRM 里记数据，以及各类研究工作。对外发布的版本重新构建成了开源项目。

收件箱分成三栏。All 放全部线程历史，Unread 放已经干完、等你过目的活，到了 Action，任务会暂停下来，等审批或者等你回答。用户可以把线程整理进文件夹，在 Activity 面板里查看分派出去的技能工人。任务可以手动启动，也可以用 cron 定时或者 webhook 触发。调度归服务端负责，宕机恢复之后，错过的定时区间只补跑一次，不会把错过的每一段都重放一遍。

运行时用 DeepAgents 和 LangGraph 做有状态执行，Hono API 服务端负责执行和存储，Electron 和浏览器客户端共享 React 界面，通过 HTTP 和服务器推送事件与服务端通信。LangGraph 的检查点会保留线程状态和审批暂停的现场，跨线程记忆和应用元数据放在独立的 SQLite 存储里，客户端断开重连之后可以回放缓冲的事件。关掉线程或者断开客户端，都不会停掉正在运行的服务端。

模型供应商不锁一家。Amazon Bedrock、Anthropic、Google Gemini、OpenAI、OpenRouter 都能接，本地模型可以走 Ollama，在 Settings > Providers 里配置好就能用。审批控制做得细，技能作者按工具配置 interruptOn 和 allowedDecisions，任务碰到要动敏感工具的节点会停下来，用户可以批准、修改提议的参数，或者直接拒绝。

限制也写得很清楚。退出桌面应用会停掉内嵌的服务端，正在跑的任务随之结束。检查点会把线程保住，进行中的那一步可能丢。想让任务长期在后台跑，需要一个常驻后端。

阿里开源 AI 代码评审工具，精度超 Claude Code

这是什么：阿里集团把内部用了两年的官方 AI 代码评审助手开源成项目 alibaba/open-code-review，一个用 AI 给代码挑毛病的命令行工具。项目 2026 年 5 月开源，目前 23.5k stars、1.7k forks，9 月 12 日发布 v1.12.0 版本，今天出现在 GitHub Trending 上。项目方在自建基准 AACR-Bench 上与 Claude Code 对比，同一底座模型下报出的缺陷更准，token 消耗约九分之一。
🔥 为什么今天值得看：拿 Claude Code 这类通用 agent 做代码评审的毛病很多人碰过，改动一大漏文件、行号对不上、提示词一动质量就抖。这个项目把不能出错的环节交给确定性工程代码，把动态判断交给大模型 agent，并用一个数据集公开的基准，把专用工具到底比通用 agent 强在哪变成了可以复核的数字。对想把 AI 加进代码评审环节的团队，这是一份现成的参考实现。
展开正文

今天出现在 GitHub Trending 上的 alibaba/open-code-review，是一个用 AI 给代码挑毛病的命令行工具，已经攒下 23.5k stars 和 1.7k forks。阿里在 2026 年 5 月把它开源，9 月 12 日刚发布了 v1.12.0 版本。

它的底子是阿里集团内部的官方 AI 代码评审助手，过去两年里服务了数万名开发者，识别出百万级代码缺陷。代码评审指程序员提交改动后，由其他人或工具逐行挑毛病。阿里在大规模内部验证之后把这个助手孵化成开源项目，采用 Apache-2.0 协议，配置一个模型端点就能跑。

现在不少人直接拿 Claude Code 这类通用 agent 干这活，README 总结了常见的翻车现场。改动一大，agent 容易挑着看，漏掉一部分文件；报出来的问题经常对不上行号。提示词稍微改几个字，评审质量又会跟着明显波动。阿里给出的诊断是，纯语言驱动的架构对评审过程缺少硬约束。

这个项目的做法是把评审流程拆成两半。不能出错的环节交给确定性的工程代码，包括精确选出该评审哪些文件、把相关文件捆绑成一个评审单元交给子 agent、按文件特征匹配内置规则，规则库覆盖 NPE（空指针异常）、线程安全、XSS（跨站脚本攻击）、SQL 注入等多语言缺陷类型。需要动态判断的环节交给大模型 agent，它可以读完整文件、搜索代码库、参考其他改动的文件，输出行级精准的评论。

效果用项目方自建的基准 AACR-Bench 衡量。基准从 50 个热门开源仓库里取了 200 个真实 Pull Request（一次公开的代码提交），覆盖 10 种编程语言，由 80 多位高级工程师交叉验证，标注出 1505 个真实缺陷作为标准答案，数据集放在 Hugging Face 上供人核对。对比采用同一底座模型，它的 Precision 和 F1 显著高于 Claude Code 等通用 agent，token 消耗只有约九分之一，完成评审也更快。Precision 衡量报出来的问题里真缺陷的比例，token 是模型按处理量计费的单位，直接对应 API 账单。Recall 这一项它低于通用 agent，真缺陷被找出来的比例更小。阿里明说这是刻意取舍，用查全率换精度，把误报压下来。

对想把 AI 加进代码评审环节的团队，这是一份可以直接取用的参考实现。工具兼容 OpenAI 和 Anthropic 的 API 端点，npm 一条命令装好，ocr review 就能评审当前改动。

长时运行 AI 代理会静默丢合规规则，扩大上下文也救不了

这是什么：VentureBeat 9 月 13 日刊出一篇客座评论，作者 Ankit Anand 是企业数据管理方向的管理顾问。文章讨论长时运行 AI 代理的一个治理风险，写进系统提示词的合规规则会在连跑数日的任务中段被挤出模型活跃记忆，任务不中断，告警不触发，合规缺口要等事后审计才暴露。作者判定扩上下文和加重 RAG 都无效，主张把业务逻辑移出生成层交给确定性规则引擎校验，并附三项可立即执行的整改动作。这是观点文章，没有新研究或新工具发布。
🔥 为什么今天值得看：AI 代理正从几分钟的演示走进连跑多日的生产任务，本期另外两条代理动态都在讲怎么让代理长跑，这条补上风险面，讲清长跑途中规则会怎么静默丢失。对管数据和管代理的团队，文章把失效点定位到架构层，给出的检查动作可以直接搬进本周排查。lost in the middle 属于研究界已有共识，这篇文章把共识压成面向数据基础设施管理者的行动框架，增量落在组织化的清单上。
展开正文

9 月 13 日，VentureBeat 刊出一篇署名 Ankit Anand 的客座评论，作者的身份是企业数据管理方向的管理顾问。文章一开头构造了一个故障现场。一个连跑多日的数据校验任务交给 AI 代理，第三天它已经吞进几千条记录，出发前写死在系统提示词里的治理规则此时已被挤出活跃记忆。系统照常运行，不崩溃，监控系统一条告警也不弹，它继续产出结果，只是不再理会那些被当作锁死的约束。几周后内部审计翻出合规缺口，团队往回追查，把根因定位在第 9 天，文章称那是模型忘掉规则的确切时刻。

作者把这种静默漂移定性为系统性架构失效，并判断常规 CI/CD 流水线和 QA 周期很少能抓住这种衰减。他引用的研究共识名为 lost in the middle。语言模型按注意力分配权重，输入的 token 序列涨到几十万，注意力被摊薄，埋在中段的内容最先被丢掉。试点环境里上下文短，规则贴着提示词，演示一切正常，规模一上来边界就守不住了，模型分不清哪些是可丢弃的对话记录，哪些是不可变的主数据规则。

两个流行修法被作者逐一排除。把上下文窗口扩到百万 token，注意力照样摊薄，失败只是被推迟，云成本先涨上去。加重 RAG（检索增强生成）同样救不了场，向量数据库擅长找语义相似的文本，没法强制状态持久化，模型执意忽略规则时，向量库拦不住它。

作者主张的修法是把企业业务逻辑当成受保护状态，物理放到文本生成层之外。神经网络负责推理，一层完全处于上下文窗口之外的确定性规则层负责符号逻辑。模型只出草稿，确定性引擎对照不可变规则校验通过后才提交动作。他称这套思路为神经-符号分离。这套架构目前停留在作者个人的主张层面，行业没有普遍采纳。

行动清单有三项，都标明本周可以动手。第一项做盘点，找出所有跨会话连跑数日的代理，要求工程团队拿出证据，证明系统会在第 4 天、第 10 天、第 30 天重新校验初始约束，拿不出证据的架构在他看来天生有漏洞。第二项针对合规边界，停止用自然语言提示词承载硬约束，把关键规则迁入确定性策略引擎，在 API 网关层对照硬编码逻辑校验模型输出，模型丢了规则，基础设施直接拦下动作。第三项落在编排层，凡是碰财务数据或主数据的任务，把代理的草稿内存和运行约束物理隔开，把模型的工作内存当临时数据，把治理规则当不可变状态。

文章结尾把矛头指向行业惯性。企业 AI 部署长期比拼生成速度，token 吞吐量和首响应时间被反复优化，作者认为撑住长期运行还需要结构完整性和确定性治理，忽视静默漂移的团队迟早要向监管解释，自己的 AI 为什么在第 9 天忘了规则。

开源音乐模型 YuE2，改歌如改谱，8 选优反超 Suno

这是什么：m-a-p 团队 2026 年 9 月 9 日在 HuggingFace 发布开源音乐生成模型 YuE2-3B，模型名标称 3B，HuggingFace 页面标注参数量 4B（BF16 精度）。输入歌词和一句风格描述，输出带人声与伴奏的完整歌曲，48kHz 立体声。在 192 个提示的 WildSongBench 基准上，按 8 次生成选最优的口径，SongBench 均分 6.9632，超过 Suno v5 的 6.8721 与 Suno v6 的 6.5562，在这张对比表的开源与闭源模型里排第一。它是 YuE 系列第二代，初代 YuE 发布于 2025 年 3 月。
🔥 为什么今天值得看：开源阵营的能力清单长期缺着完整歌曲生成这一项，能拿出来的开源选项与 Suno 分差明显，YuE2 在这张对比表的 SongBench 均分上把开源模型抬到全部已评测模型的第一位，条件是 8 选优口径，2 候选口径下仍低于 Suno v5。另一半价值在可编辑，生成前先产出 ABC 文本乐谱，旋律、和弦、风格、歌词都能分步修改，歌曲从一次性成品变成可迭代修改的文件。权重可下载，24GB 显卡可本地复现，完整分数表与评测协议随模型卡公开，这些数字任何人都能重新检验。
展开正文

m-a-p 团队 9 月 9 日在 HuggingFace 开源了音乐生成模型 YuE2-3B。开源歌曲生成追 Suno 追了一年多，这次的 WildSongBench 数据把比分翻了过来，开源模型第一次在这张对比表的 SongBench 均分上排到第一。在这份 192 个提示的评测里，YuE2 按每个提示生成 8 次再挑最优的口径，SongBench 均分 6.9632，超过 Suno v5 的 6.8721 和 Suno v6 的 6.5562，也超过开源阵营此前的最强成绩 LeVo 2 的 6.3247 与 ACE-Step 1.5 的 6.0118。同一张对比表里，2025 年 3 月发布的初代 YuE 均分只有 4.9165。

口径要先讲清。best-of-8 指同一提示生成 8 个候选，按音乐性、提示遵循度、发音错误率的优先级挑出最好的一首。常规口径是 2 个候选选 1，YuE2 在那个口径下均分 6.7316，仍排在 Suno v5 之后，反超只发生在 8 选优。每首候选的发音错误率取 4 次语音识别的最低值，对比数据更新到 9 月 12 日，共 17 组设置，模型卡把这些协议原样公开。

更大的变化在生成方式。YuE2 先写谱子再做音频，骨干是一套 AR-NAR Mixture-of-Transformers，自回归部分逐个符号地写出 ABC 记谱的乐谱和语义标记，非自回归部分并行生成音频的中间表示，再经 flow matching 生成声学潜变量，由 VAE 解码成 48kHz 立体声。ABC 是一种用纯文本记录旋律与和弦的记谱格式，规划分 full（旋律加和弦，默认）、melody（仅旋律）、off（关闭）三档，也可以直接喂进自己写好的 ABC 谱。

乐谱让改歌有了抓手。你可以手动改谱再重新渲染，也可以把乐谱、原始提示和歌词交给智能体，让它把修改意见转成乐谱、风格与歌词的变更，由 YuE2 渲染下一版。官方演示里一首叫 The Last Train 的中文流行歌走了 9 步、迭代 14 个版本，最后变成带现代和声与萨克斯独奏的英文爵士，独奏围绕两遍完整的 Twinkle, Twinkle, Little Star 展开。

翻唱方向给出了消融数字。SHS100K 零样本翻唱评测用 948 首作品乘两种风格、两种种子，每种方法生成 3792 首且不做候选挑选。带完整乐谱的 YuE2 保留原曲身份的 CLEWS mAP 为 0.647，SongEcho 是 0.419，ACE-Step 1.5 只有 0.024；去掉乐谱后 YuE2 自己掉到 0.006，翻唱能力主要来自那份符号乐谱。

工程数字同样具体。模型名标称 3B，HuggingFace 页面标注的参数量是 4B（BF16 精度），一张 RTX 4090 用 71 秒生成 3.6 分钟的歌曲，峰值显存约 11.2 GiB，24GB 显卡无需量化即可本地运行；H800 服务器配 vLLM 0.19，并发 32 时吞吐 373.53 首/小时。配套发布了解码器 YuE2-Vae（默认，听感更好）、YuE2-Vae-legacy（复现基准用）和转谱工具 SheetSage2，翻唱流程还可搭配 Qwen3-ASR 提取歌词。权重采用 CC BY-NC 4.0 非商业许可，技术报告标注即将发布，引用暂时指向初代 YuE 的论文。截至 9 月 14 日抓取，上线五天的模型已有 3,707 次下载、399 个点赞、7 个社区量化版本和 14 个 Spaces 接入。

普林斯顿提出 RLT 架构，让解码器状态跨 token 接力

这是什么：普林斯顿研究员 Yifan Zhang 发布了一份技术报告（MarkTechPost 9 月 13 日报道），提出 Recurrent Looped Transformer（RLT）架构提案。它让解码器的完整计算状态从一个 token 传给下一个 token，提示词和回答部分都算在内，到服务边界也不重置。参考配置为 48 个编码层加 48 个解码层共享权重，每个 token 执行 96 个逻辑块。
🔥 为什么今天值得看：主流 decoder-only 大模型（一类逐字生成文字的单栈架构）里，第 t 个 token 最后一层的计算结果进不了第 t+1 个 token 的第一层，位置之间只靠 KV 缓存注意力通信，跨位置的连续加工缺少一条直通通道。RLT 用状态接力给出一条路径，让每个 token 的计算量保持固定、结构深度随序列增长，为模型在内部状态里持续加工信息的推理方式和多轮对话一致性提供了架构层面的选项。报告自述为纯设计规范，未报告任何实测效率或推理质量结果。
展开正文

主流大模型里有一条断点。第 t 个 token 在最后一层算完的结果，进不了第 t+1 个 token 的第一层，位置之间只靠 KV 缓存通信。普林斯顿研究员 Yifan Zhang 的技术报告提出 Recurrent Looped Transformer（RLT）架构想接上这条断点，MarkTechPost 9 月 13 日做了报道。KV 缓存指保存下来的历史键值对，后面的 token 靠它回看之前的内容，但拿不到前面 token 算到一半的中间结果。

RLT 把模型拆成因果编码器加循环解码器。编码器并行读入序列并导出键值记忆，解码器持有一条完整状态，含最终输出和各层滑动窗口注意力的缓存（每层只保留最近若干条历史的机制），状态跨过提示词与回答的每个 token 传递，到服务边界也不重置。每个 token 先用门控（可学习的加权合并）把编码器表征与上一个 token 的输出合在一起，再走完解码计算。

参考配置为 48 个编码层与 48 个解码层共享兼容权重，每个 token 执行 96 个逻辑块，作者称这属于参数复用，每个块仍各自计算；t 个 token 后状态路径累积到 48t 个解码块，每 token 计算量固定。

报告明确声明这是设计规范，未报告任何实测效率、推理质量或扩展性结果，并警告门控与收缩可能抑制长路径，结构深度不等于推理保证。
