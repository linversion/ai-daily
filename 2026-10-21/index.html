DeepSeek 开源自用推理引擎,单卡每秒可吐 2.5 万 token

这是什么：10 月 20 日,DeepSeek 宣布把内部生产推理框架 DeepInfer 以 Apache 2.0 协议开源,同时开源 MIT 协议的 Token 编解码组件 deepseek-recipe,后者与官方 API 处理逻辑完整对齐。此前开源出去的是模型权重、TileLang 编译工具和算子库,这次给的是把大模型在大规模算力上便宜跑起来的整套自用引擎。官方公告说,希望借此帮助开发者与企业优化大规模推理的吞吐与延迟,降低算力成本、减少能源消耗。
🔥 为什么今天值得看：AI 服务最大头的长期成本在推理。用户每一次调用都要算力卡真金白银地算,推理框架这一层的效率直接决定每个 token 的成本和电力消耗。前沿实验室第一次把生产级推理栈整个开源,意味着其他团队可以对照一家日服务 155 万亿 token 规模的服务商的部署经验来改造自己的系统,私有化和公有云部署都有了降成本的参照。它同时压缩了闭源厂商靠卖 API 调用维持的价差,HN 评论区把它视为开源模型把智能做成大宗商品的又一步。
展开正文

10 月 20 日,DeepSeek 宣布把内部生产推理框架 DeepInfer 开源,协议为 Apache 2.0,同时开源了 MIT 协议的 Token 编解码组件 deepseek-recipe,它与 DeepSeek 官方 API 的处理逻辑完整对齐,让社区拿到与官方一致的部署体验。DeepSeek 在公告里解释,大模型的能力边界由模型本身划定,而能否以合理成本支撑超大规模服务,取决于一个长期未被公众了解的中间层,即推理框架。他们还在公告里引了一句古语「为善与众行之,为巧与众能之」,表示希望帮助开发者与企业优化大规模推理的吞吐与延迟,降低算力成本、减少能源消耗。

道理是这样的。训练让模型学有所成,推理让模型为人所用;用户每提一个问题,背后都有算力卡在计算作答,统筹这批庞大算力集群的软件层就是推理框架,它怎么排卡、怎么拆任务、怎么复用中间结果,直接决定每个 token 的成本和耗电。DeepSeek 此前开源的是模型、TileLang 编译工具和推理算子库,这次进入开源世界的是把大模型便宜跑起来的自家用引擎。官方表示基于 DeepInfer 已实现 V4.1 Flash 高吞吐、低延迟的大规模服务,后续新模型的推理代码也会在这个仓库持续更新,模型本身此前已经开源,这里不再展开。

工程层面,DeepInfer 目前只支持 DeepSeek-V4.1-Flash 一个模型(默认 checkpoint 为 1017 版),最初主要基于 vLLM 构建,也借鉴了 SGLang 和 TensorRT-LLM。五个系统级设计构成它的骨架。注意力部分走数据并行,MoE 结构(模型每层含许多个专家,每次调用只激活其中一部分)的专家层走宽专家并行并配备专家负载均衡,解码阶段在超节点内最高跑到 EP64 到 EP128。DSpark 是按置信度调度的投机解码,小草稿模型先快速写出 5 个候选 token,置信度头预估每个候选的接受率,调度器只验证最有价值的前缀,DeepSeek 称这能把需验证的草稿 token 削减约 30%,接受长度基本不变。SWA 有界重放指缓存命中时只重放一段有界后缀,默认保留 140 个 token,让重算成本与上下文长度无关,解码层的预填充计算量近乎减半。默认开启的零开销异步批调度让 CPU 的调度工作和 GPU 的计算重叠进行,批不变推理和确定性采样只在 NVIDIA 卡上支持,保证不同批次组合下输出一致;结构化输出可以把结果约束在正则、JSON Schema 或 EBNF 语法里。

官方基准在 NVIDIA SM100 GPU 上测得,预填充(读入问题和上下文的阶段)用 4 张卡,解码(逐字写出回答的阶段)用 64 张卡。这些自报数字读自公布的帕累托曲线,解码在 EP64 下、每秩 256 个请求时,单卡吞吐超过每秒 25000 个 token,每用户响应速度接近每秒 100 个 token,请求只剩 8 个时单用户速度超过每秒 300 个 token;预填充在每秩 4096 个 token 时约为每卡每秒 60000 个 token,65536 个 token 时接近 90000,每步耗时约 730 毫秒。

这次发布并不完整。它只提供离线推理,KV cache 系统(对话上下文的缓存,缺了它每一轮都要重算前文)、预填充与解码分离部署、跨副本负载均衡这三件在线服务的必需品都没有包含,DeepSeek 称这些部分与内部基础设施耦合紧密。官方对比表显示,vLLM、SGLang 和 TensorRT-LLM 都已支持预填充与解码分离。硬件只支持 NVIDIA SM100(需 CUDA 13)和华为昇腾 950(需 CANN 9.2),源码构建要求 Linux、GCC 13 以上和 Python 3.12。按其部署问答的说法,最小高效生产单元是 64 张预填充卡加 64 张解码卡,内部版 FlashMLA 解码内核比公开版快 5% 到 10%,端到端差距不超过 5%。

讨论中被引用的知乎技术报告披露了两个运营数字,单个集群一天服务 155 万亿个 token,谷底定价下整卡每小时营收 38 美元。这两个数字属于自报,未说明卡型,暂时无法与市场价直接对标。HN 用户 xrisk 拿它与每小时约 2.75 美元的 H100 租金行情相比,对口径提出质疑。

Mistral 发布 Voxtral 3,实时语音代理一秒应答,支持自部署

这是什么：Mistral 于 10 月 20 日发布 Voxtral 3,包含三个转写型号、一个文本转语音模型和一个基于 LiveKit 的语音代理 SDK。听、想、说合成一条实时流式管线,官方称每轮对话一秒内完成,用户插话即停,通话中可直接调用工具办事。
🔥 为什么今天值得看：此前做语音代理要分别采购转写、推理、合成三类服务,再自己拼接并压延迟。Voxtral 3 把整条链路打包成一个 SDK,并给出欧盟托管与自有部署两条落地路径,把语音代理的竞争从单个模型的榜单分推到整条交付链路。转写起步价每分钟 0.0035 美元,整链路语音代理配自家推理模型每分钟 0.04 美元,呼叫中心这类按分钟算成本的场景可以直接算账。
展开正文

10 月 20 日,法国 AI 公司 Mistral 发布 Voxtral 3。这是一套面向实时语音代理的模型家族,外加一个语音代理 SDK(软件开发包,开发者拿它直接搭应用的工具箱)。语音代理指能接电话、能对话、还能调用业务系统办事的 AI 程序,客服热线、语音前台、免提助手都属于这一类。官方称整套系统把听、想、说接成一条实时流式管线,每轮对话一秒内完成,用户开口插话时,代理立刻停下。

这条管线的分工是,实时转写模型 Voxtral Mini Transcribe Realtime 3 负责听,边收音边把语音转成文字,延迟低于 500 毫秒,覆盖 35 种以上语言,还自带轮次结束预测,即判断对方这句话说完没有、该不该接话。通用大模型负责想,官方示例用 Mistral Small 4,由它理解意图并调用工具。文本转语音模型 Voxtral Mini TTS 3 负责说,官方计费表和管线说明里也用 Voxtral Speech 3 这个名字指代它。各段按流式方式并行推进,谁也不等上一段跑完,这是官方给出一秒应答的来由。

转写矩阵分三档。旗舰 Voxtral Small Transcribe 3 每分钟 0.0040 美元,支持 50 种语言,含 24 种欧盟官方语言,带说话人分离(标出谁在什么时候说话)和关键词偏置(提前喂行业术语,提高专有名词的识别率)。Mistral 自报的基准成绩显示,它在多语转写和说话人分离上超过 Whisper、Scribe v2 和 Gemini 3.5 Transcribe,这份成绩单出自官方自测,暂无第三方复核。批处理档 Voxtral Mini Transcribe 3 每分钟 0.0035 美元,40 亿参数,是全家族最低价。实时档即上面负责听的那个型号,每分钟 0.008 美元。

说话这端,Voxtral Mini TTS 3 支持 35 种以上语言和 50 种以上方言,情绪、语速和重音随对话上下文自动调整,预置音色覆盖 18 种语言,其中有普通话。计费按官方定价表以 Voxtral Speech 3 名目收每 100 万字符 13 美元,批处理和实时走同一个接口。面向更高要求的 Pro Voice 用 30 分钟音频就能复刻一个人的音色、情绪范围和跨语言说话风格,官方把它定位给普通声音克隆不够用的专业场景。

语音代理 SDK 建在实时音视频框架 LiveKit 之上,每个环节是独立模型,换大模型、换音色、换语言都不必重写代理。通话中它能核实来电人身份、查账单、约时间,靠函数调用、网页搜索和企业自有系统的检索完成,接入支持 SIP 电话线路与浏览器、App 内的 WebRTC,也能对接现成的电话交换、IVR(交互式语音应答,即按键菜单那套)和呼叫中心软件。

部署上,Mistral 的 API 提供欧洲、美国与全球接入点,并把欧盟托管当卖点,整套系统也可跑在自有基础设施上,音频在哪处理、数据怎么流转、对话留不留存都由部署方决定,私有化需联系商务团队。语音代理 API 按推理模型分档收费,配 Mistral Small 4 每分钟 0.04 美元,换任意其他推理模型每分钟 0.08 美元。官方公告未提开放权重,现阶段拿到这套模型的途径只有 API 与商务私有化两条。

Databricks 代理记忆上线，任务通过率约为无记忆三倍

这是什么：Databricks 在代理开发平台 Agent Bricks 上线 Beta 版 Agent Memory，由托管会话、托管记忆、后台记忆管线三部分组成，跑在 Lakebase（Databricks 的无服务器 Postgres）上，架构来自 MemCurrent 研究，同一套设施已在 Genie 产品里支撑真实用户。
🔥 为什么今天值得看：代理记忆此前多停留在论文、框架插件和各团队自建的向量库里，现在变成数据平台上的托管开关，抽取、去重、检索、权限这些工程活由平台接手。官方两套基准指向同一个结论，记忆同时提升质量和压低成本，开源基准上 8.4K 输入 token 追平 103K 全量上下文的准确率。记忆存放在用户自己的 Lakebase 项目，与代理框架解耦，换模型换框架时记忆可以带走。
展开正文

Databricks 今天在代理开发平台 Agent Bricks 上推出 Agent Memory，以 Beta 形式开放。代理记忆指的是让 AI 助手跨对话记住用户讲过的事实、偏好和走过的流程，下次直接拿来用，这件事在 Databricks 上从此变成平台里的一个开关。服务跑在 Lakebase 上，它是 Databricks 的无服务器 Postgres 数据库，即开即用、由平台代管，记忆读写的延迟和扩容都交给它。底层架构来自 Databricks Research 的 MemCurrent 论文，同一套设施已经在 Genie 这个面向业务用户的自然语言问答产品里支撑真实流量。

无状态代理的账单最能说明痛点。模型本身没有跨会话记忆，每次对话结束一切清零。研究文记录了一个真实会话，用户问某产品前五大客户是谁，代理从查 SDP 缩写含义、找哪张表存用量数据开始摸索，动用 11 次工具调用和 8 个子智能体，花了近 6 分钟才答对。第二天用户换一个相关的问题，这 6 分钟要原样再花一遍。用户的偏好和上次的纠正同样留不住，要么用户重复自己，要么代理重复犯错。

开发团队的两种常见补丁各有代价。把全部历史塞回上下文，历史一长成本就涨，无关内容还会把代理带偏，Databricks 在开源记忆基准上测得全量上下文比设计良好的记忆多花约 12 倍输入 token，最长的历史上准确率反而更低。自己在对象存储或向量库上攒一套，抽取、去重、检索、权限都要自己维护，矛盾事实越积越多。Agent Memory 把这些活接了过去，分三个组件。托管会话按框架原生格式记录每条消息、工具调用和结果；托管记忆保存画像、偏好、领域知识和工作流，会话开始先注入一份记忆索引让代理知道自己知道什么，期间用关键词加语义的混合检索（既按字面匹配也按含义匹配）找细节；记忆管线在后台按需或定期蒸馏会话（从原始对话里提炼值得长期保存的事实），去掉重复，用新事实替换被推翻的内容。

数据模型分两层，这是 MemCurrent 的核心设计。情景记忆以 append-only 方式保存原始轨迹，只增不改；派生记忆存蒸馏后的结构化知识文件，顶部有自动生成的 memory.md 索引，描述每个文件放了什么。代理在线时通过工具显式写入，后台的 dreaming 管线负责隐式提炼和整体整理。

效果数字分内外两套。开源基准 LoCoMo、LongMemEval、ConvoMem 上，MemCurrent 平均 88.1%，与全量上下文的 87.8% 持平，每题输入 token 只花 8.4K，约是全量 103K 的十二分之一，这一组用 GPT 5.6 luna 兼任代理与记忆模型。内部基准由 Databricks 自建自报，从 12K 以上真实 Genie 会话筛出 114 个用例、29 名用户、2233 条历史会话，无记忆通过率 22.3%，MemCurrent 升到 68.4%，约为三倍，延迟 252 秒、418K token 为所有组里最低，弥合了无记忆与金标注入（把答题所需的记忆直接喂进上下文，相当于理论上限，78.6%）之间八成以上的差距，整体省 31% token、快 26%，这一组用 Claude Opus 4.6 做代理模型、GPT 5.6 sol 做记忆模型。消融实验（逐个拆掉部件看贡献）显示，价值主要来自派生记忆，单独拿到 66.1%，情景记忆单独 35.8%，两者叠加 68.4%；提取策略上，离线 dreaming 的 63.5% 高于在线工具的 53.9%；同场竞技的 Mem0 在内部基准只有 43.9%。回到开头那个 6 分钟的例子，工作流存进记忆后，同类跟进问题 2 次工具调用、41 秒答完。

数据主权是产品的另一层设计。会话和记忆存在用户自己的 Lakebase 项目里，与具体代理框架解耦，开发者可读取、导出、删除每个用户名下的条目，也可以给记忆管线下保留策略指令，博客举的例子是「保留持久客户偏好，忽略一次性调试笔记」。官方称用 Agent Bricks CLI 十分钟内能部署一个带记忆和会话的代理。

IBM 用 292 条自学规则让老模型登顶客服基准

这是什么：IBM 研究团队把开源工具库 ALTK-Evolve 用到客服域,较老的非推理模型 GPT-4.1 在 τ²-bench 零售域拿到 67.5% Pass^4,登顶 2026 年 10 月 12 日榜单快照,领先微调模型 RAFT-30B-A3B(61.4%)6.1 个百分点;换 GPT-5.5 自己提准则自己用,航空域以 82.0% 居榜首。方法是把代理自身任务轨迹蒸馏成行为准则贴进系统提示词,不改权重,也无需人工标注,测试集从头到尾不参与学习。
🔥 为什么今天值得看：客服代理落地的瓶颈在稳定性,Pass^4 这类四次全对才计分的指标直接对应真实业务里顾客每次是否都被正确对待。这套方法不用微调、不用换模型,任何团队都能拿自己代理的失败轨迹照做,微调路线换一个领域就要重来的问题也一并绕开。10 个百分点以上的稳定性提升,在每天接成千上万通对话的客服场景里就是真金白银。
展开正文

客服 AI 最让运营方不放心的场面,是同一个退款请求四次里办对三次。IBM 研究团队在 Hugging Face 官方博客公布了开源工具库 ALTK-Evolve 的客服域新成绩,用较老的非推理模型 GPT-4.1 跑 τ²-bench 基准,零售域拿到 67.5% 的 Pass^4,在 2026 年 10 月 12 日的榜单快照上排第一,超过在合成数据上微调出的 RAFT-30B-A3B(61.4%)6.1 个百分点。整个过程不碰模型权重,唯一的改动是在系统提示词末尾追加一段自动学来的行为准则。

ALTK-Evolve 让模型复盘自己的作业。它先把代理做客服任务留下的完整轨迹交给同一个模型,把成功与失败蒸馏成一条条短规则,例如「动订单前先验证用户身份,邮箱查不到就用姓名加邮编调接口核实」「办退换货时主动讲清分项退款明细和到账时间,不等顾客来问」,另一些规则要求一步只做一个动作,等工具返回结果再回复用户。提炼出的准则以 Markdown 列表贴在领域政策后面,参与后续所有对话。提炼与执行用同一个模型,不需要人工标注,测试集从头到尾不参与学习。

零售域的留出测试集上,全量 292 条准则把平均准确率从 78.1% 推到 82.5%,Pass^4 从 57.5% 推到 67.5%。航空域给出了另一种答案,只保留 14 条高支持度准则的紧凑版在 Pass^4 上拿到 45%,压过全量 101 条版本的 40%,而全量版在平均准确率上领先。团队据此判断,准则的剂量要按领域来调,支持度阈值没有写死的全局最优值。

换前沿模型同样有效。团队在航空域改用 GPT-5.5 自己提炼准则自己用,平均准确率从 72.5% 升到 82.5%,Pass^4 从 55.0% 升到 70.0%,稳定性增益比 GPT-4.1 在同一批任务上还多 5 个百分点,起点也高得多。按完整基准口径提交后,GPT-5.5 版以 82.0% 的 Pass^4 居航空域第一,当期各家前沿模型的提交集中在 66% 到 72% 之间;GPT-4.1 加紧凑准则版拿到 44%,排第 8,超过不开推理档的 GPT-5.2,接近 Claude Sonnet 4.5。

成本的账也在文中算清。零售域全量准则把每场对话的 LLM 开销从 0.084 美元推到 0.139 美元,涨幅 65%,开销全部落在更长的输入上。对话轮次略微变短,在基线与加准则版都能解出的共同任务集上,助手轮次平均减少 0.3 到 0.4 轮;由于每一轮都是一次串行的模型往返,轮次变少直接压低端到端延迟。准则块在每次调用中一字不差,生产环境用提示词缓存可以省回大部分输入开销。

口径需要交代清楚。上述成绩均为 IBM 团队在官方博客自报,并附上了榜单提交记录(零售 PR #542、航空 PR #551),榜单数字对应 10 月 12 日的快照。τ²-bench 由 Sierra 发布,让被测代理与 GPT-5.5 扮演的模拟顾客对话,配给领域工具和政策文档,只有最终数据库状态与预期完全一致才算任务通过,目前覆盖零售与航空两个域。这条路线的复现门槛很低,任何团队都能拿自己代理的失败轨迹照做一遍。

编程 AI 配上止损监工,预判必败就早停,成本最多省 48%

这是什么：论文 StopLoss(arXiv 2610.25525)提出给编程代理外挂一个小型监控模型。它读代理最近几步工具调用的记录,单次前向传播打出失败分数,分数超过在成功运行上校准的阈值就提前中止运行,执行器零改动。
🔥 为什么今天值得看：编程代理在注定失败的任务上烧掉的算力是纯浪费,请前沿模型当裁判又贵到不划算。StopLoss 把每次检查的成本压低一到两个数量级,四种评估设置里每个保留成功任务的成本都低于全部裁判策略,早停这笔账第一次算得过来。
展开正文

让 AI 修一个 bug,它常常一头扎进去,改文件、跑测试,直到步数用尽才发现方向从一开始就错。一篇挂在 arXiv 的新论文(编号 2610.25525)给这类编程代理配了个便宜的外部监工,名字叫 StopLoss,借自炒股里的止损单,跌破预设价位就自动卖出。监工的职责类似,预判这趟运行大概率通不过验证,就提前叫停,省下后面的算力。

监工本体是一个微调过的小语言模型。它只看代理最近的工具调用记录,也就是改文件、跑测试这些动作,一次前向传播(模型把输入扫一遍就出分)给出失败分数,分数越过阈值就中止任务。阈值在成功运行上校准,负责干活的执行器一行代码都不用改。

训练用的是结果监督,拿 GPT 系模型在 SWE-rebench 上跑完的历史轨迹,用最终验证的成败给早期片段回溯打标签,小模型由此学会早早认出失败苗头。摘要报告,失败预测在第一次检查时就从接近随机提升为可用信号,每次检查的成本比六个通用裁判模型低一到两个数量级。

省下的钱有具体数字。在 SWE-bench Verified 这项编程代理基准上,每个保留成功任务的成本降 4.5%,99% 本会成功的运行没被误杀。在成本更高的 SWE-bench Pro 子集上最多省 31%,把监工骨干换成 Qwen3-8B 后达到 48%。GPT 与 Claude 两种执行器搭配两个基准共四种设置,它的成本全部低于对照的裁判策略。它不提升代理本身的成功率,只是让失败来得更便宜。
