Toto 2.0: Time Series Forecasting Enters the Scaling Era

这是什么：Toto 2.0 是一系列开放权重的时间序列基础模型，参数量从 400 万到 25 亿不等。研究团队发布了一篇论文和对应模型，证明仅用可观测性和合成数据训练（不使用任何公开预测数据）就能在 BOOM、GIFT-Eval、TIME 三个基准上达到最佳预测效果。
🔥 为什么今天值得看：这项工作首次在时间序列预测领域系统性地展示了缩放规律（scaling law），表明基础模型可以通过扩大参数量持续提升预测质量。这让时间序列预测进入了类似 NLP 和视觉的“越大越好”时代，并且竞争性开放权重模型的发布降低了行业门槛——小成本也能获得接近 SOTA 的能力（通过更小但更高效的模型）。

时间序列预测领域迎来一个关键里程碑：Toto 2.0 系列模型正式发布。这是一个从 400 万参数到 25 亿参数的开放权重基础模型家族，首次在时间序列任务上系统性地验证了“越大越好”的缩放规律。研究团队仅使用可观测性数据和合成数据进行训练（完全没有采用任何公开预测数据），就在 BOOM、GIFT-Eval 和 TIME 三个基准上刷新了最好成绩。相比上一代 Toto 1.0，Toto 2.0 在同等预测质量下参数效率提升了 7 倍，推理速度也更快——这意味着更小的模型就能达到以前更大模型的水平，而更大的模型则能开创新的天花板。这一成果回答了时间序列领域的一个核心疑问：基础模型在预测任务上是否也能像 NLP 和视觉那样通过扩大规模持续受益？Toto 2.0 给出了肯定的答案。当然，社区也存在保留意见：有人指出缩放优势可能仅局限于特定基准或数据类型，开放权重并不等于完全可复现，且目前还没有第三方独立验证这些缩放声明。但无论如何，Toto 2.0 已经为时间序列预测的“缩放时代”铺平了道路——一个更注重模型规模、训练数据和通用性竞争的新阶段。

Mix-Quant: Quantized Prefilling, Precise Decoding for Agentic LLMs

这是什么：研究者推出了 Mix-Quant，一个专为 AI Agent 大语言模型设计的相位感知量化框架。它在推理的预填充阶段使用 NVFP4（高吞吐4位浮点量化），而在解码阶段保持 BF16 精度，实现最高3倍加速，且精度损失极小。
🔥 为什么今天值得看：AI Agent 越来越多地处理长上下文和多轮交互任务（如编程助手、自主规划等），这类场景中预填充阶段成为推理瓶颈。Mix-Quant 提供了一种实用方案，在不牺牲质量的前提下大幅加速推理，直接回应了生产级 Agent 系统对效率的迫切需求。

AI Agent 正在变得更聪明，但也更慢了。当模型处理复杂的长对话或多轮任务时，有一个阶段会严重拖慢推理速度——那就是“预填充”（prefilling），即模型需要一次性理解整个上下文的过程。针对这一瓶颈，研究者最近提出了 Mix-Quant，一种相位感知的量化框架，专门加速 AI Agent 模型的推理，同时保持输出质量。

Mix-Quant 的核心思路很简单：在预填充阶段，模型处理的是整个历史对话，计算量巨大，但研究者发现其中存在冗余，可以用更低的精度来跑。于是他们把预填充切换到一种叫做 NVFP4 的高吞吐4位量化格式，而在真正的解码生成阶段，仍保留 BF16（16位浮点）的精确计算。这种“分阶段处理”的方法，能让推理速度最高提升3倍，而在典型长上下文任务上的精度损失几乎可以忽略不计。

这是第一次有人专门针对 AI Agent 模型提出“相位感知”量化——以前的方法要么对整个推理过程统一量化，牺牲精度，要么完全不量化。Mix-Quant 抓住了预填充阶段的冗余特性，算是找到了一个很实用的平衡点。不过，目前该方案还没有公开代码或可复现的仓库，社区也在观望它在更广泛的模型和硬件上的表现。如果后续能验证稳定性，它可能成为部署生产级 Agent 系统的重要工具。

想让AI学会操作电脑上的各种软件，通常需要大量人工标注的鼠标键盘操作数据，既昂贵又费力。现在，一项名为Video2GUI的新研究展示了一条捷径——直接从网上现有的教程视频里自动提取交互轨迹。研究人员利用这个全自动框架，构建了迄今为止最大的开源GUI预训练数据集WildGUI，包含1200万条操作轨迹，覆盖超过1500个应用和网站，从剪映到Photoshop再到各类网页。

不过，目前这种方法也面临质疑。部分研究者指出，自动提取的轨迹里可能混入了视频中的错误操作、中断或无关内容，质量不如人工精标的数据；而且教程视频往往只演示常见功能，对复杂、多步骤的创意工作流覆盖不足。即便如此，Video2GUI这种“零成本”获取大规模训练数据的新思路，还是让GUI智能体的普及门槛大大降低了。

Multi-Stream LLMs: new paper on parallelizing/separating prompts, thinking, I/O

💡 HN 讨论：Multi-Stream LLMs: new paper on parallelizing/separating prompts, thinking, I/O。热度：43 points。
这是什么：马克斯·普朗克智能系统研究所发布论文《Multi-Stream LLMs》，提出一种新的架构：用多个并行消息流（分别负责提示、思考、输入/输出）替代传统单一流，让模型能在一次前向传播中同时从多个输入流读取、向多个输出流生成。
🔥 为什么今天值得看：随着 LLM Agent 被用于编程、电脑操作等实时任务，单流顺序处理成了效率、安全和可监视性的瓶颈。多流架构能让模型同时处理不同角色（如边读输入边执行、不因思考而阻塞输出），有望大幅提升 Agent 的响应速度和可用性。

大模型聊天机器人处理一个问题时，通常是一条消息接一条消息地吞吐——你发一句提示，它开始思考，然后输出回答。整个过程串行得像个电话接线员，接完一个通话才能接下一个。但马克斯·普朗克智能系统研究所的新论文《Multi-Stream LLMs》提出了一种截然不同的工作方式：让大模型同时开启多个并行“流”，分别负责接收提示、内部思考和最终输出，并且各个流之间还能互相影响——就像一个乐队，每位乐手各司其职又彼此配合。

这种架构解决的是当前 LLM Agent（比如帮你写代码、操作系统界面）中一个隐形的瓶颈：单流。当模型必须等读完所有输入才能开始思考、等思考完才能输出时，实时交互就成了奢望。而 Multi-Stream LLMs 允许模型“边读边行动”“边写边反应”，甚至思考过程不会阻塞其他流，大大提升了 Agent 的效率和安全性——因为你可以把敏感指令和日常操作放在不同的流里，互不干扰。

论文的核心改变在于：以前我们通过指令微调让模型学会处理顺序消息格式，现在则让模型学会同时处理多路并行计算，每条流有自己独立的角色（提示、思考、输入/输出），并且跨时间步存在因果依赖。换句话说，模型不但要理解多个输入流，还要学会什么时候该从哪个流读取、往哪个流写入——这是一次架构层面的“分道”设计。

社区里对这个方向争议不小。一部分研究者认为多流训练和推理的资源开销会远大于单流，而且当前 transformer 的因果注意力机制天然适合序列，强行并行可能破坏原有的迁移优势。但也有不少人觉得，既然 Agent 场景已经暴露出单流的实时性缺陷，这条路径值得下重注研发。目前该工作仍处于 demo 阶段，离主流应用还有很长的路要走，但它至少提供了一个清晰的路线图：下一次大模型的能力飞跃，也许不是靠更大的参数量，而是靠更聪明的“分工”方式。
