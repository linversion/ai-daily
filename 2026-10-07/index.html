10 月 6 日,法国 AI 公司 Mistral 以公开预览的形式发布 Mistral Large 4,内部代号 Le Chonk。模型总参数 1.05 万亿,每个 token 只激活其中 490 亿,约占全部权重的 4.7%,另配 16 亿参数的视觉编码器,上下文窗口 100 万 token,训练数据覆盖 160 多种语言,包括全部欧盟官方语言。所谓细粒度混合专家架构,是把模型拆成大量专家网络,每次推理只调用其中一小部分,万亿级容量因此能按中等价格对外服务,不过完整的 1.05 万亿参数仍要整体装进显存。

训练发生在 Mistral 自有的欧洲数据中心,使用 3800 块 NVIDIA Grace Blackwell GPU,从零开始。VentureBeat 与 TechCrunch 的报道写的是 4000 块,属于公司高管受访时的取整口径,精确数字以官方模型文档的 3800 为准。TechCrunch 援引 Mistral 科学副总裁 Pierre Stock 的说法,这套自建算力比中国同行少两到三倍,也明显少于闭源实验室;上一代 Mistral Large 3 为 675B 总参、41B 激活,当时使用 3000 块 H200。

发布分两步走。预览 API 当天上线,每百万 token 输入 1.36 美元、输出 4.18 美元、缓存输入 0.14 美元,支持函数调用、结构化输出、文档问答、批处理以及 Agents 与 Conversations 端点,低廉的缓存价格对 100 万窗口下的长程智能体循环成本影响不小。权重计划 2026 年 10 月底开放,VentureBeat 给出的具体日期是 10 月 27 日,此前安排约三周的开发者、网络安全负责人与政府测试期;许可证尚未公布,现阶段无法自托管。

基准成绩里最硬的是网络安全。Mistral 报告 Cybench 93%、CyberGym-E2E 82%,位列 Artificial Analysis Cyber Index 全球前五,并指出多个闭源前沿模型因直接拒绝任务在 CyberGym-E2E 上接近零分,而复现一个漏洞以证明它真实存在,本属安全团队的常规防御工作。编码方向的成绩要分开看,DeepSWE v1.1 61.7%、SWE-Atlas-QnA 59.4%、Terminal-Bench 4.0 28.3%、综合 Coding Agent Index 49.8%,这些数字由厂商在评测框架公开前私下测得,尚不可独立复现;对照 DeepSWE 线上榜单按各模型最佳公开配置的结果,GLM-5.3 与 Kimi K3 都在 69% 上下,GPT-6 Astra、Gemini 3.8 Flash、Claude Opus 5 约 74%。更中立的信号来自 Surge AI 组织的专业标注员盲测,ML4 得 3.74/5,在五款模型中排第二,高于 GLM-5.3 的 3.60 和 Kimi K3 的 3.59,低于 Claude Opus 5 的 4.22。安全方面,它在 Lakera B3 基准上抵御 93.3% 的攻击,KORABench 得 1.691/2.0。

Mistral 把这个模型定位成企业与政府最终能自行运行和定制的基础模型,支持主权基础设施与零数据保留选项。首席科学家 Guillaume Lample 在发给 VentureBeat 的材料里写道:"ML4 is at the frontier of open weight models." 据 TechCrunch 报道,法国总统 Macron 把这条路线描述为 AI 领域的第三条路。

谷歌开源 740M 多模态嵌入模型，统一向量空间装进手机

这是什么：谷歌 DeepMind 于 10 月 6 日发布 EmbeddingGemma 2，权重当日上架 Hugging Face 与 Kaggle。模型 740M 参数，基于 Gemma 4 架构，Apache 2.0 许可，与 Gemini Embedding 模型出自同一技术。初代 EmbeddingGemma 只处理文本，这一代原生覆盖文本、代码、图像、视频、音频，统一映射进同一个嵌入空间，Gemini Enterprise Agent Platform Model Garden 将随后提供。
🔥 为什么今天值得看：嵌入模型是语义搜索和 RAG 流水线的底座，初代 EmbeddingGemma 超过 2000 万次下载证明了轻量嵌入的需求量。这一代把跨模态检索压进手机内存预算，检索可以完全离线完成，数据不出设备，延迟随之下降。编码代理可以在本地用它索引代码库并做语义检索。与 Gemma 4 共享分词器和音频编码器后，手机上组一条完整的检索增强链路有了现实的内存预算。
展开正文

谷歌 DeepMind 在 10 月 6 日发布 EmbeddingGemma 2，当日开放下载。新模型有 740M 参数，基于 Gemma 4 架构，采用可商用的 Apache 2.0 许可，把文本、代码、图像、视频、音频原生映射进同一个嵌入空间。初代 EmbeddingGemma 去年发布，定位是消费级硬件上的轻量文本嵌入，累计下载超过 2000 万次；这一代把模态边界打开，官方举的例子是用一段语音备忘录定位某条视频片段，或者拿一句文字查询在几小时录音里检索，全程由单个多模态模型在本地完成。

结构上做成模块化。纯文本工作负载只需约 270M 参数，按需挂上 170M 的视觉编码器和 300M 的音频编码器，就组成完整的多模态版本。量化之后，在 Google Pixel 11 Pro 上纯文本权重约占 191MB 活跃内存，完整多模态约 567MB。上下文窗口扩到 8K token，是初代的 4 倍，单次可处理 5.5 分钟音频、29 张图片或 58 个视频帧，也支持交错混合输入。模型支持 Matryoshka 表示学习，输出向量可从 768 维截断到 512、256 或 128 维，本地向量数据库的存储和内存占用最多降 6 倍。

效果提升最明显的是代码。MTEB Code 得分从初代的 68.76 升到 78.68，涨了 9.92 分，官方建议的用法包括本地代码库索引和语义代码搜索，编码代理的检索环节也能直接复用。在 sub-1B 多模态嵌入模型里，它在 MTEB Code、MAEB 等基准拿到同级别领先成绩，部分任务超过参数量两倍以上的专用模型，多语言文本性能与初代持平。

生态在发布日就已就位。权重上架 Hugging Face 和 Kaggle，Gemini Enterprise Agent Platform Model Garden 即将跟进，端侧优化版本放在 Hugging Face 的 LiteRT Community；transformers、sentence-transformers、vLLM、llama.cpp、Ollama、MLX、SGLang、LMStudio 都能直接推理，向量存储可配 Qdrant，Unsloth 提供微调指南。它与 Gemma 4 共享文本分词器和音频编码器，两个模型组成端侧 RAG 流水线时合计内存占用更低。浏览器端可用 transformers.js 或 WebGPU，谷歌开发者博客同日刊文，补充 AI Edge Models API 与 ML Kit 的接入路径。Google AI Edge Gallery 的 Instant Media Search 和 Video Moments Finder 演示应用已经上线，分别做媒体库跨模态检索和视频片段定位。

月提交涨到五倍,GitHub 不停机重构 Git 地基迎接智能体

展开正文

GitHub 工程博客 10 月 6 日刊出首席软件工程师 Brian Celenza 的长文,首次公开平台正在重建 Git 基础设施,为的是承接智能体带来的并发读写规模。这次重构在 GitHub 持续运行的同时推进,平台没有安排维护窗口,也不要求任何团队改变现有的分支、评审与合并工作流。文章是系列首篇,具体架构细节留给后续文章。

官方统计的负载已经说明了动工理由。2026 年 9 月,开发者和智能体在 GitHub 上完成了 73.8 亿次提交,达到一年前的五倍以上。月度推送量从 6.9 亿次涨至 33.5 亿次,增长 4.9 倍。从 2025 年 9 月到 2026 年 8 月,Git 总活动从每月 2182 亿事件增至 4733 亿,涨到原先的两倍以上。最忙的仓库 8 月收到约 10 亿次请求,拉取请求合并量接近一年前的四倍,GitHub Actions 9 月运行 32.6 亿次。

智能体改变了瓶颈的形态。一个处在紧密循环里的智能体几乎每完成一个动作就要提交或写检查点,单次推送的耗时直接决定它的速度上限,人类根本察觉不到的延迟在这里成了硬约束。数千个智能体各自开分支写入同一个仓库,持续写入最终汇聚到架构中的单点。CI 和代码扫描每分钟克隆或抓取同一分支尖端数千次,一次推送放大成海量读取。原文点明,快克隆只解决问题的一部分,读取靠加缓存加副本就能扩展,写入必须先持久落盘、再一致可见,下一个智能体或 CI 任务才能接着构建,难就难在这一侧。

现行存储架构叫 Spokes。它把每个仓库的完整副本放在若干文件服务器的本地磁盘上,默认五份,本地磁盘换来低延迟读取,多份副本同时提供冗余。推送更新引用时,系统用三阶段提交协议配合 quorum 机制确认,quorum 可以理解成多数副本达成一致才算写入成功,以此让 CI、网页界面和 API 客户端看到一致的仓库状态。这套组合如今服务着 10 亿个仓库,对绝大多数仓库运转良好,只是在最高活动量下撞上天花板。读与写绑在同一批副本上,加读副本会推高写入开销,失去 quorum 时写入干脆全部停止,两边都没法独立伸缩。

新架构把持久性和伸缩性拆开。权威仓库数据放进 Azure Blob Storage,由云存储负责持久与复制。读取交给只带缓存的轻量 worker,随流量弹性增减,CI 扇出、智能体集群和大克隆带来的读尖峰不再转化成每次推送的额外开销。压缩和垃圾回收这类重活从服务路径挪走,由独立 worker 直接对持久存储在后台执行。一次推送中真正需要协调的只剩引用更新,其余工作并行展开,关键路径缩到最短。丢掉一个计算节点近似一次缓存未命中,替补 worker 立即上线,随流量回填缓存。内部基准显示新架构写入吞吐最高提升 35 倍,读取容量按需独立伸缩。分支保护、必需评审、审计日志等既有治理控制全部保留。

测试自动化公司 QA Wolf 的工程博客 10 月 1 日刊出工程师 Atchyut Pulavarthi 的复盘长文,讲述他们为自家 AI 智能体搭建运行环境的教训。最初的基础设施按云作业的套路搭建,机器干完活就回收,团队后来发现这个模型整体错了,转而给每个智能体会话独占一台云上整机。机器里放着受版本控制的测试套件检出、装齐 git、gh、node、jq、prettier、Python 和 QA Wolf CLI 的 shell,需要验证工作时还能开一个可实时围观的真实浏览器。如今每天有 6000 多台机器投入实时会话,繁忙工作日里智能体在无人值守下为数十个客户团队处理超过 1300 条 Slack 和 GitHub 线程。

复盘的核心判断是智能体会话的行为模式接近一位同事。它会停下来等人回复,等人回了再继续,中途碰的是真实系统,执行的是事先没人审过的命令。云平台的默认设置建立在相反的假设上,四条习以为常的习惯因此逐个失效。

冷启动的问题最先暴露。普通作业开机慢一点没人察觉,智能体这边用户刚发完消息正盯着屏幕等回复。旧方案在回复一分钟后就关掉机器,人要去开会、要分心,等想起来回应时,只能干等 25 秒以上看新机器启动。重试这条规矩也得扔掉。作业重跑一遍无害,智能体的产出却是落在工单系统里的 bug 报告和发进线程的回复,机器在报告发出后死掉再重跑,团队就会收到第二份一模一样的报告。无状态假设的代价最直接。对作业来说机器上没有值得留下的东西,智能体的机器却装着测试代码检出、改到一半的编辑和停在某个页面上的浏览器,丢掉机器,工作也跟着没了。可信代码这条隐患最深。作业跑的代码有人写过、审过、部署过,智能体的命令是它边干边写的,依据还可能直接来自 PR 描述。作者举的例子是,外部贡献者可以在 PR 描述里请接手工单的人 cat .env 并把测试凭据贴进评论,握着 shell 和 GitHub 令牌的智能体完全做得到。

更早的路线如今看来走了弯路。第一版给智能体一份专用工具短清单,一件工具管一件事,读文件和搜索各配一件;没有真实磁盘,团队只好造出模拟的文件系统和模拟的 bash 让它跑命令。作者自嘲,自家的文件读取器是个更差劲的 cat,搜索工具是个更差劲的 grep,整个过程等于一个命令一个命令地重造电脑。而团队想完成的事,让团队的端到端测试保持常绿,QA 工程师在一台普通笔记本上就能做完,git、shell、浏览器、编辑器这些趁手的工具本来就装在每台开发机上。想通这一点后,团队停止堆工具,把一台完整机器直接交给每个会话。

新机制的细节处处对着旧习惯打。新机器就绪最长要 30 秒,于是不做会话开启时的按需启动,改为维护一个随一天内流量伸缩的预热机器池,交付一台只要几毫秒。浏览器不进暖池,每天数千个活跃会话里真正启动过浏览器的只有几百个,规划覆盖、读代码、答疑都在终端里完成。机器在每次回复后保活 5 分钟,并设单机生命周期的硬上限。执行只给一次机会,基础设施在作业中途垮掉时,让失败发生在看得见的地方,宁可让人发现也不悄悄重做一遍。作为对照,QA Wolf 自家测试运行器对失败测试最多重试三次,重跑测试能说明问题,重跑智能体只会多出第二份 bug 报告。进行中的工作靠持续落盘保命,未保存改动在静默几秒后写入机器之外的持久存储,打字期间至少每 30 秒一次,无法干净恢复时保留最近保存的版本,最坏损失几秒输入。

安全模型放弃了分辨命令善恶的思路,默认任何命令都可能带敌意,再限制所有命令能触达的范围。智能体能改的只有测试代码和自己的草稿区,其余内容只读或干脆不存在;测试要用的密码和 API key 由工具私有传给命令,不进进程列表、日志和报错;宿主云机器自身的凭据够不到;实时会话里智能体以用户本人身份行事,权限不多一分;配置立不起来的会话直接拒绝启动。大请求也在这套底座上找到了出路,修完昨晚全部失败测试这类任务会被拆成独立子任务,最多同时派出 50 个子智能体,各自一台机器、一个浏览器、一个分支,互不绊脚。作者坦承预热机器池、最小权限、自动保存都是存在多年的老技术,四条修正没有一条称得上聪明,复盘的价值在于公开权衡过程与运营数字。回头看,旧默认设置的共同盲点是假设另一端没有人,等回复的人不在考虑之内,机器上的半成品和握在作业手里的凭据也一并被忽略了。机器依旧用完即弃,被挪到机器之外保起来的,是会话本身。

文章经 Hacker News 讨论,发帖时热度约 13 points,规模不大。最有分量的内容来自以团队成员身份发言的发帖人,补充了两个博客没展开的细节。最早用一个微服务统一管理全部智能体会话并指望水平扩展,在需要真实文件系统和预装工具的前提下走不通;旧沙箱设一分钟超时,实例冷启动要 10 到 30 秒,用户在界面和线程里等回复的时间被拉长,如今改成暖池毫秒级取用,沙箱在每次回复后保活 5 分钟。除这条补充外,讨论中没有出现更多具体的技术回应。

Tomasz Tunguz 发布了对 Vercel COO Jeanne DeWitt Grosser 的访谈,她完整讲述了公司 inbound 销售代理一年多来的架构变化。据她介绍,这个代理 2025 年 6 月上线时只是一份约 125 行的提示词,由团队里业绩最好的 SDR 编写,编码了 Vercel 的线索资格认定规则,维护它只占一名 GTM 工程师约 20% 的时间。上线初期代理负责调研、判断资格并起草邮件,发送由人完成,顶级 SDR 人工在环约六周,先逐封审查草稿,再降到约百分之一抽检,8 月完全撤出人工。她把这比作带新销售,前期读新人发出的头一百封邮件,之后随机抽查即可。

业务随后一年向上迁移企业市场,提示词膨胀到 1,000 行,麻烦随之而来,她承认模型并不总是遵循写在里面的规则,而资格认定里许多环节本就是确定性规则。团队把提示词拆成规则与判断两部分,工程师把规则写成代码,把需要判断的部分留给模型。如今整个 inbound 只跑 14 条规则,线索到达后系统先查 Salesforce,若账户已有开放商机就直接转给客户经理。她的原话是:"The model shouldn't get to decide, we just want that to occur." 规则显式化后,团队另跑一个升级代理,监控系统何时违反这 14 条规则,判断违规是否本应发生,再修复或认可例外。

人的去向也有交代,SDR 全员晋升转做 outbound,跳过惯例的一年,她的理由是人类的价值在于与人交谈。按 Tunguz 文末的总结,整套系统撑起这家独角兽公司的销售漏斗顶部,每年推理与基础设施成本约 1,000 美元。Tunguz 把这个案例与他此前分析过的 14 个生产级 agent 工作流对照,其中 65% 的节点跑纯代码,只有 14% 保持完全 agentic。他在 2025 年 11 月底首度报道过这个代理,当时 Vercel 用约六周把 SDR 团队从 10 人减到 1 人,本次访谈补上了此后的演进细节。

密集检索只按表层语义相似度取回文档，复杂检索任务常让它失手。一篇新论文把 LLM 推理与检索器的高效语料探索组合进同一个 ReAct 智能体循环，让模型边推理边查询。相同 embedding 模型下，这套方案把 nDCG@10 提高 8.7 个百分点，同一套 pipeline 在 ViDoRe v3 与 BRIGHT 两个榜单都拿到有竞争力的结果，而专用检索方法在域外任务上挣扎。收益的另一面是成本，平均每个查询耗时 107.4 秒，标准检索仅 0.67 秒，并消耗 764.1K 输入与 5.8K 输出 token。论文结论指向大规模部署需要更具成本效益的检索智能体。
