Claude Code 上线官方插件评测，有没有用跑出数字

这是什么：Anthropic 给命令行 AI 编程工具 Claude Code 发布了官方插件评测流程，核心是一条新命令 claude plugin eval。这条命令拿贴近真实用法的提示词运行插件，给 Claude 的产出打分，再和不加载插件的运行对照。插件开发中过去没法度量的三件事，技能有没有被触发、插件改过或换新模型后还有没有效、是否强于不装插件的裸模型，现在都能跑出数字。功能需要 Claude Code v2.1.269 及以上版本，2026 年 9 月 11 日经 MarkTechPost 报道。
🔥 为什么今天值得看：插件生态一直缺一把统一的尺子。作者写完插件，通常只能自己试几下确认能跑，用户装上后效果如何、插件更新后有没有退化，全凭感觉。这条命令把加载插件和不加载插件当成两臂同时跑，用差值 Δ 衡量插件的真实贡献，两臂都拿满分就说明插件没起作用。评测还能挂进持续集成流程，每次改动后自动运行并按及格线拦截，插件质量从作者的口头承诺变成卡得住发布的硬指标。对靠插件吸引安装量的开发者，这既是质检工具，也是对外证明价值的凭据。
展开正文

9 月 11 日 MarkTechPost 报道，Anthropic 为 Claude Code 发布了官方插件评测流程，核心是一条新命令 claude plugin eval。插件作者过去只能凭感觉判断自己的作品有没有用，这条命令拿一批贴近真实用法的提示词运行插件，给 Claude 的产出打分，再和不加载插件的运行对照，把「有用」两个字变成可以复查的数字。

用例放在插件目录下的 evals 文件夹里，每个用例是一个子目录，装着一份 prompt.md 和一个 graders 文件夹。提示词怎么写就原样发给 Claude，prompt.md 头部可以设置最大轮数（默认 10 轮）、超时（默认 300 秒）等参数。打分规则叫评分器，共 6 种。regex、tool_used、tool_order、file_exists 这 4 种从对话记录和磁盘文件直接计算，不产生额外费用；llm 和 baseline 这 2 种要请裁判模型出手，前者按作者写好的文字标准打分，后者拿产出对比参考答案，按真实调用计费。不想手写用例，claude plugin eval init 能读一遍插件，问清什么算好结果，替你起草用例和评分器并试跑。

这套评测的关键在差值 Δ。每个用例默认跑两遍，加载插件一遍，不加载一遍，两个分数相减，得到插件的真实贡献。文档示例里单个用例加载插件得 1.00，不加载得 0.33，Δ 是 +0.67；6 次运行估算花费 0.41 美元，耗时 74 秒。两遍都拿满分的用例，功劳属于 Claude 本身，插件没帮上忙。Anthropic 点名了最常见的第一个发现，Δ 接近零、同时技能触发类评分器失败，说明用户用自然的话提问时 Claude 没选用这个技能，这类行为缺陷是只查清单语法和结构的 claude plugin validate 发现不了的。带 with-only 标记的评分器（通常是 tool_used Skill）只作为指示报告，不计入分数，因为不带插件的运行里没有技能可触发。

结果落在 evals/results 目录下带时间戳的 report.html 里，逐条给出每个评分器的判定，账户支持时报告还会同步发布到 claude.ai，加 --no-publish 可以关掉。评测也能接进持续集成当门禁，文档的 CI 示例带 --trust-plugin、--threshold 0.8、--max-cost-usd 20 等参数，主模型用 claude-sonnet-5，裁判模型用 claude-haiku-4-5。及格线由 threshold 决定，max-cost-usd 给单次花费封顶，评测不过关，这次改动就过不了门。

成本要提前算清。一套评测大致跑用例数 × 运行次数 × 臂数次 agent 调用，每个计费评分器每次运行另加约 3 次简短的裁判调用，两次运行的结果也会有波动。每次评测都是真实的模型调用，费用计入套餐或 API 账户；官方提醒，用量超限时的报错可能伪装成功能回归，先查用量再下结论。新流程要求 Claude Code v2.1.269 及以上版本，插件目录里要有 plugin.json 或 .claude-plugin/plugin.json 清单。插件的价值从作者口头担保变成跑分说话，中间就差这一条命令。

OpenAI 全双工语音模型 GPT-Live-1 上线 API

这是什么：9 月 10 日，OpenAI 把语音模型 GPT-Live-1 开放进 API。这个模型能一边听一边说，语音行业管这叫全双工，此前这套能力只在 ChatGPT 里，现在开发者可以调用它搭建自己的语音应用和电话客服。按分钟计费，每分钟 0.05 美元，发布当天即可使用。API 版新增打断处理、电话线路部署、12 种新语音、用 system prompt 调整语气语速等能力。
🔥 为什么今天值得看：传统语音代理由语音转文字、大模型、文字转语音三段拼接而成，每段交接都累积延迟、丢失对话节奏，用户一打断流程就容易乱，开发者要写大量协调代码。GPT-Live-1 用单个模型直接处理输入和输出音频，语音层被大幅简化，延迟和打断处理同步改善。它还能把推理与工具调用委托给后端模型，简单任务配便宜模型、复杂任务配强模型，成本按任务调节。订餐、客服这类电话场景对反应速度极其敏感，这套能力直接决定产品能不能落地。Yelp、Speak 等公司已经接入。
展开正文

打电话给餐厅订位，接电话的是个 AI，你说到一半突然想改时间，直接开口打断它。这个在人跟人对话里再平常不过的动作，对机器一直是难题。9 月 10 日，OpenAI 把语音模型 GPT-Live-1 开放进 API，ChatGPT 里那套能边听边说的语音能力，此前只在 OpenAI 自家产品里，现在开发者可以按每分钟 0.05 美元的价格调用。

全双工指的是能同时听和说，像两个人打电话，一边讲一边留意对方有没有插话。过去做语音代理，行业通行做法是把三样东西拼起来，先用语音识别把声音转成文字，交给大模型想答案，再用语音合成把文字变回声音。每交接一次都会慢半拍，语气和节奏容易在转换中丢掉，用户一打断流程就乱，开发者要写大量协调代码去兜底。

GPT-Live-1 把听和说放进同一个模型。它说话的同时还在听，被打断能自然接住，背景吵闹或者双方沉默时也不会出戏。OpenAI 公布的评测数字是，在考察停顿处理、轮次交替、打断和应和这些真实对话行为的 Full Duplex Bench 上，它比上一代 GPT-Realtime-2.1 高 30 个百分点，轮次响应延迟和交互行为提升明显。搭配 GPT-6 Astra 的中等推理档时，它在衡量语音代理端到端智能的 Tau3 评测里排第一。

这个模型只负责听和说的前台，动脑子的活交给后台。推理和工具调用可以委托给后端文本模型，排班、订单查询这类高频简单任务交给 Luna 这类模型，复杂客户问题交给 Astra，深度、速度和成本按任务自己搭配。语言学习公司 Speak 的早期评测显示，语言辅导给学习者留出更多思考时间，辅导老师抢话打断学习者的情况比原来的轮次制系统减少近 80%。一位医疗行业客户的联合创始人兼 CTO Tony Stoyanov 的说法是，对比原来的级联方案，代码库简化了 80%，删掉 2.3 万行代码。Yelp 把它接进电话产品 Yelp Host，处理预订和点餐来电，通话处理率明显提升，来电者说出的句子也更完整自然。

API 版还补了一批工程细节。模型原生输出语音识别转写文本和回复文本，字母数字识别强，支持关键词偏置，让识别偏向开发者指定的词，减少人名菜名听错。它本身没有轮次概念，但原生支持轮次检测，习惯按轮次开发的团队能沿用原来的写法。语气、语速、说话风格通过 system prompt 调整，也就是开发者写给模型的人设和指令。电话线路可以直接部署，从餐厅预订到客服热线。语音库从原来的一小组扩到 Quartz、Ripple、Vesper 等 12 种，覆盖更多口音、方言和语言，未来几个月继续增加。0.05 美元每分钟的价格覆盖语音层本身，后台配什么模型由开发者决定，想用自己的定制声音需要联系销售。

Hacker News 上讨论最热的是拿它做语言学习。有开发者想做带课程的语音家教，也有人抱怨实时转写听不清初学者的含糊发音，模型会回应自己没说过的话，打算先用更准的 Scribe v2 转写再喂给它。有人质疑部分宣称音频到音频的模型内部其实仍靠转写，听不出发音细节。怀疑者的理由更直接，电话机器人让人糟心了三十年，一个 API 改变不了这个印象。支持者认为这回模型能调用工具，语音代理真正能干活，人类客服可以腾出手处理复杂问题。

Google 开源 Tunix，大模型后训练压缩到一个 YAML

这是什么：Google 于 2026 年 9 月 11 日在官方开发者博客发布开源框架 Tunix，用来在 Google Cloud TPU 上完成大模型后训练。TPU 是 Google 自研的 AI 加速芯片，后训练指大模型预训练完成后继续调教的阶段。Tunix 把监督微调（SFT，拿人写好的标准答案教模型模仿）、人类反馈强化学习（RLHF，让人给回答打分、模型照分数改进）和偏好优化（DPO、PPO 及自定义奖励信号）收进同一套接口。用户写一个 YAML 配置文件（一种用缩进表达层级的配置文本）描述任务，框架自动处理多块芯片的分工与通信。代码开源在 GitHub，支持 pip 安装，附 Colab 示例笔记本。
🔥 为什么今天值得看：过去做一次后训练，研究者常要在多个框架和硬件之间搬运代码，设备怎么分、芯片怎么通信、训练断了怎么存，都要自己写。Tunix 把这些编排工作压缩进一个 YAML 文件，框架自动完成设备放置、mesh 构建和通信优化，等于把 DPO、PPO 这类高级调教技术的工程门槛降了一截。对在 Google Cloud 上租用 TPU 的研究者和中小团队，这是一条更省事的上手路径；对开源社区，训练基础设施多了一个由 Google 维护的新选项。官方同时给出后续方向，会增加更多后训练方法并更深度接入 Google Cloud AI 生态。
展开正文

9 月 11 日，Google 在官方开发者博客介绍了新开源的框架 Tunix，专门用来在 Google Cloud 的 TPU 上做大模型后训练。TPU 是 Google 自研的 AI 加速芯片，后训练指的是大模型完成预训练之后继续调教的阶段。一个只经过预训练的模型基本只会接话，要让它稳定完成对话、写代码这类具体任务，还得靠后训练继续教。

后训练的常用手段不少。监督微调（SFT）拿人写好的标准答案教模型模仿；人类反馈强化学习（RLHF）让人给模型的回答打分，模型照着分数改进；偏好优化里的 DPO 拿成对的偏好数据直接调整模型，PPO 是一种经典的强化学习算法，模型靠奖励信号在试错中学习。Tunix 把这些方法收进同一套接口，还支持自定义奖励信号。

官方点出的痛点很具体。传统后训练往往要在多个框架和硬件类型之间做复杂编排，设备怎么分、训练断了怎么接着跑，都得研究者自己写代码张罗。Tunix 的做法是把底层的 TPU 拓扑抽象掉，用户在一个 YAML 文件里写清模型、方法、数据和 TPU 节点，剩下的交给框架。YAML 是一种用缩进表达层级的配置文本，写起来像一张填空表，博文给出的最小配置只有四行。

model_name: "my_llm_checkpoint"
post_training_method: "dpo"
data_path: "gs://my-bucket/dataset"
tpu: "projects/my-project/locations/us-central1/tpuNodes/my-tpu"

框架自动完成的部分包括 mesh 构建和通信优化。mesh 指多块芯片如何连线分工的安排，Tunix 会自动把模型切分到各个 TPU 核心，同时处理模型并行（模型太大时拆到多块芯片）和数据并行（同一模型复制多份并行处理不同数据）。断点保存与恢复也内置其中，大规模训练中断后可以接着跑。速度上它借助 XLA（Google 的编译工具，把计算翻译成芯片上的高效指令）为每种后训练算法的通信模式生成专门的内核。生态上它原生集成 JAX 和 Haiku（Google 系的深度学习框架和模型库），已有的模型定义不用改就能复用；安装对 Python 用户就是一条 pip 命令的事，官方在 Colab（Google 的在线代码笔记本）里放了示例，代码开源在 GitHub。

博文还设了一节讲范式转变，标题是从手动调参走向自主循环，配上智能体循环和样本训练轨迹的示意图，示意训练由循环自动推进的更大图景。需要分清的是，正文实际交出的能力是 YAML 单文件配置加自动编排，自主循环眼下属于愿景性表述，没有对应的已发布功能，官方也没有给出时间表，只承诺未来支持更多后训练方法并更深度接入 Google Cloud AI 生态。另外正文文字没有给出性能对比数字，结果只以样本轨迹图的形式展示，发布当天的信息全部来自官方一手来源，实际表现要等独立使用者的反馈。

字节跳动新基准专考模型自建工具，64 次自改仅 34 次有效

这是什么：字节跳动 Seed 联合新加坡科技设计大学、佐治亚理工、M-A-P、TokenWave.AI 发布评测基准 HarnessDev，9 月 11 日经 MarkTechPost 报道，论文和项目页已公开。它和现有基准考的东西不同，打分对象是模型亲手搭建的 agent harness，也就是模型干活时用的一整套工具和流程脚手架，模型用自己搭的工具跑任务，跑出的答案只用来给工具算分。基准分 Creation（从裸种子搭建）和 Evolution（按执行反馈自改）两轮，6 个模型在 5 个基准共 2,207 个任务实例上完成首测，64 次自我改动里只有 34 次与盲测成绩方向一致。
🔥 为什么今天值得看：现有基准把 harness 当成固定不变的常量，只量答案。Terminal-Bench 2.1 榜单显示，同一份权重的 GPT-5 在 Terminus 2 里解出 35.2% 的任务，在 Codex CLI 里解出 49.6%，差别全部来自工具环境。工具环境是成绩里最大的隐形变量，此前没有专门考试。HarnessDev 把它变成考题，首次给出一批可对账的量化结论，比如自建工具在写作、ML 实验领域追平人类参考，在代码、搜索领域大幅落后，比如自我改进的反馈信号只有 53.1% 的次数与盲测同向。以后评估模型自建工具、自我进化的说法，有尺子可量了。

考试判卷，AI 行业历来只看模型交出的答案。字节跳动 Seed 联合新加坡科技设计大学、佐治亚理工、M-A-P 和 TokenWave.AI 发布的新基准 HarnessDev 换了判卷对象，专给模型亲手搭建的干活工具打分。这套工具学名叫 agent harness，模型干活时用的一整套工具和流程脚手架，执行循环、外部工具、上下文管理、状态记录、故障恢复、结果验证都装在里面。它对成绩的影响大得惊人。Terminal-Bench 2.1 榜单显示，同一份权重的 GPT-5 在 Terminus 2 环境里解出 35.2% 的任务，换进 Codex CLI 后解出 49.6%。过去的基准把这套脚手架钉死不动，HarnessDev 把它本身搬上考桌。

考试分两轮。Creation 轮里，每个模型领到同一份裸种子，只提供文件、搜索、进程三类基础原语和结果、轨迹记录器，循环、规划器、验证器、重试、停止规则一概没有，原样交卷得 0 分。模型凭任务族说明、一份简短设计教程和 1 到 3 个开发样例搭出完整 harness，随后代码冻结。Evolution 轮里，模型基于冻结代码，用 100 个 SWE-bench Pro 任务和全部 89 个 Terminal-Bench 2.1 任务的执行反馈修改自己，每个正式版本还要到 630 个从未见过的 SWE-Pro 实例上接受盲测。打分看两项，任务成功率和执行 token 消耗。

首份成绩单来自 6 个模型，Opus 4.8、GPT-5.5、Gemini 3.1 Pro、DeepSeek V4 Pro、Qwen 3.7 Max 和 Seed 2.0 Pro，在 5 个基准共 2,207 个任务实例上各自建 3 套 harness。结果分化严重。写作和机器学习实验两个领域，模型自建工具追平甚至反超人类参考，Opus 4.8 在 EQ-Bench3 拿 84.6，参考线 83.7；MLE-bench 上 Opus 4.8 和 Gemini 3.1 Pro 分别得 32.9 和 32.4，人类参考只有 24.0。代码和搜索两个领域差距拉开，整体平均分最高的 Opus 4.8 得 67.8，人类工程师参考 harness 是 86.2；搜索基准 BrowseComp 的最好成绩 52.6 出自 GPT-5.5，参考线高达 92.2。论文注明，这三项参考成绩取自 OpenAI 的 GPT-5.6 报告，属于外部结果，没有重新跑分。

自我进化那轮的数字更冷。9 条进化线共产出 73 个正式版本、64 次相邻改动，反馈信号与盲测成绩同向的只有 34 次，占 53.1%，带明确正向证据的只有 2 次，单次提交本身就能带来约 ±4.75 分的波动。模型写的代码还有大片从来不跑，108 个代码组件实例里 18 个从未触发，全部属于状态和内存类；11 套 harness 定义了 State 类，26,679 条执行轨迹里连一次中途存档（checkpoint）都没出现过。高光时刻也有，Opus 4.8 察觉 100 次运行里 99 次报告成功、实际只有 48 次通过，追到过早宣告完成的病根，给自己加了一道完成闸门。

对每天用 AI 干活的人，换执行器（在 harness 里实际跑任务的模型）的实验最有参考价值。统一换成 Gemini 3.1 Pro 执行后排名重新洗牌，Qwen 3.7 Max 在 BrowseComp 涨了 17.6 分，Opus 4.8 在 SWE-Pro 却从 69.3 跌到 33.0，部分原因是其中一套 harness 把 120 步上限写死给了原执行器，它的搜索 harness 重复查询率也从 10.1% 飙到 88.2%。工具质量绑着执行环境，搬家之前先体检。

展开正文

2026 年 9 月 11 日，OpenAI 工程博客挂出一篇由 Jon Lee、Chaomin Yu、Ben Ries 三位工程师署名的长文，第一次系统讲清 ChatGPT 背后的在线存储平台 Habitat。规模数字先摆出来。它现在每秒处理超过 7000 万次请求，折算下来一分钟 42 亿次、一天超过 6 万亿次；每周服务超过 10 亿用户，全球大约 80 亿人口里差不多每 8 个人就有 1 个；管理的数据超过 500 PB，换成 5 亿多 GB，相当于大约 200 万部 256GB 手机加起来的容量；部署覆盖近 40 个地理区域。行业常规是按 10 倍规模设计、指望撑上几年再做下一步，作者写道：「过去三年，我们的规模每年都以超过 10 倍的速度增长。」你在 ChatGPT 里登录、改 Codex 设置这类动作，背后都有多次数据查询，全是它在兜底。

起点很低。2024 年年中，Habitat 只是一个 Python 客户端库，挂在 ChatGPT 主服务器旁边，产品工程师不用研究数据库，数据存在哪、谁能访问这类杂活全部由库包办，底层数据主要放在 Azure Cosmos DB，配合 Valkey 缓存、Nanobase 和对象存储。没有行政推动，它靠口碑在内部快速铺开。

到 2025 年年中，库这种形态撑不住了。库的代码散在几十个业务服务里，改一次协议要让所有服务协调升级。文章复盘了一次典型翻车，团队想把最关键的数据迁到多个区域分布的 Cosmos DB 账号上，先在客户端加路由逻辑、埋好开关，等几十个服务逐一升级就花了好几天；随后加影子流量验证分片逻辑、修 bug，每一步又是数天。最后开关还没稳定启用，一个团队因为无关原因把服务回滚到带 bug 的旧客户端，恰好引发了大家拼命想躲开的那次故障。这次教训让 OpenAI 下决心把 Habitat 抽成独立服务，部署、观测和安全管控从此有了单一控制点。

服务继续用 Python 写，是算过账的。团队清楚 Python 的开销在 100 倍规模下必然撑不住，重写早晚要来，但他们押注等真到迁移那天，自家的 Codex 和 GPT 编程模型能把成本打下来，原文写明这个判断已被证明正确，文章章节目录里也列出了「从 Python 迁移到 Rust」。眼下最磨人的是尾延迟，一次用户请求背后是几百次数据库调用，用户体感取决于最慢的那一次。Python 的 asyncio 只能并发等待网络读写，绕不开 GIL 的单线程限制，CPU 任务一多，协程就要排队等调度，实测调度延迟能到几百毫秒，个别情况好几秒。应对办法是把每个进程的并发压得很低，再用海量 Python worker 进程横向扩。

文中给出两个踩坑案例，细节完整。特性开关工具 Statsig 默认每分钟无抖动拉取全量配置，一个 pod 里最多 8 个 Python 进程会同时停下解析一份巨大配置文件，修复办法是精简配置、拉长刷新间隔、给后台任务加抖动。连接池默认 LIFO 复用连接，突发流量过后最慢的节点反而被分配更多请求，越慢越堵，改成 FIFO 才打破循环，如今负载均衡主要交给 Istio 和 Envoy。

这是两篇系列的第一篇，只讲演进史。下篇会接着讲多租户可靠性、读性能的分层优化，以及和 Azure Cosmos DB 的合作怎么继续扩。

OpenRouter 同名模型换后端表现不一，两个用法避坑

这是什么：9 月 11 日，开发者 Simon Willison 在博客发文，提醒 OpenRouter 用户留意模型行为不一致的坑，主要现象由 Mohamed Moustafa 整理发现。OpenRouter 是聚合多家大模型提供商的调用服务，官方卖点是自动处理回退、为每次请求挑选最具性价比的选项，接入方只需调用一个统一接口。由于各家提供商运行的服务软件、优化和设置不同，同一个模型名被自动路由到不同提供商时，请求行为可能不一致。有的提供商运行视觉模型却缺少视觉能力，推理力度参数的处理方式也因提供商而异。文中给出两个对策，用 provider.only 参数锁定提供商，用 /endpoints 方法查询某模型的可用提供商列表。
🔥 为什么今天值得看：对把 OpenRouter 接进自己产品的开发者，这个坑直接影响结果稳定性。同一个模型名，今天路由到 A 提供商，明天可能换成 B 提供商，能不能看图、推理力度怎么处理都跟着变，测试时的表现和上线后的表现对不上，排查时还容易先怀疑自己的代码。这篇短文把差异的来源指到了各家提供商的服务软件这一层，配合锁定提供商与查询提供商列表两个用法，开发者能把这个变量固定住。

9 月 11 日，开发者 Simon Willison 在博客里提醒 OpenRouter 用户留意一个容易被忽略的坑，现象主要由 Mohamed Moustafa 整理发现。OpenRouter 是一个聚合多家大模型提供商的调用服务，官方卖点写着自动处理回退，并为每次请求挑选最具性价比的选项，接入方只要调用一个统一接口，请求就会被转发给当时合适的后端提供商。麻烦在于，各家提供商运行的服务软件、优化和设置并不相同，同一个模型名被自动路由到不同提供商时，请求行为会跟着变化。有的提供商运行视觉模型时甚至缺少视觉能力，reasoning effort（推理力度）参数的处理方式也会因提供商而异，代码没改，效果却可能变样。

对策有两个。请求里加上 provider.only 参数，指定只路由到某一家提供商，把变量固定下来。想先摸清某个模型背后有哪些选择，调用 /endpoints 方法，传入模型 ID 就能拿到可用提供商列表。这篇短文没有把行为差异归为 OpenRouter 的产品缺陷，差异的根源在各家提供商自己的服务软件，图省心和要稳定之间，用户可以用这两个用法自己拿捏。

这是什么：一篇发表在个人博客并登上 Hacker News（拿到 30 分）的实操教程，演示了如何在 MacBook Pro M5 48GB 上搭出一套完全本地的 AI 编程环境。方案由三部分组成，Ollama 负责在 Mac 上跑开源模型，OpenCode 充当编程助手干具体的活，Docker 沙箱工具 sbx 把整套环境隔离进容器。作者认为 48GB 内存是本地开发的甜蜜点，刚好带得动 30B 级模型加一份可观的上下文。
🔥 为什么今天值得看：它用具体数字回答了一个常见疑问，一台笔记本到底带不带得动本地 AI 编程。48GB 内存被排成明确的预算，模型占大头，上下文主动砍到 64K 防止内存耗尽，沙箱固定预留 3GB，读者拿自己的内存容量一对照就能判断能不能复制。沙箱隔离还补上了安全短板，模型幻觉出的危险命令被关在容器里，够不到真实系统。作者提到公司里的前沿模型同样被要求在沙箱里运行，这套做法在正式工作场景已经过验证。

48GB 内存的 MacBook Pro 能不能当 AI 编程的主力机？一篇登上 Hacker News 的实操教程用一套完整配置给出了肯定答案。作者在自己的 MacBook Pro M5 48GB 上组合了三件工具，Ollama 在本地跑模型，编程助手 OpenCode 负责读代码改代码，Docker 沙箱工具 sbx 把整套环境关进容器。他的判断是 48GB 正好够跑 30B 级开源模型，还留得出一份可观的上下文，属于本地开发的甜蜜点。

内存这本账算得很细。主力模型选了量化版 qwen3.8:27b-mxfp8，占用约 32GB，能在 OpenCode 里连续数小时无人值守地跑任务。量化可以理解为把模型文件压缩得更省内存，能力略降，换来普通笔记本也装得下。作者特意把它的上下文限制在 64K，也就是一次对话最多记住约 6.5 万个 token，不设限的话内存一耗尽系统就会卡死。深度文件分析交给更大的 gemma4:31b-mxfp8，它拥有 256K 上下文。这份预算里还要单独留 3GB 给沙箱。

隔离这一步的动机很直白，本地模型同样会幻觉，一条乱执行的命令足以毁掉你的电脑。OpenCode 被放进 sbx 容器后，通过 host.docker.internal 这个地址访问宿主机上的 Ollama 服务，模型留在宿主机上，操作都在容器内完成，出了问题也波及不到真实系统。想照抄的读者要注意，运行 sbx 必须登录 Docker 账号，作者承认这个要求在开发者社区里普遍不受欢迎，但目前绕不过去。

GitHub 上一个运营了一年半多的数学建模开源项目 MathModelAgent 出现在 9 月 12 日的 Trending 榜上，它在两天前发布了 v0.0.19，做了一次彻底的架构转型。数学建模比赛（国内国赛、美国 MCM/ICM 这类赛事）要求队伍在几天内完成建模、编程和论文，这个项目瞄准的就是把整套流程交给 AI。作者两年前为此自己写了一套多 Agent 框架，让建模手、代码手、论文手分工协作，这次他把自研框架整个砍掉，项目改造成一组 SKILLS，可以理解为装进 AI 助手的技能包，直接装在 Claude Code 或 Codex 里运行。

安装只需一条 npx skills add 命令，装好后输入 /1start-mathmodel，问题分析、建模、编码、绘图、论文排版自动串联完成，作者称中间无需人工干预。项目内置 17 套 Typst 赛事模板，覆盖国赛、华数杯、华为杯、MCM/ICM 等，自动匹配赛事类型，产出可直接提交的 PDF。论文交付前还要过 9 步自动验收，从文本泄漏检测、数值一致性校验到 Typst 编译和 PDF 可视化检查，目标是拦住低级错误。配套知识库内置 AHP、TOPSIS、ARIMA、GA 等模型的选择决策树和常见易错模式，用来降低模型幻觉。

开源工具 Hyperresearch 把 Claude Code 变成逐条核验引用的深度研究 agent

这是什么：开源项目 hyperresearch 出现在 2026 年 9 月 12 日的 GitHub Trending 榜上，约 2.6k star、259 fork。这是一个 MIT 协议的 Python 工具，用 pip 安装后把编程助手 Claude Code 变成深度研究 agent，也就是让 AI 自己上网查资料、读论文、写研究报告的工具。输入一个问题，它跑一条 16 步的流水线，产出一份经过多轮审查的报告，读过的材料全部存进本地知识库留给下次使用。
🔥 为什么今天值得看：AI 生成研究报告最常被诟病的是引用不可信，编造的引文、已撤稿的论文、把一条通稿的多次转载当成多方印证，都是高频事故。hyperresearch 把审查做进流程本身，草稿要过 4 个批评者这一关，引用逐条核验后才能出稿，撤稿来源硬性拦截。多数同类工具跑完一次就把材料丢掉，它把读过的资料存成 markdown 文件建库，下次研究先查库再上网，资料可以反复复用。对需要 AI 帮忙做调研的人，每条引用都能回查，比报告措辞漂亮更实用。

GitHub Trending 今天出现了一个叫 hyperresearch 的开源项目，已拿到约 2.6k star。它把 Claude Code 改造成深度研究 agent，也就是让 AI 自己查资料、读论文、写报告的那类工具。一条提示词进去，16 步流水线跑完，交出一份多轮审查后的研究报告。

它最花力气的地方在可信度。草稿完成后，README 所列的语料、辩证、深度、广度四类对抗式批评者并行攻击草稿；负责修改的补丁器在权限层被锁成只能读和改既有文字，整篇重写在物理上做不到。出稿前逐条核验引用，检查每条引用是否真的支撑它所在的那句话，编造的引文和未声明的撤稿来源都会被硬性拦下；同一篇通稿被 5 家转载，只按 1 个独立信源计票。

读过的每份材料都落进一个 markdown 加 SQLite 索引的持久知识库，markdown 文件是本体，SQLite 只是可重建的索引，下次研究先查库再上网。项目自称在 DeepResearch-Bench RACE 榜单领先，README 同时写明这是内部基准的前瞻外推，第三方验证尚未完成。运行分三档，轻量查询约 30 到 40 分钟，默认完整档 1.5 到 2.5 小时，论文级长跑可选，4 到 8 小时处理 300 到 450 个来源。
