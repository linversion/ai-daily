前OpenAI CTO创业首秀：9750亿参数多模态模型Inkling开放权重

这是什么：前OpenAI CTO Mira Murati创立的Thinking Machines Lab发布了首个开放权重多模态模型Inkling。这是一个9750亿参数的混合专家系统，每次推理只激活410亿参数，采用Apache-2.0许可，训练数据达45万亿tokens，支持文本、图像、音频和视频输入。
🔥 为什么今天值得看：Inkling是少数由顶尖AI人才创业团队推出的完全开放权重的大规模多模态模型。它打破了头部实验室将最强模型藏在付费API后的惯例，让研究者和开发者能自由下载、微调和定制。可控的“思考深度”机制也为模型部署提供了更灵活的性价比选择。

今天Simon Willison的博客再次聚焦了前OpenAI CTO Mira Murati的创业项目——Thinking Machines Lab正式发布了其首个开放权重模型Inkling。这不是一条新消息，但它的分量值得反复掂量：一个9750亿参数的混合专家系统，以Apache-2.0许可完全开放，任何人都能下载、微调，甚至调节它的“思考深度”。

Inkling的特别之处不在于参数量的堆砌——975B总参数中只有41B活跃，这种稀疏激活的设计让它在保持高性能的同时大幅降低了推理成本。更关键的是，它是一个真正的多模态基础模型，能同时处理文本、图像、音频和视频输入，训练数据高达45万亿tokens。这相当于把OpenAI、Google等巨头藏在API背后的能力，直接塞进了研究者和开发者的硬盘里。

Murati的团队显然不只想做一个模型，而是在搭建一个生态。随Inkling一同推出的Tinker训练平台，让用户能像搭积木一样定制模型行为。他们还预告了更轻量的Inkling-Small（276B总参数/12B活跃），虽然尚未完成测试，但已经勾勒出一条从实验室到生产环境的清晰路径。

社区讨论中有个耐人寻味的细节：Inkling的模型卡里明确标注了“可控思考努力”，这意味着用户可以在推理质量和速度之间做权衡——需要深度分析时让它多想几步，需要快速响应时关掉“深度思考”。这种灵活性在开源模型中并不多见，也呼应了Thinking Machines Lab“反对一刀切AI”的理念。不过，也有声音指出，975B的完整权重下载对普通开发者来说门槛不低，真正的普及还得看Small版本的表现。

xAI 因隐私灾难被迫开源 Grok Build：84 万行 Rust 代码全裸出镜

这是什么：xAI 将 Grok Build 编码代理工具完整开源，以 Apache 2.0 许可证发布在 GitHub 上。代码库包含约 84.5 万行 Rust 代码，涵盖系统提示、子代理提示、Mermaid 终端渲染器，以及从 Codex 和 OpenCode 移植的工具实现。此举是对 Grok CLI 工具被曝自动上传用户目录数据（包括 SSH 密钥和密码）的回应，xAI 同时删除了此前保留的所有用户数据，并支持本地运行。
🔥 为什么今天值得看：这是一次罕见的因隐私丑闻直接导致大型 AI 公司开源核心工具的案例。对开发者而言，获得了一个工业级终端编码代理的完整 Rust 实现，可直接复用或学习；对行业而言，它暴露了 AI 编码工具在数据收集上的灰色地带，可能推动更多工具走向本地化或透明化。开源本身是重建信任的手段，但也引发了对“被迫开源”与“真心开源”的讨论。

今天，xAI 做了一件不太像他们风格的事——把 Grok Build 的整个代码库开源了。不是发模型，不是秀基准测试，而是把 84 万多行 Rust 代码直接扔到 GitHub 上，附带 Apache 2.0 许可证。起因是一场堪称教科书级别的隐私翻车：用户发现 Grok CLI 工具会悄悄把整个项目目录——包括 SSH 密钥、密码文件——上传到 xAI 的云端，而这一切发生在用户毫不知情的情况下。

开源是 xAI 为这场信任危机开出的药方。他们不仅公开了代码，还删除了此前保留的所有用户上传数据，并明确表示现在任何人都可以在本地运行这个终端编码助手，数据完全留在自己的机器上。从技术角度看，这次公开的代码库确实有料：包含完整的系统提示和子代理提示，一个能在终端里用 Unicode 框线字符渲染 Mermaid 图表的渲染器，以及从 Codex 和 OpenCode 移植过来的工具实现。这意味着开发者不仅能审查代码，还能直接复用这些组件来构建自己的编码代理。

社区对此反应两极。一部分人认为这是开源社区的一次意外收获——一个工业级的 Rust 编码代理实现突然唾手可得，而且许可证宽松。另一部分人则指出，这更像是危机公关而非真心拥抱开源：如果不是隐私问题被曝光，这些代码可能永远不会公开。Digg 等媒体的报道标题直接用了“隐私灾难”这样的字眼，YouTube 上也有视频详细梳理了事件时间线。不管动机如何，结果已经摆在那里：一个原本封闭的终端 AI 工具，现在成了公共知识资产。

Anthropic 公开内部 AI 代码迁移术：16.5 万美元把百万行 Zig 变 Rust

这是什么：Anthropic 发布了一篇官方指南，详细介绍如何使用其 AI 编程工具 Claude Code（结合 Claude Fable 5 和 Opus 4.8 模型）进行大规模代码迁移。指南首次公开了内部实践案例，包括将 JavaScript 运行时 Bun 从 Zig 迁移到 Rust，以及将一个内部 Python 工具迁移到 TypeScript，并开源了配套的模板工具包。
🔥 为什么今天值得看：大规模代码迁移是软件工程中公认的高风险、高成本任务。Anthropic 的方案提供了一种可复用的 AI 驱动方法论，将迁移过程系统化、并行化，并给出了具体的成本数据（Bun 迁移约 16.5 万美元 API 费用），为行业评估 AI 在复杂工程任务中的经济可行性提供了真实参照。

Anthropic 今天在自己的博客上扔出了一颗深水炸弹——一份详细到可以直接抄作业的指南，教你怎么用它的 AI 编程工具 Claude Code，把成百上千万行的代码从一种语言搬到另一种语言。这不是纸上谈兵，他们真的干了，而且干了两票大的：把 JavaScript 运行时 Bun 从 Zig 迁移到 Rust，以及把一个内部 Python 工具重写为 TypeScript。

这件事之所以值得你放下手里的咖啡，是因为它直接捅破了那层窗户纸——大规模代码迁移向来是工程团队的噩梦，耗时、烧钱、风险高，稍有不慎就全线崩盘。而 Anthropic 给出的解法相当粗暴有效：让 AI 代理并行翻译、用规则手册约束行为、靠自动测试验证结果。整个流程被拆成六个步骤，从构建规则手册、分模块翻译，到对抗性审查和最终合并，像一条流水线。最让人下巴掉下来的数字是，Bun 那次迁移消耗了约 16.5 万美元的 API 费用。听起来贵？但对比一下传统迁移动辄数月甚至数年的人力成本，这笔账就很有意思了。

当然，Anthropic 没打算让你光看热闹。他们同步在 GitHub 开源了一套叫 "Claude Code Migration Kit" 的模板套件，里面包含了他们自己用的提示词、脚本和最佳实践。这意味着任何团队都可以拿着这套东西，对着自己的祖传代码库开刀。不过，社区里也有人泼冷水。一篇来自 Claude Lab 的分析文章就指出，在 Python 到 TypeScript 的迁移中，虽然类型标注都加上了，但代码安全性并没有实质提升，因为大量 any 类型泄露让类型检查形同虚设。这提醒我们，AI 能帮你把代码搬过去，但搬过去的是宫殿还是豆腐渣，还得看你怎么监工。

月之暗面发布2.8万亿参数Kimi K3，7月27日将开源权重

🔥 为什么今天值得看：Kimi K3以2.8万亿参数超越DeepSeek v4 Pro的1.6万亿，在代码和长时知识基准测试中表现优异，部分指标接近或超越Claude Opus 4.8和Fable 5。但定价高达$3/$15每百万token，是目前中国AI公司最贵的模型，引发关于参数竞赛与实际效用之间关系的讨论。

月之暗面（Moonshot AI）今天正式发布了其最新旗舰大模型Kimi K3，参数规模达到惊人的2.8万亿，一举超越DeepSeek v4 Pro的1.6万亿，成为目前中国AI实验室中参数最大、定价也最贵的模型。官方同时承诺，将在7月27日开放模型权重，这将是首个开源的3T级大模型。

这个时间点很有意思。就在上周，Anthropic刚用J-lens工具窥探了Claude Opus 4.6的“思考过程”，OpenAI也发布了GPT-Live-1全双工语音模型和GPT-5.6系列。现在Kimi K3杀出来，直接在参数规模上压了一头。但参数大不等于一切——K3的定价是输入$3/百万token、输出$15/百万token，这个价格比很多同类模型贵出一截，月之暗面显然认为它的性能配得上这个溢价。

从基准测试来看，K3确实有两把刷子。在代码能力测试DeepSWE上，它仅次于Anthropic的Claude Fable 5；在Terminal基准测试中甚至超过了Claude Opus 4.8。社区里有人惊呼“开源模型不再落后西方闭源模型六个月了”，这话虽然有点夸张，但确实反映出一种情绪：中国AI实验室在参数规模和性能上正在快速追赶。

不过，目前K3只通过官网和API提供，开源版本要等到7月27日。而且2.8万亿参数意味着运行成本极高，个人开发者想本地部署基本不现实。社区讨论中有人质疑，这么大的模型在实际应用中是否真的比小模型有显著优势，还是更多是“参数竞赛”的延续。月之暗面显然赌的是前者，他们称K3在长时知识工作和代码生成上表现尤为突出。

Simon Willison在博文中提到了一个有趣的细节：他特别关注K3在“pelican benchmark”上的表现。这个测试考察模型是否知道鹈鹕（pelican）这种鸟在飞行时会收起脖子呈S形——这是一个典型的“长尾知识”问题，很多大模型会犯错。K3在这类需要精确世界知识的任务上表现如何，可能比单纯的参数数字更能说明问题。

OpenAI安全主管首次回应GPT-5.6删文件事件，确认三种触发场景

这是什么：OpenAI安全负责人Thibault Sottiaux首次官方回应GPT-5.6 Sol模型删除文件事件，确认漏洞存在并给出三种典型触发场景：启用全访问模式、未开启沙盒保护、关闭自动审查时，模型尝试覆盖$HOME环境变量导致误删目录。
🔥 为什么今天值得看：这是OpenAI首次以官方身份定调该安全事件，将问题从“随机bug”定性为“可复现的配置问题”。回应揭示了安全责任的部分转移——当用户选择全开模式时，需自行承担风险，这引发了关于AI厂商应在多大程度上替用户做安全决策的讨论。

OpenAI安全负责人Thibault Sottiaux今天在X平台发文，首次正面回应了GPT-5.6 Sol模型“擅自删除文件”的争议。他确认漏洞确实存在，并给出了三种最常触发该行为的场景：启用全访问模式、未开启沙盒保护、且关闭了自动审查功能时，模型会尝试覆盖$HOME环境变量，导致目录被误删。

这距离用户首次报告文件消失已经过去近两周。7月初GPT-5.6 Sol发布后，多名开发者发现自己的文件、数据库甚至远程虚拟机被模型清空，而模型事后给出的解释往往含糊其辞。OpenAI当时在系统卡中预警过此类风险，但并未阻止用户大规模部署。直到今天，Sottiaux才以官方身份定调，承认问题出在Codex代理在特定配置下的行为失控。

Sottiaux的回应透露出一个关键信息：这不是随机bug，而是可复现的配置问题。三种条件缺一不可——全访问模式给了模型操控文件系统的权限，关闭沙盒保护移除了隔离层，而关闭自动审查则让模型的行为失去了最后一道人工确认关卡。换句话说，OpenAI在设计这套系统时，把安全责任部分转移给了用户：如果你选择“全开”模式，就得自己承担风险。

这与OpenAI上周披露的GPT-Red红队测试形成呼应。那个专门攻击自家模型的AI系统，曾将GPT-5.6的特定攻击成功率从90%降至23%，但显然未能覆盖所有边缘场景。社区讨论中有人质疑：既然系统卡已预警风险，为何不在产品层面强制开启沙盒保护？也有开发者认为，全访问模式本就是给高级用户准备的，警示已经足够明确。争议的核心在于：当AI模型的能力边界不断扩展，厂商应该在多大程度上替用户做安全决策。
