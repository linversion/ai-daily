Meta 发布 Muse 系列：能自己搜图修图的 AI，还顺手给视频加了原生音频

这是什么：Meta 发布新一代媒体生成模型 Muse 系列，包含图像模型 Muse Image 和视频模型 Muse Video。Muse Image 是一种代理型图像生成模型，能通过调用搜索工具、编写代码和自我精炼来生成更准确、更符合复杂指令的图像；Muse Video 则是文本到视频生成模型，首次在 Meta 视频模型中引入原生音频支持。同时推出 Content Seal 不可见水印系统用于内容溯源。Muse Image 已正式可用，Muse Video 为预览版。
🔥 为什么今天值得看：这是 Meta 首次将代理能力引入图像生成模型。相比传统的“提示词到图像”模式，Muse Image 能主动拆解任务、使用外部工具并自我纠错，大幅提升了复杂指令的遵循度和生成结果的可靠性。这标志着 AI 创作工具从被动生成向主动解决问题的范式转变。Muse Video 的原生音频能力则让 AI 视频向完整的视听体验迈出关键一步。

今天 Meta 正式推出了新一代媒体生成模型 Muse 系列，包含图像模型 Muse Image 和视频模型 Muse Video。这不是一次简单的滤镜升级——Muse Image 被设计成一个“代理型”模型，它能自己调用搜索工具、编写代码来生成或修改图像，甚至在生成过程中自我纠错，直到结果符合你的复杂指令。Muse Video 则首次为 AI 生成的视频带来了原生音频支持，不再是无声的默片。

这套新模型的核心突破在于“代理能力”。以往的图像生成模型，你给它一句提示词，它吐出一张图，好坏全凭运气。Muse Image 不一样，它背后有一个叫 Muse Spark 的联合规划系统，能把你的指令拆解成多步骤任务。比如你说“把这张照片里的咖啡杯换成一只正在喝咖啡的猫，光影要匹配”，模型会先分析原图的光源方向，再搜索合适的猫咪素材，最后通过代码进行合成——整个过程像一个小型创意团队在协作，而不是一个只会按快门的机器。这种“测试时计算缩放”机制，意味着模型在回答你之前，会花更多算力去思考和验证，从而大幅提升复杂指令的遵循度和图像的真实感。

Muse Video 同样值得关注。除了高视觉保真度，它首次在 Meta 的视频生成模型中加入了原生音频生成能力，让画面中的动作有了对应的声音。虽然目前还只是预览版，但方向很明确：AI 生成的视频正在从视觉奇观走向完整的视听体验。

伴随模型发布的还有一套名为 Content Seal 的不可见水印系统，用于标记 AI 生成内容的来源。这算是行业标配动作，但在深度伪造日益泛滥的今天，每一次工具升级都伴随着更强的溯源需求。

社区讨论中，有人对“代理型图像生成”这个概念感到兴奋，认为这可能是未来 AI 创作工具的分水岭——从被动生成到主动解决问题。但也有声音指出，工具调用和自我精炼虽然提升了上限，却可能让生成过程变得更慢、更贵，普通用户在移动端能否体验到完整能力还是个问号。毕竟，让模型自己去搜索和写代码，背后的算力账单不会太好看。

Anthropic 把 AI 编程和办公助手送进政府，FedRAMP High 合规环境开测

这是什么：Anthropic 将 Claude Code 和 Claude Cowork 引入政府领域，通过 FedRAMP High 授权环境提供公开测试版。Claude Code 帮助政府技术团队构建和现代化软件系统，Claude Cowork 处理备忘录编写、RFP 审查、个案处理和演示文稿制作等日常文书工作。配套推出 Claude for Government Desktop 桌面应用，内置符合政府预算、组织架构和审计要求的治理功能。
🔥 为什么今天值得看：这是 Anthropic 首次将 AI 编程和办公工具以 FedRAMP High 最高安全标准推向政府市场。政府机构长期面临合规与效率的矛盾——AI 能提效，但审计和授权流程复杂到让 IT 主管望而却步。Anthropic 这次不仅拿到认证，还专门设计了适配拨款制度的计费方式、层级化权限管理和防篡改审计日志，直接瞄准政府采购和监管的痛点，可能加速 AI 在公共部门的落地节奏。

Anthropic 今天宣布，旗下两款 AI 工具——Claude Code 和 Claude Cowork——正式进入政府领域，通过 FedRAMP High 授权环境向美国公共部门提供公开测试版。这意味着政府机构现在可以在严格合规的云环境中，用 AI 来写代码、审合同、起草备忘录，甚至处理个案文件。

这不是简单的“政府也能用”式开放。Anthropic 专门推出了 Claude for Government Desktop 桌面应用，把商业版的功能打包进一个满足联邦安全标准的壳里。FedRAMP High 是美国联邦政府最高级别的云安全认证之一，通常用于保护最敏感的未保密数据，比如执法记录、财政信息、医疗档案。拿到这个授权，说明 Claude 在政府核心业务中的可用性往前迈了一大步。

更值得关注的是配套的治理能力。政府客户不是普通企业，预算走拨款流程，组织架构层级森严，审计要求近乎苛刻。Anthropic 显然做了功课：计费方式适配拨款制度，管理员可以通过 SCIM 组映射按部门、职级精细分配权限，所有操作记录进防篡改的 hash-chained 审计日志，连 ATO（运营授权）支持文档都准备好了。这套组合拳瞄准的是政府 IT 主管最头疼的问题——不是 AI 能不能用，而是用了之后怎么向审计部门交代。

Claude Code 和 Claude Cowork 的分工也很清晰。前者面向技术团队，帮助政府机构构建和现代化软件系统，本质上是一个懂政府合规边界的 AI 编程搭档；后者则处理日常文书工作，从 RFP（招标需求书）审查到演示文稿制作，把公务员从文件堆里解放出来。Anthropic 在官方博客里强调，这是“为政府预算、组织架构和审计要求量身定制的”，不是拿商业版改个皮肤就上架。

社区讨论中，有人指出这可能是 AI 厂商争夺政府云市场的关键一步。微软、Google 早已在 FedRAMP 赛道上布局，Anthropic 这次带着 Claude 的编程和办公能力切入，差异化在于“不是通用聊天机器人，而是具体任务工具”。不过也有安全研究者提醒，即便有 FedRAMP High 认证，AI 在政府场景中的幻觉和偏见风险依然存在，防篡改日志只能追溯问题，不能预防问题。

开源模型工具调用差？开发者用四招让DeepSeek击败Opus

这是什么：开发者 Ahmad Awais 首次公开分享了一项技术细节：通过编写一个“工具输入修复层”，他让开源模型 DeepSeek V4 Pro 在内部评估中击败了闭源模型 Opus 4.7。该修复层已在 AI 命令行工具 Command Code 中运行约两个月，并计划于月底开源。
🔥 为什么今天值得看：这项分享的价值在于，它颠覆了“开源模型工具调用能力差”的普遍认知，指出问题往往出在僵化的接口设计而非模型本身。它提供了一套具体、可复现的工程方法，通过极低的成本（四个修复函数、两行正则）显著提升开源模型在工具调用任务上的可靠性，为开发者提供了“优化接口”而非“更换模型”的新思路。

今天，开发者 Ahmad Awais 在 Hacker News 等社区详细分享了一项令人印象深刻的工程实践：他通过编写一个“工具输入修复层”，让开源模型 DeepSeek V4 Pro 在内部评估中击败了闭源模型 Opus 4.7，成功率高达 60%。这个修复层已经在名为 Command Code 的 AI 命令行工具中运行了两个月，但这是首次公开其背后的设计哲学和具体代码逻辑。

这项工作的出发点，源于一个许多开发者都感同身受的痛点——开源模型在“工具调用”时总是笨手笨脚。Awais 在观察了数十亿 token 的交互数据后发现，问题往往不出在模型本身，而出在我们给模型设定的“合同”太死板了。他总结出，无论是 DeepSeek、GLM 还是 Qwen，模型在生成工具调用参数时，犯的错误并非随机，而是一个极其有限的组合集，总共就四种：把可选字段发成 null 而不是直接省略；把数组发成 JSON 字符串；给单个参数错误地包了一层 {}；或者在该传数组的地方传了个光杆字符串。针对这四种情况，他写了四个 30 到 100 行的小修复函数，并按严格顺序执行，就解决了约 90% 的工具调用失败问题。

最有趣的一个失败案例，是 DeepSeek-Flash 在写文件路径时，偶尔会输出 Markdown 自动链接格式，比如 [notes.md](http://notes.md)。这不是幻觉，而是模型在聊天训练中被奖励出的“职业病”——它习惯性地把链接渲染成聊天气泡里的样子，却忘了自己正在给文件系统下指令。修复方法仅仅是两行正则表达式。Awais 由此提出一个更深刻的观点：与其说这是“能力差距”，不如说是“工具混淆”。模型知道怎么写路径，只是没被明确告知这个路径是给 fopen 用的，而不是给聊天框看的。通过在 schema 层面用 pathString() 替代通用的 z.string()，就能从根源上堵住这类泄漏。

在架构设计上，Awais 做了一个关键反转：从“先预处理再校验”改为“先校验后修复”。他的第一版方案是先对输入进行标准化处理，结果导致一些恰好长得像 JSON 的文件内容被静默篡改，造成了难以察觉的数据损坏。新方案则让校验器先跑一遍，只在报错的具体字段上精准施放修复技能，修完再校验一次。这不仅避免了误伤有效输入，还免费获得了一套按模型和工具维度统计的修复率监控，能在用户察觉之前就发现模型在特定任务上的性能退化。

对于那些无法通过输入修复解决的关系型约束——比如 readFile 要求 offset 和 limit 必须成对出现——Awais 的策略是“教函数理解模型的意图”。如果模型只传了 limit，就默认 offset 为 0；只传了 offset，就默认 limit 为 2000。然后把做出的选择透明地返回给模型：“注意：未提供 limit，已默认设为 2000 行。如需更多或更少，请重试并同时提供 offset 和 limit。”这种“能修就修，修不了就透明地猜”的策略，让模型在下一轮对话中能够自我纠正。

社区对这份分享反响热烈，许多开发者表示深有同感，认为“工具调用差”的锅确实常常应该由僵化的接口设计来背，而不是直接否定开源模型的能力。Awais 透露，Command Code 的 v1 版本计划于月底开源，届时这套修复层也将公开，这无疑为那些苦于开源模型工具集成难题的开发者提供了一个极具实操价值的范本。

4.4K views · 63 reactions | how did we make deepseek outperform opus 4.7? i've been thinking about why "open model bad at tool calling" is almost always a harness problem, not a model problem. context: spent the two days looking at billions of tokens in Command Code (tb open source ai cli) using deepseek. I ended up writing a tool-input repair layer. the trigger was watching deepseek-flash fail on the simplest /review run, every shellCommand and readFile call bouncing back with a raw zod issues blob, the model unable to recover because the error wasn't in a form it could read. by the end deepseek v4 pro was beating opus 4.7 6/10 times on our internal evals. a few things i learned that feel general: 1/ the failure modes aren't random they're a small finite compositional set. across deepseek-flash, deepseek v4 pro, glm, qwen, the same four mistakes repeat almost exactly: - sending `null` for an optional field instead of omitting it - emitting `["a","b"]` as a json *string* instead of an actual array - wrapping a single arg in `{}` where the schema expected an array (an "empty placeholder") - passing a bare string where an array was expected (`"foo"` instead of `["foo"]`) four repairs, ~30-100 lines each, ordered carefully (json-array-parse must run before bare-string-wrap or `'["a","b"]'` becomes `['["a","b"]']`). that is the whole catalogue. when i hear "this open source model can't do tool calls" i now assume one of those four, and so far that's been right ~90% of the time. 2/ the funniest failure mode is also the most revealing. deepseek-flash, when asked to edit or write a file, sometimes emits the path as a *markdown auto-link*: filePath: "/Users/x/proj/[notes.md](http://notes. md)" our writeFile tool obediently trued creating files literally named `[notes.md](http://notes .md)` until we caught it. this is not a hallucination. it's the post-training chat distribution leaking through the tool boundary the model has been rewarded for auto-linking in conversational output, and is applying that prior in a context where it makes no sense. the fix is two regex lines that unwrap only the degenerate case where link text equals url-without-protocol real markdown like `[click](https://x .com)` passes through untouched. this is also conditioning of their own tools during RL which were different from all other tools we write and ofc can't predict. "tool confusion" is a more useful frame than "capability gap." the model knows how to format a path. it just hasn't been told clearly enough that this path is going to fopen, not into a chat bubble. so we encode that hint at the schema level `pathString()` instead of `z.string()` and the leak is plugged for every path field at once. 3/ the design choice that mattered was inverting preprocess-then-validate to validate-then-repair. my first attempt was the obvious one: a preprocessing pass that normalized inputs (strip nulls, parse stringified arrays, etc.) before zod ever saw them. it broke immediately, writeFile content that *happened* to be json-shaped got rewritten before it hit disk. silent corruption, easy to miss in a smoke test. then i made it less greedy - parse the input as-is. if it succeeds, ship it. valid inputs are never touched. - on failure, walk the validator's own issue list. for each issue path, try the four repairs in order until one applies. - parse again. on success, log `tool_input_repaired:${toolName}`. on failure, log `tool_input_invalid:${toolName}` and return a model-readable retry message. the structural insight here is: when you preprocess, you encode a prior about what's broken. when you let the validator complain first, the schema is the prior, and you only spend repair budget at the exact paths the schema actually disagreed at. the validator is doing the work of localizing the bug for you. it's the same shape as cheap-then-careful everywhere else try the fast path, fall back on evidence. (this also gives you per-tool telemetry for free. you can watch repair rates per (model, tool) and notice when a model regresses on a specific contract before users do.) 4/ shape invariants and relational invariants need different fixes. the four repairs above all handle shape problems wrong type, missing key, wrong container. but read_file had a *relational* invariant: "if you provide offset, you must also provide limit, and vice versa." deepseek kept calling `readFile({ absolutePath, limit: 30 })` and getting an `ERROR:` back. you can't fix this with input repair, because each field is independently valid the bug is in the relationship between them. so i taught the function the model's intent instead. `limit` alone → `offset = 0`. `offset` alone → `limit = 2000` (matches common read tool ops default). then surfaced the decision back to the model in the result: "Note: limit was not provided; defaulted to 2000 lines. To read more or fewer lines, retry with both offset and limit." no `Error:` prefix, so the tui doesn't paint it red. the model sees what we picked and can self-correct on the next turn if our guess was wrong. transparency over silent magic wins big. repair where you can. extend semantics where you can't. surface the choice either way. zoom out: a lot of what looks like model capability is actually contract design. a strict schema is a choice with a cost it filters out noise, but it also filters out recoverable noise from any model that hasn't memorized the exact json contract you happened to pick. the largest commercial models eat that cost invisibly and are linient on tool calling because they've seen enough of every contract during pretraining; open models pay it loudly and get dismissed for it. the harness is where you mediate between distributions. four small repairs (i'm sure more to follow as we have three more merging today), two regex lines for auto-links, one relational default, one prefix change. the model didn't change. the contract got more forgiving in exactly the places it needed to be. deepseek v4 pro now beats opus 4.7 6/10 times on our internal evals. imo "skill issue" applies to the harness more often than the model. | Ahmad Awais

Claude Cowork 登陆手机和网页，AI 代理开始跨设备替你加班

这是什么：Anthropic 将原本仅在桌面端可用的 AI 工作代理 Claude Cowork 扩展至 Web 端和移动端（Beta 阶段，Max 用户优先），用户现在可以在手机或浏览器上启动、监控和收取任务结果，任务可在设备离线时在云端继续运行，完成后推送通知到手机。
🔥 为什么今天值得看：根据 Anthropic 内部数据，大多数 Claude Cowork 用户并非程序员，而是在处理报告、研究、内容创作等通用知识工作。跨设备、后台运行是 AI 代理真正融入日常工作流的关键一步，标志着编码代理的竞争正在向更广泛的办公场景蔓延。

今天 Anthropic 官方宣布，原本只能在桌面端使用的 AI 工作代理 Claude Cowork 正式登陆 Web 端和移动端。这意味着你可以在手机上启动一个任务——比如让 AI 帮你整理季度报告的数据、创建一份演示文稿——然后关掉电脑去喝咖啡，任务会在云端继续跑，手机随时弹出进度通知。

TechCrunch 同日的报道点出了一个更值得玩味的背景：根据 Anthropic 内部使用数据，大多数 Claude Cowork 用户其实不是在写代码，而是在处理报告、研究、内容创作这类通用知识工作。这解释了为什么 Anthropic 要急着把 Cowork 从桌面解放出来——编码代理的战场已经烧到了办公室的每一个角落，而跨设备、后台运行恰恰是真正融入日常工作流的关键一步。

目前这个功能处于 Beta 阶段，优先向 Max 订阅用户逐步开放。Anthropic 在支持文档里也提醒用户注意安全边界——Cowork 可以自主操作浏览器、读写文件，所以别在不受信任的环境里让它处理敏感数据，也别给它访问你不想让它碰的账户权限。

社区讨论里有人兴奋地称之为“真正的 AI 同事”，但也有人泼冷水：后台运行意味着你更难实时监督 AI 在干什么，一旦它跑偏，等你发现时可能已经浪费了不少计算资源和时间。不过从 Anthropic 的节奏来看，让 AI 代理从“你盯着它干活”进化到“它自己默默把活干完然后通知你”，这条路线已经走得很坚决了。

腾讯开源295B混合专家模型Hy3，性能对标5倍参数旗舰

这是什么：腾讯发布295B参数的混合专家（MoE）大语言模型Hy3正式版，采用Apache 2.0开源许可。相比4月底的Preview版本，正式版收集了50余个产品的反馈，使用更高质量的数据扩展后训练，在产品和生产力任务上的实用性显著提升。
🔥 为什么今天值得看：Hy3用21B活跃参数撬动295B总参数容量，官方称性能可媲美2-5倍参数量的旗舰开源模型，大幅降低了高性能大模型的推理成本。产品驱动的后训练策略也让模型更贴近真实应用场景，而非单纯追求榜单分数。

腾讯今天正式开源了其295B参数的混合专家（MoE）大语言模型 Hy3，采用 Apache 2.0 许可。这不是一个简单的技术预览版——相比4月底发布的 Hy3 Preview，正式版吸收了来自50多个产品的反馈，在后训练阶段下了狠功夫，让模型在真实产品和生产力任务上的实用性有了肉眼可见的提升。

Hy3 的架构设计很有意思：295B 总参数中只有 21B 活跃参数，这意味着它用相对较小的推理成本，就能撬动巨大的模型容量。官方给出的性能对比相当激进——声称其表现不仅超越同尺寸模型，甚至可以媲美参数规模 2 到 5 倍的旗舰开源模型。如果这个说法站得住脚，那意味着你用一张消费级显卡就能跑出接近千亿参数模型的效果，这对中小企业和独立开发者来说是个不小的诱惑。

模型支持 256K 上下文长度，这已经成了当下大模型的标配门槛。但真正值得关注的是后训练策略的转变：腾讯没有闭门造车，而是把模型放进 50 多个产品里跑了一圈，收集真实世界的反馈来优化训练数据质量。这种“产品驱动”的后训练思路，比单纯刷榜单分数更接地气，也解释了为什么他们敢强调“实用性”而非仅仅“跑分”。

社区讨论中，有人拿它和智谱的 GLM-5.2 做对比——同样是开源路线，同样在参数效率上做文章。不过 Hy3 的 Apache 2.0 许可比某些“伪开源”模型要友好得多，商用几乎没门槛。当然，295B 的总参数量对硬件要求依然不低，量化版本和社区适配工具链的跟进速度，将决定它能否真正走进普通开发者的工具箱。
