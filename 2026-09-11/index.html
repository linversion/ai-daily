OpenAI把Codex的运行时开放成公共服务，公测上线

这是什么：MarkTechPost 报道，OpenAI 于 9 月 10 日把 Agents API 推入公开测试，所有开发者可直接使用。它构建在开源的 Codex harness 之上，由 OpenAI 托管维护。harness 指代理的运行骨架，负责管理上下文、调用工具、协调子代理这些让代理持续干活的工程环节。开发者现在一次 API 调用就能创建持久会话（Session，一种能持续接任务、可中途纠偏的代理实例），官方示例使用 gpt-6-astra 模型，多子代理并发上限设为 3 个。定价不收额外服务费，按 token、工具和容器时间计费。当前数据仅驻留美国，且不支持零数据保留，受监管工作负载暂时无法使用。
🔥 为什么今天值得看：在这次发布之前，开发者想用 OpenAI 做代理有两条路，Agents SDK 自己集成，Responses API 自己编排状态。Agents API 补上了完全托管的第三条路，集成成本在官方对比中列为最低，会话状态也交由 OpenAI 保存。让代理连续可靠地跑几天，属于最难啃的工程部分，这部分负担现在移到了 OpenAI 一侧。Blaxel、Cloudflare、E2B、Modal、Vercel 等 9 家云和沙箱厂商第一时间提供一等集成，说明代理运行环境正在成为云厂商争抢的新位置。对普通用户而言，底层搭建变简单之后，能长时间自主干活的 AI 应用才有机会批量出现。
展开正文

9 月 10 日，OpenAI 把 Agents API 送进公开测试。MarkTechPost 报道称，所有开发者现在都能调用这个接口，它把驱动编程代理 Codex 的那套 harness 开放成了公共服务。harness 可以理解成代理的运行骨架，代理替人持续干活时，总得有东西帮它管理对话记忆、挑选和调用工具、把大任务拆给子代理，这些工程活过去要开发者自己搭。如今 OpenAI 托管并维护这套骨架，开发者一次 API 调用就能创建一个能连续干活的代理，公告里的示例用的是 gpt-6-astra 模型。

OpenAI 团队表示，在把 Codex 扩展到大规模的过程中，他们看清了长时运行的代理需要什么，一套会管理上下文、协调子代理的骨架，加上能让代理连续可靠跑几天的基础设施。代理在哪里跑是主要的架构决策，官方给了三种沙箱选择，也允许不用沙箱。OpenAI 托管沙箱复用 Codex 和 ChatGPT 背后的隔离基础设施，可预装文件、软件包、技能和插件；自托管方案是在自己的环境里运行 codex exec-server，用受限密钥注册，通过 WebSocket 向外连接，所有连接都从内侧发起；第三种是伙伴沙箱，Blaxel、Cloudflare、Daytona、DigitalOcean、E2B、Modal、Oracle、Runloop、Vercel 这 9 家厂商提供一等集成。

骨架内置的能力集中在四件事上。会话接近上下文上限时，系统自动压缩早期内容，开发者不用自己写压缩逻辑；工具搜索按需加载工具定义，既省 token 又保住模型缓存；程序化工具调用让代理并行发起调用并链式衔接，结果先在代码里过滤合并，只把相关数据放回上下文，支持 MCP、自定义函数和网络搜索等内置工具；开启多代理模式后，主代理把复杂任务拆成独立部分，每个子代理持有自己的上下文，主代理负责协调并汇总，公告示例中并发上限设为 3 个。OpenAI 还把 harness 和模型放在一起维护，每次模型发布都提供版本化访问。

在 OpenAI 自己的对比里，Agents API 集成成本最低，会话状态由 OpenAI 保存，Agents SDK 居中，Responses API 最费事，历史记录要开发者自己管。收费上没有额外服务费，按 token、工具和容器时间计费。限制同样明确，数据只驻留美国，不支持零数据保留（一种要求服务商合同承诺完全不保存客户数据的合规安排），受监管行业的工作负载暂时用不上。OpenAI 同时公布了几组早期客户数据，并注明由厂商提供，并非独立基准。Ciridae 的评测分从 0.71 升到 0.85，子代理流程延迟降到原来的四分之一；SafetyKit 迁移案例审查流程后，单案成本下降 60%；Hypha 把骨架和沙箱分离后，失败的代理响应减少 86%；Nash.ai 在全球物流网络中运行着数千个长时代理。

DeepSeek 新模型把 AI 记忆压到每 token 890 字节

这是什么：DeepSeek 发布并开源 DeepSeek-V4.1-Flash，一个 552B 参数的多模态混合专家模型（另带 196B Engram 参数），上下文窗口 100 万 token，消化输入时每个 token 激活 8B 参数、生成时激活 16B。全局 KV cache 压到每 token 890 字节，约为上一代 V4-Flash 的 1/4、初代 V1 的 1/437。权重以 MIT 协议上架 Hugging Face，API 已上线并保持错峰半价。
🔥 为什么今天值得看：长任务的智能体把大模型服务变成了输入密集型负载，百万字上下文加反复消化输入，缓存的容量和带宽成了新瓶颈。DeepSeek 官方直言缓存命中费用常占智能体成本的大头，缓存每小一号，长任务的账单就轻一分。890 字节这个数字决定百万字上下文能不能便宜地常态运行，也让开源阵营在成本战里握住了正面武器。
展开正文

AI 智能体干活的时间越拉越长，账单的大头慢慢挪了地方。模型每读一段上下文，都要把读过的内容暂存成一份便签，业内叫 KV cache，相当于模型的短期记忆，之后生成答案时反复取用。任务拖到百万字级别，这份记忆会撑爆显存和固态硬盘。DeepSeek 官方在发布公告里写道：“Cache-hit charges often account for a large share of agent costs.” 缓存命中的费用常常占智能体成本的一大块。它刚发布的新模型 DeepSeek-V4.1-Flash，就是冲着这笔账来的。

新模型是一套 552B 参数的混合专家架构，另带 196B 的 Engram 参数，官方称它是新架构家族中最小的模型，原生支持视觉理解，上下文窗口开到 100 万 token。它消化输入时每个 token 只激活 8B 参数，生成回答时激活 16B，两头不对称，读得快也读得省。权重以 MIT 协议上架 Hugging Face，vLLM、SGLang、Transformers 三条部署路径都通，API 分 low、high、max 三档推理。

压记忆靠三层办法。第一层是新的因果编码器-解码器结构，40 层拆成 20 层编码器加 20 层解码器，受 YOCO 启发，解码器不算自己的全局 KV，改用投影权重从编码器最终隐藏状态里推出来，于是 prefill（模型消化输入的阶段）只跑 20 层编码器，计算量近乎减半。第二层是 CSA2 跨层复用，每层被固定分到 Full、Reindex、Reuse 三种模式之一，多数层直接沿用别层算好的主 KV 和索引，18 层编码器按压缩比 2 分三组、20 层解码器按压缩比 1 分五组。第三层是 FP4 量化，把缓存数字从高精度压成 4 位低精度格式（E2M1 加每 16 通道一个 E4M3 scale，遵循 NVFP4 但去掉全局 scale），经量化感知训练，存储比上一代的 FP8 几乎减半。

三层办法叠起来，全局 KV cache 压到每 token 890 字节，约为上一代 V4-Flash 的 1/4、初代 V1 的 1/437；再配合 Decoder SWA Bounded Replay（滑动窗口注意力只重放最后 128 个 prompt token 来重建状态），持久化缓存约为 V4-Flash 的 1/8。部署侧还有配套，短窗口的 SWA KV 不再写固态硬盘，放进只占宿主内存 10% 的分布式池，存活分钟级，全局 KV 则保 72 小时。上下文从 4K 涨到 100 万，单个 token 的解码计算量只多 1/4。

成绩方面，max 推理档下 Terminal-Bench 2.1 拿 90.6，高于 Opus-5 的 89.1 和 GPT-5.6 Sol 的 88.8，DeepSWE v1.1 拿 74.2，同样压过两家的 74.0 和 73.0，Codeforces rating 到 3471。短板也写在同一张表里，GPQA Diamond 的 90.9 低于两家的 93.4 和 94.1，更难的 Terminal-Bench 4.0 只拿 31.2，落后 Opus-5 的 51.8。训练用掉 45T 多模态 token，文本与多模态 7 比 1，稀疏注意力从 64K 上下文从头训起，到 34T token 处扩到 1M；后训练没有新算法，靠可验证 agent 任务的大规模合成、跨脚手架强化学习（Claude Code、Codex、OpenCode 等）加上 40 多位教师的 on-policy 蒸馏。基座用 V4-Pro-Base 三分之一的总参数、四分之一的激活参数，在世界知识和编码上打平。

价格跟着架构一起动。API 错峰时段半价，官方建议把灵活任务排到低谷去跑；旧模型 V4-Flash 与 V4-Flash-Vision-Exp 退役，老名字暂时自动路由到新模型；有 2000 块 GPU 加存储集群的大部署需求，官方欢迎直接来谈。同一天 OpenAI 把跑 Codex 的运行时开放成一次调用的公共服务，DeepSeek 给出的回应在账单另一头，把长任务的记忆成本压下来，而且连权重一起交出去。

OpenAI 把自家先用的数据智能体开卖，成绩单却不给看

这是什么：OpenAI 于 9 月 10 日在 ChatGPT Work 中上线 Data agent。它连接企业的数据仓库、BI 仪表盘、Slack、Google Drive 等数据源，自动排查数据变化，并把结论做成仪表盘、建议和可执行的后续动作。这款产品由 OpenAI 内部自用的数据工具泛化而来，是其第一次作为对外商品发布，ChatGPT Work 对标 Anthropic 今年 7 月上线的 Cowork。
🔥 为什么今天值得看：对普通员工，取数不再排队等数据分析师，Shah 的期待是销售和市场人员能自助拿到答案。对数据团队，工作重心转向维护访问控制和审计轨迹，而不是写一次性查询。更关键的是透明度问题。VentureBeat 的标题点明 OpenAI 跳过了 Databricks 等对手正抢着发布的东西，也就是公开基准。企业在采购时只能听到 OpenAI 关于流程的说法，拿不到可比的准确性数字。OpenAI 自己的定位则是与 Databricks、Snowflake 合作而非竞争，赌跨工具编排的广度能赢过单一工具的深度。
展开正文

OpenAI 的员工曾经和很多公司的人一样，碰到数据问题只能排队等答案。他们给自己造了一个工具，现在这个工具变成了卖给企业的产品。当地时间 9 月 10 日，OpenAI 在 ChatGPT Work 里上线 Data agent，它会连接企业的数据源，自己排查数据发生了什么变化，再把结论整理成仪表盘、建议和可以直接执行的后续动作。ChatGPT Work 对标的是 Anthropic 今年 7 月推出的 Cowork。

这件产品的来历不寻常。OpenAI 今年 1 月在工程博客里介绍过内部数据平台，服务超过 3500 名工程、产品和研究人员，覆盖 600 多 PB 数据和 7 万个数据集。在那个规模下，光找到正确的表就可能比分析本身还费时间。内部工具靠 schema 元数据、人工标注、对表结构的代码级分析，加上跨会话延续纠错的记忆层，逐步解决了这个问题，9 月 8 日 OpenAI 又补充披露了内部使用情况。负责 OpenAI 企业技术垂直业务的总经理 Arpan Shah 接受 VentureBeat 专访时说：“一年前如果你问我，有多大比例的数据问题能全程无人介入地得到解答，那只是公司里很小的一部分。今天 OpenAI 的每个人都能自助解决自己的数据问题，而这个缺口我们也一直从外部听到。”

OpenAI 强调的卖点不是又多一个数据连接器，而是跨工具编排上下文。Shah 说，你当然可以连上 Redshift、Databricks 或者 Snowflake，但当 Data agent 运行时，它能同时从 Slack 和 Google Drive 拉取上下文，在工具之间来回调度，再把信息送回各个生态。支持的数据仓库包括 Amazon Redshift、Google BigQuery、ClickHouse、Databricks、MongoDB、Snowflake 和 Datadog，文件源有 Google Drive 和 SharePoint，仪表盘覆盖 Omni、Oracle BI、Power BI、Sigma、Tableau 和 ThoughtSpot。Shah 列出的动作示例包括带着数据联系客户负责人、给管理层准备汇报、自动刷新演示文稿里的图表。

争议恰恰出在最该给数字的地方。这类产品的厂商发布时通常把检索准确性基准放在最前面，OpenAI 却没有公布任何公开评测，只有一套和自家数据工具对比的内部测试。Shah 把内部反复打磨的流程称为 hill climbing，说这让模型已经非常擅长数据工作。VentureBeat 的报道指出，OpenAI 给出的是关于流程的说法，而不是关于准确性的说法。被问到是否给客户构建跨工具的持久上下文层时，得到的回答也是否定的，Shah 的解释是“把各种上下文按各自状态拼接，而不是自己生成一个全新的上下文层”。对照组就在同一周，Databricks 发布研究声称其 Adaptive Instructed-Retriever 在回答质量上匹配 Claude Sonnet 5、GPT-5.6 Luna 和 DeepSeek-V4-Flash，平均 5.8 秒作答，速度是两倍以上。想横向比较两家产品的企业，眼下没有第三方数字可看。

OpenAI 把自己摆在和 Databricks、Snowflake 合作而非竞争的位置，赌的是公司工具越多，跨工具编排越比单一工具的深度值钱。对普通员工，Shah 的期待是销售和市场人员不再需要找数据分析师取数。数据工程团队也不会消失，工作重心从写一次性查询转向维护访问控制和审计轨迹，让自助式智能体在安全边界内运行。至于它到底答得准不准，OpenAI 没有给出可查的证据，市场只能自己上手验证。

这个工具把搬运的活儿包了下来。它会自动检测本机装了哪些助手，把技能放进各自约定的目录，安装范围分项目级和全局两种，默认用符号链接让所有助手指向同一份文件，更新一处全体生效。技能可以从 GitHub、GitLab、任意 git 地址、本地目录或直链压缩包获取，私有仓库走同一条命令，认证优先复用本机 git 凭证，凭证不会被读进工具进程。分发时用 -a 指定助手，--all 把全部技能装给全部助手，装好之后另有 use 免安装试用、find 交互搜索，list、remove、update、init 分别负责查看、卸载、更新和新建技能模板。

项目今年 1 月在 GitHub 上创建，star 已经到 31.1k，9 月 8 日发布了 v1.5.25。它不生产技能，只负责搬运和兼容格式，落到普通人身上最实际的变化是，换一个编程助手时，攒下的技能可以原样带走。

Meta 发布了新助手 Muse，按官方说法，它能替用户承担杂活，网购、处理邮件、规划行程都算它的活，这也是 Meta 第一次真正把 AI 重心从娱乐挪向生产力工具。The Verge 专栏作者 Emma Roth 上手后的感受是两面的，活儿基本都能干，但它对她本人的了解程度让她发毛。

Muse 靠一台云端虚拟计算机替用户操作。作者把 Google 账号连上去并授权读取、删除邮件，数千封推广邮件被一次清空，移动端登录页反复出错，她最后改在笔记本电脑上连好了账号。她又连了 Amazon，让它按指定尺码、风格和颜色挑运动背心，下单前它注意到购物车里有别的商品，主动问要不要移除，最终只买了背心。它还能生成类似 Gemini Notebook 的 AI 播客、图片、视频和叫 artifact 的交互式网页。版权规则执行得有点歪，它拒绝画红裤子卡通老鼠，却痛快生成了带苹果 logo 的发布会场景，还把 App Store 图标认成 Photos，把 Maps、Music 和本来的 Photos 应用认成 Calender。

真正让作者不安的事出在 Feed 标签页之后。她问 Muse 从她身上看出了什么，它一口气报出动漫、CrossFit、拉布拉多犬、佛罗里达野生动物这些具体兴趣。她追问数据来源，Muse 回答：“说实话，Instagram 在应用里任何地方都不给你看这份清单，我是从账号的 API 数据里读到的，它比界面显示的多。”作者去设置里翻了广告主题列表，只有健身、音乐、电子产品这类粗分类，对不上 Muse 报出的细节。Feed 页还推送了她正在探亲的那个州的新闻，Muse 承认这是从 Amazon 订单的收货地址推出来的。The Verge 就这些数据权限联系了 Meta，发稿前没有收到回应。

作者的结论是，Muse 干低风险杂活称职，还会主动维护个性化建议的 ideas 清单和 goals 清单，但一想到让一个比自己还了解自己的助手去翻私人邮件、碰信用卡，她就放心不下。她认为这种不信任才是产品普及路上真正的坎。

#10research评分 7.8/10genuinely_new

AI 抄专家作业反而退步，Salesforce 改成只改错处

这是什么：Salesforce 团队 9 月 8 日发布论文（arXiv 2609.09134），发现在为弱模型演化出的 harness（围绕模型搭建的系统提示、工具集等外部工作台）上，让弱模型模仿专家的完整操作轨迹做微调，7 个企业智能体任务全部退步 4 到 30 个百分点，覆盖 Qwen3-Coder 和 Gemma 4。论文随后提出 on-policy 专家纠错流水线，不再整段照抄专家，而是让模型自己先做，专家只重写它做错的那一步。
🔥 为什么今天值得看：小模型加定制 harness 是企业压低智能体成本的主流路线，模仿专家轨迹又是最常见的训练手段，这份数据说明两者叠在一起会全面失灵，并且讲清了失灵的机制。论文给出的纠错流水线提供了替代做法，也提醒工程团队把模型权重和 harness 当成一对需要同步更新的组件，只动其中一样可能让另一样跟着失效。对计划用便宜模型落地企业 agent 的团队，这是一份可以直接照做的配方。
展开正文

企业都想让便宜的小模型替自己干智能体的活。除了训练模型，工程师还会给模型配一套外部工作台，包括系统提示、工具清单、执行钩子和上下文管理，业内把这套脚手架叫 harness。Salesforce 团队 9 月 8 日发布的论文（arXiv 2609.09134）研究的正是模型和这套工作台怎样一起升级。

团队先在 7 个企业智能体任务上，围绕一个较弱模型自动演化 harness，发现更强的专家模型用这套工作台反而更顺手，于是按常规思路让弱模型模仿专家的完整操作记录来微调，相当于把学霸的解题过程整本抄下来学。结果 Qwen3-Coder 和 Gemma 4 两个模型在全部 7 个任务上退步 4 到 30 个百分点，而同样的模仿训练放在没演化过的工作台上本来是有效的。

论文把病根找了出来。弱模型学来了专家的规划套路，自己的执行能力跟不上，它原本的操作风格又和为自己定制的工作台互相咬合，换了打法反而处处脱节。团队因此改用 on-policy 专家纠错，让模型自己先做一遍，再由一个元级 MLE 智能体自动定位它实际做错的那一步，专家只重写这一步。模型的规划风格得以保留，工作台升级和模型适配的收益也叠加了起来。论文把这总结为一种保住兼容性的低成本协同演化配方，对想把企业 agent 跑在小模型上的团队有直接参考价值。
