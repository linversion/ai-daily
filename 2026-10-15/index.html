语音基准换冠军，Grok Voice 3.0 每天数百万对话

10 月 14 日，SpaceXSI 发布语音到语音模型 Grok Voice 3.0，官方将其定位为“世界最智能的语音模型”，称其在解决客服来电上创下新纪录，延迟低于一秒。发布方的前身是 xAI，经 SpaceX 收购后两次更名，官网仍使用 x.ai 域名。模型当天进入 Voice Agent API，定价每分钟 0.08 美元，折合每小时 4.80 美元，与 Grok Voice 2.0 持平，调用 grok-voice-latest 的存量 agent 已自动完成切换，开发者无需改动。

在 Artificial Analysis 的独立测试中，Grok Voice 3.0 以 86.9 分登上 Speech-to-Speech Index 第一名，领先 GPT-Live-1(Astra, Medium)的 83.2 与 Gemini 3.8 Live(Ext. Thinking, High)的 82.6，也高于自家上一代的 81.3。这项指数综合了语音推理、τ-Voice 以及盲测对战中的偏好与任务成功率。分项成绩包括 Big Bench Audio 语音推理 98.5%，Speech Agent Arena 人类偏好 Elo 1070，衡量停顿、轮换与打断应对自然度的 Full Duplex Bench 为 97.0%。

榜单里同样有对发布方不利的数字。在考察口音、背景噪声与打断场景下客服通话处理能力的 τ-Voice 上，Grok Voice 3.0 得分 71.6%，落后 GPT-Live-1 的 74.5%；官方选择的叙述角度是，新模型的首音频响应延迟低约 40%，等于在智能与响应速度之间重新划出一条取舍线。成本是另一块筹码，按 Artificial Analysis 的 Big Bench Audio 单任务成本核算，Grok Voice 3.0 为 0.025 美元，低于 GPT-Live-1 的 0.030 美元与 GPT-Realtime-2.1 的 0.055 美元。

企业场景的背书来自 ServiceNow 的开源基准 EVA-Bench，该基准覆盖 200 多个真实企业场景，按准确率与客户体验联合评分，Grok Voice 3.0 取得 74% 的最高准确率，联合评分同样居首。ServiceNow 高级产品总监(Agentic Evals and RAI)Nitin Aggarwal 在官方稿中写道："Grok Voice 3.0 sets a new Pareto frontier on EVA-Bench... setting a new standard for what enterprises can expect from AI on the front line of customer service."

比榜单更硬的是生产数据。Tesla 车辆中每天由 Grok Voice 3.0 处理数百万次对话，驾驶者可以用 Connectors 完成查日历、回邮件等简单请求，把订咖啡、订晚餐交给 Grok Bot，全程免手操作，Grok Bot 的语音模式也由这一代模型驱动。Starlink 呼叫中心用它每天接听 2 万通多语种客服电话，约 70% 无需人工介入，四分之一的销售来电在挂断前完成购买；一个基于 Grok Voice 3.0 搭建的 agent 能独立走完验证客户、排查硬件、发放退款、寄出更换设备的全流程。

需要保留的审慎之处是，基准分数引自 Artificial Analysis 10 月 13 日的测试，生产规模数字来自厂商自述，τ-Voice 上与 OpenAI 的差距客观存在，“世界最智能”属于发布方的官方定位。Unite.AI、Superpower Daily 等媒体的跟进报道基本复述官方口径，独立的横向验证还需要更多时间与样本。

编码 agent 出圈,Amp 重度用户周耗百亿 token

这是什么：OpenAI 官方博客发布 Amp 客户案例,展示其近期密集上线的一批能力,包括 Sign in with ChatGPT 登录集成(换取更多 token 额度与 GPT-6 Astra 访问)、GPT-6 Astra 承担写作设计营销等编程外工作、GPT-Live-1 驱动的 Calling Puck 实时语音(手表可用),以及在 GPT-6 Astra 上测试的 Ultrafast 极速模式。
🔥 为什么今天值得看：编码 agent 的竞争正从写代码扩展到完整工作流。这个案例把计费方式、模型能力、语音交互和响应速度放进同一个产品流程,是 agent 出圈的可参考样本,Sign in with ChatGPT 也显示登录入口正在成为模型分发渠道。需要记住它属客户证言,数字均来自 Amp 一方。
展开正文

先交代来源属性。这是 OpenAI 官方博客最新发布的客户案例,主角是 AI 编程 agent 产品 Amp 和它的 CEO Quinn Slack。客户案例的本质是客户证言加产品展示,发布方是 OpenAI 官方渠道,立场天然偏向自家模型,以下事实与引语均出自原文,阅读时需要带着这层属性。

Amp 想做的是帮开发者把想法变成能运行的软件,覆盖从决定做什么、写代码到设计页面的全过程。它会根据实际效果替用户选择和推荐模型,OpenAI 模型占 Amp 全部 token 用量的大头。这次案例重点展示的,是 Amp 近期密集上线的一批新能力,它们共同把 agent 从代码里推了出来,推进写作、设计、营销这些过去靠人做的环节。

成本是最先被摆上台面的问题。Quinn Slack 描述,Amp 部分重度用户每周要消耗 100 亿 token,而如果人们盯着每一笔用量精打细算,就不敢放手让 agent 去试,也就摸不到它真正的上限。为此 Amp 上线了 Sign in with ChatGPT 集成,用 ChatGPT 账号登录即可获得更多 token 额度和 OpenAI 模型访问权,其中包括 GPT-6 Astra。他说:"Sign in with ChatGPT 让人们可以拥有那种不用数着每一个 token 的感觉。一旦你真的放开手让 agent 去跑、给它更长的活动半径,你就会意识到它到底能做多少。"

编程之外的工作由 GPT-6 Astra 接手。Amp 团队只有 20 个人,没有专职营销,面向新用户的体验改进、让更多人通过搜索发现 Amp 的增长工作都交给了 agent。Quinn Slack 的说法是:"我们没有专门投入一个人,但我们专门投入了一个 agent。"他补充说团队对写作和设计风格非常挑剔,但对 GPT-6 Astra 的产出相当满意。这种用法延续到了他家里,他把自家住宅的平面图交给 GPT-6 Astra 转成 Blender 3D 模型,再和孩子一起把模型改成游戏,比如在房子里加一条懒人河,或者绕着屋子追大蒜,灵感来自祖母讨厌大蒜。他强调,这类事情在几个月前还做不到。

交互形态的变化集中在 Puck。Puck 是 Amp 内置的对话式助手,负责启动和管理其他 agent,可以让它开一个 agent 去排查 bug、协调几个 agent 同时干活,或者找回之前关于某个技术问题的讨论。新推出的 Calling Puck 由 GPT-Live-1 驱动,支持实时语音交互,在手表上也能用。Quinn Slack 的想象是,人离开电脑甚至出门跑步的时候,也能靠语音让 agent 继续干活。

速度层面的变量是 Ultrafast。Amp 正在 GPT-6 Astra 上测试这个模式,更快的响应可能改变人们使用 agent 的方式。眼下常见的做法,是在等待期间在几个 agent 任务之间来回切换,模型变快之后,用户需要同时照看的 agent 可能变少,agent 也可以在交回结果前多花时间自查。Quinn Slack 的原话是:"人们还没见过一个又这么好、又这么快的模型。"

这份案例值得读的地方,在于它把编码 agent 出圈所需要的整条链路摆上了台面,计费与登录方式、模型的多面手能力、语音调度入口、响应速度,彼此咬合才撑得起每周百亿 token 的用法,Sign in with ChatGPT 更是暗示登录入口正在变成模型的分发渠道。限制同样要说清楚,文中全部数字和体验来自 Amp 一方,由 OpenAI 官方博客转述,没有第三方评测,Ultrafast 也没有公布提速幅度和上线时间表,目前仍在测试。把它当作一个可参考的产品化样本是合适的,直接推成行业结论则需要更多独立证据。Amp 给自己定的下一步,是把编码之前和之后的更多环节也装进 agent。

谁给 AI 裁判打分？Netflix 交出三阶段生命周期答案

这是什么：Netflix 技术博客发布 11 位成员署名的工程长文，首次系统公开其 LLM-as-a-Judge 生命周期方法论。增量包括 RART(Reasoning-Aligned Rubric Tuning)推理对齐调优方法、Generator/Judge/Reflector/Meta-Judge 四组件架构、纯标签对齐会退化的消融实验、门卫加评论者双角色部署，以及约一个月移动端线上实验与每周漂移监控的完整数据，文末指向同名研究论文。
🔥 为什么今天值得看：大规模 LLM 生成内容普遍依赖裁判模型做代理评估，裁判自身的可信度此前多停留在原则讨论。Netflix 把它落成有基准、有指标、有人工签字、有回滚的生产流程，消融实验证明只对齐标签会让裁判退化，推理对齐是防止这种退化的关键。任何要在线上跑 AI 生成内容的团队都能拿这份流程对照自查，评估由此从一次性脚本变成可长期运营的工程资产。
展开正文

任何用 LLM 大规模生成文本的团队都会撞上同一堵墙。输出太多，人工读不完，也就无从知道哪些出色、哪些平庸、哪些有害。Netflix 的推荐解释场景是个典型，会员在片目详情页看到一句基于自己观看历史的自然语言推荐理由，测试期间每周要生成数十万条，片目库还在不断变化。人工全量评审不可行，业界通行解法是 LLM-as-a-Judge，让第二个模型替人工给第一个模型的输出打分，速度快、成本低。它在带来便利的同时也带来一个新问题，原文的发问是："Who evaluates the evaluator?"(谁来评估这个评估者)。更麻烦的是裁判一旦漂移，悄悄退化并开始放行坏输出，下游系统不会有任何报警。

Netflix 技术博客的这篇长文由 11 位成员署名，给出的答案是像运营生产系统一样对待裁判，给它完整的生命周期管理。核心原则被写成一句话："An LLM judge must never operate alone."(LLM 裁判绝不能独自运行)。文章标题把生命周期概括为构建、对齐、监控三个环节，正文进一步展开为四个阶段，基准数据创建、裁判训练、部署、人在环对齐与漂移监控，每个阶段都有明确的人工负责人。四个自动化组件贯穿全程，Generator 生成解释，Judge 给出 pass/fail 标签和书面理由，Reflector 负责修订评分细则，Meta-Judge 检查 Judge 拒绝一条解释的理由是否站得住。

构建阶段是人力投入最重的一段。内部写作专家定义解释必须满足的准则，撰写详细标注指南，手工构造对抗性难例，标注者对每条样例给出 pass/fail 判定并写下书面理由。现成的通用基准覆盖不到这种短小、绑定具体片目和参考片、依赖上下文的任务，于是团队用三类来源自建基准，专家手写的对抗样例、用 LLM 合成再交人工评分的边界样例、从生成器真实输出中抽取的解释。两个细节决定了后续成败。基准每周追加一批新的人工评分样本，避免随片目和用户习惯变化而过期；每个 fail 标签都附带自由文本理由，这些理由正是下一阶段对齐裁判推理的原料。

对齐阶段要抓的失败模式很隐蔽，裁判可能与人类标签完全一致，结论对但理由错。文中举了一个例子，会员看过一部音乐剧，属于带年轻女主角的家庭奇幻片，还有知名群像卡司，系统推荐了同样带年轻女主角的家庭奇幻冒险片，裁判给出 FAIL，理由乍看合理，细看却不完整，两部片子既不共享歌曲也不共享群像卡司。这种错误在标签一致率仪表盘上完全隐形，却会让裁判在解释拒绝原因时给出误导反馈。Netflix 的解法叫 RART(Reasoning-Aligned Rubric Tuning，推理对齐的评分细则调优)，Judge 是一个由评分细则参数化的固定提示词模板，调优只迭代改写细则文本，无须重训底层模型。Meta-Judge 把 Judge 的拒绝理由与人类理由逐条对比，它自身先经人工校验，与训练有素的标注员判断几乎全部吻合；标签不一致和标签对但理由错这两类错误一起交给 Reflector 修订细则。消融实验给出了关键证据，在三条必须准则之一上，只用标签分歧的 vanilla 循环把细则改写成退化形态，specificity 与 reasoning agreement 逐轮下滑，最终低于初始细则，而 RART 在同一准则上保持稳定并有所提升，原因在于靠不健全推理达到的正确标签无法泛化到新数据。三项指标按准则独立追踪，分别是 specificity(fail-recall，团队最看重，漏过坏解释是信任隐患)、recall(pass-recall)和 reasoning agreement。

部署后，同一个对齐好的裁判身兼两职。作为门卫，它按必须准则逐条打分，解释必须通过全部必须准则才有资格展示。作为评论者，它把拒绝理由附回生成器的提示词，驱动自我修订，形成先生成、再评审、后修订的循环。1000 条解释、最多 12 轮修订、4 个生成器的对照测试显示，增益集中在头几轮，而且修订放大的是本来就强的生成器。团队最终用最强生成器配 3 次重试预算，仍不达标就丢弃，理由是两种后果不对等，一条坏解释是信任隐患，少一条解释只是放弃一次机会。线上效果靠一次约一个月的移动端对照实验验证，看到解释的会员把观看转向此前没看过的内容，更多浏览会话以有意义的播放收尾，两项效果均统计显著，期间没有出现会员发起的下架请求或投诉升级。作者同时提醒，与标注者的离线一致只是必要条件，裁判通过的解释是否真对会员有用，只有线上实验能回答。

监控阶段针对的问题在于上线时对齐良好并不能长期保持，片目在变，高标准的定义也在变。每周抽取约 300 条解释做人工评审，按门卫的处理结果分层并偏向新片目，至少 3 名标注者独立评分，多数票作为真值。裁判的及格线随人类标注者自身分歧幅度浮动，要求其成绩不低于平均标注者 2 个标准差，难题周会自动放宽区间。任何一项指标掉出区间即构成漂移事件，触发带着扩充基准回到训练阶段再调优，修订后的细则不自动上线，须有人读完签字批准，旧细则保留以便即时回滚。人工周评还能发现指标抓不到的问题，模糊形容词堆成的词汤、单口喜剧元数据相似但调性完全不同、参考片本身不合适等，这些反复出现的模式会反哺构建阶段的准则，或者变成裁判之外的产品规则，比如禁止某些片型充当参考片。

文末给出五条可迁移经验，先投资带理由标注的基准再动手做裁判，调优时对齐人类的推理过程、只盯标签会被糊弄，一个对齐好的裁判复用为门卫和评论者以摊薄对齐成本，从第一天就规划监控，让人的介入成为制度设计。这篇博文同时总结了同名研究论文 The Lifecycle of LLM-as-a-Judge for Large-Scale Recommendation Explanations。对要把 LLM 生成内容放上生产线的团队，它示范的评估工程是把裁判当成有负责人、有周检、有回滚的长期资产来运营。

面壁智能的 MiniCPM-V 4.7 35B-A3B 还在持续施工。模型 10 月 7 日在 HuggingFace 上线，10 月 14 日模型卡仍在更新，一周内陆续补上了 DSpark 投机解码草稿模型、FP8 量化版本和降低灾难性遗忘的 SRFT 微调方法。它是 MiniCPM-V 系列第一个 MoE 架构的多模态模型，总参数 35B，每个 token 只激活约 3B，语言骨干来自 Qwen3.5/Qwen3.6，视觉模块基于 SigLIP2。

MoE 模型上手机的麻烦在于专家权重总量远超设备内存，按需加载会让解码卡顿到无法交互，锁定专家子集又会削弱能力。官方的工程解法分三层。Lookahead Expert Scheduling(LES)利用跨层路由预测，提前预取下一层可能用到的专家，预测只负责预取与调度，计算仍遵循模型原本的 token 级路由，漏掉的专家照常加载，因此不损失精度。细粒度逐层量化压缩专家权重的存储占用与内存流量。DSpark 投机采样与前两者配合，草稿模型先草拟一批候选、主模型一次校验，解码吞吐因此提高。三项叠加后，这个 35B 总参的模型在 iPhone 17 Pro Max 上以 3GB 内存实现每秒 13 个 token 以上的解码，官方称其为首个能在端侧流畅无损推理的开源 MoE。

效率维度上，官方评测显示 Instruct 模式下 35B-A3B 以更少的推理时间取得高于 Qwen3.6 35B-A3B 的综合得分，把性能与耗时的帕累托前沿往前推了一格。视觉侧沿用 LLaVA-UHD v4 的 ViT 内早期压缩，支持 4x/16x 混合视觉 token 压缩，开发者可按任务在细节与成本之间调配。部署面铺得也宽，iOS、Android、HarmonyOS 三端可用，Rockchip、后摩、Intel、AMD、Arm 芯片拿到 day-0 支持，SGLang、vLLM、llama.cpp、Ollama 均可推理，上线一周已衍生 47 个量化模型和 7 个微调模型。

Apigee hybrid 的原生 MCP 支持随 1.17.0 版本正式 GA。MCP(Model Context Protocol)是让大模型按统一格式发现并调用外部工具的开放协议,规定了请求响应模式、认证要求与速率限制的描述方式。这次更新的重点在部署位置,MCP 数据平面整个跑在客户自己的 Kubernetes 集群里,代理的请求流量与工具执行都留在自有基础设施内,运行时只从控制平面拉取配置更新,敏感数据不出企业环境。

接入侧不需要为代理重写接口。开发者在管理平面用 OpenAPI 规范定义好 API,平台会自动生成 MCP manifest,格式为标准 JSON-RPC 描述,任何 MCP 兼容的代理框架都能直接加载,把存量 API 当作原生工具调用,省掉定制集成代码。安全策略原样复用,所有调用仍经过网关强制执行 OAuth 2.0、API Key 和限流策略,受监管行业与延迟敏感负载是官方点名的主打场景。

可观测性一并到位。API Insights 可以查看 MCP 流量与热门工具的性能,Cloud Trace 能把一次代理调用的整条链路做成瀑布图追踪。文档站新增了专门的 MCP 章节,覆盖清单格式、安全考量与合规实践,并附带完整的代理工作流示例项目。

智能眼镜要当好随身助理,先得解决一直看与少用电的矛盾。奇景光电(Himax)10 月 14 日官宣,其 WiseEye HX6538 超低功耗 AI 处理器已集成进阿里巴巴 Qwen Glasses N1,共同构成常开视觉感知系统。官方口径下,这颗芯片以约 5 毫瓦的功耗独立完成实时端侧视觉推理,公司称该数字处于业界领先水平。

方案的省电逻辑分两层。HX6538 基于 Arm Cortex-M55 CPU 与 Ethos-U55 NPU,在眼镜常规影像通路之外单独运行视觉识别模型,持续执行人形与事件检测。其上是分层视觉唤醒机制,小芯片检测到相关人或事件时,才把主机唤醒做进一步的 AI 处理,其余时间主机保持非活跃,整机功耗因此被压下来,续航随之延长。

按奇景产品文档,WiseEye2 方案由超低功耗 CMOS 图像传感器与 HX6538 AI 微控制器组成,较上一代 WE1 芯片推理速度快 32 倍、能效高 50 倍(官方口径),同功耗级别可运行更复杂的模型、返回更准确的结果;量产模组为 HX6538 搭配 640×480 分辨率的 HM0360 传感器,封装尺寸 20.5×21.5×4.92 毫米。

奇景光电 CEO Jordan Wu 在公告中说:"在 WiseEye 早先被一家全球领先科技公司用于其最新智能眼镜之后,阿里巴巴为 Qwen Glasses 选用它,进一步验证了 WiseEye 在超低功耗运行、常开感知与端侧 AI 处理上的优势。"从供应链视角看,这颗躲在影像通路旁边的 5 毫瓦协处理器把常开视觉的电力成本降到了整机可以承受的量级,也给 AI agent 式的主动感知与实时服务留出了电池余量。
