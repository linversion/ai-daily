Cloudflare 给 AI 代理造了台电脑：虚拟文件系统加三种执行后端

这是什么：Cloudflare 的开源项目 cloudflare/computer 登上了 GitHub Trending，它在仓库描述里写得很直白——Give your agent a computer（给你的 AI 代理一台电脑）。这台“电脑”本质上是一个跑在 Durable Object 里的虚拟文件系统，权威状态存在 SQLite，再通过 workspace.runtime.exec 这一个统一入口，让代理调用三种执行后端：完整 Linux 容器、Dynamic Worker 里的 just-bash shell、或 Dynamic Worker 里的 JavaScript 模块。仓库创建于 2026 年 6 月 5 日，最近一次推送在 8 月 6 日，目前为预览版。
🔥 为什么今天值得看：今天的 AI 代理普遍有两个痛点：一是没有持久“家”，文件和上下文每次对话结束就散；二是文件存储和执行环境往往是两套孤岛，状态对不齐。Cloudflare Computer 把“权威状态存哪”和“在哪执行”统一进同一个对象，给代理一个真正可反复回去的工作目录。更关键的是方向信号——它和同期 Google 牵头的 Agent Plugins 打包标准拼在一起，正好构成“底层运行时 + 上层打包分发”的完整代理基础设施图景，说明代理生态正从“各写各的脚本”往“有公共地基”的方向收。

Cloudflare 的开源仓库 cloudflare/computer 最近一次推送停留在 8 月 6 日下午，它在 GitHub 上的描述只有一句——Give your agent a computer。直译过来就是“给你的 AI 代理一台电脑”，但这台“电脑”既不是硬件，也不是又一个 agent 框架，而是一个让代理拥有持久文件系统和可插拔执行后端的基础设施层。仓库最早创建于 2026 年 6 月 5 日，目前仍在密集迭代。

它要解决的核心问题很具体：今天的 AI 代理普遍缺一个“家”。大模型本身是无状态的，对话一结束，文件、上下文、刚写完的产物就散了；而就算接上外部存储，执行环境（跑 shell、跑代码）又往往是另一个孤岛，文件状态和执行状态对不齐。Cloudflare Computer 把这两件事统一进同一个对象里——一个 Durable Object 持有权威状态，状态用 SQLite 存储，再通过 workspace.runtime.exec(source, { backend }) 这一个入口决定怎么执行。

执行后端目前有三种。Container 模式把 SQLite 状态以真实 FUSE 挂载投到一个沙箱容器里，容器侧的 computerd 守护进程负责把文件系统挂起来，再通过 capnweb RPC 通道把改动同步回去，跑的是完整 Linux 用户态、真实二进制和真实网络。Isolate shell 模式在 Dynamic Worker 里跑 just-bash，直接通过 Workers RPC 访问权威 Workspace，省掉了一次额外的存储和同步往返。Isolate JavaScript 模式则在一个全新的 Dynamic Worker 里执行 ECMAScript 模块，带结构化输入输出、持久相对导入、配置好的库，以及 Workspace 支撑的 node:fs/promises 和受信的 ws:git、ws:artifacts 模块。一个 Workspace 可以在稳定 ID 下注册多个后端，按需懒加载，也可以完全不带后端单独当文件系统用。

这件事的意义要看和谁放在一起。同期 Google 正牵头拉上 Amazon、Microsoft 推 Agent Plugins 打包标准——一个管运行时，一个管打包分发，两件事拼在一起，正好构成“底层运行时 + 上层打包格式”的完整图景，说明代理生态正从“各写各的脚本”往“有公共地基”的方向收。性能上，官方在 docs/19_performance.md 里给了 benchmark：computerd 的 FUSE 挂载在元数据密集操作上比真实磁盘还快，但在大块顺序 I/O 上略逊一筹。

不过必须把话说在前面。这个项目目前明确标注为 PREVIEW ONLY，API 不稳定、设计随时可能改，README 自己也写明“适合实验、探索和原型，不适合生产使用”，docs/ 目录里的规范是前瞻性的设计意图，而非当前代码现状。仓库还声明不接受未经请求的 PR，公开贡献只走 issue 和 discussion。社区讨论也几乎为零——仓库本身没有公开评论数据，相关介绍主要集中在 explainx.ai、developersdigest.tech 等几篇第三方博客的转载里，且都是二手转述而非独立评测。换句话说，这是一次方向信号，不是一个明天就能上生产的工具。

谷歌加入Agent Plugins，统一AI插件打包格式

这是什么：Google、Amazon、Microsoft、OpenAI、Cursor、Vercel 等厂商联合发布了 Agent Plugins 1.0.0，一个厂商中立的开放规范，用于把 AI 代理的技能（Agent Skills）和工具连接（MCP 服务器）打包成一个可移植的目录。Google 同时宣布以核心维护者身份加入该项目，并已在其 Agents CLI 和 Data Agent Kit 产品中上线支持。
🔥 为什么今天值得看：在这之前，Agent Skills 和 MCP 各自都是可移植的，但把它们装在一起的那层“外壳”不可移植——每个 IDE 和编码代理的目录结构、清单字段、MCP 配置形状都不一样，开发者要为不同客户端维护多份几乎相同的副本。Agent Plugins 把这个“盒子”标准化了：一份插件包可以在 Antigravity、Gemini CLI、Claude Code、Cursor 等多个客户端中通用，降低分发成本，也让代理生态在打包层开始走向统一。

Google Developers Blog 今天发布了一项看起来平淡、但写 AI 编码插件的开发者绕不开的更新：Agent Plugins 1.0.0——一个由 Google、Amazon、Microsoft、OpenAI、Cursor、Vercel 等厂商共同支持的开放规范，用来把 Agent Skills 和 MCP 服务器打包成一个可移植的目录。Google 同时宣布以核心维护者身份加入该项目，由 Kevin Hou 代表，并已把支持落地到自家的 Agents CLI 和 Data Agent Kit 中。

这个规范要解决的问题非常具体：写一个 AI 编码技能并不难，难的是把它发到第二个客户端。原本 Agent Skills 和 MCP 各自都是可移植的——一个是可复用的指令与资源，一个是连接工具与服务的协议。但把它们装在一起的那层“外壳”不可移植：每个 IDE 的目录结构、清单字段、MCP 配置形状都不一样，传输方式还要各自猜。结果就是开发者为了同时支持 Antigravity、Gemini CLI、Claude Code、Cursor，要把同一份代码 fork 出好几份，然后看着它们慢慢漂移。

Agent Plugins 的回答克制得近乎朴素——一个插件就是一个目录。目录里有 plugin.json 清单、skills/ 子目录（每个技能一个子目录，沿用 Agent Skills 规范）、mcp.json（每个 MCP 服务器条目都带显式类型），还有一个以反向域名命名的 com.example.client/ 扩展命名空间，留给各家客户端放自己专有的钩子、命令。plugin.json 本身几乎只有两行实质内容——一个 $schema 引用和一个 name 字段。组件不能在清单里内联声明，也不能重新定位，客户端无需学习任何发现路径或优先级顺序。

这种克制还体现在它的失败模型上：skills/ 不存在就跳过，某个 mcp.json 条目启动失败不会拖垮整个插件的其他技能，独立的组件独立失败。这是把“健壮性”做进目录结构本身，而不是依赖运行时补救。

但更值得注意的是规范有意不做什么。Agent Plugins v1 明确不包含安装机制、分发协议、权限模型、沙箱要求、信任与来源验证，也没有用户体验约定。原文把这些列为“未来的考量”（future considerations），而非悄悄省略。Google 给出的理由很直接：IDE、CLI 和企业托管平台在安装、策略、审批上的义务差异很大，强行统一反而会绑住各家手脚。

这种“只做打包层”的克制，让 Agent Plugins 在更大的生态里有一个清晰的位置。原文把它和另外三层并列：Agentic Resource Discovery（ARD）负责“发现”——让客户端问“这个任务有什么资源可用”；AI Catalog 负责“描述”——已有提案把 application/agent-plugins+json 注册为已知类型，让目录条目可以像指向 agent card 或 mcp.json 一样指向 plugin.json；Agent Plugins 负责“打包”；底层的 MCP 和 Agent Skills 负责“运行”。每一层都可以独立采用，互不强制——你可以发一个没有目录条目的插件，也可以索引一个不是插件的资源。

需要提醒的是，Agent Plugins 并不是“万能插件标准”。它解决的是“一个技能如何同时塞进多个客户端的盒子”这个分发问题，没有触及谁有权装、装进来可不可信这些更敏感的层面。原文也明确建议：如果你只是给单个客户端发一个 MCP 服务器，单独一份 mcp.json 仍然是更简单的答案；只有当多个组件需要一起打包、一起迁移时，插件格式才划算。

和今天同期的 Cloudflare Computer 形成互补：Cloudflare 在做代理的运行时（持久文件系统、可插拔执行后端），Agent Plugins 在做代理能力的打包和分发标准。一个解决“代理在哪里跑”，一个解决“代理的能力怎么搬”，代理生态正在从单点工具走向分层基础设施。打包本身是枯燥的活，但原文那句收尾值得记住——“枯燥的基础设施恰恰应该共享，而不是被重新发明五次”。

DeepMind 气旋 AI：粗分辨率反而更准，多出一天预警

这是什么：Google DeepMind 发布了用于热带气旋（飓风/台风）预报的 WeatherNext 系列 AI 模型，并在 Nature 发表论文，同时开源模型代码和权重。这个模型用一个单一 AI 模型同时预测气旋的路径、强度和风结构三项指标，平均比过去多给出一天的提前量——三天预报的准确度相当于过去两天预报的水平，相当于过去十年气象学的进步幅度。在 2025 年飓风季，它帮助美国国家飓风中心对飓风 Melissa 做出了历史性预报，提前预判了它的快速增强和牙买加登陆。
🔥 为什么今天值得看：气旋预报一直有一个矛盾：路径由全球大尺度气流驱动，传统上用粗分辨率全球模型效果最好；强度却由气旋核心区精细的热力学过程决定，传统上要靠高分辨率局部模型。两种方法长期割裂，路径准了强度就差，强度准了路径又跟不上。WeatherNext 用单一 AI 模型同时把这两件事做到 SOTA，本身就打破了气象学的方法边界。更值得普通读者关心的是实际价值：热带气旋过去 50 年造成全球超过 70 万人死亡、1.4 万亿美元损失，多出一天提前量，意味着沿海城市和救援团队多一天组织撤离和准备。DeepMind 选择开源权重和代码，也让各国气象机构、学术机构有机会基于同一套模型做本地化预测。

Google DeepMind 今天在 Nature 发表了一项让气象学家有点意外的研究。他们开发的 WeatherNext AI 模型，在热带气旋（也就是飓风和台风）的路径、强度和风结构三项预测上同时达到了最先进水平，平均给预报员多争取到一天的提前量——三天预报的准确度，相当于过去两天预报的水平。这种提升幅度大约相当于过去十年的气象学进步。

数字背后的现实是：过去 50 年里，热带气旋在全球造成了超过 70 万人死亡、1.4 万亿美元经济损失，而预报一直是和时间赛跑。在 2025 年飓风季，WeatherNext 帮助美国国家飓风中心（NHC）对飓风 Melissa 做出了一次历史性预报——提前预测到它的快速增强和牙买加登陆，让地面团队赢得了关键准备时间。

真正反直觉的地方在数据分辨率。气象学界长期以来的共识是：分辨率越高、预测越准，强度预报尤其依赖核心区精细的热力学过程。但 WeatherNext Cyclones 只需要 28×28 公里的输入数据，比传统模型粗了约 100 倍，依然能做出优秀的强度预报；更小的 WeatherNext 2-mini 用 111×111 公里的粗分辨率，性能同样不错。这一点连 DeepMind 自己的科学家都觉得意外，原文里明确说“如何在这种分辨率下产出如此准确的预测，仍是一个开放的研究问题”。

关键技术是 Functional Generative Networks（FGNs）。它让模型能高效生成大量不同的预测样本，用来刻画天气固有的不确定性。今年的集成规模从去年的 50 个扩大到 1000 个成员，能在单块 TPU 上一分钟内完成一份 15 天预报，把“罕见但后果严重”的尾部风险——比如 Melissa 那样的快速增强——也纳入预报员的可视范围。模型用两种数据共同训练：近 20 TB 的全球大气数据和 IBTrACS 数据库里近 5000 个历史气旋的专家整理观测。

DeepMind 同步开源了 WeatherNext 2、WeatherNext Cyclones 两个模型的代码和权重，还发布了一个能在免费 Colab notebook 上单 TPU 运行的 WeatherNext 2-mini。配套的 Weather Lab 界面也做了更新，除了气旋路径，还能可视化温度、降水、风速等全球天气。比起本期其他几条产品和工具新闻，这条更像是一个信号：AI 不只是在改写聊天和编码，也在重新定义基础科学问题该怎么解。

但需要把限制说清楚。原文里提到的“多出 24 小时提前量”是平均意义上的统计结论，并不意味着对每一个气旋都能稳定多给一天。模型评估区间是 2023—2024 年的历史气旋，实际表现还要看未来几个飓风季的真实考验。社区层面目前没有公开讨论，第三方转载都集中在新闻复述层面，缺少独立评测；DeepMind 自己在文末也提醒：正式的天气预警仍以各国气象部门为准。

LiteRT.js 发布：把 AI 推理搬进浏览器，最高提速 3 倍

这是什么：Google 发布了 LiteRT.js，它是边缘 AI 推理运行时 LiteRT 的 JavaScript 绑定，让开发者把 .tflite 模型直接放进网页运行，推理过程全部在用户本地浏览器完成。首版提供 npm 包 @litertjs/core、API 文档和一批实时演示（YOLO26 目标检测、Depth Anything V2 深度估计、Real-ESRGAN 图像放大、EmbeddingGemma 向量搜索）。
🔥 为什么今天值得看：Web AI 推理过去主要靠 TensorFlow.js 这类纯 JavaScript 方案，性能一直是瓶颈。LiteRT.js 把 Google 在 Android、iOS、桌面端用了很久的原生运行时通过 WebAssembly 搬进浏览器，再叠加 WebGPU/WebNN 硬件加速，等于给 Web 开发者一条接近原生的推理路径。叠加数据不出设备、没有服务器成本这两点，它把“在网页里跑像样的 AI 模型”从概念演示往实际可用推了一步。放在整期里，它与 Google Maps 代理化共同构成 Google 把 AI 往边缘和消费端铺的布局。

Google 把它的边缘 AI 推理运行时 LiteRT 搬到了浏览器里。新发布的 LiteRT.js 是 LiteRT 的 JavaScript 绑定，开发者拿一套 .tflite 模型文件，就能在网页里直接做机器学习推理，而不必把请求发回云端。官方列出的三个卖点都很直白：用户数据留在本地、没有服务器成本、实时交互延迟更低。

性能是这次更新的核心叙事。LiteRT.js 没有沿用 TensorFlow.js 那套纯 JavaScript 内核，而是把 LiteRT 原生的跨平台运行时通过 WebAssembly 直接暴露给浏览器，再叠加三层硬件加速——CPU 走 XNNPACK、GPU 通过 ML Drift 配合 WebGPU、NPU 则押注还在 Chrome 和 Edge 里实验的 WebNN API。官方在一台 2024 款 M4 芯片的 MacBook Pro 上做了基准测试，结论是在经典计算机视觉和音频处理模型上，LiteRT.js 比其他 Web 推理运行时最多快 3 倍；如果对比对象换成同一台机器上的 CPU 执行，走 WebGPU 或 WebNN 路径能带来 5 到 60 倍的提速。需要留意的是，这些数字来自受控的浏览器环境，官方明确写了真实表现会因本地 GPU 能力、散热降频和浏览器驱动优化而不同。

对开发者更实际的部分是迁移成本被压得很低。已有的 .tflite 模型可以直接拿来跑；PyTorch 模型通过 LiteRT Torch 一步转换就能接入；AI Edge Quantizer 还允许针对不同模型层定制量化方案，在大幅缩小模型体积的同时尽量保住精度。官方同时发布了 npm 包 @litertjs/core 和一批现场演示，包括用 YOLO26 做实时目标检测、用 Depth Anything V2 把摄像头画面转成 3D 点云、用 Real-ESRGAN 把图片放大四倍，另外还有一个基于 EmbeddingGemma 的浏览器内向量搜索 demo。

定位上需要说清楚一件事：LiteRT.js 不是 TensorFlow.js 的替代品。官方的原话是把它称为“执行 .tflite 模型时 TensorFlow.js 的一次有力演进”，并为老 TF.js 用户专门写了在现有流水线里调用 LiteRT.js 的迁移说明。换句话说，它是 LiteRT 生态在 Web 端的延伸，而不是把 TF.js 推翻重来。Google 在路线图里点明了两个后续方向——继续推进 WebNN 对原生 NPU 的支持，以及针对设备端生成式 AI 做优化；对于想在浏览器里跑大模型的开发者，单独提供了 LiteRT-LM.js。

把这件事放在整期里看，Google 这一回合在 AI 全栈上同时落子：一端是 Google Maps 把外卖、订酒店、买票都变成 AI 代理能干的事，另一端是 LiteRT.js 把推理运行时铺到每一个打开的网页。前者面向普通消费者，后者面向 Web 开发者，共同的方向都是把 AI 往离用户更近的边缘推。

当然也有需要冷静的地方。WebNN 目前只是 Chrome 和 Edge 里的实验性 API，NPU 这条加速路径短期内还指望不上；3 倍和 5-60 倍两个数字都来自 M4 MacBook Pro 这个相当强劲的基准设备，在普通笔记本或手机浏览器上能不能复现，官方自己也提示“个人表现会有差异”。浏览器端 AI 推理要真正成为主流，硬件碎片化和 WebNN 的落地进度仍是绕不开的两道坎。

code-review-graph：让 AI 只读必要代码

这是什么：code-review-graph 是一个本地优先的代码智能工具，用 Tree-sitter 把代码库解析成一张图（函数、类、导入是节点；调用、继承、测试覆盖是边），再通过 MCP 协议把"和当前任务相关的最小代码集"喂给 AI 编程助手，避免模型每次都读整个仓库。最新 release 是 2026 年 7 月 18 日的 v2.3.7，基准数据在 8 月 2 日重新抓取过。
🔥 为什么今天值得看：随着代码库变大，AI 编程工具反复读全量代码带来的延迟和 token 成本会快速上升。这个项目把"该读哪些文件"从凭经验的 grep，变成可沿着代码结构图精确计算的爆炸半径——这是一个具体、可量化的工程问题，正好补上了本期 Cloudflare Computer（代理运行时）和 Agent Plugins（打包标准）之间的上下文层。

一个叫 code-review-graph 的开源项目最近重新冲上 GitHub Trending，它要解决的问题很具体——AI 编程工具在做代码审查时，常常要把整个仓库翻一遍，既慢又烧 token。

它的做法是在本地给代码库建一张"地图"。具体来说，用 Tree-sitter 把代码解析成抽象语法树（AST），再把它存成一张图：函数、类、导入这些是节点，调用、继承、测试覆盖这些是边。当 AI 助手需要审查一次改动时，工具不是把整个仓库丢给它，而是沿着图的边去算这次改动可能影响哪些调用方、依赖和测试——也就是项目方所说的"爆炸半径"（blast radius），最后只把这些相关文件喂给模型。

效果怎么衡量，是这条新闻最容易被误读的地方。项目方在 6 个开源仓库（fastapi、flask、httpx、express、gin 以及它自己的代码库）上跑了一组基准测试，把"喂整个仓库"的 token 数和"喂图谱查询结果"的 token 数做对比，得出每问 token 中位数减少约 65 倍，最佳情况是 fastapi 的 376 倍。但项目方自己也明确写了三件事：第一，"喂整个仓库"是一个理论上的上限，真实的 agent 不会这么干，它至少会先 grep 再读最相关的几个文件——项目方另外跑了一个"现实基线"（agent_baseline）来衡量这种更现实的对照；第二，376 倍是单个最大仓库的最佳值，不是典型结果，区间其实在 36 倍到 376 倍之间；第三，在另一个针对单文件小改动的基准里，图谱的上下文反而比直接读改动文件还多，因为多了结构元数据。换句话说，65 倍这个数字是"代码审查"这个特定场景下的中位数，不是放之四海皆准的提速倍数。

准确性方面也有类似的诚实标注。爆炸半径分析在 13 个评测 commit 上平均 F1 是 0.69，但用来打分的 ground truth 是从同一张图推导出来的，逻辑上是"循环"的，所以 recall=1.0 只能理解成上限，而不是"100% 召回"。诚实的 co-change 模式（用同一次 commit 里实际共同修改的文件做对照）目前在每个 commit 上都返回 0，作者坦承这个模式还没修好，不能作为有效测量。这是少见的把"我也不知道自己准不准"写在 README 里的开源项目。

它的工程取向也值得注意。整个图谱构建和查询都在本地 CI runner 上完成，源代码不会发到任何外部服务；图谱通过 MCP（Model Context Protocol）协议暴露给 AI 工具，按需查询而不是全文加载；GitHub Action 会在每个 PR 上贴一条带风险评分的置顶评论。语言覆盖超过 30 种，从 Python、Go、Rust 到 Terraform、Verilog、Jupyter 笔记本，还支持用一个 languages.toml 文件扩展自有语言而不需要 fork。安装是 pip 一行，再用一条 install 命令自动检测并配置本机的 AI 编码工具——官方列出支持的就有 Codex、Cursor、Claude Code、Gemini CLI、Windsurf、Zed、Continue、OpenCode、Qwen、Qoder、Kiro、GitHub Copilot（含 VS Code 与 CLI 两版）、CodeBuddy、Antigravity 等十余种。

时间线上，最新 release 是 2026 年 7 月 18 日的 v2.3.7，基准数据则在 8 月 2 日从干净克隆的固定 SHA 上重新抓取过——新版因为节点嵌入文本更丰富，图谱返回的 token 数比 5 月那次还略高，所以 65 倍其实是相对保守的数字。v2.3.4 起每次审查都会附带一个 context_savings 估算，v2.3.5 在 CLI 里加了 Token Savings 面板和 --verify 参数（用 OpenAI 的 cl100k_base tokenizer 交叉校验，文档称在 222 个样本文件上和真实 GPT-4 token 数差距在 1% 以内）。

放在这一期里看，code-review-graph 处在 Cloudflare Computer（给代理一台"电脑"）和 Google Agent Plugins（给代理一种统一打包格式）之间——前者管运行时，后者管分发，它管的是上下文：在大仓库里，到底该让代理读哪几行。这是一个具体的、可量化的工程问题，而不是又一个抽象的"AI 重新定义软件工程"。

今天 Hacker News 上一篇题为《xAI Ignores Laws And Profits》的评论文章重新引起关注，主题是马斯克旗下 xAI 在田纳西州孟菲斯的 Colossus 数据中心如何用环境与社区为代价，换来了 AI 算力的极速扩张。文章立场鲜明——它不是中立报道，而是一篇明确批评的评论，里面几乎所有判断都需要当作"作者认为"来读，而不是已证事实。

接下来是作者认为最讽刺的部分。2026 年 7 月 30 日，xAI 与密西西比州环境质量部门达成协议：在 2027 年 7 月之前移除这 69 台"临时"涡轮机，并改用一座天然气电厂。作者强调，整个协议中没有提到任何罚款或处罚——也就是说，过去两年的违法排污换来的是"按州里认可的时间表慢慢整改"，而不是经济代价。文章还指出，配套的废水处理工程已经延期：原计划 2026 年上线，但官员上月被告知要等到 2027 年 Q1 才会重启施工，期间数据中心继续抽当地含水层。

文章把这一选址放在更大的种族与环境正义议题里。孟菲斯是一个黑人占多数的城市，作者认为 Colossus 这种带污染风险的设施之所以能落在这里，正是美国长期"红线政策"（redlining）把少数族裔社区划到工业污染区的延续。文章还提到，除了看得见的烟雾，社区组织和一些学术研究开始担心次声波（频率低于 20Hz、人耳听不见）污染对睡眠、神经系统的潜在影响，并指出孟菲斯周边已聚集 10 到 15 个数据中心。

作者还顺手扒了一遍 xAI 自己的"事实对照虚构"FAQ，发现不同声明之间相互矛盾：一边说涡轮机已经移走，一边又说它们被搬到附近另一个站点；一边说孟菲斯主数据中心不会有涡轮机，一边又说它们会通过变电站接到 Electrolux 厂区的 12 台永久机组。作者的结论是公司刻意回避明确说明整体计划。
