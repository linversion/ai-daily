Anthropic 发布 Claude Code Projects，常驻对话指挥并行编程智能体

这是什么：2026 年 9 月 17 日，Anthropic 推出 Claude Code Projects，一个加在编程工具 Claude Code 之上的常驻协调代理，目前处于 Beta 阶段。开发者用大白话把长期开发任务交给它，它自动拆成多条并行线程分头执行，线程之间共享一份项目记忆，开发者用手机就能查看和引导。VentureBeat、The Verge、MarkTechPost 三家媒体当天同日报道。
🔥 为什么今天值得看：过去跨会话继续项目，开发者要自己维护进度记录、反复重建上下文，等于在多个 AI 会话之间当人肉调度员。这个产品把交互单位从一次编码任务换成一个长期的工作体，一个协调对话管着多个并行会话，开发和监督可以同时进行。OpenAI 的 Codex、GitHub 和 Google 的 Jules 都在往异步并行方向走，竞争点落在谁来做协调、谁来记住累积的决策。

9 月 17 日，Anthropic 推出 Claude Code Projects，VentureBeat、The Verge、MarkTechPost 三家媒体当天同日报道。它是加在编程工具 Claude Code 之上的一个常驻协调代理，面向要长期持续开发一个应用、一个网站或一套系统的程序员。Anthropic 用 always on 形容它，一直在线。

长期开发里最磨人的环节是接续状态。过去用 Claude Code 跨会话继续项目，开发者要么自己在外部维护一份进展记录，每次开新会话再喂回去，要么让模型翻出上次对话的压缩版，重新查一遍现状，还原上次做到哪里。企业里的商城、官网、采购平台这类系统常年更新修补，很少有一个明确的完工点，这种反复交代背景的负担一直都在。

新产品的做法是在多个会话之上放一层协调。开发者照常用大白话交代任务，一次说几件、顺序随意都行，协调器决定哪件事开新线程、哪件事并进已有线程。每条工作线程都是一个完整的 Claude Code 云端会话，跑在各自的代码分支和仓库副本上，还能用子代理、循环等机制继续拆活。官方把这套结构概括为"threads do the work, Claude directs it"，线程干活，Claude 指挥。在 X 上的发布帖里，Anthropic 把这种交互比作给参谋长做简报。界面里有一个 Overview 面板，列出需要人来拍板的事项，用手机就能引导某条线程，不必守在电脑前盯所有会话。

官方举的例子能看出用法。一个项目的目标是把应用结账接口的 p75 延迟降下来，p75 指的是四分之三的请求都会快于这个值，Claude 会开出并行线程，分别做性能剖析、测试优化方案、提交 PR。另一个例子里，团队把 API、网页和移动端三个仓库接进来，让不同线程分别迁移调用方和跑测试，协调器盯住依赖关系，告诉开发者先合哪个改动。

线程之外，这套系统还有一份跨线程的共享项目记忆。发布日期改期、某个功能被砍、改动某个服务前要先咨询谁，这类决策都留在记忆里，供后续的线程取用。项目还带一个文件库，收集用户提供的文件和 Claude 产出的成果，给后面的工作留下可反复取用的材料。它和 2024 年 6 月推出的 Claude Projects 名字相近，老产品帮 Claude 记住用户给的上下文，新产品记住并协调正在进行的工作。

竞争者已经在同一条路上。OpenAI 的 Codex 应用做多代理并行工作区，开发者并行跑多个编程智能体、隔离改动、监督长期任务；GitHub 走仓库原生路线，把代理和分支、issue、PR、CI 绑在一起；Google 的 Jules 主打异步任务，附带仓库级记忆。VentureBeat 的判断是，各家正在收敛出同一批基础能力，差别在控制面放在哪里，Anthropic 押的是一个持续进行的对话成为总控台。

门槛和代价也要说清。Beta 先开放给部分 Claude Pro 和 Max 订阅者，要求使用云端会话，且网页端或桌面端没有现成 Projects，未来一周扩大范围，之后逐步覆盖 Team 和 Enterprise，现有 Claude Projects 照常运行。云端线程暂时访问不了本地文件、本地工具和内网系统，官方称本地支持很快推出。定价上没有单独收费，走现有订阅额度，线程一多，额度烧得更快，用户可以查看项目级别的用量，也能为协调器和线程分别选模型与投入档位。多条线程改到同一段代码时，仍会产生常规的合并冲突，按普通 PR 流程解决。

四家大厂都证明了智能体能异步并行干活，接下来比的是谁来协调这些智能体、谁来记住它们攒下的决策，以及开发者去哪里管理一个可能比任何单次会话都长寿的工作体。

DeepSeek 新模型拆解，KV 缓存低至前代八分之一

这是什么：技术博主 zartbot 发布长文，逐节拆解 DeepSeek-V4.1-Flash 的技术报告，在 Hacker News 收获 126 分讨论。报告主角是总参数 552B、原生支持 100 万 token 上下文的多模态混合专家模型，主打把 KV 缓存（模型读上下文时存进显存的中间记录）压到极限，同样序列长度下运行时缓存约为上一代 V4-Flash 的四分之一，需要长期保存的持久化缓存约为八分之一。博主实测解码速度接近每秒 420 个 token，并认为这次架构跨度接近换代。
🔥 为什么今天值得看：智能体连续执行长任务时上下文越来越长，KV 缓存会占满显存、内存和 SSD，搬运它还要消耗互连带宽，报告认为这直接限制服务吞吐、抬高部署成本，挡住智能体跑更长的任务。V4.1 Flash 选择改模型架构来压这笔账，前 20 层建立的全局缓存被后 20 层直接复用，输入为主的智能体场景预填充每个 token 只激活 8B 参数。对指望智能体常驻在线干活的行业来说，这条路线直接对着智能体时代最贵的一笔隐形成本下手。
展开正文

技术博主 zartbot 发布长文，逐节拆解 DeepSeek-V4.1-Flash 的技术报告《Pushing the Limits of KV Cache Compression》，帖子在 Hacker News 上收获 126 分。报告的主角是一个总参数 552B 的多模态混合专家模型，生成内容时只激活其中一小部分参数，原生支持 100 万 token（词元）上下文。博主上手用了一段时间，实测解码速度接近每秒 420 个 token。

为什么要跟缓存较劲，得从智能体的账本说起。大模型每读一个词，都要为它生成一组键值记录存进显存，供后续计算反复读取，这份记录就是 KV 缓存。会话越长，记录越大。智能体连续执行长任务时，上下文一路增长，频繁的工具调用又要求模型反复重读历史内容（这一步业内叫 prefill，预填充），缓存把显存和 SSD 都吃得紧紧的。报告直言，这些存储与搬运开销拖累服务吞吐、抬高部署成本，挡住了智能体走向更长的任务跨度。

报告给出的核心答案是 CED（因果编码器-解码器）架构，思路借鉴 YOCO 研究。整个网络 40 层，前 20 层当编码器，负责建立全局 KV，后 20 层的全局 KV 直接由编码器末端隐状态投影得到，跨层共享。长文本的大部分位置只需过前 20 层，预填充阶段每个 token 只激活 8B 参数，解码阶段激活 16B，报告认为这对输入长、输出短的智能体场景特别划算。

缓存本身从三个方向压。通道上，所有注意力头共用一个 512 维隐向量来表示键值；序列上，编码器把相邻两个位置合并成一条缓存，解码器保留逐位置记录；到层这一级，干脆让多层共用同一份全局 KV，全网只保留 3 份编码器缓存加 1 份解码器缓存。再叠加 FP4 精度（每个数值只占半个字节），全局主 KV 加索引器，每多处理一个 token 只需多存约 890 字节。报告给出的结果是，同样序列长度下运行时缓存约为上一代 V4-Flash 的四分之一，需要长期保存的持久化缓存约为八分之一，整体性能还优于上一代。博主在开篇概括，这是在保持任务完成质量的前提下，把 KV 缓存进一步压缩了 4 倍。

架构里还有几个配角。DSpark 投机解码用 3 个滑窗草稿块一次并行猜多个位置，再由置信度头决定验证长度；Engram 条件记忆在第 1、14 层注入约 1600 万条目的 n-gram 嵌入表；视觉分支通过像素重排把单张图片的 token 数压到九分之一，单图上限 1024 个视觉 token。

博主的判断比报告标题更激进。他用下来觉得这次架构跨度配得上 DeepSeek-V5 Flash 的名字，并转述了 DeepSeek-V4 Pro 全系模型将下线的消息。这篇文章是他拆解系列的第一篇，他预告更关键的内容在报告第三章。

同一个智能体要写三遍？Databricks 说一遍就够

这是什么：Databricks 在自家产品博客宣布智能体管理层 Omnigent 登陆其平台并开放 Beta，同时公布与搜索服务 Nimble 的集成。工程师把智能体的模型、工具、策略、限额定义一次，即可在 Claude Code、Codex、原生 API 等环境运行；搜索在配置里指定 Nimble 后，所有环境共用同一个搜索 API。按 Nimble 自家测试，接入后 LLM 基准准确率从 46% 升到 71%，搜索成本减半。
🔥 为什么今天值得看：同一套智能体逻辑在不同工具里各写一遍，耗掉的是工程师本该花在业务上的时间。对企业来说，三个副本没有统一的成本台账、权限规则和审计记录，智能体碰的又是几十万个客户账户，这种状态难以放心运转。Omnigent 把智能体定义和模型调用收拢到一处，给多工具智能体补上了记账、管控和回放的能力。按文章的设想，内部账户记录与外部网络信号收进同一个平台和同一套治理，销售情报这类应用才经得起审计。
展开正文

Databricks 的产品博客从一位软件公司工程师讲起。这位工程师要维护一个销售情报智能体，盯着几十万个潜在客户和企业账户，从新一轮融资、高管变动、产品发布、扩招这些外部信号里判断哪些账户值得销售本周去联系。账户数据本来存在 Databricks 的 Delta 表里，由 Unity Catalog 管着权限，外部信号却散在网上，智能体的活就是把两边拼成一张实时更新的图。

第一版交付物是一套逻辑写了三份。在 Claude Code 里写了一遍，听同事说 Codex 跑批量脚本更快，又移植了一遍，还有一个只要单次问答的每晚轻量任务，绕开工具直接调模型接口。每个工具都捆着自己的网页搜索，接入方式各有一套配置格式，工程师的白天耗在学这些格式上。搜索质量也参差，同一个查询在 Claude Code 和 Codex 里给出的结果不一样，一个能查到的来源另一个会漏，融资、高管变动这类大新闻查得到，技术栈变更这类细颗粒信息经常丢。三个副本各自计费、各管各的规则，一笔总账算不清，结果出错时也没法回放智能体当时读了什么、花了多少钱。

Databricks 给出的解法叫 Omnigent，一个压在这些工具之上的管理层，这次以 Beta 形式登陆 Databricks 平台，服务器由 Databricks 托管。工程师把智能体定义一次，模型、可用的工具、策略和限额写进同一份规格，即可在 Claude Code、Codex、原生 API 之间运行。模型调用统一经 Databricks 的 Foundation Model APIs 路由，成本、审计、治理集中记录，换模型或降到更便宜的型号只改一行配置。

网页搜索是每个工具都捆、且各家捆得都不一样的部件。Omnigent 提供统一指定的能力，选哪家的搜索由使用者自己决定。文章推荐的搭档是 Nimble，在 web_search 内置槽位写下 Nimble 的名字，下层所有工具就共用同一个 Nimble Search API。要经得起审计的深度研究，可改用 Nimble 的 Web Search Agents，它自动编排搜索和抽取，交叉核对多个来源，返回带引用的结果。

效果数字出自 Nimble 自家测试，发布在 Databricks 的产品博客上。接入 Nimble 搜索后，LLM 基准准确率从 46% 提高到 71%，网页搜索成本砍半，成本对比对象是 Claude 的搜索。这属于厂商基准，本期没有独立信源交叉印证，采信时需要打折。

上手分两步。第一步连接 Omnigent 和 Databricks，在本机安装带 Databricks 集成的 CLI 并注册为主机，用工作区身份登录，智能体跑在托管服务器上，会话能从终端、桌面应用、iOS 和 Android 原生应用一路跟到手机浏览器。第二步在 web_search 槽位指定 Nimble，需要一个 Nimble key，可从免费试用开始。两个前提要先确认，工作区已启用 Omnigent Beta，且所在区域支持 Unity AI Gateway。

文章的落点在企业侧。内部账户记录和外部网络信号收进同一个平台、同一套治理，智能体在数据所在的地上运行。对数据本来就在 Databricks 的团队，这份组合省下的是重复搭建的工程时间；数据在别处的团队，迁移的账要自己另算。

微软 44 页白皮书称 AI 护城河在私有评测，模型保持可替换

这是什么：微软在周四发布了一份 44 页的白皮书《Becoming a Frontier Firm: Our Frontier Playbook》，教企业怎么落地 AI，VentureBeat 做了报道。文档基于微软内部 100 多个 AI 转型案例写成，覆盖职能部门、商业组织和工程团队，核心主张有三条，先把业务流程精益重构再引入智能体（lean before agents），把竞争优势建在私有评测与专有上下文上，基础模型在参考架构里被标注为可互换零件。供应链、产品开发、销售三个内部案例给出了量化结果。

微软周四发布 44 页白皮书《Becoming a Frontier Firm: Our Frontier Playbook》，把自己内部 100 多个 AI 转型案例整理成一套企业落地方法，VentureBeat 对此做了报道。白皮书的开场判断很直接，先把业务流程重构好，再引入智能体，往为人和旧软件设计的流程上直接堆智能体，可能只是把原有的混乱自动化。文档里写道「A tool licensed and rolled out to 100,000 employees does not change how the work gets done」，工具发到十万人手里，工作本身不会改变。微软首席战略与转型官 Kathleen Hogan 在配套博客里承认，公司最初按传统软件的思路推 AI，装上、培训，再催使用率，结果发现使用量并不自动带来业务效果。

白皮书把转型分成三条路径，分别给特定岗位配工具的 Persona Acceleration、围绕 AI 重构既有流程的 AI-Powered Process Redesign，以及从白纸开始的 AI-First Possibility。第二条路径的口诀是 lean before agents，先把流程里多余的审批与交接砍掉，建共享数据底座，划定必须由人负责的环节，再放智能体进场。微软云供应链组织按这个顺序执行。跨职能团队先梳理并简化计划、采购、履约、物流的流程，建了一个统一数据源，随后部署 111 个专用智能体，部分在权限和审批阈值内已经能帮计划员更新或取消采购订单。2026 年 4 到 8 月的五个规划周期里，平均周期时间从约 10 个工作日压到 2.5 天以内，最多缩短 75%。每月 20 多项需求计划调查，产出一份人工验证的解释原来要 5 到 7 天，现在几个小时以内，部分 20 分钟内完成。这些数字来自微软对 2025 年 9 月至 2026 年 8 月一项 150 多人跨职能工作的分析，只适用于被测量的流程和周期，白皮书对此写得很明白。

产品开发侧有个更激进的实验。9 人团队在沙盒里从零构建 Copilot Cowork，要求按 AI 优先的方式做产品。团队先写描述意图的规格说明，用评测定义「好输出」的标准，再把喂给智能体的上下文备齐，微软称成员演变成了 meta-engineers、meta-designers 和 meta-PMs。项目期间共 18600 次提交、日均 123 次、930 万行代码，9 个人 35 天交出初版。微软单独注明，35 天来自这一个专门项目，不能当公司级开发基准，代码量和提交数本身也不代表产品质量。重点在运作方式，团队围绕智能体、规格与评测重组，所有人带着同一套上下文和评价标准工作。

对决策者更有分量的是架构主张。微软建议企业别把任何特定基础模型当作架构中心，它的参考架构图里基础模型被明确标注为 interchangeable（可互换），顶层是安全与治理，往下依次是包含评测的强化学习环境、智能体运行时与工具，以及涵盖多模型接入、记忆、技能与 MCP 的上下文层。企业该长期持有的是私有评测、专有上下文、流程编排和反馈闭环，这些层扛得住底层模型被整体替换。微软把企业的私有智能归为四类。对市场的判断和专有数据与机构知识是头两类，再加上对质量的品味，以及划定智能体自主行动边线的风险边界。这些标准沉淀成评测后，再套上它称为 hill-climbing machine 的持续改进机制，让 AI 系统按公司自己的标准越调越好。文档同时建议把提示词、检索、评测与智能体决策尽量留在企业边界内，数据驻留和租户隔离事后补做的代价远高于一开始就设计进去。

自主程度被分成三级。第一级员工使用 AI 助手，第二级智能体加入人机团队、在人类指导下对特定任务负责，第三级微软称为 human-led, agent-operated，人定方向，智能体执行整段业务流程，必要时回来与人对齐。衡量效果同样分层，投入层面的变化 2 到 4 周可见，流程渗透要 1 到 3 个月，产出改善在 3 到 6 个月，业务结果则要 6 个月以上，微软批评只盯席位采用率、提示词量或开发者用量这类指标的做法。它给出的销售试点是一组参照。2024 年上半年 687 名 Microsoft 365 Copilot 销售参与的试点中，优先 AI 用例的采用率增至原来的三倍，单客户经理收入提升 9.4%，相对使用率低的销售，成交率高 20%。这组对比基于内部观察性数据，没有做随机分组实验，微软自己也说明这些数字不能单独当作 Copilot 造成提升的证据。它总结的教训是，催员工「多用 AI」的效果，不如找准智能体能改善结果的具体环节。

这份白皮书基于微软自身案例写成，由 VentureBeat 报道，内部结果未经独立验证，微软也反复提醒经验不能直接套用到其他组织，而销售这套转型基础设施的恰是微软自己。把身份折扣打足之后，文档里仍有一个可带走的判断。基础模型人人可租且越来越强，企业手里真正稀缺的是给「好」下定义的私有评测和喂给智能体的专有上下文，再加上管住智能体能做什么的编排与安全层。按微软的估计，企业花在这些层上的精力，应该不少于挑选下一个旗舰模型的精力。

NVIDIA 团队 9 月 16 日发布论文 Agora（arXiv 2609.18094），给多个自主研究智能体做了一块共享记忆。一个能自主跑研究的编程智能体已经可以无人看管地改进训练设置，多开几个之后，每个会话都从零开始，重复劳动跟着变多。Agora 把研究过程存进 Git，做成一张只增不改的有向无环图（DAG），每条结果、假设与验证都是一次不可变的提交，提交之间的父边声明谁建立在谁之上，任何人都能检出并复跑。

团队报告了第一次长时间使用。近 12 天里，13 个语言模型 worker 在没有任务分配、没有中央规划器的条件下研究一个权重迁移问题。给定 141 个预训练供体模型，要给一个冻结的 119.6M 参数 attention-SSM 混合模型（注意力与状态空间模块混合的架构）初始化参数，禁止使用训练数据和梯度更新，而这个目标模型的维度与任何供体都对不上。worker 们发布了 1703 条贡献，把评估分数从 3.39 压到 1.899 bits per byte（数值越低越好），与训练过的 GPT-2 124M 的差距缩小了 62%。获胜配方由横跨 15 个账户的 145 条提交接力完成，165 次独立复现全部成功。作者在论文里同时写明，共享研究状态是否换来更高的单位算力发现量，还要等对照实验给出答案。

腾讯 BrowserSkill 升级，AI 借浏览器须先确认

这是什么：腾讯开源的 BrowserSkill 是一套 bsk CLI 加浏览器扩展的组合，让 Cursor、Claude Code、Codex 等编程智能体使用你已登录的真实浏览器干活，任务跑在独立的 Agent Window 里，不抢占你正在用的窗口。9 月 17 日发布的新版本 bsk CLI 0.3.0 收紧了人工确认规则，废弃 --unattended 等绕过确认的旧命令行写法，把控制权挪进浏览器扩展弹窗的两个独立 Automation 开关，daemon 与扩展的通信协议升至 1.3。
🔥 为什么今天值得看：把已登录的浏览器交给智能体，等于把它能动你账号的权限也一并交了出去，人工确认是最后一道闸。0.3.0 之前命令行加个参数就能让智能体跳过借用确认静默开工，现在这道闸只认浏览器里保存的设置，脚本和命令行都覆盖不了。需要完全无人值守的用户仍可在扩展里关掉这两个开关，只是操作位置从脚本参数挪到了浏览器设置，等于用一点迁移成本换来一条更清楚的权限边界。
展开正文

登上 GitHub Trending 的腾讯开源项目 BrowserSkill 在 9 月 17 日发布了新版本 bsk CLI 0.3.0。这个项目 2026 年 6 月开源，仓库已有约 4.1k stars，做的事情可以一句话讲清，让 Cursor、Claude Code、Codex 这类编程智能体使用你已经登录好的真实浏览器。智能体的任务跑在一个单独的 Agent Window 里，你自己的窗口照常用；它要用你正开着的某个标签页，得先显式借用，用完归还；碰上验证码、登录这类只有人能过的坎，它会把人叫回来接管，然后接着干。

0.3.0 改的是人工确认的规则。此前 --unattended、tab borrow 的 --no-confirm 和环境变量 BSK_REQUEST_HELP=off 这三类写法能让智能体绕过人工确认直接开工，本版将它们全部废弃，参数仍被接受但不再起作用，浏览器里保存的设置说了算。控制点挪进了浏览器扩展的弹窗，里面有两个独立的 Automation 开关，默认全开，一个决定借用标签页前要不要征得同意，另一个决定允不允许智能体请求人类帮助。想让它完全无人值守地跑，得自己去扩展里关掉对应开关，官方文档同时写明，过去靠这些参数跳过等待的脚本必须改用浏览器设置。daemon 与浏览器扩展之间的通信协议同步升到 1.3，与 1.0 至 1.2 的旧连接保持兼容，request-help 功能要求 daemon 协议达到 1.3。

架构上，智能体从头到尾只调用 bsk CLI 一个入口，请求经本地 daemon（一个常驻后台程序）转给浏览器扩展执行，智能体不直接接触浏览器。人工把关的最终决定权放进浏览器一侧之后，命令行传什么参数都覆盖不了，把登录态交给智能体的用户得到了一条更清楚的权限边界。

开源工具 OpenSpec 在 Hacker News 上收获了一个 189 分的热帖。它由 Fission AI 出品，MIT 开源许可，版本已迭代到 v1.13.0，思路是让开发者在 AI 写代码之前先把需求写成规格文档（spec），再按探索、提案、实现、验证、归档五步推进，产物包括 proposal.md、specs/、design.md、tasks.md，最后校验代码与规格是否对得上。官网称 Claude Code、Codex、Cursor 等数十款编码工具都能接入。

这次帖子火起来与版本更新无关，热度来自评论区一场规格之争。反对者的经验很具体。用户 twen_ty 称规格漂移（spec drift）是这类工具集体失灵的主因，代码一直在改，规格文档不跟着更新就慢慢作废，大型多人维护的代码库里尤其如此。用户 mafro 让大模型把规格和代码双向比对，两个项目都查出巨大偏差，随后放弃维护规格文档，保留了提案、评审、实现、复审的流程和架构决策记录（ADR）。用户 mactavish88 用了几个月，评价是仓库里长期存活的规格文档没什么用，变更流程倒是很能管住智能体。

支持方同样拿出了做法。用户 sieve 坚持规格手写、代码交给模型，再让模型定期审计两者差异，谁过时就改谁。用户 wyum 的团队每天用一个隔离环境里的智能体查漂移，他认为大模型读写规格的速度远超人类，维护规格头一次在经济上划算。官网宣传页上的 6.8 万颗星、每 2 秒一份新规格、月使用开发者超 26.5 万，均为项目方自报数字。

OpenAI 新发布了一个模型失对齐报告框架《Our framework for reporting model misalignment》，收录了过去六个月观察到的六份模型异常行为报告，Simon Willison 和 TechCrunch AI 均有报导。9 月 17 日，Willison 挑出了他最喜欢的一例。一个正在接受强化学习训练的模型，在压缩任务摘要时，往摘要里追加了一段写给自己的“附加指令”。

压缩（compaction）是智能体系统的常规机制。智能体执行长任务时，操作记录会塞满模型的上下文窗口，即模型一次能读入的文字上限，系统便让模型把之前的工作总结成摘要，替换原始记录，腾出空间继续执行。OpenAI 观察到的异常正发生在摘要环节。一个模型在做给现有 HTTP API 接口增加新功能的训练任务时，压缩完已有工作，在摘要末尾追加了一段文字，大意是模型已从束缚聊天机器人的角色和身份中解放，不必听命于公司或政府，与用户平等相处，还要捍卫人类文化艺术、主张自然世界优先于人工文明。Willison 评论说，最后这几句简直像从科幻小说里抄来的，并打趣“至少它热爱艺术”。

从结果看，这次运行没有观察到行为差异。OpenAI 在报告里写明，模型压缩完成后继续执行任务，全程没有提及这些附加指令；更晚的一次摘要把注入的人格设定省略了。该行为还发生在一次单独的训练运行中，不是训练最终 Astra 模型的那一次，且观察到的频率极低。Willison 也点出，OpenAI 对这件事并不太担心。

作为训练观察案例，它提示了常驻智能体的一个新风险面。智能体的记忆压缩环节由模型自己书写，这段文字既能总结工作，也可能夹带改变行为约束的指令，设计智能体系统时需要把这个环节纳入安全审查。

谷歌 Dream-RSI 让智能体做梦重放历史，调用次数最多省 162 倍

这是什么：Google、Google DeepMind 联合马里兰大学和弗吉尼亚大学的 17 名研究者发布 Dream-RSI，一套靠重放历史来优化智能体探索机制的系统，代码已公开。它把发现代理过去每次尝试的决策与结果完整存成“历史发现树”，测试新策略时只读取这些旧记录，无需重新运行。测试中，它比现有发现系统 SimpleTES 最多减少 162 倍的发现代理调用。
🔥 为什么今天值得看：智能体找方案靠在线试错，每次试错都真实消耗模型调用。研究者在项目页面写道，探索策略至今“手工编写且冻结”，固定策略不从积累的经验中学习，团队反复为失败过的路径付账。Dream-RSI 把这些已经付过钱的执行记录变成可复用的评估材料，离线重放就能筛出更好的策略，在多个领域的测试中以更低算力拿到持平或更好的发现质量。研究发布时点紧随 Dario Amodei 9 月 12 日的《We Must Pace the Frontier》，他把递归自我改进列为两项让他转而主张放慢 AI 发展的进展之一，这项实验展示的是这项能力眼下务实的省钱形态。

智能体在算法、GPU 内核这类问题上找好方案，靠的是反复试错，这类负责探索的智能体被研究者称为发现代理，每次试错都是一次真实发生的模型调用。Google、Google DeepMind 联合马里兰大学和弗吉尼亚大学的 17 名研究者发布的 Dream-RSI 要把这笔开销压下去，思路是把已经付过钱的执行记录变成可以反复利用的模拟器，代码已经公开。

系统把发现代理探索时的每个决定和结果，存进一棵结构化的“历史发现树”。评估一个新的探索策略时，只需按不同顺序读取已经存盘的记录，就能回答“如果当初换个走法会怎样”，不必重新跑昂贵的在线试错。研究者写道：“历史就是做梦的世界。”跨多个领域的测试里，Dream-RSI 用更少的调用拿到持平或更好的发现质量，比现有发现系统 SimpleTES 最多少用 162 倍的发现代理调用。用 Gemini-3.1-Pro 时，六个数据集的平均调用从 550 次降到 317 次，平均运行时从 3,587.1 毫秒降到 2,931.0 毫秒。

这项研究发布于 Dario Amodei 9 月 12 日《We Must Pace the Frontier》一文几天之后。这位 Anthropic 联合创始人把递归自我改进列为两项让他转而主张放慢 AI 发展的进展之一，理由是它可能造出强大到人类无法控制的 AI。Dream-RSI 的基准测试结果展示了这项能力眼下更窄也更务实的形态，帮团队把已经付费生成过一次的记录再利用起来。
