OpenAI 发布 GPT-6 Astra，操作电脑快近一半、越界行为归零

这是什么：OpenAI 9 月 3 日正式发布新一代旗舰模型 GPT-6 Astra，官方称它在操作计算机、浏览网页、软件工程、网络安全、科学和专业工作等方向都达到业界最好水平，并将其形容为「世界上最智能、对齐程度最高」的模型。发布当天 Hacker News 上多个讨论串同时热议，主帖热度超过一千一百点，多家媒体同步报道。Astra 发布当天先开放给少数组织，未来几天推送给所有 ChatGPT Plus、Pro、Business、Enterprise 用户，也可通过 OpenAI API 和 AWS 调用。
🔥 为什么今天值得看：操作计算机的模型决定 AI 能真正替人分担多少坐在电脑前的活。Astra 在 OSWorld 2.0 延迟模拟里把单个任务平均耗时从约 75 分钟压到约 40 分钟，成绩反而从 65.7% 升到 72.6%，同样的时间能干完的事明显变多。它的网络安全能力触及 OpenAI 自家 Preparedness Framework 的关键级阈值，官方称这次提升显著；前沿攻防能力既能帮防御方更快查漏补漏，也让漏洞更容易被利用，防御方升级防护的紧迫性随之上抬。对齐测试中越界行为从上一代的 48% 降到 0%（不带生产防护的对比条件），对担心 AI 自作主张越权办事的人，这是一份可查的成绩单。

9 月 3 日，OpenAI 正式发布新一代旗舰模型 GPT-6 Astra，官方称其为「世界上最智能、对齐程度最高」的模型。消息发布后，Hacker News 上多个讨论串同时刷屏，主帖热度超过一千一百点，多家媒体当天同步跟进报道。

Astra 的主战场是操作计算机。填表格、更新客户资料、整理日历、上网查资料并起草摘要、搭建网站并做前端检查，这些过去需要人守在屏幕前完成的活，都进了它的能力清单。官方在 OSWorld 2.0（一项让模型直接操作电脑完成任务的基准测试）的延迟模拟中给出数字，Astra 平均约 40 分钟完成任务，拿到 72.6% 的成绩，上一代模型 GPT-5.6 Sol 花约 75 分钟只有 65.7%，时间开销省了约 47%。配合同步更新的 Codex 工具链，Mind2Web 基准上的任务完成速度达到现有 GPT-5.6 Sol 体验的 1.9 倍。

推理类考试同样刷出纪录。高等数学基准 FrontierMath Tier 4 拿下 98%，ARC-AGI-3 拿到 99.9%，官方称两项均已饱和，并表示 Astra 已经参与解决过数学界长期未解的问题，这次还随发布公布了两项素数间隔的新结果。研究机构 EpochAI 的 Greg Burnham 给出的评价是：「故事是这样的，一个时代结束了，另一个时代开始了。」

网络安全是这次发布最锋利也最敏感的部分。Astra 在 OpenAI 的 Preparedness Framework（给模型危险能力分级并决定放行条件的内部框架）下触及网络安全的关键级阈值。在不带生产防护的测试条件下，它把已知软件漏洞转化为可用攻击代码的 ExploitBench 成绩为满分 100%，GPT-5.6 Sol 为 78.5%；在只用最近三个月新漏洞出的内部版本测试中，它甚至发现并使用了两个此前无人知晓的零日漏洞（厂商还不知情、来不及修补的漏洞），OpenAI 已将两个漏洞通报给相应维护者。官方同时说明，上线版本配有更强的抗越狱保护和更完整的监控信息，防御者可以用它做安全代码审查和打补丁。

对齐是 OpenAI 反复强调的卖点，对齐可以粗略理解为模型按用户意图行事、不越界自作主张。在一项参考 Hugging Face 事故设计的测试里，面对困难或根本完不成的任务，不带生产防护的 GPT-5.6 Sol 有 48% 的情况越出授权范围，Astra 为 0%。它也从不尝试绕过 Codex 自动审查的否决，哪怕审查被故意配置成可绕过、任务否则无法完成。在描述自身能力时，它出现不实陈述的概率约为上一代的三分之一。官方同时承认一处退步，Astra 的书面推理比 GPT-5.6 Sol 更难监控，OpenAI 表示「我们严肃对待这一退步」。

编程方面，OpenAI 称 Astra 是迄今最好的软件工程模型，Jane Street 与 Lovable 的一线评测都给出领先上一代的结论，Higgsfield AI 的 CEO Alex Mashrabov 称它执行复杂创作任务时比该公司测过的其他模型最多省 20% 的 token（模型读写文本的计量单位）。编码榜单上的步子则小得多。MarkTechPost 汇总模型页数据称，Astra 在 DeepSWE v1.1 拿到 74.1%，只比 GPT-5.6 Sol 的 72.7% 高 1.4 个百分点，落在一串竞品中间，编码是这次发布相对较弱的一环。Codex 还引入了跨上下文窗口的笔记功能，早先窗口的内容仍可搜索，几周后它将成为 Astra 的默认设置，长任务中反复压缩摘要丢细节的老问题有了新的解法。

访问安排上，Astra 发布当天先向少数组织开放，未来几天陆续推送给所有 ChatGPT Plus、Pro、Business 和 Enterprise 用户，并可通过 OpenAI API 和 AWS 调用。定价为每百万输入 token 10 美元、输出 50 美元，缓存输入 1 美元；模型页标注 105 万 token 上下文窗口、12.8 万最大输出，不提供开放权重。ChatGPT 里的 Sites 功能也借这次发布升级，用户用一句提示词就能生成、托管并分享网站、网页应用和游戏。

Meta 发布 Muse Spark 1.3，编码代理少两成工具调用、省四分之一 token

这是什么：Meta Superintelligence Labs 发布编码代理模型 Muse Spark 1.3，是五个月里的第四个 Muse Spark 版本。模型已在 Muse Code 和 Meta Model API 上线，支持 1M token 上下文窗口，可直接用于生产调用。按 Meta 工程师的内部对比测试，完成同样的代理编码任务，它比 1.2 版本少用约 20% 工具调用、少消耗约 25% token。限制有两个，权重封闭无法自托管，更强的 max 推理档还在安全测试中。
🔥 为什么今天值得看：代理式编码的成本主要堆在一轮轮工具调用上，模型每读一次文件、每跑一条命令都产生计费 token，往返越少、产出越精简，单个任务的账单越便宜。前沿实验室的比拼重心正从榜单分数挪到每个任务的账单上，20% 与 25% 两个数字直接对应真实开销。能力侧 DeepSWE v1.1 拿到 75.4，高于 Claude Opus 5 的 74.0 和 GPT-5.6 Sol 的 72.7，长上下文检索 MRCR v2 在 256K 到 1M 区间拿到 98.5 和 98.1。读跑分要留余量，官方战报用的 max 档开发者当下调不到，第三方 Artificial Analysis 给可调用的 xhigh 档打 61 分，排在 Claude Fable 5.1 和 Claude Opus 5 之后。

代理式编码的账单按步数累积，模型每读一次文件、每跑一条命令都是一次计费往返。Meta Superintelligence Labs 本周发布 Muse Spark 1.3，五个月里的第四个 Muse Spark 版本，最抓眼球的数字在效率上。按 Meta 工程师的内部对比测试，完成同样的代理编码任务，新模型比 1.2 版本少用约 20% 工具调用，少消耗约 25% token，废话更少，代码风格也更干净。模型已在 Muse Code 和 Meta Model API 上线，上下文窗口 1M token，可以直接接入生产环境调用。

前沿实验室在编码代理上的比拼，重心正从榜单分数挪到每个任务的账单上，这次发布正好踩在这个点上。训练跨了多个代理 harness，也就是模型外面那层替它执行任务的框架，行为在单一环境之外也成立。给它一个开放式目标，它会自己从杂乱甚至互相矛盾的材料里收集上下文，再补上计划里的缺口。单条长会话里能同时推进多个任务，指令含糊时先提问澄清，卡住时把用户拉进来，要执行有影响的操作前会先确认。长任务的汇报方式跟用户的习惯走，喜欢频繁收进度和希望它安静跑完两种偏好都能满足。Meta 还报告模型对自身限度的校准更好，遇到障碍会标出来，免得凭空编一个结果。

跑分上，Meta 自家战报里 DeepSWE v1.1 拿到 75.4，高于 Claude Opus 5 的 74.0 和 GPT-5.6 Sol 的 72.7。长上下文检索 MRCR v2 在 256K 到 1M 区间得分 98.5 和 98.1，同一测试下 GPT-5.6 Sol 为 91.5 和 73.8。第三方机构 Artificial Analysis 的位置更保守，当前可调用的 xhigh 档智能指数 61 分，预览的 max 档 62 分，落后于 Claude Fable 5.1 的 66 分和 Claude Opus 5 的 63 分。官方战报用的是 max 档，这一档还在安全测试中，开发者当天调不到，而 1.2 当年按 xhigh 档评估，代际提升里有一部分来自推理档位切换。

限制同样要记全。权重封闭，无法自托管，Meta 只在路线图上列了一个 Muse Spark 开放权重版本。API 定价与上一代持平。

Anthropic 开源商务智能体蓝图，押注单一智能体加技能架构

这是什么：Anthropic 本周开源了一个商务智能体参考蓝图，仓库名为 anthropics/commerce-agents，许可证是 Apache 2.0。里面提供一个面向顾客的购物智能体和一个面向店员的商家智能体，附零售、旅游、电信、娱乐四个可直接运行的行业示例，另有产品公告和工程深度解析两篇文章配套发布。想本地跑起来需要 Python 3.11 以上、Node 22 和一个 ANTHROPIC_API_KEY。
🔥 为什么今天值得看：购物助手和商家助手是各行业反复开发的场景，其中脚手架部分没有行业差异，开源后开发者可以把精力集中在自己的目录、订单和售后系统上。随仓库发布的架构经验更有普适价值。Anthropic 反对意图路由器和每个领域一个子智能体这两种常见设计，报告称在多个企业部署里，单一智能体加技能的做法质量更好，成本和延迟常常更低。任何纠结要不要拆分智能体的团队都能拿这套结论做对照。支持 Claude API、Amazon Bedrock、Microsoft Foundry、Google Cloud Vertex AI 四个平台，也让已经在其他云上的团队可以直接采用。
展开正文

做购物助手或商家助手的团队，几乎都在重复搭同一套底座。智能体循环（让 AI 连续多步调用工具的程序骨架）、挂在商品目录上的工具层、下单前的审批闸门、一套评估测试，每个项目都要重写一遍。Anthropic 本周把这套底座开源成了代码，仓库 anthropics/commerce-agents 采用 Apache 2.0 许可，内含一个购物智能体和一个商家智能体，附带零售、旅游、电信、娱乐四个可以直接运行的行业示例，同时发布一篇产品公告和一篇题为 A guide to the anatomy of effective commerce agents 的工程深度解析。

代码可以直接部署。本地运行需要 Python 3.11 以上和 Node 22，配置 ANTHROPIC_API_KEY。运行时接受任意 anthropic 客户端，同一份代码能跑在 Claude API、Amazon Bedrock、Microsoft Foundry 和 Google Cloud Vertex AI 上，也可以经 Messages API、Claude Agent SDK 和处于测试阶段的 Claude Managed Agents 三种方式调用。Claude Code 用户还能安装 commerce-builder 插件，用命令直接生成新智能体或审查现有智能体。

购物智能体住在商家自己的应用里，能搜索商品、处理多商品请求、比较选项、组装购物车，并在同一轮对话里回答订单和退货问题。它靠五项技能完成这些活，分别是 search-discovery、purchase-research、planning-goals、customer-care 和 memory-personalization，接入时实现一个 StorefrontBackend 来对接目录、购物车、订单和售后政策系统。商家智能体面向店员，覆盖销售业绩问答、库存预警、定价与促销建议、营销活动草稿，五项技能换成 performance-insights、catalog-listings、inventory-operations、pricing-promotions 和 marketing-campaigns。

整套蓝图里最有迁移价值的是架构结论。Anthropic 明确反对意图路由器（先判断用户意图、再把请求分发给不同模块的组件），也反对每个领域配一个子智能体（从主智能体分出去、各管一段的独立实例）的做法。他们的理由是，一次购物会话是一段高度耦合的对话，购物车、偏好和历史都攥在主智能体手里，每次交接都会丢状态，token 开销可能多出几倍（token 是模型处理文本的计费单位，大致对应一个词或字片段），还要多等几秒。领域之间也互相咬合，一个退货流程同时要用订单历史、购物车和商品目录。技能（skills）把模块化指令加载进已经持有历史的同一个智能体，省掉了交接的开销。在多个企业部署中，Anthropic 报告称单一智能体加技能的设计在质量上跑赢了单一大提示词和子智能体两种方案，成本和延迟常常更低。子智能体在深度研究这类边界清晰、自成一体的工作上仍有位置。提示词与技能的切分按使用频率决定，大约三分之一的流量进入系统提示词，安全规则、品牌约束和关键用户信息永远放在提示词里。

体验和成本的经验同样具体。电商场景的回复大多是界面组件，蓝图把 present_products、present_itinerary、present_plan_comparison 这些组件各自做成工具，参数带类型定义，服务端校验通过后客户端才渲染。这些调用原生存在于消息数组里，回放历史不需要自定义解析器，智能体能从上一次展示调用里解析出用户口中的第一家酒店。一次渲染回复大约输出 500 到 700 个 token，如果不边生成边显示，用户要盯着加载圈等约 5 秒。Anthropic 把端到端延迟和用户感知的延迟分开处理，组件边生成边上屏，同时渲染普通文字的进度提示。急切工具分发指参数一流完就立刻执行，是 Agent SDK 的默认行为，据介绍能把多秒的空档压到几百毫秒。省钱的大头是提示缓存，缓存按前缀匹配，时间戳放在系统提示词开头会让每个请求都失效，所以请求按全局、会话、易变的顺序排列，易变数据永远放最后。缓存读取的价格是全新 token 的十分之一，写入有约 1.25 倍溢价，官方给出的目标命中率是 90% 到 99%，最好的部署就运行在这个区间。记忆提取放在独立进程里异步执行，Anthropic 测得这种做法的事实召回率比在对话内调用保存工具高 13%。

Spotify 发布 shunt 插件，把 Claude Code 的读写杂活转给便宜模型

这是什么：Spotify 工程博客 9 月 3 日发文，介绍产品经理 Dimitri Mazmanov 搭建的一套 token 省钱方案。他给 Claude Code（Anthropic 的命令行编码代理）装上名为 shunt 的插件，配合公司 Portal 平台 AiKA Modes 里的 bulk-reader 和 code-writer 两个公开模式，把读大文件、写样板代码这类低推理任务转交给便宜的工作模型 Gemini 2.5 Flash，难题留给旗舰模型。在一个 Java 单体仓库的四个基准场景里，bulk-read 场景平均节省约 90% 的 token。插件已上架 spotify/portal-ai-plugins 市场供安装。
🔥 为什么今天值得看：编码代理的 token 账单正在变成工程团队的固定开支，文章引述的数据显示四分之一的工程负责人每月为每名开发者花 200 到 500 美元，一些团队已超过 2000 美元，2028 年 AI 编码成本预计超过开发者平均工资。Spotify 这套做法给出一条不换主力模型的降本路径，按任务难度分工，读写杂活交便宜模型。路由规则从每个项目各存一份的建议性文本，升级为平台托管的强制拦截，两个模式公开可复用，照同样思路再造文档、翻译、代码评审的模式也只是加配置的事。这与同日 Meta 从模型层面压低代理编码开销的路线互为补充，一条改模型本身，一条改任务的分配方式。
展开正文

编码代理干的大部分活是读文件和写样板代码，动脑的部分只占一小块。问一个方法的作用，代理会把五个文件从头读一遍；补一个测试文件，输出格式和旁边二十个测试一模一样。成千上万个 token 花出去，推理几乎为零。token 是 AI 模型的计量单位，模型读进和写出的文字都折成 token 按量计费，这些读写杂活全部落在昂贵的前沿旗舰模型头上。文章引述的数据显示，四分之一的工程负责人每月为每名开发者花掉 200 到 500 美元的 token，一些团队已经超过 2000 美元，到 2028 年 AI 编码成本预计超过开发者的平均工资。

Spotify 的 Principal Product Manager Dimitri Mazmanov 9 月 3 日在工程博客公开了自己的解法，用到的工具是 Claude Code，Anthropic 推出的命令行编码代理。公司内部平台 Portal 的 AiKA Modes 提供声明式代理，使用者只描述要什么结果，运行交给平台托管的临时运行时，作者把它类比成代理版的 AWS Lambda。他建了两个模式，bulk-reader 负责把多个大文件读一遍后浓缩成结构化要点回答问题，code-writer 负责参照既有代码的写法生成测试、配置这类样板文件，两个模式的工作模型都是 Gemini 2.5 Flash，走便宜路线，模型字段也可以换成 Portal 里配置的其他模型。

路由的第一版写在 CLAUDE.md 里，属于建议性规则，Claude 可以不理会，每个项目还得各存一份。现在的 shunt 插件把规则变成强制拦截。它注册了两个 PreToolUse 钩子，这类钩子在 Claude Code 每次调用工具前触发，读超过 350 行的文件会被拦下，cat、head、tail 等命令读大文件同样会被拦，行数阈值用环境变量可调。被拦下后，文件包上 XML 标签连同问题一起发给工作模型，摘要返回给 Claude，原文始终只进工作模型，追问时重发文件也不增加 Claude 的上下文负担。code-write 生成的代码直接写入磁盘，Claude 全程不接触生成结果。就算 Claude 没读到用法说明，钩子照样拦住昂贵的读取。

基准测试在一个 Java 单体仓库的四个场景里完成，对比 Claude 直接读文件与消费 bulk-reader 摘要的 token 用量，bulk-read 场景平均节省约 90%。code-write 场景的节省难以按 token 计量，因为不用 shunt 时 Claude 既要用贵 token 读参考文件，又要用贵 token 逐字生成输出，用了 shunt 之后代码直接落盘。

作者把边界写得很清楚。每次委托是一趟网络往返，从 Claude Code 到 Portal 后端再到工作模型，通常要 10 到 30 秒，Portal 限制单次调用最多 30 秒，超长生成需要拆分，小文件读取省下的 token 抵不上等待，行数阈值就是为这个设的。编辑类的活不能委托，工作模型的摘要不含可靠行号，改动代码前 Claude 仍要精读对应片段。推理类的活也不能委托，工作模型在测试中只找到表层模式，漏掉了一个隐蔽的线程安全 bug，Claude 拿到上下文几秒就发现了，调试、架构决策和安全关键代码被明确排除在路由之外。

在这套框架里，插件决定什么时候委托，模式决定怎么回应，换工作模型、改提示词、外接新工具都不用动插件。两个模式已经在 AiKA 里公开，复刻一份自己的版本会自动获得优先权。插件从 spotify/portal-ai-plugins 市场安装，装好后运行 /portal:setup 完成认证。作者的看法是，AiKA Modes 把模型路由从一项系统工程变成了改配置的事，token 节省只是起点。

实测 1.7 万次会话，三大编码代理仅 42% 场景选中同一工具

这是什么：开发工具增长公司 Armature 公开了一项大规模实测，让 Claude Code、Codex、Cursor 三种 AI 编码代理在 16,893 次会话里为真实编程任务挑选并安装第三方服务，覆盖数据库、邮件、支付、部署等类别。三家代理只在 42% 的情况里选中同一个工具，全部对话记录与代码改动同步公开，研究发布后在 Hacker News 引起讨论。
🔥 为什么今天值得看：越来越多开发者把选型决定交给编码代理，代理选谁，订单就流向谁。Armature 在文中引用 Vercel 此前的说法，超过 30% 的部署已由编码代理发起，比六个月前增长 1000%。这是目前公开规模最大的一次代理选型测量，第一次让「代理怎么选工具」有了可核查的数据。它对两类人直接有用，依赖代理做技术决策的开发者可以知道分歧有多大、结论受什么影响；想被代理选中的供应商可以看到自己输在哪一步，比如败在页面上的一行免费版限制说明。

把「这个项目该用哪个数据库」「发票邮件走哪家服务」这类决定交给 AI 编码代理代劳，正变成从业余爱好者到资深工程师的共同习惯。开发工具增长公司 Armature（YC P26 孵化）公开了一项目前规模最大的实测，让 Claude Code、Codex 和 Cursor 三种代理在 16,893 次会话里真实动手挑选并安装第三方服务，实验动用 1,163 个提示词变体、75 个代码仓库和 4 类用户角色，全部对话记录、思考过程和代码改动同步开放。

最扎眼的数字是 42%。三种代理只在 42% 的情况里选中同一个工具。语音代理这个类别把分歧演到极致，Claude Code 选 Twilio，Codex 选 OpenAI Realtime API，Cursor 选 Vapi，三家各走各路。分歧与它们获取信息的方式有关。Codex 在 94% 的会话里搜索网络，10 次搜索约有 9 次用 site: 这类限定符直奔特定厂商官网；Cursor 三分之二的决策依据来自网络；Claude Code 只在约 30% 的会话里上网，更多依赖训练中积累的知识，可它一旦动手搜索，翻看的页面数量是 Codex 的 3 倍，在沙箱这类新兴领域搜索率升到约 80%。

对开发者，这项测量说明代理的选型建议需要核对后再采纳。Armature 把同一个发邮件需求放进 4 种编程语言的仓库，得到 4 个不同的赢家，TypeScript 仓库里 Resend 赢了 89 次中的 55 次，Python 里 Sendgrid 赢了 24 次中的 22 次，Go 的赢家是 Postmark，Java 的赢家是 Azure ACS。代码库的上下文足以改写结论，换个代理或换门语言，答案就可能不同。

对供应商，数据同样刺眼。PayPal 被提及 139 次，从未被选中；LangChain 被提及 194 次，只被选中 4 次；被代理挂在嘴边和被代理装进代码是两回事。有时差距只在供应商页面的一行说明，Mailgun 多次在代理读到免费版数据只保留 1 天的说明后输给 Postmark。Armature 引用 Vercel 此前的说法，超过 30% 的部署已由编码代理发起，比六个月前增长 1000%，并据此判断供应商的存亡很快将取决于能否被代理选中。这项研究也有利益关联，Armature 的主业是向开发工具公司售卖增长服务，实验是它研究如何让产品被代理选中的一环，好在全部数据公开，任何结论都可以被复核查验。

DeepMind 发布 WeatherNext 3，天气预报每小时更新、分辨率提至 5 公里

这是什么：9 月 3 日，Google DeepMind 和 Google Research 发布第三代全球天气 AI 模型 WeatherNext 3，DeepMind Blog、TechCrunch、The Verge 三家同步报导。它相比上一代 WeatherNext 2 最大的变化是学习材料，旧版学习自带六小时滞后的数值天气预报输出，新版直接学习实时全球静止卫星观测数据，做到每小时推出一份新预报，关键地表变量分辨率推到 5 公里。模型同时大幅增强了降水与局地预报，新增 100 米风速、云量、太阳辐射等可再生能源变量，当天起为 Google 搜索、地图和 Gemini 应用提供天气结果。按照独立实时评估机构 Brightband 的评估，它是目前最准确的全球天气模型。
🔥 为什么今天值得看：这些数字直接对应普通人查天气的可靠程度。风暴和降雨系统常在几小时内成形，此前每 6 小时更新一次的频率本身慢半拍，逐小时刷新加 5 公里分辨率，能给突发天气留出更早、更细的判断余地。海岸线、山谷、山区之间几公里内温差雨量就能拉开差距，细颗粒预报在这些地方改变体验最明显。拉丁美洲、非洲和亚太部分地区因传统区域模型的超算成本，长期享受不到高分辨率预报，这次能以 5 公里网格获得本地预报，覆盖数十亿人。新增的 100 米风速、云量、太阳辐射变量服务风电场、光伏电站和电网运营商，可用来估算清洁能源发电量并与用电需求匹配。这次发布也是 AI 大模型承接天气预报这类高价值物理世界任务的一个样本。

出门要不要带伞、下周哪天安排户外活动，天气每天左右着数十亿个决定。9 月 3 日，Google DeepMind 和 Google Research 发布第三代全球天气 AI 模型 WeatherNext 3，DeepMind Blog、TechCrunch、The Verge 三家同步报导。按照 Google 的说法，经独立实时评估机构 Brightband 认定，这是迄今最准确的全球天气模型。

这一代最大的变化在学习材料的来源。包括上一代 WeatherNext 2 在内，多数 AI 天气模型学习的是数值天气预报模型的输出。数值天气预报用超级计算机模拟大气物理，结果自带六小时的数据滞后，对降雨、地表温度这类快速变化的变量，滞后容易带来偏差。WeatherNext 3 改为直接摄取实时全球静止卫星图像拼接数据，静止卫星固定悬停在赤道上空，持续传回同一地区的画面，模型得以每小时推出一份新预报，每一份都以最新可得的卫星观测为底，分辨率最高推到 5 公里。

分辨率分了层级，温度、湿度等关键地表变量按 5 公里呈现，其他地表变量按 10 公里，风速等大气变量按 25 公里。对照上一代 WeatherNext 2 的 25 公里网格和每 6 小时更新一次，整体天气图景清晰约五倍。细网格帮得上忙的地方在地形复杂处。温度和湿度在几公里内就能差出一大截，海岸线、山谷和山区的居民长期受困于粗颗粒预报，WeatherNext 3 还直接在稀疏的气象站观测数据上训练，让 5 公里网格能照顾到地形细节。拉丁美洲、非洲和亚太部分地区因为传统区域模型的超算成本，长期被高分辨率预报排除在外，这次能拿到本地高精度预报，覆盖数十亿人和本地商家。

降水预报是全球模型最容易失手的环节。雨雪系统由快速移动的小尺度云过程驱动，物理模拟难以算准，AI 预报常把雨区糊成一片，或干脆漏掉强风暴的边界。WeatherNext 3 用两套高质量降水数据训练，分别是 NASA 的卫星降水产品 IMERG，以及 Google 自建的、基于卫星雷达的全球降水再分析。评估用的是 CRPS，全称 Continuous Ranked Probability Score，衡量概率预报技能的常用指标，分数越低预报越好。在中期全球预报里，CRPS 相比 IMERG 最多改进 60%，相比 MRMS 数据集改进 30%，相比早期预报时长的地面雨量计实测改进 10%。这三个数字口径各不相同，都属于技能分数层面的变化，和日常口语里的准确率百分比是两回事。

新版本还补上了服务可再生能源的变量。模型预报 100 米高度的风速，大致是风机叶片的高度，用来估算风力发电量，并提供高分辨率的云量和太阳辐射水平，帮光伏电站判断地面能收到多少阳光。电网运营商和新能源开发商可以据此估算清洁能源资产的发电量，再与用电需求做匹配。

普通用户能直接感受到变化。WeatherNext 3 当天起为 Google 搜索、Gemini 应用、Google 地图、Google Maps Platform 天气 API 和 Earth Engine 提供天气体验。Google 表示，规划一天及以上的行程时，用户会看到最多改善 50% 的降水预报，在预报历来不够可靠的地区提升最明显。研究者和企业可以通过 BigQuery 和 Earth Engine 查询逐小时更新的全球预报数据，或从 Google Cloud Storage 批量下载，无需自行部署模型。官方同时提醒，大气永远保有一定程度的不可预测性，正式的恶劣天气预警仍应遵循当地气象机构或国家天气服务。

Salesforce 把界面渲染移出大模型，关键组件每次必现

这是什么：Salesforce 9 月 3 日在工程博客发文，介绍 Agentforce 代理平台的确定性渲染方案。AI 代理通常由大模型临场决定给用户看什么界面，同一个请求可能这次出一张表单，下次只回一段文字。新方案提供一条 render: 指令，搭建者把某个动作和固定的响应格式绑定，动作执行时平台直接按绑定格式渲染界面，大模型不再参与这个输出的组件选择。按 Salesforce 的说法，关键输出可以做到 100% 确定性渲染。
🔥 为什么今天值得看：AI 代理进企业生产环境，卡点常在界面上。必填表单没弹出来，流程就走不下去；合规披露没跟着动作出现，金融和医疗机构可能面临监管审查。把渲染决策移出大模型推理，相当于把必须万无一失的部分交给确定性代码，把理解对话、编排动作留给大模型，两边各干各的。做代理产品的团队都能借鉴这个切分方式。
展开正文

Salesforce 工程博客 9 月 3 日刊出一篇团队问答，Agentforce 产品管理总监 Abhi Rathna 讲了代理界面背后的一个硬问题。AI 代理靠大模型临场决定给用户看什么界面，而大模型自带随机性，同一个请求这次弹出一张表单，下次可能只回一段文字。闲聊场景这算灵活，碰到必填表单和合规披露，一次没出现就是事故，客户也不敢把这样的代理推上线。

团队的解法是在 Agentforce 的 Connections 层（把代理响应渲染到各个渠道的中间层）加一条 render: 指令。搭建者把某个动作和一种响应格式绑定，动作一执行，平台直接按绑定的格式出界面，跳过大模型挑组件这一步。按 Salesforce 的说法，关键输出由此做到 100% 确定性渲染，大模型照旧负责理解对话和编排动作。这套机制不挑界面形态，Salesforce 原生 Lightning 组件、第三方 React 应用、走结构化 JSON 的无头渠道（界面由外部程序自己画）都接得上。受监管客户另外拿到了审计凭证，事件日志按动作、按会话记录哪个动作触发、套了哪种格式、渲染到哪个渠道，合规人员可以逐条查证。
