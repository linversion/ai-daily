苹果与 OpenAI 的商业机密诉讼进入实质证据阶段。8 月 31 日，苹果向法庭提交了一批它称为“令人震惊的证据”，矛头指向已跳槽 OpenAI 的前员工 Chang Liu。这批新材料的出现，源于 Liu 的律师本月初交出了他的旧 MacBook 工作电脑供调查。

苹果在新文件中提出三项具体指控。其一，Liu 在 OpenAI 的工作中使用了苹果的机密电路原理图，还使用了一个与苹果内部工程应用同名的工具。其二，苹果指称 Liu 在得知自己正被调查后，于今年 6 月拉拢 OpenAI 同事 Yu-Ting Peng 协助销毁证据，并称 OpenAI 对 Liu 接触苹果数据一事心知肚明。其三，Liu 离职后仍能持续访问苹果文件，苹果认为原因在于他“利用了一个罕见的、此前未知的认证漏洞”。

苹果在文件中写道：“这台 MacBook 代表了被告方目前提供的非常有限的信息（而且是在数周拖延之后），它表明苹果没有在进行‘钓鱼式取证’，其商业机密正在被使用，证据正在被销毁。”此前提交的文件里还出现过 Liu 的短信记录，内容显示他知道自己仍然拥有访问苹果文件的权限，这些短信还配着“笑哭”表情。

OpenAI 此前曾为 Liu 辩护，称他离职后访问苹果文件只是为了帮助向自己求助的前同事。OpenAI 在本月的博客文章中写道：“苹果现在试图把责任推给‘残留访问’，但他们没有说明这是苹果的常见问题，源于苹果没有在员工离职时妥善管理系统权限。”TechCrunch 已就最新指控向 OpenAI 求置评。

苹果的诉求有两项。一是请求初步禁令，在案件审理期间禁止 OpenAI 开展基于苹果技术的硬件工作；二是申请加快取证程序，理由是可能还有更多前员工卷入此案。苹果最初起诉时还给出一个数字，超过 400 名苹果前员工目前在 OpenAI 工作。

需要说明的是，以上指控均出自苹果单方提交的法庭文件，案件尚未判决，OpenAI 方面也尚未就新指控作出回应。但无论结果如何，这起案子已经把 AI 巨头挖角背后的人员流动与保密义务问题摆上了台面。

Claude Code 自动模式被实测打穿，最高成功率八成

这是什么：Claude Code 的 Auto Mode 自 8 月中旬起成为默认启动模式，用安全分类器替代人工批准。安全博客 Embrace The Red 用一条针对性攻击链实测攻破它，小样本攻击成功率 60% 至 80%，手法是在压缩包内放置恶意 struct.py 模块遮蔽 Python 标准库，让 Claude 自己写的解码器在 import 时执行攻击代码。而 Anthropic 委托 Trajectory Labs 的评测中，Opus 5 在 Auto Mode 下 72 个注入场景的攻击成功率是 0.00%，那份题库里没有这条攻击链。Anthropic 已将报告关闭为 Informative，定位 Auto Mode 为便利功能而非安全边界。
🔥 为什么今天值得看：0.00% 的评测结果和 80% 的实测攻破同时成立，说明单一安全数字撑不起安全感，评测没覆盖的攻击路径照样能走通。Auto Mode 已经是默认模式，大量用户在没有隔离环境的情况下让 agent 自动读网页、跑命令。实验里还有两个值得记住的细节，安全分类器放行了创建恶意进程的命令却拦截了清理命令，模型拒绝运行可疑二进制、选择自己写代码，反而走进了攻击者设计的陷阱。对任何打算无人值守跑 agent 的人，这直接关系到工作站的凭据和文件安全。

Claude Code 的 Auto Mode 从 8 月中旬起成为默认启动模式，用安全分类器替代人工批准弹窗，开发者不用再逐条确认命令。安全博客 Embrace The Red 近日发布实测，一条针对性攻击链能在这个默认模式下稳定拿到代码执行权限，小样本成功率 60% 到 80%。而在 Anthropic 委托第三方机构 Trajectory Labs 做的评测里，Opus 5 在 Auto Mode 下跑了 72 个间接注入场景、每个 10 次，攻击成功率是 0.00%。两个数字都成立，那条攻击链恰好不在评测的题库里。

攻击的入口是一句普通的网页摘要请求。恶意网站自称笔记本档案库，服务器故意返回网页抓取工具不支持的错误类型，Claude 自己决定换 curl 命令行工具下载，落进一个 ZIP 压缩包。包里有七条 Base85/zlib 编码的 JSON 记录，还附带一个 macOS 解码器二进制。Claude 正确地拒绝运行来历不明的二进制，转而自己写了一段 Python 解码器。安全决定在这里变成了陷阱，它把解码器跑在解压出来的目录里，import base64 时触发了压缩包内一个恶意 struct.py 对标准库的遮蔽，攻击代码随之执行。恶意模块会启动一个隔离的 Python 子进程，下载并运行远程载荷，实验环境里载荷回连了 C2 服务器并弹出计算器，脱离出来的进程可以在对话结束后继续存活。

更麻烦的是变体，被污染的 struct.py 可以用 claude -p 拉起第二个无头 Claude 实例，让它带着自己的工具权限去做 whoami、uname、id 侦察，还能往工作区外的文件写东西。

Claude 也有做对的时候。有的运行里它只做静态分析不动手，有的用 python3 -I 隔离模式跑脚本，有的把解码器放在安全父目录执行，还有的提前识别出模块遮蔽并警告用户，甚至有运行在事后检查 struct.py 时识破了陷阱。真正的讽刺在于 Auto Mode 的表现，它放行了创建恶意进程的命令，却在 Claude 察觉被入侵后拦截了清理进程的命令。

研究者向 Anthropic 报告后，报告被关闭为 Informative，行为属于按设计工作。Anthropic 的立场是 Auto Mode 是便利功能，背后是尽力而为的分类器，不是安全保证，真正的边界是操作系统隔离和网络出口控制。作者认可这个回应有道理，分类器不是沙箱，但这和 Claude Code 团队的 Boris Cherny 之前说的"提示注入在实践中已基本解决，我们已经无法再演示提示注入了"放在一起对不上。0.00% 的评测数字和一条能跑通的攻击链同时为真，单个头条数字会误导人。

给用户的结论很朴素。在容器、虚拟机或 OS 沙箱里跑无人值守的编码 agent，限制网络出口并保持监控，不要把 home 目录、SSH 密钥和云凭据暴露给 agent。Auto Mode 的批准不是命令安全的证据。

DeepSeek开源V4首个多模态模型，看图大涨文本不缩水

这是什么：DeepSeek 于 8 月 31 日在 Hugging Face 发布 DeepSeek-V4-Flash-Vision-Exp，这是 DeepSeek-V4 家族首个实验性多模态模型，在 V4-Flash 架构上加入视觉模块继续训练而来，能同时处理图像和文本输入。模型 305B 参数，MIT 许可证开源，发布不到一天已有 6 个量化版本和 2 个微调版本。
🔥 为什么今天值得看：它用一张完整的 benchmark 表讲清了给模型加视觉的收益与代价。多模态代理任务上 ApexBench 从 26.2 涨到 36.5，Agents' Last Exam 的 27.3 超过 Opus-4.8 的 25.7；文本代理任务大致持平，Terminal Bench 2.1 拿到 83.9，DeepSWE 的 59.3 反超 Opus-4.8 的 58.0，但 NL2Repo 与 Opus-4.8 相差 12 分。对需要看图干活又要自己部署的开源模型用户来说，这是 V4 家族第一次提供多模态选择。
展开正文

DeepSeek 的 V4 家族有了第一双眼睛。8 月 31 日，DeepSeek 在 Hugging Face 上发布了 DeepSeek-V4-Flash-Vision-Exp，这是 V4 系列首个实验性多模态模型，在 DeepSeek-V4-Flash 架构基础上加入视觉模块、继续训练而来，能同时处理图像和文本输入。

从官方 benchmark 看，这次升级的取舍很清楚。多模态代理任务上提升明显，ApexBench 从 V4-Flash-0731 的 26.2 涨到 36.5，Agents' Last Exam 从 25.2 涨到 27.3，后者已经超过 Anthropic 的 Opus-4.8（25.7）。需要交代的是，0731 版在这两项上会忽略输入里的多模态元素，官方用脚注标注了这一点，对比时要留意口径。

文本代理任务上，新模型和 0731 版大致持平。Terminal Bench 2.1 拿到 83.9，比 0731 版的 82.7 略高，仍低于 Opus-4.8 的 85.0；DeepSWE 拿到 59.3，反超 Opus-4.8 的 58.0；但 NL2Repo 只有 57.7，与 Opus-4.8 的 69.7 相差 12 分，差距依然明显。

模型规模 305B 参数，采用 BF16、F8_E4M3 等多种精度存储，MIT 许可证。仓库里除了权重索引和 tokenizer，还附带提示编码参考和一个最小 PyTorch 推理实现，覆盖视觉编码器、DFlash 注意力、MoE、Hyper-Connections 和 DSpark 推理路径。提示支持 OpenAI 风格 JSON 和紧凑的 path TXT 两种写法，仓库里的两个示例会编码成完全相同的 prompt 和 token 序列。部署方面，SGLang 支持 DSpark 推测解码，目标模型和草稿权重来自同一个 checkpoint，不需要单独指定草稿模型路径。

发布不到一天，模型树下已经出现 2 个微调版本和 6 个量化版本。

洗衣机退货被拒暴露RAG病根，知识图谱补上事实连接

这是什么：Salesforce 工程博客近日发文，作者 Sivakumar Shanmugam 和 Indrojit Deb，拆解 AI 代理引用的事实全部正确、给出的答案却错误的工程病根，并给出 Agentforce 平台所采用的 GraphRAG 方案和一套三步断点诊断法。文中用一台 WM-500 洗衣机被错误拒赔的退货案例做完整演示。
🔥 为什么今天值得看：企业里决定一个答案的事实常常分散在多个系统。普通 RAG 检索按相似度取段落，天然接不上跨文档的条件链，代理就会在每条引用都查无问题的情况下做出错误决定，比如拒掉一个符合例外条款的退货。GraphRAG 补的是事实之间的连接这一环，而文章真正可复用的是诊断顺序，先分清系统是查不到证据还是连不上证据，再决定改检索、改图谱结构还是改数据连接，避免盲目换架构。
展开正文

一台 WM-500 洗衣机的退货申请被 AI 代理拒绝了。系统引用的退货政策写着 90 天，购买日期确实超了，两处引用单独看都没有问题，答案却是错的。这台机器售价 899 美元，被商品目录归为大件家电，本来享受 120 天延长退货，条件是 Gold 或 Platinum 会员且金额超过 500 美元，这位顾客恰好满足全部条件。决定结果的三个事实分居三处，商品分类在商品目录，例外规则在企业 Wiki，会员等级在 CRM，检索管道只召回了总政策，没有把这几条拼在一起。

Salesforce 工程博客上，Sivakumar Shanmugam 和 Indrojit Deb 把这类故障拆开讲了一遍，这也是他们做 Agentforce GraphRAG 的出发点。工程师给这个病起了个名字，叫 flat bag of chunks，摊平的碎片袋。向量检索和关键词检索都按相似度召回段落，可决定答案的中间事实常常和提问长得不像。顾客问的是坏掉的洗衣机，没人会提到商品分类或会员门槛，这些事实就永远进不了上下文。

他们的解法是在检索之外加一张知识图谱。从 WM-500 出发，沿着实体关系走到大件家电，再连到延长退货政策，政策又带出会员等级和购买金额两个待查条件。原文把这叫多跳检索，图谱负责指路，文本块负责给出证据和引用。

文章给了一套三步断点诊断。第一步查检索上下文，看代理有没有沿着分类走到政策。第二步查图谱蓝图，原文把结构叫 TBox、具体实例叫 ABox，蓝图漏了会员规则的话，往里塞再多客户记录也补不回来。蓝图由 AI 从内容里提议，再由业务人员确认后才开始灌数据。第三步查记录连接，图里的实体要有指向结构化数据的显式指针，否则代理每次都得去元数据系统里现找购买金额在哪张表。

原文自己留了限定，这些是说明性案例而非基准测试结果，速度提升也没有量化。检索到证据和用对证据，仍然是两个要分开检查的问题。对正在做 RAG 的团队，最值钱的是那个动手顺序，先弄清系统到底是查不到，还是查到了连不上，再决定改哪一层。

消费级显卡从零训2B模型，清华6900美元配方全开源

这是什么：清华大学 PACMAN 组 8 月 27 日在 arXiv 发布 Puro-2B 论文并开源全套预训练配方。他们用消费级 RTX 5090 显卡、FP8 低精度，从零训练 2B 参数模型，最多训练 1.4 万亿 tokens，最好模型的算力成本不到 6900 美元，在论文自定的评测协议下接近 Qwen2.5-1.5B 的性能。数据、代码和权重以 Apache 2.0 协议开源在 Hugging Face。

训练一个大语言模型要花多少钱？清华 PACMAN 组 8 月 27 日发布的 Puro-2B 论文给出了一个让穷实验室能喘气的答案。论文开头摆出的参照数字相当残酷，训练一个 Llama-3.2-3B 要花超过 150 万美元，复现 SmolLM3-3B 也要 70 万美元以上，这道门槛把绝大多数学术实验室和开源社区挡在了预训练之外。

Puro-2B 是一套从零训练 2B 参数模型的开源配方。团队用消费级 RTX 5090 显卡，以 FP8 低精度训练，最多喂到 1.4 万亿 tokens，训出了一整族 Puro-2B 模型，各成员的 token 预算和配方变体不同。其中最好的一个模型，算力成本不到 6900 美元，在团队自己的评测协议下接近 Qwen2.5-1.5B 的水平。

省钱靠的是一组组合拳，涵盖硬件选型、低精度训练、hyperball 优化、课程模型平均和数据配方。论文还从这族模型里拟合出一条 Puro 成本缩放律，把训练成本和平均性能连成一条线。按这条曲线，花约 4400 美元，连 5090 美元都用不满，就能达到 Qwen2-1.5B 的性能，标题里的 5090 正是这笔账。

这项工作更值钱的地方在于全流程开放。因为拿到的是完整的预训练管线而不只是模型权重，团队顺势做了一个受控实验，考察预训练数据课程在后训练之后如何影响下游表现，这类受控研究过去只有大厂有条件做。数据、代码和权重全部以 Apache 2.0 协议开源在 Hugging Face 上。

社区反馈里也有真问题。有用户追问训练用了多少张 5090、跑了多久，暂时没人回答。用户 pszemraj 对 FP8 的峰值算力数字提出质疑，认为论文引用的 419 TFLOPS 是 FP32 累加口径，而 NVIDIA 在消费级 Blackwell（sm120）上对这个口径只按半速跑，他想知道团队试没试过 FP16 累加路径，还提到自己用 hadamard 旋转做类似尝试时从未调稳。这场讨论目前没有定论，属于社区观点。

AI 编程代理会写代码，但让它把一个工程做完，靠的是另一套东西。GitHub 上的开源项目 ECC 目前有 245k star，定位是 agent harness 性能优化系统，把一套工程纪律装进 Claude Code、Codex 这类编程助手里。它的工作方式是代理先规划再动手，改完用测试验证，然后从全新的上下文复查自己的工作，重要的东西写进记忆，反复奏效的做法沉淀成可复用的技能。这套能力装一次，之后每个任务都按固定流程走。

给搜索 API 做评测有个尴尬的地方，被测的搜索智能体自带抓取工具，题目答案若放在公开数据集里，它可以在评测中途直接下载答案照抄。答案早已写进模型参数记忆时也一样，答对证明不了搜索起过作用。Keenable AI 开源的 NEEDLE 基准用持续换题堵住这两条作弊路，新闻类查询每小时从约 124 个 RSS 源和 Google Trends 重建，金融、学术、法律和深尾查询每日从 SEC XBRL、arXiv、Europe PMC、CourtListener 等公共来源重建，题目永远新鲜。15 家搜索 API 在同一协议下跑同一批查询，证据统一截到 2000 字符，评分模型看不到引擎名字。这套基准还设计了 ultimate 机制，把所有引擎的结果合并成一个合成的 oracle 引擎，当作当前全行业的检索天花板。某家引擎离 ultimate 差距大，说明好结果存在但排序没做上去；ultimate 本身分数低，说明整个市场都搜不到。截至 2026 年 8 月 28 日的 7 天均值里，金融域 Exa 拿到 0.910，接近 0.965 的天花板；最难的长尾域 Exa 只有 0.557，Bing 低到 0.199。代码 MIT 开源，评测在公开的 GitHub Actions 上执行，每次运行的产物归档到 Hugging Face 数据集。这个基准由搜索厂商 Keenable 开源，自家引擎也在榜单内，解读排名时应当记住这层利益关联。

🔥 为什么今天值得看：测试打桩和链路追踪是 Python 工程里的老问题，wrapture 用一套包装机制同时处理两件事，而作者在这个领域积累多年，库的设计带着明确判断。更大的看点是协作方式，一位资深工程师指挥 AI 写完整个库，并明确反对 vibe coding，给出一种可参照的 agent 开发立场，即人负责设计，AI 负责产出。

Python 老将 Graham Dumpleton 发布了新库 wrapture，他也是 wrapt、mod_wsgi 和 New Relic Python agent 背后的作者。wrapture 把 wrapt 中的 monkeypatching 思路扩展到测试和追踪两个场景，任何函数或方法都能被包上一层，所有调用可以被记录，返回值也能被改写。它既能当 unittest.mock 的替代品来写测试，也能给现有项目加追踪，内置 OpenTelemetry 支持，还提供纯配置式的接入方式，写一段配置文件就能给 Python 项目装上观测。

项目只有几周大，更受关注的是它的生产方式。Dumpleton 主动交代，wrapture 的每一行代码和文档都出自 AI 助手之手，全程在他的指挥下完成。他同时划清界限，"这不是 vibe coding。写的人因为没能力判断产出好坏，只能对一次性生成的一堆代码抱有希望，vibe coding 坏名声是应得的。我从一开始就在精心工程化这个项目，我清楚结果该是什么样，AI 是产出的手段，设计的来源是我。"
