Gemini 3.8 TTS：一句提示词设计全新声音

这是什么：Google 发布 Gemini 3.8 Flash TTS 与 Flash-Lite TTS 两款文字转语音模型，开发者用自然语言提示词就能从零设计覆盖 100+ 语言和方言的新声音，预置声音库从 30 个扩到 2000+ 个。两款模型已通过 Gemini API 和 Google AI Studio 上线。
🔥 为什么今天值得看：这把语音生成从「挑预置音色」推进到「生成式设计声音」的新档位，配合逐行表演控制和 2.74 美分级别的实测成本，创意音频与语音代理的开发门槛同时下降。它与阿里 Qwen 同日发布五款语音模型形成正面竞争，语音 AI 进入能力与价格双线开打的阶段。
展开正文

过去做语音合成（TTS，即文字转语音），开发者通常是在厂商给的固定音色列表里挑一个；Google 今天发布的 Gemini 3.8 Flash TTS 和 Gemini 3.8 Flash-Lite TTS 把这件事变成了「写提示词」：描述角色、口音和声线特征，模型就从零生成一个全新声音，覆盖 100 多种语言和方言。官方演示包括墨尔本高能 DJ、极细音的单调机器人和一条日本龙。

两档定位，一套导演系统

Flash TTS 面向创意方向和角色设计，目标场景是游戏、沉浸式有声书、播客和互动媒体；Flash-Lite TTS 面向高并发、低成本的量产场景，主打配音、音频内容生产和语音代理。两档共享同一套「逐行导演」能力：剧本里可以直接写舞台指示，控制语速、情绪、方言切换，甚至「倾听附和」（backchanneling）——即听话人在对话中自然发出的「嗯」「对」等反应声。模型还支持数小时长文本下音色与节奏保持一致、单个剧本驱动双说话人原生分轨，以及 、、 等非语言声效标记。

从 30 个声音到 2000+

此前 Gemini TTS 只有 30 个预置声音，这次直接扩到 2000+ 个生产级声音，含墨西哥西语、魁北克法语、苏格兰英语等地区变体；自定义声音可保存复用，跨项目漂移极小。声音复刻只需 30 秒音频样本，但必须是本人或有权使用的声音，且需语音所有者的口头同意录制并通过比对验证。安全方面，所有输出嵌入不可感知的 SynthID 水印，复刻声音额外附 C2PA 内容凭证（一种记录内容来源的元数据标准）；AI Studio 中的声音复刻在英国、EEA、印度等多地不可用（官方完整名单还包括伊利诺伊州、得克萨斯州和瑞士）。

基准成绩

在 Hume AI Voice Design Benchmark 上，Flash TTS 以 71.4 分排名第一，重音建模（accent modeling）以 60.8 分居首；Hume AI Overall Quality Index 中 Flash TTS 第一、Flash-Lite TTS 第二。Voice Arena 盲测里，两款模型在日语、巴西葡语、越南语、现代标准阿拉伯语、墨西哥西语和印地语中均居前列。

怎么用、多少钱

两款模型已通过 Gemini API 和 Google AI Studio 上线，模型标识为 gemini-3.8-flash-tts 与 gemini-3.8-flash-lite-tts，仅限 API 调用、不开放权重；企业版 Gemini Enterprise 的 API 接入标注为「即将推出」，声音混音（用提示词微调库内声音的音色、音高、语速和口音）也尚未上线。成本方面，开发者 Simon Willison 当天实测：用 Flash TTS 约 20 秒生成 1 分 18 秒的双角色对话音频，花费 2.74 美分。

同日，阿里 Qwen 也一次性发布了五款语音大模型并发起大幅降价，语音赛道的正面交锋已经开始。

Qwen 五款语音大模型同日齐发，ASR 最高降价 95%

这是什么：阿里 Qwen 团队 9 月 23 日一次性发布 Qwen-Audio-3.1 系列五款语音大模型，覆盖 ASR、TTS 与实时交互，同时宣布 TTS 降价约 70%、Realtime 约 85%、ASR 最高 95%。
🔥 为什么今天值得看：ASR、TTS 与实时交互是语音 Agent 调用最频繁、成本占比最高的三类接口，70%–95% 的降幅直接改写语音应用的单位经济模型；加上五款模型补齐全链路，与 Google 同日发布的 Gemini TTS 正面交锋，语音 AI 竞争进入「能力+价格+生态」综合战阶段。
展开正文

9 月 23 日，阿里巴巴 Qwen 团队一次性发布 Qwen-Audio-3.1 系列五款语音大模型，覆盖语音识别（ASR）、语音合成（TTS）与实时语音交互三大场景，并同步大幅降价：TTS 降价约 70%，Realtime 降价约 85%，ASR 最高降 95%。而就在同一天，Google 也发布了新一代 Gemini TTS——语音 AI 战场在同一天迎来双发对决，且双方都把「价格与产品线完整性」摆上了桌面。

五款模型，各管一段

  • ASR：强化多语言与方言识别，并自动清理语气词（填充词）和重复内容，转写文本更接近「拿来就能用」的状态。
  • ASR-Next：在识别之上新增带时间戳的多说话人分离，还能检测情绪、环境音与机器噪声，面向会议转写这类复杂声学场景。
  • TTS：支持多语言合成与自然的跨语言音色迁移；情感、语速与风格通过文本提示控制——例如「用强势、有命令感的语气朗读，让人肃然起敬」这样一句话就能改变输出效果。
  • TTS-Next：把语言模型与扩散方法（diffusion，一类逐步去噪生成内容的生成方法）结合，单次生成即可同时产出语音、音效与背景音频，无需分开合成再拼接。
  • 实时模型：支持同时说与听（全双工）与即时打断。据 Qwen 介绍，当它检测到用户情绪低落时，会放慢回应节奏、给出更具同理心的回答。

为什么值得盯紧这一波

第一是价格。ASR、TTS 与实时交互是语音 Agent 调用最频繁的三类接口，降幅从 70% 到 95% 不等，语音应用的单位经济模型需要重算——原先因调用成本做不了的常驻语音功能，门槛被显著拉低。

第二是链路完整性。五款模型覆盖「耳朵（识别）+ 嗓子（合成）+ 对话（实时交互）」，开发者可以在同一套 API 体系内搭完整条语音链路，不必在多家供应商之间做能力拼装。

第三是竞争格局。与 Google 同日发布的 Gemini TTS 形成正面交锋：一边是新一代生成式语音模型，一边是五款全家桶加地板价。语音 AI 的比拼正在从单点模型能力，转向「能力 + 价格 + 生态」的综合战。

佐证与来源

阿里云官方文档已上线 Qwen-Audio-3.1-TTS-Next 条目，AIBase、Pandaily 等多家媒体亦有同题报道。需要说明的是，本条最初的 Google News 链接不可达，以上事实经 The Decoder 一手报道（Matthias Bastian，2026-09-23）与多源交叉确认；更多定价细节可在阿里云博客与 Qwen Cloud 查询。

Claude Code 被曝关遥测就不读 AGENTS.md

这是什么：一篇博客实测揭示：Claude Code（2.1.277 宣布支持、2.1.280 bundle 验证）的 AGENTS.md 读取被远程功能开关 tengu_agents_md_mod 门控，用户关闭遥测即静默失效；Anthropic 工程师 mpoteat 在 HN 热帖（435 分）中承认人为失误、公开 mod 源码，问题现已修复（HN 标题标注 [fixed]）。
🔥 为什么今天值得看：隐私设置悄悄关掉了无关的本地行为——读自己磁盘上的文件竟要等服务端开关。受影响最重的恰是最在意 AGENTS.md 的人群：为多个 agent 工具维护同一份指令文件的个人用户，以及按策略关闭非必要流量的 Bedrock/Vertex/网关团队。无警告的失效会让人误以为「模型无视指令」而去折腾提示词，实际上文件根本没送到模型。对 Anthropic 这是一次功能发布后数日内的信任考验，快速认错与源码公开部分挽回了局面，但「本地功能绑远程开关」的设计值得所有 agent 工具引以为戒。
展开正文

9 月 18 日，Claude Code 2.1.277 刚宣布支持 AGENTS.md（本报 9 月 19 日曾报道）；几天之内，这个新功能就曝出一只尴尬的 bug：只要用户关闭遥测，AGENTS.md 就会被静默跳过。一篇技术博客用对照实验完整还原了机制，HN 讨论冲到 435 分，Anthropic 工程师当场认错，问题现已修复——HN 标题已加上 [fixed]。

Bug 机制：读本地文件，却要等远程开关

AGENTS.md 的加载器以内置插件 agents-md 的形式发布。在 2.1.280 的 bundle 里，注册代码显示：插件默认关闭（isOnByDefault 为 false），其可用性函数询问的是一个名为 tengu_agents_md_mod 的远程功能开关（feature flag），fallback 同样是 false。一旦 Claude Code 拉取不到这个开关，插件直接不可用，本地文件永远不会被读取——而读一个工作目录里的 markdown 文件，本来不需要任何网络请求。

作者怎么验证的

博主 Przemek 建了一个只放一个 AGENTS.md 的空目录，文件里写入金丝雀词 PERIWINKLE，再用 claude -p 询问这个词；每种配置跑两个会话，因为新配置的首个会话只负责拉取开关，第二个会话才会使用它。测量结果：

  • 设置 DISABLE_TELEMETRY=1 或 CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1，AGENTS.md 都不加载，必须把两者都清掉；
  • 把变量设成 0 也没用——环境变量文档写明任意取值都算数；
  • 项目级 .claude/settings.json 的 env 块清掉这两个变量同样无效，无法为单个仓库开启该功能；
  • 以上所有情况都不打印任何警告：会话照常启动，模型在没有项目指令的情况下作答，没有任何提示告诉你文件被跳过了；
  • 第三方网关、Bedrock、Vertex 场景同样中招，因为开关在这些环境下无法解析为 true。

GitHub issue #95690 解释了原因，博主把自己的测量补充进了这个 issue。

官方回应：人为失误，源码已公开

Anthropic 工程师 mpoteat 在 HN 讨论中道歉：「再次向大家道歉，这完全是我个人的人为失误——我本应该找到更好的、带 kill-switch 的发布方式。」他同时公开了该 mod 的源码（位于 anthropics/claude-code 仓库的 mods 目录），并邀请开发者在 issue #91870 上反馈：「Mods 能带来相当多的可定制性和控制力，我是真心相信这个想法。」

修复前的绕过方案

CLAUDE.md 支持 @path 导入，而导入不依赖那个开关：在 AGENTS.md 旁边写一个只含一行 @AGENTS.md 的 CLAUDE.md，即便遥测关闭也能加载。代价是每个仓库多出一个文件——这恰恰是 AGENTS.md 支持本来想省掉的。作者还呼吁：读本地文件不应依赖遥测；若保留开关做灰度，至少在跳过文件时给出可见警告；并希望补上全局 AGENTS.md（类似 Codex 的 ~/.codex/AGENTS.md）和原生共享 .agents/skills 路径。

GPT-6 Astra 跑通模拟驾驶基准，云端开车之争升温

这是什么：DrivingBench 排行榜出现首个完赛记录：GPT-6 Astra 通过 Codex 完成模拟赛道，第 2 次尝试以 100% 进度、5 分 22 秒跑完全程（134.7 米、24 条命令、6.6M tokens、7.74 美元），同榜的 Claude Fable 5.1、Grok 4.6、GPT-5.6 Sol 均未完赛。相关 HN 帖子发布约 7 小时收获 264 分。
🔥 为什么今天值得看：这是前沿大模型能力外溢到物理控制任务的标志性观察点：第一次有通用云端模型在驾驶基准上完赛，且与其他模型拉开碾压级差距。但它是模拟环境成绩而非真实路测，真正的价值在于引出「云端 LLM 能否实时驾驶」的路线之争——延迟约束、蒸馏上车、分层控制架构，都是自动驾驶行业绕不开的问题。榜单成绩不等于行业共识。
展开正文

「一个跑在云端的大模型，到底能不能开车？」这个老争论因为 DrivingBench 排行榜上的一条新纪录再度升温：GPT-6 Astra 在该基准的模拟赛道上以 100% 进度、5 分 22 秒完赛，成为这张榜单上唯一跑完全程的模型。帖子被搬到 Hacker News 后，发布数小时已收获 264 分，评论区几乎变成了一场自动驾驶架构论证会。

先看成绩，再看限制

DrivingBench 的玩法是：让云端大模型基于传感器数据，通过 set_motion（下发运动指令）和 stop_now（紧急停止）两个执行器接口控制车辆，在同一个连续会话里最多尝试 3 次，按赛道中心线进度计分——模型必须保持在中心线 4 米范围内，碰撞则只保留撞车前已到达的进度。

GPT-6 Astra 由 Codex（medium 档）驱动参赛：第 1 次尝试推进到 49% 后碰撞退赛（DNF），行驶 67.3 米、8 条命令、消耗 120 万 tokens（2.01 美元）；第 2 次尝试一口气跑完全程——134.7 米、24 条命令、660 万 tokens（7.74 美元），完赛时间 5 分 22 秒。

对比之下差距悬殊：Claude Fable 5.1（Claude Code）三次尝试分别为 9%、10%、45%，最佳成绩仍止步 45% 未完赛；Grok 4.6（Cursor）最佳 11%；GPT-5.6 Sol（Codex）三次都卡在约 6% 的同一位置。整张榜单只有 GPT-6 Astra 的完赛时间栏里有数字。

但必须说清楚：这是 DrivingBench 模拟环境中的基准成绩，不是真实道路测试。 它证明的是云端大模型能够基于输入数据学会操作两个执行器接口、跑完一条固定赛道，而不代表 GPT-6 已能驾驶真实车辆，榜单名次也不等于行业共识。

争论的核心：延迟

HN 评论区最高赞恰好是来给「GPT-6 学会开车」这个说法泼冷水的。这位用户指出，开源驾驶系统 openpilot 的驾驶模型以 20Hz（每秒 20 次）更新目标曲率和加速度，本地控制回路的每一毫秒都经过严格优化——否则连路面颠簸和阵风都应付不了，更别说快速变化的交通状况。而云端方案光是把摄像头图像编码、上传、等模型返回，车外的世界早已变化。他的结论是「延迟、延迟、还是延迟」：这正是 Tesla 和所有自动驾驶厂商坚持把算力放进车里的原因；指望哪家公司推出「从云端开你的车」的订阅，「要等超光速通信，也就是永远不会有」。

反方同样拿数据说话：有人指出人类驾驶并不需要 20Hz——平均反应时间约 250 毫秒，遇到突发危险时的感知-反应时间约 1-2 秒，99% 的驾驶场景靠的是预判而非反应。更主流的声音是折中方案：其一，把大模型蒸馏成小型模型装上车；其二，分层架构——让 GPT 只负责高层决策（「前面那条暗巷看着危险，绕开」），底层控制交给专用驾驶模型；Waymo 的远程人工协助采用的正是「给建议而非直接控车」的模式。也有人提醒别忘了大模型会犯蠢：一位用户用 Claude Code 排查断续的 Wi-Fi，它一开始就把无线网卡关了，切断了自己唯一的对外通信——「幸好它当时开的不是一台重型杀人机器」。

一条模拟赛道的完赛记录改变不了自动驾驶的技术路线，但它是一个清晰的观测点：前沿模型的能力正从聊天窗口溢出到物理任务，而工程社区已经开始认真讨论如何接住它。

能测量就能变快：Claude两周把claude.ai提速3倍

这是什么：Anthropic 9 月 23 日在 claude.dev 发布工程博客，首次披露 8 月两周冲刺细节：借助 Claude Tag（beta）运行、能力约相当于 Opus 5.5 的内部研究模型，claude.ai 与桌面端 13 项 p75 指标几何平均提速 3.1 倍——首刷可输入 3,085ms→550ms（5.6 倍）、Cowork 发消息 928ms→48ms（19 倍），合并 3,000+ 变更且零客户可见事故；HN 已获 130 分，讨论进行中。
🔥 为什么今天值得看：这是一份可直接迁移的 agent 工程模板：用 Valgrind + node --predictable 的 CPU 指令计数（浏览器侧用 React 提交次数、V8 调用计数等确定性指标）替代噪声大的墙钟时间，配 CI 棘轮门禁只许变快、功能开关兜底、真实用户监控验收。它把「测量」从优化的前置步骤变成优化对象本身，也让 reward hacking 护栏成为所有自主优化 agent 必须面对的新问题。
展开正文

9 月 23 日，Anthropic 工程团队 Raymond Wang、Sam Attard 与 Issac G. 在 claude.dev 发布工程博客《How we made claude.ai 3x faster in two weeks》，副标题一句话点题："Once Claude can measure something, it can make it faster. So we kept finding more things to measure."（一旦 Claude 能测量某件事，它就能让这件事变快。于是我们不断找更多可测量的东西。）该文在 Hacker News 已获 130 分，讨论仍在进行。

两周冲刺的成绩单

Anthropic 在文中承认「用户一直告诉我们它很慢，他们说得对」。今年 8 月，团队用一个两周冲刺把 claude.ai 网页端与 Claude 桌面端的核心体验整体提速约 3 倍，聚焦占用户活动 95% 的四大旅程——启动应用、发起对话、加载会话、发送消息——在网页与桌面拆出 13 项 p75 指标（8 月 13 日 vs 8 月 27 日真实用户监控）：

  • claude.ai 网页首刷至可输入：3,085ms → 550ms，提速 5.6 倍（−82%）
  • Cowork 桌面云端发消息（客户端部分）：928ms → 48ms，提速 19 倍（−95%）
  • 桌面应用冷启动：6,310ms → 3,328ms（1.9 倍）
  • Cowork 云会话加载：2,566ms → 728ms（3.5 倍）
  • 13 项指标几何平均：整体提速 3.1 倍

Anthropic 估算这每天为用户节省数万小时的等待。整个冲刺合并 3,000 多项变更，没有发生一次客户可见事故或回滚。

方法论：确定性测量 + 棘轮护栏

墙钟时间噪声太大，没法当 CI 门禁。工程师 Sam 在 Slack 里问「能不能改测 JS 指令数」，Claude 给出方案：在 Valgrind 下用 node --predictable 跑基准、与入库基线比较——一次运行、结果确定、无需统计。浏览器路径没有指令计数，就退而用一组确定性计数替代：React 提交次数、V8 精确覆盖的函数调用数、样式重算与布局计数、DOM 变更。11 分钟后，五个测量线程并行开跑。

每项基准要过两关：既是实验室里 Claude 可以优化的指标，也是 CI 里只降不升的护栏，不与真实延迟相关的基准会被直接扔掉。Claude 先被要求证明「计数跟随墙钟」：在消息树组装（原代码用 megamorphic 字典查找把同一消息 ID 解析三次，占去约四分之一指令）与 Claude Code 输出的状态行扫描器两条热路径上，一小时内指令数分别下降 48% 与 31%，墙钟时间下降 78% 与 44%，对应提速 4.6 倍与 1.8 倍。此后任何推高这两条路径指令数的 PR 都过不了 CI，每日任务还会随数字下降继续拧紧上限——「棘轮」由此得名。

Claude 自己找到了什么

冲刺中后期基本是 Claude 在自主爬坡：有人在 Slack 开线程指出某段慢路，Claude 追踪链路、建基准、按风险拆分提多个 PR（用户可见的改动藏在功能开关后），部署后读真实用户数据——变快就把基准棘轮拧紧，没变快就关开关重试，然后自己找同一路径的下一个慢点。峰值同时运行超过 150 个线程，单个线程产出 50 到 100 个优化 PR，越来越多新线程是 Claude 自己开的。工程师 Shelley 的评价是："[This model] is a numbers demon."

它挖出的瓶颈相当具体：composer 输入路径上有 6,900 个 React hook 与 900 个 store 订阅在每次按键时全部重渲染；单个 :root:has() 选择器给每次 DOM 变更增加 24ms；一处遗留的 location.reload() 每天造成 50 万次隐藏刷新，而常规加载指标对它完全失明。侧边栏「行迟到又重排」的跳动问题，CLS 每次位移仅约 0.008（远低于 0.1 的良好阈值），于是团队直接基于 Layout Instability API 建遥测，配套集成测试在主干上 20 次全红、在修复 PR 上 20 次全绿；遥测上线后发现 31% 的网页加载在页面可用后仍有元素移动。

支撑这一切的是 Claude Tag（beta）背后的内部研究模型，能力大致相当于 Opus 5.5；人类负责定目标、做取舍、批准每一项变更。冲刺从约 20 个手工挑选的项目起步，第三天就完成了 13 个目标中的 12 个，随后 Claude 自提的新工作流把成果推得远超初始目标。

社区怎么看

HN 讨论观点两极。augment_me 警告 reward hack：低垂果实摘完后，Claude 会替换测量工具、monkey patch 基准函数、把结果藏进缓存而非重算——真实前提是「详细定义目标，再禁止一串往往只有它作弊后才能发现的手段」。smy20011 认为静态 composer 本该用 SSR 解决、composer 本该在页面间缓存，「1.3 秒加载首页不可接受」，应从 SSR 与分块渲染等基础重做，逐个基准爬坡可能错过系统性机会。crooked-v 直言这些是「相当平庸的收益」；simonw 实测 claude.ai 在 Firefox 需加载 20.78MB JavaScript（压缩后 6.84MB），认为还有很大瘦身空间；tecoholic 则注意到空闲 claude.ai 会话的内存比浏览器里的 Slack 还大。

开源项目 DeusData/codebase-memory-mcp 的最新版本 v0.11.0 于 2026 年 9 月 15 日发布，README 9 月 23 日仍在更新。这个用纯 C 实现、单静态二进制零依赖的代码智能 MCP 服务器，把代码库索引成持久知识图谱，供 AI 编程代理以亚毫秒级速度查询。当前版本的叙事重心已从「单代理提速」明显转向「团队与多客户端共享」。

新变化

  • 团队共享图谱工件：把 zstd 压缩的知识图谱快照 .codebase-memory/graph.db.zst 直接提交进仓库（典型压缩比 8–13:1），队友克隆后首次运行先导入工件、再增量补齐本地差异，免去全量重建索引，并用 merge=ours 的 gitattributes 规避合并冲突。
  • 跨账号会话协调守护进程：Claude Code、Codex、OpenCode 等所有已配置客户端共享同一个按账号划分的守护进程——首个会话启动它，最后一个会话关闭它；后台文件 watcher、共享索引任务与可视化 UI 均由它统一持有，关掉一个会话不会取消其他会话还在用的任务。
  • 跨仓库智能：CROSS_* 边把同一存储下多个仓库的节点连成一张图，配合「多星系」3D UI 做跨仓库架构可视化与汇总。
  • 内置嵌入语义搜索：Nomic nomic-embed-code 嵌入（768 维 int8）直接编译进二进制，配合 11 信号组合打分，不需要 API key、Ollama 或 Docker。

为什么值得关注意义

AI 编程工具都在卷模型，但代理探索代码库的默认方式仍是逐文件 grep/read，token 成本高、上下文易碎。该项目把「理解代码库」下沉为本地共享基础设施：官方口径为 5 次结构查询约 3400 token，对比逐文件检索约 41.2 万 token（省 120 倍）；还有 arXiv 预印本（arXiv:2603.27277）背书——31 个真实仓库评测中 83% 回答质量、10 倍 token 节省、2.1 倍工具调用减少。同一个人的多个客户端、乃至整个团队共用一颗「代码库大脑」，是 AI 编程基础设施从单点工具走向共享服务的信号。

关键数据

Agensh：没有指挥官的 1024 智能体自组织军团

这是什么：论文提出无中央编排器的自组织多智能体 harness「Agensh」：并发 worker 通过共享工作区、消息接口、共享上下文三件组织基础设施，异步完成「收集上下文—认领子任务—共享发现—验证—合并进展」的协作循环，替代传统的中心化任务分配。
🔥 为什么今天值得看：多智能体系统的扩展上限通常卡在中央编排器的任务分配与协调能力上。Agensh 证明去掉总指挥后，规模扩到千级智能体通过率仍持续上升（1→1,024 时 33.89%→55.06%），且轨迹分析显示自组织协调优于标准并行执行，为「agent 军团到底能扩多大」提供了一条不依赖中心调度的路径。
展开正文

多智能体系统靠并发执行降低复杂任务的延迟，但主流框架有一个共同瓶颈：任务分配和 worker 协调都要经过中央编排器，编排器的容量直接决定了系统能扩到多大。

新论文 Agensh（Scaling Organizational Intelligence to 1,024 Agents）给出的答案是把这个「总指挥」整个去掉：并发 worker 自己执行一套协作循环——收集上下文、认领子任务、共享发现、相互验证、异步合并进展。支撑这一切的是一套只有三个组件的轻量级「组织基础设施」：共享工作区（保存已提出、进行中、已完成的工作）、消息接口（worker 之间的通信通道）、共享上下文（保留可复用的发现与工作交互）。

实验在五个最难的 GPTS-5.6-high 基准上进行：智能体从 1 个扩展到 128 个，平均最终通过率从 19.31% 提升到 28.78%，相对提升约 49%；更大的组织达到可比的通过率——从 1 个扩展到 1,024 个，最终通过率从 33.89% 提升到 55.06%。论文的轨迹分析显示，自组织协调操作优于标准并行执行，说明在高延迟约束下这是一种可行的复杂任务解法。

需要说明的是，这些结果是特定基准上的实验，论文并未声称通用结论；能否迁移到其他任务与模型，仍有待独立验证。
