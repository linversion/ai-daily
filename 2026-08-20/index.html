MCP规范改为无状态核心，AI代理可像Web服务一样水平扩容

这是什么：2026-07-28 发布的 MCP 规范移除了传输层的状态会话：initialize 握手与 Mcp-Session-Id 均被删掉，协议核心彻底无状态化。代理服务因此能像普通 Web 服务一样做标准轮询负载均衡、在 Serverless 平台上缩到零，并获得对客户端完全透明的故障转移，解决了扩容必须靠会话亲和与粘性路由的问题。
🔥 为什么今天值得看：有状态会话把客户端与某个容器的内存状态绑定，如果战力扩展到多实例，负载均衡会把后续请求送到没有这段会话的 pod，出现 400。这迫使运维加配置会话亲和、共享 Redis 兜底，扩容和故障转移都拖着。协议无状态化让每个请求自描述、由任意实例独立处理，直接给高并发代理服务铺平了水平扩展、Serverless 缩容和透明故障切换的土壤。这是 MCP 发布以来最大的一次架构变化，也是 AI 代理从单点演示走向可规模部署基础设施的标志一步。
展开正文

当一家企业把代理工作流从演示推向上万台用户时，瓶颈往往出在协议本身。MCP 最早在 2024 年底设计，默认为本地单客户端对单服务器，走的是状态化路径：客户端先用 initialize 握手换一个 Mcp-Session-Id，之后每次工具调用都带上它，把自己锁在持有会话状态的那个容器上。Google 在自己的云上铺开时撞上这堵墙，普通轮询负载均衡器并不清楚哪个容器存着哪段会话，第二个请求打到另一个 pod 就直接返回 400 Session Not Found；要绕开还得配置粘性路由，流量无法均匀分布、扩容低效；容器一旦重启或崩溃，会话立刻丢失，把瞬时错误抛回正在对话的用户。跑远程 MCP 服务还得靠共享的 Redis 会话库或网关级深度包检查兜底，成本和延迟同步上涨。

于是 Google 牵头、联合 Hugging Face 等伙伴成立 MCP Transports Working Group，把状态从传输层剥离。2026-07-28 规范发布后，握手与 Mcp-Session-Id 被移除，客户端信息、协议版本、能力等元数据全部内联进每条请求。任何容器实例都能独立处理任意输入请求。由此拿到的是标准轮询负载均衡、能在 Google Cloud Run 这类 Serverless 平台上空闲归零的运行方式，以及容器崩溃、滚动、扩容时对客户端完全透明的故障转移。GitHub MCP 服务器随后升级，直接移除了 Redis 会话存储。Mcp-Protocol-Version、Mcp-Method、Mcp-Name 被提升为标准 HTTP 头，网关与负载均衡器无需深度包检查就能限流、路由、审计，还配上了带 ttlMs 的缓存字段。

交互性任务在无状态世界里也有了对应解法。MRTR 用 InputRequiredResult 加 requestState，把一段需要用户确认的对话拆成自包含步骤，确认后重发可由任意实例接续。Tasks 扩展从实验特性升格为一等协议扩展，耗时 10 到 60 秒的长跑任务立即返回 taskId 转后台，客户端用 tasks/get、tasks/update 轮询进度。安全上新增 Issuer Verification（RFC 9207）与 Resource Indicators（RFC 8707），工具参数全面采用 JSON 数据模型。Roots、Sampling、Logging 正式进入弃用，保留至少 12 个月迁移窗口。四款 Tier-1 SDK 全部发布了适配新规范的 beta。

Agent 插件 1.0.0 规范发布，技能工具一次打包跨客户端复用

这是什么：多个厂商联合发布了 Agent Plugins 1.0.0，一个开源、供应商中立的打包规范，用来把 Agent Skills 和 MCP 服务器装进一个可移植的插件目录。Google 以核心维护者身份加入这个由亚马逊、Cursor、微软、OpenAI、Vercel 组成的群体，并已把支持推进到自己的 Agents CLI 和 Data Agent Kit 两个产品里。
🔥 为什么今天值得看：技能和 MCP 服务器本身早已各自可移植，缺的是一直要把它们放进同一个包的这个外壳，而这个外壳在过去几乎每个客户端都在重复发明。统一目录结构和 manifest 之后，开发者不必再针对不同编码代理给各自的 IDE 维护成套独立包装，一次打包就能跨客户端运行。Google 的加入意味着跨厂商的标准化又多了一个重要支点，插件作者不用在覆盖所有客户端和维护质感之间二选一。
展开正文

假设你写好了一个 Agent 技能，又配了对应的脚本和 MCP 服务器，三者合起来能查询团队的报表数据库，并把结果生成每周摘要。这把技能迁移到第二个客户端时，麻烦来了。技能没问题，MCP 服务器也没问题，有问题的是装它们的那个外壳。每个客户端对目录布局、清单元数据、MCP 配置的写法都有自己的一套，于是你只能把包分叉成两份去维护，看着它们逐渐走样。Google 在开发者博客里点破了这个根因：问题从来不在组件本身，而在那个包住它们的清单。

为了让这份包装不再各写各的，Google 与亚马逊、Cursor、微软、OpenAI、Vercel 一起维护了 Agent Plugins 1.0.0，一个供应商中立的插件打包规范。它的核心约束很简单：插件就是一个固定目录，plugin.json 只要求 $schema 和 name 两个字段，其余组件都放在规定位置，客户端走进来就能认，不用靠猜测推断传输方式。技能放进 skills/ 下的独立子目录，MCP 服务器在 mcp.json 里逐个声明并标清类型，stdio、Streamable HTTP、HTTP+SSE 都覆盖。

这个规范刻意把范围压得极小。plugin.json 不能重定位组件，也不能内联声明它们；skills/ 缺失时客户端就加载现有内容继续，mcp.json 里某个服务器启动失败不会拖垮整个插件的技能，组件独立加载、独立失败。末尾那个 com.example.client/ 反向域名目录是专属某一客户端的扩展空间，别的客户端不认识就忽略，既保住可移植的核心，又给不可移植的部分留了合法的去处。

按理说，封装只是其中一环。找插件靠 Agentic Resource Discovery（ARD），ARD 已把插件视作一类独立的 agentic 资源；AI Catalog 是 ARD 索引的入口格式，提出把 application/agent-plugins+json 注册为已知类型，让目录条目能指向 plugin.json。这样发现、描述、打包、运行各司其职，每层独立可用、独立被采用。Google 已经在 Agents CLI 和 Data Agent Kit 两个产品里落地了这套格式。

规范也留了明确的取舍：它不是所有场景都需要。只向单一客户端派发一个 MCP 服务器，mcp.json 单独使用反而是更简单的答案；只有当你手里的组件本来就要结伴迁移时，插件才真正值得一用。

阿里云发布Qwen3.8-27B FP8量化版，把多模态代理压进消费级硬件

这是什么：阿里云 Qwen 团队 8 月 13 日发布 Qwen3.8-27B-FP8，把 27B 参数的多模态模型按 FP8 细粒度量化（块大小 128）压缩进量化权重，官方称性能与原始模型几乎一致。它原生理解图像和视频，支持 262144 token 上下文（可经 YaRN 扩到 100 万），兼容 Transformers、vLLM、SGLang 等主流框架。
🔥 为什么今天值得看：多模态与长上下文历来是内存黑洞，27B 双重夹击下本地几乎跑不动。FP8 把权重从 16 位压到 8 位，配合块 128 的细粒度缩放，内存占用与推理开销显著下降而精度损失很小，等于把一个能看、会代理的多模态模型压缩到消费级硬件能接住的程度。这让本地跑代理（能自主读文档、看视频、多步骤执行）从口号变得可行，是模型端把基础设施落向普通开发者桌面的标志一步。
展开正文

要在一台消费级显卡上跑起一个能读图、看视频、还能自己规划多步任务的 27B 参数多模态模型，内存和算力是第一道坎。阿里云 Qwen 团队在 8 月 13 日发布 Qwen3.8-27B-FP8，思路是用更细的量化把模型压小：FP8 的含义是权重从常见的 16 位浮点降到 8 位，这次用的是块大小为 128 的细粒度量化，也就是按小块分别做缩放，尽量减少精度损失带来的性能损耗。官方给出的说法是量化后的性能指标与原始模型几乎一致，换来的是内存占用和推理速度都更适合落在量产硬件上。

这个 FP8 版本不只解决跑不快的问题，它同时也让消费级硬件有机会触及 Qwen3.8 这一代的核心能力。模型本身是带视觉编码器的因果语言模型，原生理解图像和视频，能承担编码、专业工作、研究这类长周期代理任务。原生支持 262144 token 上下文，需要更长场景时可通过 YaRN 扩展到 100 万 token，vLLM、SGLang、TokenSpeed 等主流推断框架里都给了配置方式。它与 Hugging Face Transformers、vLLM、SGLang 等生态直接兼容，等于把部署路径也一并铺好。在官方基准里，它和上一代 Qwen3.6-27B 对比普遍占优，举例 SWE-bench Pro 拿到 61.7，DeepSWE 1.1 拿到 42.2，MathVision 无 CI 到 90.0。

对想本地跑干的人，这套压下来的内存和速度，意味着多模态代理不必再绑在云上。配上推理强度控制 reasoning_effort 和保留思考痕迹的 preserve_thinking，一个能看、能思考、能接工具的 27B 级代理可以更接近普通开发者的桌面，而不是停留在机房专用卡。这也是本期代理基础设施落地的一个代表：模型本身走到了消费级硬件能接住的尺度。

Google 开源 Tunix 后训练库，消除 TPU 空转

这是什么：Google 首次公开发布了一款面向 JAX 的后训练库 Tunix，专门用于训练多轮、会调用工具的 LLM 推理 agent。它解决的是这类训练里 TPU 资源被空转浪费的问题：当 agent 停下来执行代码、查数据库或等待网络返回时，昂贵的算力会闲置。Tunix 用高并发的异步滚动加上实时流式的生产消费流水线，把算力从等待中解放出来，同时提供了可插拔的 agent 与环境接口。
🔥 为什么今天值得看：agent 的强化学习训练正从单轮对齐转向多轮决策，模型要在循环里反复推理、调用工具、环境交互，这种过程中硬件利用率极易掉下来。如果 TPU 常空转，训练成本会成倍上升，很多团队因此不敢做 agent 级强化学习。Tunix 把吞吐最大化、流水线可视化都做好了，把多轮 agent 训练从少数大厂才玩得起的门槛，往下拉了一个台阶。
展开正文

训练能多步推理、主动调用工具、与外部环境交互的 agent，比训练普通聊天模型难得多。难点主要在于，当 agent 停下来执行代码、查询数据库或等待网页搜索返回时，昂贵的 TPU 往往处于空转状态，利用率骤降。Google 本周发布的后训练库 Tunix，正是冲着这个痛点来的：它把异步滚动和高并发流水线结合起来，让 TPU 几乎一直处于忙碌状态。

传统同步式滚动会在两处拖慢训练。一是执行气泡，当 rollout 同步等待环境初始化或返回状态与奖励时，加速器上就会出现空档；二是尾随者效应，分批生成的整体延迟被组里最慢的一条轨迹拖住。Tunix 用基于 asyncio 的高并发异步滚动解决这两点，一个 agent 暂停等待工具执行时，推理引擎会立即转向为其他活跃轨迹生成 token。生产端持续吐出完成的轨迹，消费端把这些变长轨迹动态分组后实时流式注入训练器，避免训练侧被迫空等整批数据。

同时，Tunix 提供可插拔的接口。开发者继承 ConversationAgentBase 实现自己的 agent，或继承 BaseTaskEnv 接入 SWE-bench、WebArena 这类开源环境，大概几分钟就能把新环境搬进来，训练代码基本不用改。库本身原生建在 JAX、Flax、Optax 上，支持 Pathways 多主机分布式训练，也集成了 vLLM-TPU 与 SGLang-Jax 两类推理引擎，并附带一套轻量级 RL 指标和 Perfetto 可视化，帮开发者定位 TPU 饥饿出现在流水线的哪一步。

Unsloth Dynamic V3.0 量化首秀：Qwen3.8-27B 走进消费级硬件

这是什么：Unsloth 首次为其 Qwen3.8-27B GGUF 引入 Dynamic V3.0 量化方法，一次推出从 1-bit 到 16-bit 共 18 种精度的量化文件，最小约 6.19 GB。官方声明在同等大小下其 top-1% 准确率优于所有其他 GGUF 供应商 10% 以上，并配有一套推荐采样参数和输出长度建议。

火山引擎开源了 OpenViking，一个自进化的上下文数据库，当前版本 v0.4.15。它把 AI Agent 的记忆、RAG 检索和技能统一进一套 viking:// 虚拟文件系统，代理像操作本地文件一样用 ls、tree、find 浏览自己的上下文，而不是只对接黑盒向量库。

每个条目被整理成三层：L0 摘要、L1 概述、L2 细节，加载只到任务需要的深度，以压低 token 消耗。每次查询会保留目录浏览轨迹，结果不对时能回看是哪条路径生成的，便于调试。会话结束后自动沉淀为长期记忆，异步抽取用户偏好与代理经验。检索先定位高分目录，再逐层下钻，让结果带着周围上下文一块返回。集成层面对接 Claude Code、Codex、Cursor、OpenClaw 等多个代理。

官方基准数据来自项目自测：LoCoMo 与 tau2-bench 上准确率从原生记忆的 24% 到 57% 提升到 80% 到 83%，输入 token 减少 34.3% 到 91.0%，查询延迟降低 58.45% 到 66.10%；tau2-bench 上附加经验记忆让零售任务成功率提升 6.87 个百分点、航司任务提升 11.87 个百分点。主要项目按 AGPLv3 开源，无功能阉割；另提供托管与自托管商业版。
