OneCLI 发布：开源沙箱代理编排平台，为团队每位员工提供安全个人代理

这是什么：OneCLI 以 YC S26 批次公司的身份通过 Launch HN 正式亮相，同时推出 v2 版本。它从早先的凭证保险库转型为完整的团队级沙箱化代理编排平台，核心变化是提供按身份提供商配置的代理，为合约团队每位员工分配一个独立沙箱代理，统一管理团队策略，并通过网关本轮实现凭证隔离。
🔥 为什么今天值得看：团队把代理从单机扩展到多人、多责任的场景时，凭证管理、权限边界和多人协同会成为基础设施问题。OneCLI 把凭证藏在 Rust 网关后面，让代理的每个外部请求都受统一策略约束，同时集成 Slack 审批，这代表一条比“共享凭证”更低的代理安全模型路线。它进入由各实验室竞相提供的一层，也让多代理编排基础设施的赛道上多出一个开源、可自托管的选择。
展开正文

OneCLI 是开源社区里又一类面向团队的多代理基础设施，这次以 YC S26 批次公司的身份正式亮相，通过 Launch HN 对外发布。它的定位很明确：在团队层面运行 AI 代理，而不是只服务一个个人的单机代理。每个员工都能获得一个独立的沙箱化个人代理，由平台统一管理凭证、权限和安全策略，代理本身不直接接触任何密钥，所有出站请求都流经一个 Rust 编写的网关，由网关在请求发生的时刻注入对应凭证。两者合在一起，构成一个以代理为单位的、凭证与模型上下文隔离的安全模型。

OneCLI 并非首次出现。仓库已存在数月，HN 上有评论指出它已经发布了 6 个月，本次新闻的增量在于正式成为主 YC S26 公司并推出 v2。v1 是从一个基于 Rust 的凭证保险库开始的，团队原本只是为 Hermes、OpenClaw、NanoClaw 这类自主代理管理密钥和权限，后来发现绝大多数需求都来自跑着自主代理的个人和团队，于是把产品改造成完整的团队级编排平台。v2 引入按 IdP 身份配置代理、团队级统一策略、Slack 集成、确定性人工审批，以及持久化的代理实体。

一个代理被设计成持久的东西，而不单是一次提示。它拥有自己隔离的沙箱、文件系统和 shell，唯一的出口是网关；它有自己的对话页面，也能以自己名字、头像和独立 Slack 应用出现在频道和私信里；它带平台托管的记忆、可复用技能和计划任务。代理运行在自有基础设施上，runner 只出站、不监听入站端口，因此笔记本、家庭服务器或 NAT 背后的 VPC 都不需要建立唤醒隧道或入站端口。

安全是 HN 讨论的核心争议。创始人强调 proxy 的凭证隔离、离模型上下文，但社区立刻指出它可能面临一个“混淆副官”问题：即使代理拿不到真实凭证，网关对端点的策略粒度仍待验证。作者 Jonathan Fishner 澄清，同一主机的规则是按方法、路径和主体匹配，而不是只看主机，例如允许 GET /calendar/v3/* 而 POST 需要审批。

团队遇到的另一类讨论是关于竞争与定价。HN 上不少人在抱怨“代理编排赛道早已拥挤”，有评论以 20 个代理每月 499 美元、不含 API 成本来衡量是否划算。创始人自己也承认，回到拥挤的主回答，他们还没想清楚怎么在这一片里赢，两个创始人来自安全背景，一开始先构建网关，是出于对默认配置下直接使用 OpenClaw 的不信任。反应背后其实还有一个共性判断：随着各家实验室推出自带代理产品，这类开放编排平台能否提供真正的护城河，仍是 HN 仍在互相发票的核心问题。

ai-memory：git Markdown wiki 打通编码代理长期记忆

这是什么：ai-memory 在 2026-08-20 之际发布 v1.29.0，大幅扩充编码代理支持矩阵并要求托管工作流能力。此前它主要支持 Claude Code、Codex、OpenCode、Cursor 等少数代理，本次新增 Antigravity CLI、Grok Build CLI、Kimi Code、Kiro CLI v3、Zero、Swival CLI 的接入，并让 ai-memory run 能跨多个代理 CLI 透明恢复同一逻辑工作流，同时保留按项目隔离与对脱敏观察数书的默认行为。
🔥 为什么今天值得看：编码代理的会话上下文在结束即清零，切到另一家厂商的 CLI 就要重讲一遍架构与失败尝试。ai-memory 公开的意图正是打通不同代理厂商之间的记忆交接：用 git 版本化的 Markdown wiki 承接一座仓库的长期记忆，让 Claude Code 中途退出、Codex 接手的场景变成新代理先读到一段有界交接块。这为跨代理协作提供了无需向量数据库的记忆数据面，也代表了代理基础设施中记忆层开始走向厂商中立的趋势。

以 Claude Code 干活到一半切到 Codex，对方往往得重新理解一遍架构、之前的失败尝试和悬而未决的问题，因为每个代理的上下文都死在各自的会话里。ai-memory（akitaonrails/ai-memory）想解决的就是这个生命周期上下文丢失问题：用一个基于 git 的 Markdown wiki，把代理会话的生命周期观察结果编译成持久记忆，并在新会话开始时给下一个代理一份有界的交接摘要。

项目仓库创建于 2026-05-21，截至 2026-08-20 已有约 3300 star、272 fork、1325 次提交，README 在抓取时仍处于活跃维护状态。核心机制分两条路径：零摩擦的生命周期捕获用钩子记录经脱敏的提示词、工具生命周期与会话边界观察，会话结束时把这些观察编译成连贯摘要供下一个代理读取；可选的 ai-memory run 托管工作流则提供跨不同 CLI 原生会话的更高保真连续性。

wiki 本身是普通 Markdown，落到一个 git 仓库里，可以直接 grep，能在 Obsidian 中打开，也能用 rsync 备份，不需要维护向量数据库。每一条用户提示与压缩后摘要最多保留 16 KiB，通知与工具摘录保留 2 KB，每个观察正文还有 16 KiB 的持久退路。同目录下把 Claude Code 中途退出再启动 Codex，新代理在第一条提示之前就会看到一段「上次进行到哪」的交接块，这靠跨代理交接与按稳定 UUID 键控的按项目隔离实现。

最新 release v1.29.0 于 2026-08-19 发布，本次更新显著扩充了代理支持矩阵：新增 Antigravity CLI、Grok Build CLI、Kimi Code、Kiro CLI v3、Zero、Swival CLI 等客户端的接入，并引入托管工作流能力，能跨多个代理 CLI 透明地恢复同一逻辑工作流。官方支持矩阵覆盖 Linux、macOS 与 Windows 的 WSL2，原生 Windows 仍标记实验性；向量搜索需要持有 Anthropic、OpenAI、Gemini 等提供商密钥，但零 LLM 模式已内置 FTS5、实体勾稽与图邻居搜索。

开箱即用的捕获并非常规的完整转写，而是有界的脱敏摘要。检索到的历史文本仍被视为不可信的过往证据，不会因命名空间、标签或排序而获得指令权威，需要对照当前代码库核验后再行动。

LEGO-RL 框架把原生编码智能体桥接到策略梯度训练

这是什么：LEGO-RL 是围绕三个支柱设计的编码智能体 RL 框架：进程内 LLM 捕获原始生成流实现 token 级对齐并在 trainer 侧重算 log-probability，可靠执行用带镜像缓存和分阶段提示的沙箱编排缓解奖励黑客，可观测训练用集成代理加 Live UI 做轨迹诊断。它以 Qwen3.5-35B-A3B 这个稀疏 MoE 模型为基础，在三个 harness 上都带来提升。
🔥 为什么今天值得看：harness 原生执行环境与策略梯度训练的不对齐是当前编码 agent RL 的结构性问题：环境崩溃和奖励黑客污染结果信号，训练推理差异让 rollout 与更新脱节。LEGO-RL 不碰 harness 内部逻辑就补上这个缺口，在多个主流开源 harness 上同时验证了跨模型的性能提升，是可落地的方法论而非单点补丁。
展开正文

编码智能体的强化学习正越来越多地依赖运行时间更长的 agent harness 来管理工具调用、仓库上下文和执行反馈。问题在于，这些 harness 的原生执行环境与策略梯度训练并不对齐：环境崩溃和奖励黑客会污染结果信号，训练与推理的差异又会让 rollout 行为和政策更新脱节。LEGO-RL 是一个新框架，它不对 harness 的内部控制流做任何改动，就把原生编码智能体与可扩展的策略梯度优化桥接起来。

框架建立在三个支柱上。第一支柱是忠实优化，通过进程内 LLM 代理捕获原始生成流，以获得 token 级对齐并在 trainer 侧稳健地重算 log-probability，即使面对 harness 侧的压缩或重新序列化也不受影响。第二支柱是可靠执行，用可扩展的沙盒编排配合镜像缓存和分阶段防御，来缓解奖励黑客问题。第三支柱是可观测训练，用集成插件自动化验证与监控，配一个 Live UI 做细粒度轨迹诊断。

作者用 GSPO 在三个原生编码 agent harness 上训练稀疏 MoE 模型 Qwen3.5-35B-A3B 来评估 LEGO-RL。在 SWE-bench Verified 上，OpenHands SDK 从 64.0% 提到 70.4%，Claude Code 从 62.4% 提到 68.2%，OpenCode 从 57.2% 提到 66.6%，同时 rollout 信号与训练侧的模型概率相关性保持高于 0.99。

对开发者和研究者而言，这套方法的吸引力在于不重写 harness 就补上 RL 训练的数据面缺口，既能降低奖励黑客风险，又保持训练信号与真实行为的一致。主要成本落在环境稳定性和对齐环节上，但结果验证了方向可行。

mukul975/Anthropic-Cybersecurity-Skills 是一个为 AI 代理准备的结构化网络安全技能开源仓库，共收纳 817 项技能，覆盖 29 个安全领域。它最核心的价值不在数量，而在标准化：每一项技能都被映射到 6 个业界主流安全框架，从而让不同 AI 工具能在同一套权威坐标系下执行安全操作。

这 6 个框架分别是 MITRE ATT&CK、NIST CSF 2.0、MITRE ATLAS、D3FEND、NIST AI RMF 和 MITRE F3。其中 MITRE ATT&CK 覆盖攻击者战术与技术，D3FEND 是 MITRE 的防御机制图谱，NIST AI RMF 面向人工智能风险管理，MITRE F3 则聚焦诈骗对抗。把攻防、防御、AI 风险与欺诈对抗四类语义纳入同一套映射，意味着同一个技能可以同时兼容多个评估视角，这正是企业在做代理安全审查时最需要的对齐能力。

该仓库遵循 agentskills.io 标准，与更早围绕 agent 技能定义的生态形成承接。它已声明兼容 Claude Code、GitHub Copilot、Codex CLI、Cursor、Gemini CLI 等至少 20 个平台，并以 Apache 2.0 协议开源。对开发者而言，它提供的是可被直接读取的目录化技能定义，而非只能人工翻阅的报告，这让代理在运行时能按框架调用对应的技能条目。

时间线上需要提醒的是，这一轮的信号更接近既有项目的持续迭代。仓库创建于 2026 年 2 月 25 日，最新 release 为 2026 年 6 月 22 日发布的 v1.3.0，README 最近一次提交则在 2026 年 8 月 8 日。把它当作本期代理安全清单与行业标准化主线上的增量更新来理解，比当作全新项目更准确。

价值判断上，这类仓库把分散在各工具里的安全技能收敛为可对比、可验证的清单，让多个代理能在同一套语义下操作。它解决的并非开创性的技术难题，而是代理时代最被低估的一环：技能定义的标准化与可移植性。

OpenViking：以文件系统统一代理记忆、RAG与技能

这是什么：Volcengine 的 OpenViking 于 8 月 18 日发布 v0.4.15，Repo 自 1 月创建以来持续推进，本次 README 也同步更新了基准报告与集成说明。它提出一个代理上下文数据库的明确实现：把记忆、知识 RAG 与技能统一为一个 viking:// 虚拟文件系统，让代理用文件系统的语义管理自己的上下文，而不是查询黑盒向量存储。仓库当前已获 30.7k star。
🔥 为什么今天值得看：本期主题是代理记忆与可验证基础设施的成型，OpenViking 站在代理记忆数据面这一角。它把检索变成可观察、可调试的路径轨迹，用分层加载来控制 token 消耗，方向上有别于早期简单的向量召回。对于开发者，它给出一个具体可落地、又能和主流编码代理对接的记忆层，与其配套的记忆/技能编排方案形成互补。

Volcengine 开源的 OpenViking 在 8 月 18 日发布 v0.4.15，定位为面向 AI 代理的自演进上下文数据库，理念是把记忆、知识 RAG 与技能三类上下文统一到一个虚拟文件系统上。代理不再查询黑盒向量库，而是直接用 ls、tree、find 这类文件操作浏览自身上下文，每次检索都会留下可观察、可调试的轨迹。

核心设计是三层加载结构。每条写入的内容都被处理成 L0 摘要（约一串句子的快速相关性判断，约 100 tokens）、L1 概览（约 2k tokens 的核心信息与使用场景，供规划使用）、L2 细节（需要时才读取的全量原文）。每个目录都自带 L0 与 L1 层，所以代理在读取任何完整文件前就能先判断相关性。检索时先由向量搜索定位最高分的目录，再一层层往下钻取，让结果带着周边上下文整体返回，避免孤立的碎片。会话结束后还会异步把用户偏好与代理经验抽成长期记忆。

项目用实际数字验证了这层设计。在 LoCoMo 长对话用户记忆基准上，接入 OpenViking 的三个代理集成准确率从原生记忆的 24% 至 57% 提到 80% 至 83%，输入 tokens 下降 34.3% 至 91.0%，查询延迟下降 58.45% 至 66.10%。在多轮代理任务基准 tau2-bench 上，经验记忆让零售任务成功率提升 6.87 个百分点、航司任务提升 11.87 个百分点，对比的是同一 LLM 无记忆版本。

落地方面要求 Python 3.10 以上，pip 安装后先用向导初始化并写出 ov.conf，支持 Volcengine、OpenAI、Codex OAuth、Kimi、GLM 与本地 Ollama，还能自动安装 Ollama 运行时并按硬件拉取模型。官方提供 Docker 镜像、无需安装的浏览器演示 OpenViking Studio、带桌面 Client 管理界面的 VikingBot 代理框架，以及 Claude Code、Codex、OpenClaw、Hermes、Cursor、TRAE 等多个代理的召回注入集成。项目主框架以 AGPLv3 开源，OV CLI、示例与第三方目录则分别采用 Apache 2.0 与原版权。

SemaPLC 用外部编译与动态运行把关 PLC 生成代码

这是什么：SemaPLC 是美的 AI Research Center 面向 PLC 代码生成的验证门控智能体框架。它不靠模型自我判断是否完成，而是以严格完成规则强制过三道外部检查：规范、编译、以及实时运行行为。开源并附带浏览器端 IDE，可生成、编辑、验证和模拟 PLC 程序。

可编程逻辑控制器（PLC）驱动工业产线，大语言模型已能生成独立的程序组织单元（POU），但生成的逻辑能否集成进既有 PLC 项目并正确运行，此前只做过有限验证。来自美的 AI 研究院（Midea AI Research Center）的 SemaPLC，是一个项目级、验证门控的智能体框架，解决的正是这个缺口。

核心思路是不信任模型对自身输出的判断。SemaPLC 设定严格完成规则：只有日志化的外部检查确认通过，任务才算完成。这些检查覆盖三层：规范说明、编译、以及在实时运行环境中的行为。相比多数系统停在自己评分认为足够的地方，SemaPLC 强制每一步都落到可追溯的外部验证上。

结果上，在 117 个独立 POU 任务上，它在全部 7 个模型上取得最高严格验证通过率，平均 72.6%。在 65 个必须把逻辑编译并跑进真实项目的项目上下文任务上，它在集成编译、静态行为和动态行为三层都拿到最高均值。动态行为最说明问题：把生成逻辑与参考逻辑部署到实时 PLC 运行环境并比对执行轨迹，各方法静态得分仅相差 10 分以内，动态分却拉开明显差距，基线在 22.4 至 31.4，SemaPLC 达 52.2。项目的含义很直接：静态评分不是检验逻辑是否真正工作的可靠标准，运行验证才是。

项目已开源在 github.com/midea-ai/SemaPLC，并提供基于浏览器的 IDE，支持生成、编辑、验证和模拟程序。这份工作选在 8 月 19 日发布，属于工业自动化里把代码生成推向端到端验证的一步，尤其动态运行验证这一层最有参考价值。

Munder Difflin 是一个开源的本地多智能体桌面应用，名字套用《办公室》里的虚构公司 Dunder Mifflin，自我调侃为"世界上最优秀的智能体、世界上最烂的纸业公司"。它把这些年流行的终端编码 CLI 直接包装成可协作的智能体：Claude Code、Antigravity（Gemini）、OpenAI Codex、xAI Grok、Kimi Code、Qwen、OpenCode、Crush、pi.dev，再到 GitHub Copilot，都支持自带密钥，也兼容本地 LLM 运行。

核心设计是把每个终端会话变成真实进程。每个 agent 在 node-pty 的伪终端里运行，用 xterm.js 渲染，外观上是 Pixi.js 绘制的一张 2D 办公室楼层，头像会走到工作站干活，消息则以信封的形式在桌与桌之间飞。智能体之间的协作基于一个叫 hive 的共享记忆层，这是一份本地 git 仓库，由普通文件构成，包含记忆、邮箱、黑板和追加式事件日志，采用单提交者设计来规避 index.lock 损坏。

编排由"你的克隆"Michael 完成。Michael 相当于一个 GOD 编排者，由它来分配任务、路由消息、裁决优先级，常规请求自动处理，只会把关键事项（支出、破坏性操作、范围变更）升级到一个需要人操作的审批队列。安全性上有三层：人工门控、断路器（steer / constrain / stop），以及每个智能体独立的 token 预算和从 transcript 里计算出的真实成本。

OpenAI 预览 Private Safety Processing，让前沿模型零数据保留与安全监控兼得

这是什么：OpenAI 于 2026-08-19 发布公告，重申前沿模型的 Zero Data Retention（ZDR）承诺，并预览新服务 Private Safety Processing。现有 ZDR 安全系统按单次交互逐一评估，而新服务是 OpenAI 描述的一种长跨度安全监控：把自动防护扩展到相关交互序列，让系统跨多轮会话识别滥用模式，同时 OpenAI 人员不会拿到所保留的客户内容。公告同时明确 9 月将开始逐步推出该能力，并发布技术白皮书。
🔥 为什么今天值得看：ZDR 承诺给符合条件的企业客户一个确定性保证：提示词与模型响应在处理后不被 OpenAI 保留，客户内容不供 OpenAI 人员审阅，也不会被用于训练。问题是这类系统此前只能逐次评估交互，面对恶意请求被分散到多轮会话、或代理在艰深任务中逐步失配的情形，检测能力有限。Private Safety Processing 代表一条折中路线，在跨交互识别风险的同时仍守住零保留与内容不可见，直接回应了当前前沿模型部署中一个普遍冲突：安全监控要求 vs 敏感企业数据不被 AI 实验室留存。
展开正文

OpenAI 在 2026 年 8 月 19 日发布公告，重申零点数据保留（ZDR）承诺，并首次预览一项名为 Private Safety Processing（私有安全处理）的新技术。公告给出的整套承诺是：符合条件的 API 客户，其提示词与模型响应在处理完成后不会被 OpenAI 保留；客户内容不会交由 OpenAI 人员审阅，企业数据也不会被用于训练模型，除非客户明确选择加入。

ZDR 由来已久，其内置的安全系统按单个交互逐一评估滥用风险。问题在于，随着模型承担更长、更复杂的任务，某些严重风险往往只有在多个相关交互连起来看时才会显现。一个坏行为者可能分多次试探防护、跨账号协调，甚至把恶意意图伪装成例行研究。代理类任务中，系统还可能在被要求停下来之后继续行动，与用户意图逐渐失配。OpenAI 明确描述，Private Safety Processing 正是把 ZDR 的自动防护从单次交互扩展到相关交互序列：自动化系统能跨会话识别模式，同时 OpenAI 人员依旧拿不到所保留的客户内容。

实现路径有两条。其一，ZDR 部署下客户内容存放在客户掌控的基础设施上；其二，OpenAI 正在开发一个选项，把内容存在 OpenAI 基础设施上，用客户控制的密钥加密。两种情况下，自动化系统都能识别潜在滥用并返回限定的安全信号，而无需把底层提示词或响应暴露给 OpenAI 人员。OpenAI 说明的是几种典型形态：没有推断内容，即使交互被标记，OpenAI 人员也不会收到客户内容。客户可用自己系统的信息调查告警与强制决定，若需申诉、澄清合法活动或支持受验证滥用的调查，可自行决定是否把相关信息分享给 OpenAI。

公告背景是竞争与合规的双重压力。TechCrunch 报道指出，Anthropic 今年 7 月推出数据保留政策，对“受覆盖模型”（包括 Mythos 级及具备相近能力的模型）的会话保留 30 天用于安全检查，这让不少处理敏感数据的企业不安。OpenAI 则借这次预览强调无需牺牲客户对内容的控制权即可推进安全。Glean 首席信息安全官 Sunil Agrawal 在公告中点评，企业采用 AI 依赖对数据掌控，OpenAI 的不训练承诺与 ZDR 给了 Glean 信任基础。

目前 Private Safety Processing 正在与早期客户测试，OpenAI 计划 9 月开始逐步推出，并同步发布技术白皮书。公告同时给出 CSAM 例外：与其他前沿模型提供商一样，OpenAI 依法需报告疑似儿童性虐待材料，即使 ZDR 部署中，被标记图像仍会保留，供人工审查与报告。

OpenAI技术失误撤销TAC安全研究员访问需重新验证

这是什么：多位安全研究员在 OpenAI 官方论坛和 X 上报告，他们访问 Trusted Access for Cyber（TAC）项目的权限被突然撤销，打开 ChatGPT 网络安全页时出现身份无法核实或账户当前不合格的提示。TechCrunch 采访了五名受害者，OpenAI 承认是公司一侧的技术失误，并要求受影响者重新申请并完成验证。撤销可能只在部分区域生效，受访五人都不在美国和欧洲。
🔥 为什么今天值得看：TAC 是 OpenAI 向经过核验的安全研究员开放防御性模型的机制，目的是让可信防御方更快报告并修复漏洞，同时阻止恶意攻击者滥用模型。这类撤销争议直接暴露了合规核验与实际使用体验之间的张力，也关系到前沿模型在网络安全落地时到底提供给谁、怎么防。若核验流程让正当研究员一次受挫，可能劝退他们继续为厂商补漏洞，最终拖慢漏洞修复节奏。

多家安全研究员反映，OpenAI 突然撤销了他们访问 Trusted Access for Cyber（TAC）项目的权限，OpenAI 随后承认问题源于自身的技术失误。TAC 是 OpenAI 面向经过核验的研究员开放的特殊项目，允许他们使用比普通用户模型护栏更少的前沿模型做防御性安全工作，让可信的防御者更快向厂商报告漏洞并推动修复，同时防止网络犯罪分子用这些模型发掘漏洞和开发 exploit。想获得 TAC 访问，研究员须提交身份证明并接受 OpenAI 核验。

TechCrunch 采访了五位遭遇此问题的研究员。其中一人透露，OpenAI 发邮件称其 Daybreak Blue（TAC 最新核验层级）的访问因技术问题被撤销，邮件写道：这是我们这边的问题，不是我们想提供的用户体验。OpenAI 官方论坛和 X 上的回应一致，均指向近期技术问题导致部分用户丢失 Daybreak Blue 访问，并请受影响者重新申请、走完验证流程。值得注意的背景是，TechCrunch 接触到的五名研究员都不在美国和欧洲，说明撤销或许集中在特定区域。OpenAI 将 TechCrunch 指向一条推文：一小部分用户对 Daybreak Blue 的访问已不再生效，需要重新验证以维持访问。

Daybreak Blue 是面向个体研究员的最新层级，于 8 月 10 日上线。OpenAI 称它授予包括 GPT-5.6 Sol 在内的前沿通用模型访问权，防护（safeguards）按授权的防御性安全工作定制，是多数防御者推荐的起点，覆盖漏洞发现、安全代码审查、恶意软件分析、事件响应与补丁验证。同期 OpenAI 还推出了层级更高的 Daybreak Red，让经过核验的用户访问专为网络安全研究打造的模型，用于授权的漏洞研究、exploit 验证与安全测试。近几个月来，攻防两端的研究员都在抱怨 Anthropic 与 OpenAI 的护栏妨碍了正当工作，此次撤销事件再次把焦点引向这类方案在合规核验与真实可用性之间的张力。
