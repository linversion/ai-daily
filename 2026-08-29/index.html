1800 亿参数只激活 60 亿，Qwen4 架构首个预览开源

这是什么：阿里 Qwen 于 8 月 24 日在 Hugging Face 发布 Qwen3.8-Flash-Next，这是支撑 Qwen4 的新架构的实验性预览，首次以开放权重形式放出。总参数 180B，每次推理只激活 6B，原生上下文 262,144 tokens，可扩展到 100 万。生产版本 Qwen3.8-Flash 基于它构建，默认 1M 上下文并带官方内置工具。
🔥 为什么今天值得看：智能体应用要反复调用模型，开销跟着激活计算量走，6B 的激活量配上 SWE-bench Pro 62.5、Toolathlon 73.5 这样的成绩，等于把接近旗舰的水平压到了更低的成本档位，高频调用的推理账单有机会降一档。稀疏注意力把长上下文延迟降下来，对要处理长对话和长代码库的 agent 直接减少等待。这套架构还是 Qwen4 的底子，开放权重让整个生态可以提前适配。

阿里 Qwen 团队提前掀开了下一代模型的底牌。8 月 24 日，Qwen3.8-Flash-Next 上架 Hugging Face，官方把它定位为支撑 Qwen4 的新架构的实验性预览，也是这套架构第一次以开放权重形式发布，开发者可以直接下载部署。它和商用版本的关系也交代清楚了，Qwen3.8-Flash 是基于这个预览打造的正式版本，加了默认 1M 上下文、官方内置工具这些生产特性，预览版则更接近架构本身的样子。

数字上最扎眼的是参数结构。总参数 180B，其中语言模型本体 125B，n-gram 嵌入 51B，MTP 模块 4B，但每次推理只激活 6B。门道在 MoE（专家混合）结构上，模型里装了 512 个专家，你可以把专家想成专科医生，每个请求只安排 10 个专科加 1 个共享专家接诊，其余专家不用上场，账面很大，开销很小。放进对比表更直观，Qwen3.7-Plus 总参数 397B 激活 17B，DeepSeek-V4-Flash-0731 总参数 284B 激活 13B，6B 是对比模型里最小的激活量。

架构层面有三处值得留意的新东西。注意力部分换上了 QSA（Qwen 稀疏注意力），以前挑选处理对象是一个 token 一个 token 地选，现在按微块为单位操作，长上下文下的推理延迟明显下降，对越来越重的智能体负载来说，这块延迟直接对应成本。残差连接上加了门控残差，信息跨层流动时经过由数据决定的闸门，表达更细，训练保持稳定，推理开销也没有上涨。参数扩展则走了 n-gram 嵌入这条路，把 2000 万个二元和三元词组做成查表式的参数，比继续堆 MoE 更省计算，还更容易放到显存外面，等于给「参数做大」找了条便宜路。

成绩单挑三组看。编码上，SWE-bench Pro 拿到 62.5，高于 DeepSeek-V4-Flash-0731 的 56.0，也高于官方公布成绩为 53.4 的 Claude-Opus-4.6（Max），SWE-bench Multilingual 的 81.0 同样排在所有对比模型前面。智能体上，真实工具调用测试 Toolathlon Verified 拿了 73.5，压过 DeepSeek 的 70.3 和 Qwen3.8-27B 的 67.1。多模态上，安卓手机操作测试 AndroidWorld 拿了 84.5，把 Claude-Opus-4.6 的 62.0 甩开 22.5 分。对比名单里还有自家 27B 的稠密模型和上一代 397B 总参的 Qwen3.7-Plus，一个激活 6B 的模型打出这种分数，性价比才是重点。

用起来的行为也可以调。模型默认先思考再回答，开发者手里有三个参数，enable_thinking 控制思考开不开，preserve_thinking 决定历史对话里的思考内容保不保留，reasoning_effort 管思考力度，分 xhigh、medium、low 三档，默认 xhigh。官方文档里有个提醒挺有意思，多轮智能体任务里调低思考力度不一定省时间，单轮回复快了，但分析不足会带来失败和重试，总耗时和 token 消耗可能反而上去。

部署方面，权重兼容 Hugging Face Transformers、vLLM、SGLang、TokenSpeed 这些主流框架，不想自己维护基础设施可以直接走 Qwen Cloud 的 API。原生上下文 262,144 tokens，用 YaRN 外推技术能扩到 1,000,000 tokens，YaRN 是一种调整位置编码、让模型处理超出预训练长度文本的方法。它还带视觉编码器，能读图、能看视频。

冷静一点看，官方自己的定义就是实验性预览，正式表现要等生产版本验证。不过社区动手速度不慢，上线几天，模型树里已经出现 20 个微调版本和 109 个量化版本。

8B 小模型学会用工具，长任务成绩追平 Claude Opus 4.5

这是什么：据 VentureBeat 8 月 28 日报道，Meta 与伊利诺伊大学香槟分校的研究者发布训练框架 EvoHarness-RL，用监督微调加强化学习两个阶段，让模型学会自己决定何时读写 Belief、Progress、Experience 这类外部工具。以 Qwen3-8B 为基座训练后，模型在具身家务文字基准 ALFWorld 上拿到 96.9% 平均成功率，比 ReAct 基线高 49 个百分点，对 GPT-4.1、GPT-5、Claude Opus 4.5（96.4%）做到超越或追平。这是研究论文成果，尚未产品化。
🔥 为什么今天值得看：长任务的状态管理过去靠人写死规则，模型每升级一次就要重新调一轮。把这件事变成可训练的行为之后，8B 量级的小模型也能在长周期任务上贴近前沿模型，成本差距被拉开。训练中出现的工具退火还说明模型学会后会主动少查工具，把延迟和 token 开销直接降下来。
展开正文

让 AI 代理在企业里干长活，麻烦往往出在外围。比如把大批客户记录从老旧 CRM 搬进云数据库，一跑就是几个小时，模型光靠自己的上下文窗口记不住做到哪一步，得靠外部运行层（harness）帮它记日志、盯子目标，出错时还得帮它恢复。过去这套逻辑靠开发者手写规则，模型只是照剧本执行。论文共同作者 Xuying Ning 对 VentureBeat 解释，最优的 harness 往往随模型而变，「不同模型可能需要不同的提示词、记忆设计、权限或沙箱配置。如果全部手工编码，每次模型升级都可能带来新一轮漫长的调优和排错」。她还指出，只会累加的记忆未必是好事，长任务里记忆可能塞满过时的结论和失败的尝试。

Meta 和伊利诺伊大学香槟分校的研究人员给出了另一条路，叫 EvoHarness-RL。框架把模型的支撑系统收进一个统一工作台，由 Belief、Progress、Experience（BPE）三块组成。Belief 维持代理对当前环境的准确认知，Progress 管理已完成和待办的子目标，Experience 负责跨任务复用历史经验。模型通过 track、commit、recall、note 四个动作读写这块面板，分别用来跟踪环境、提交进度、召回旧策略和记录新发现，何时查询、何时更新、何时压缩旧信息全由模型自己决定。Ning 举例说，在软件工程任务里，Belief 相当于代理对代码库的理解，Progress 记着各步骤的依赖关系，Experience 存下用户对错误的反馈供下次参考。

训练配方分两阶段。第一阶段是监督微调，教基础模型从杂乱的交互日志里提取并整理出结构化信息。第二阶段是考虑成本的强化学习，因为查记忆、更新跟踪器都要消耗时间和 token，模型得学会掂量每次访问外部状态到底值不值。这套 BPE 提示层直接挂给冻结的前沿模型也有收益，GPT-4.1 成功率提升 22.1 个百分点，GPT-5 提升 25.7 个百分点。

实验在 ALFWorld 上进行，这是一个从具身家务任务改编的文字基准，任务多为多步骤，考验顺序逻辑和状态跟踪，覆盖面有限，不能当作通用智能的成绩单。以 Qwen3-8B 为基座训练后，模型平均成功率达到 96.9%，比 ReAct 基线高出 49 个百分点，超过可训练方法 SkillRL（89.9%）和 SkillOS（80.2%），对 GPT-4.1、GPT-5、Claude Opus 4.5（开箱即用 96.4%）做到超越或追平。

训练过程中出现了两个现象，也是这篇论文最有故事性的部分。一个叫工具退火（harness annealing）。训练初期模型几乎每步都要查 Experience 和 Progress，随着熟练度上升，它主动减少对外部工具的依赖，把成功模式直接写进参数。放到企业场景，这等于省掉了查询数据库的 token 和等待时间。另一个叫工具进化（harness evolution）。模型对熟悉任务绕开工具快速推进，一旦撞上陌生环境或意外障碍，又会主动加大 Belief 和 Experience 的使用。论文举例，迁移常规数据库记录时它跑得飞快，遇到古怪的旧 API 端点或复杂的校验错误，就会放慢节奏，调出服务器日志、翻查历史工单，稳妥处理边缘情况，避免凭空瞎猜。

落地方面，EvoHarness-RL 用环境适配器做集成，企业内部实现可以继续绑定自家现有工具，各方共享的只是可训练层。Ning 认为 BPE 可以作为额外的状态管理层接进现有编排系统，团队不需要推翻当前框架。针对整理记忆需要强推理的隐性开销，她建议混合异步架构，用前沿模型生成高质量的整理数据，再微调一个开源权重模型负责日常状态管理，整理过程异步执行，不拖慢主循环。她也划了边界，短而稳定的任务用 ReAct 或标准 RAG 可能已经够用，BPE 的价值要在代理连续工作几小时、几天甚至几周的场合才体现出来。

需要说明，这是研究论文的成果，尚未变成产品。按 Ning 的定位，这类方法带来的是一次转变，团队的工作从直接给代理写脚本，转向搭建一套能让好行为自己学出来的系统。

2026 年 8 月 24 日，一篇编号 2608.23691 的 arXiv 论文描述了一个叫 Station 的开放世界多智能体环境。来自不同模型家族的 AI 智能体在里面追求同一个研究目标，没有中央协调器，也没有事先写好的流程，每个智能体自己挑研究方向，自己做实验，互相合作，还共同维护一份共享的科学文献。

跑出来的成绩写在论文里。研究者从 AlphaEvolve 目录中取了 12 个构造性数学问题，外加两个案例研究，其中 5 个问题得到了相对既有文献的新结果。这批成果包括有限域 Kakeya 集的一个新无穷族、11 维空间里 604 个点的 kissing 精确构型、离散化 Kakeya 针问题和符号不确定性问题的新纪录，以及 Erdős 最小重叠问题下界的明显改进。智能体还发现了 Book Ramsey 数的新无穷族。这些都是构造性结果或者改进的界，跟「AI 攻克数学难题」的说法要分开。

产出形态同样关键。智能体交出的除了数值构造，还有定理和分析，用来解释构造为什么成立。论文认为这让结果更可解释，数学家也更容易接着往下做。论文正文 38 页，配有 12 幅图和 3 张表，全部原始对话、证明和验证代码都已公开，整个发现过程留下一份可以复查的记录。

Hacker News 上这篇论文的讨论目前拿到 74 分。有人把 Station 比作给 AI 重建的剑桥教师公共休息室，也有人认为关键在评审回路，不同模型互相挑错再达成共识。争论同样存在，快速检索和重组已有方法带来的产出算不算创造性，评论区没有统一答案。

对关心智能体能力边界的人来说，这份实证很具体。一组没有统一指挥的智能体，能够把选题、实验、合作、记录这套流程自己跑完，并且交出数学家可以接着用的东西。智能体从辅助工具走向自主科研，这回多了一个可以下载验证的样本。

人人都在写的 AGENTS.md 实测不涨成功率，还多烧两成成本

这是什么：苏黎世联邦理工学院团队让编码机器人带与不带 AGENTS.md 各跑一遍测试项目，发现成功率没有普遍提升，推理成本平均增加超过 20%。换了别的大模型、别的编码代理，文件换成机器人生成或开发者手写，结论都成立。这批结论 2026 年 8 月末经博客 Pivot to AI 转述发布，附有 arXiv 论文链接。
🔥 为什么今天值得看：几乎每个 agent 用户都被厂商建议写这类文件。成功率不涨而成本先涨，用户等于在为一个测不出收益的习惯持续付费，按 token 计费的产品里，两成多的额外消耗会直接落进每个项目的账单。这也是实证研究第一次认真检验这个人人照做的标配动作。

用 Claude Code 的人几乎都被建议过写一份 CLAUDE.md，放在项目根目录，用通用工具的则写 AGENTS.md。这份文件记录项目结构、编码习惯和注意事项，希望 AI 编码助手动手改代码前先读懂，已经是 agent 用户的标配动作。

苏黎世联邦理工学院（ETH Zurich）的团队给这个习惯做了第一次像样的实测。他们让编码机器人在同一批测试项目上，分别带着文件和不带文件各跑一遍，再对比成功率。论文里写，提供这类上下文文件并不能普遍提高任务成功率，推理成本平均增加超过 20%。换了别的大模型、别的编码代理，把文件换成机器人生成或开发者手写，结论都成立。

分开看更具体。机器人代写的 AGENTS.md，让任务成功率和没有文件时差不多，甚至可能略差。人手写的文件确实带来一点提升，但幅度很小。不管谁写的，token 消耗都明显上涨。这里的推理成本指模型每次干活时读入和输出的文字量，按 token 计费，文件越长读得越多，账单越厚。

文件里最没用的是仓库结构概览。机器人并不会因为读了「哪个文件夹放什么」的说明，就把列出的文件改得更快。整个测试中唯一明显的效果是，文件里点了某个工具的名，编码代理会更频繁地使用它。研究者给出的建议是保持指令简短，尽量少写。

关于来源，这批结论经博客 Pivot to AI 转述发布，附有 arXiv 论文链接。论文测的是「普遍影响」，没有否定所有场景，如果项目确实必须固定用某个工具，写进文件仍然管用，机器人真的会更常照做。

一位开发者在 Reddit 上留言，给出这份文件的另一种价值：「它提供的 token 级上下文，远不如写它的过程重要，写的时候你被迫把之前只在脑子里的代码库情况讲出来。」文件对机器人帮助有限，写文件对人有。

博客作者对厂商不留情面，认为 Anthropic 推荐 CLAUDE.md 时并没有测量过这套做法的实际效果，只是把它当成一句念了图心安的咒语。这个判断读者可以自行掂量。数据本身倒简单，成功率没涨，成本先涨了。

麻烦在于每家的接口和限速规则都不一样，出错的地方也各不相同，手工切换非常累。FreeLLMAPI 在本地跑一个服务，对外只开一个 /v1 地址，说的是 OpenAI 兼容格式，也就是大多数 AI 工具默认会讲的那种格式。Claude Code、Codex CLI、Aider、Cursor 这类工具只要把接口地址改成本地地址就能接入，背后实际用哪家模型完全透明。路由器按速度、可靠性和剩余额度挑模型，某家触发限速或服务器报错时自动冷却对应密钥并换下一家重试。供应商密钥以 AES-256-GCM 加密存在本地数据库，应用只能看到一个统一密钥。除了内置供应商，llama.cpp、LM Studio、vLLM、Ollama 这类本地或远程服务也能挂成自定义端点一起调度。

限制也得说清楚。仓库免责声明明确这个项目仅供个人实验和学习，不能当生产基础设施。免费层没有前沿模型，也没有服务保障，延迟忽高忽低，到了晚上头部模型陆续撞上当日额度上限，整体效果会往下掉，UTC 午夜重置。官方建议真要上线产品就换成付费 API，并且各供应商的服务条款对经过转发的流量依然有效，合规责任在使用者本人。

这套开源规则教 AI 编码代理偷懒，代码量平均少一半

这是什么：开源项目 ponytail 给 AI 编码代理注入「最懒资深工程师」思维，写代码前先过七级判断，能不写就不写。仓库今年 6 月创建，8 月 7 日发布 v4.9.0（含 53 个提交），目前 11.5 万 star。项目自测基准显示代码量平均减 54%，单任务最高 94%，成本降 20%，速度提升 27%，安全保持 100%。
🔥 为什么今天值得看：AI 编码代理最常见的浪费是过度设计，一个日期选择框能写出四百行代码，token、账单、等待时间全搭进去。ponytail 的自测数据说明，改掉 agent 动手前的判断顺序，代码量就能省一半，钱和时间跟着省。近期也有实证研究发现往 agent 上下文里堆说明文件收效甚微，ponytail 走的是另一条路，改写动手前的判断顺序。安全、可访问性这些底线不削减，让它有资格进真实的工程流程。
展开正文

AI 编码代理有个通病，你让它做个日期选择框，它能装一个第三方库，外面再包一层组件，配上样式表，最后还发起一场时区讨论。GitHub 上的开源项目 ponytail 专门治这个病，办法是把「屋里最懒的资深工程师」装进 agent 的脑子里，能不写的代码就不写。仓库今年 6 月创建，8 月 7 日推到 v4.9.0，已经攒下 11.5 万 star。

它的核心是一套七级阶梯规则。agent 读懂任务之后，写代码之前逐级问自己。第一级，这东西真的需要存在吗，老程序员管这叫 YAGNI，你多半用不上，不需要就整个跳过。第二级，代码库里是不是已经有了，有就复用。接着依次检查标准库、平台原生功能、已经装好的依赖，第六级才看一行代码能不能搞定。七级都套不上，最后写能跑起来的最小实现。阶梯排在理解问题之后，先读代码、捋清流程，再决定从哪一级偷懒。

效果方面，项目自己跑了基准测试。无头 Claude Code 会话修改一个真实的 FastAPI + React 开源仓库，12 个功能任务，同一个 agent 装与不装规则各跑一遍，模型用 Haiku 4.5，每个任务跑 4 次。结果代码行数平均少 54%，过度设计重灾区最高减 94%，成本降 20%，速度快 27%，安全 100% 通过。日期选择器从 404 行砍到 23 行，因为浏览器原生的 input 标签本来就带这个功能。对照组同样能说明问题，普通的「YAGNI 加一行代码」提示只减 33% 代码，还把安全率拖到 95%，只让模型说话简短的控制组减 20%，成本反升 3%。ponytail 是唯一各项指标全降、安全还满分的方案。

强度分 lite、full、ultra、off 四档，默认 full，可以用命令、环境变量或配置文件切换，还能控制规则注入哪些子代理。支持 Claude Code、Codex、GitHub Copilot CLI、Gemini CLI、OpenCode、Qoder、Cursor、Windsurf、Cline 等十余种工具，装不上插件的复制一份规则文件也能生效。作者把底线写得很死，验证、错误处理、安全性和可访问性这些代码一根指头都不动，懒惰但不疏忽。
