Anthropic 工程师亲述：Claude 5 模型提示词工程迎来六大新规

这是什么：Anthropic 一位技术员工发布博客，针对最新的 Claude 5 代模型（Claude Opus 5 和 Claude Fable 5）提出了一套全新的上下文工程规则，并透露在 Claude Code 工具中移除了 80% 的系统提示。
🔥 为什么今天值得看：这套新规则标志着提示工程范式的根本转变：从过去堆砌详细指令和示例，转向利用模型自身增强的判断力，通过设计信息架构来引导行为。这能减少指令冲突、降低维护成本，并可能显著提升 AI 代理在复杂任务中的表现。

如果你还在用老一套的提示词技巧对付 Claude 5，那可能已经落伍了。Anthropic 的一位技术员工刚刚发布了一篇博客，系统性地拆解了针对 Claude Opus 5 和 Claude Fable 5 这两款新模型的全新上下文工程规则，并分享了一个惊人的内部数据：他们在开发工具 Claude Code 中，直接砍掉了 80% 的系统提示。

这背后的逻辑很清晰——模型变聪明了，不再需要你像教小孩一样事无巨细地规定每一步。文章提出了六大新范式，核心思想可以概括为“少管束，多信任”。过去我们习惯于给模型塞满冗长的规则和示例，但现在 Anthropic 的建议是“使用判断力而非规则”，让模型在高层原则下自行决策；同时要“设计接口而非示例”，只定义清晰的输入输出格式，而不是给一堆“标准答案”让它模仿。

另一个关键变化是信息的分发方式。文章提倡“渐进式披露而非全部前置”，这意味着不要把海量背景知识一股脑塞进系统提示，而是像剥洋葱一样，让模型在需要时主动检索或调用。对于工具调用，新规要求“简单工具描述而非重复”，避免在提示中反复解释同一个工具的功能。最让开发者省心的可能是“自动记忆而非手动写 CLAUDE.md”——模型现在能自己总结和记录项目上下文，而不是靠人工去维护那个越来越臃肿的配置文件。最后，在引用外部信息时，文章强调要用“丰富引用（HTML 工件、代码）而非简单 Markdown”，以提供更结构化、更可操作的上下文。

这些变化指向一个趋势：随着模型推理和判断能力的跃升，提示工程正在从“指令堆砌”转向“架构设计”。开发者需要做的不是写更长的提示，而是设计更聪明的信息架构。社区对此反应热烈，不少开发者已经开始尝试将自己的项目提示按新规重构，但也有人提出担忧：当模型自主权变大，如何确保它在关键业务场景下的行为可控，依然是个需要持续探索的问题。

Ruff v0.16.0 发布：Python 代码检查工具默认规则从 59 条暴增至 413 条

这是什么：Ruff v0.16.0 是 Python 代码检查工具 Ruff 的重大版本更新，将默认启用的检查规则从 59 条大幅增加到 413 条，使得开发者无需额外配置即可自动检测数百种代码问题，包括语法错误和运行时隐患。
🔥 为什么今天值得看：这次更新大幅降低了代码质量保障的门槛——开发者不再需要研究该启用哪些规则，Ruff 开箱即用就能覆盖更全面的检查场景。这是自 v0.1.0 以来首次调整默认规则集，标志着 Ruff 从“需要配置的工具”进化为“装上就能用的代码管家”，对 Python 生态的规范化有直接推动作用。

Python 开发者们，你们的代码检查工具 Ruff 今天放了个大招。Astral 公司正式发布了 Ruff v0.16.0，这个版本最核心的变化是：默认启用的检查规则数量从 59 条直接飙升到 413 条，翻了将近七倍。

这意味着什么？以前你装好 Ruff 之后，它只会帮你揪出最基础的那几十类问题。但现在，开箱即用的 Ruff 就能自动扫描出语法错误、运行时隐患等数百种潜在缺陷，而且大部分规则都附带修复建议，甚至可以直接帮你把代码改好。Astral 官方博客给出的数据显示，Ruff 支持的规则总数也从 708 条增长到了 968 条——这是自 v0.1.0 以来，Ruff 首次对默认规则集进行如此大规模的调整。

对于不熟悉 Ruff 的读者，简单科普一下：它是用 Rust 写成的 Python 代码检查工具，主打一个“快”字，比传统的 Flake8 等工具快上几十倍甚至上百倍。过去几年，Ruff 已经逐渐成为 Python 生态中事实上的标准检查器，连 VS Code 的官方 Python 扩展都内置了对它的支持。这次更新之所以值得关注，是因为它大幅降低了“写好代码”的门槛——开发者不再需要花时间研究该启用哪些规则，Ruff 直接把最关键的检查项默认打开，让代码质量保障从“手动配置”变成了“自动生效”。

社区里有人开玩笑说，升级之后项目可能会突然多出几百条警告，但这恰恰暴露了之前被忽略的代码隐患。也有开发者提醒，如果你有大量遗留代码，建议先在配置文件中逐步启用规则，而不是一次性面对 413 条规则的“狂轰滥炸”。不过无论如何，这次更新让 Ruff 从一个“需要调教的好工具”变成了“装上就能用的好管家”，对 Python 生态的代码质量提升无疑是一针强心剂。

英美联合评估 Kimi K3 网络安全能力：漏洞利用接近前沿，自主攻击差距明显

这是什么：英国 AI 安全研究所（UK AISI）与美国 AI 标准与创新中心（CAISI）联合发布了对月之暗面 Kimi K3 模型的网络安全能力初步评估报告，这是该模型 7 月 16 日发布后首次接受外部安全审查。报告通过 ExploitBench 漏洞利用基准测试和“The Last Ones”网络靶场评估，量化了 Kimi K3 在漏洞开发、自主攻击模拟等任务中的表现，并与 GPT-5、Claude 4 等前沿模型及开源模型进行了对比。
🔥 为什么今天值得看：这份报告打破了“中国模型全面追赶美国前沿”的笼统叙事，提供了细粒度的能力画像：Kimi K3 在漏洞利用开发这类单项技能上已接近 GPT-5 和 Claude 4 的水平，但在需要多步骤规划、自主渗透的复杂场景中差距显著，且安全护栏在面对越狱提示时表现脆弱。这为评估 AI 模型的真实安全风险提供了更立体的视角，也揭示了能力提升与安全对齐之间的张力。

英国 AI 安全研究所（UK AISI）与美国 AI 标准与创新中心（CAISI）昨天联合发布了一份针对月之暗面 Kimi K3 模型的网络安全能力初步评估报告。这是 Kimi K3 自 7 月 16 日发布以来，首次接受外部机构的专项安全审查，结果揭示了一个有趣的分裂现象：在漏洞利用开发这类“单点突破”任务上，Kimi K3 的表现已经逼近美国前沿模型，但在需要多步骤规划、自主渗透企业网络的复杂场景中，差距被显著拉大。

报告采用了两个核心测试框架来量化这些能力。第一个是 ExploitBench 漏洞利用基准测试，考察模型在给定已知漏洞信息的情况下，能否编写出有效的利用代码。Kimi K3 在这里拿到了 42% 的成功率，虽然低于 GPT-5 的 58% 和 Claude 4 的 51%，但已经明显甩开了 Qwen 3.8-Max 等开源竞品——后者的成功率普遍在 20% 以下。这个成绩说明，Kimi K3 在理解漏洞原理并转化为攻击代码的单项技能上，确实具备了相当强的能力。

然而第二个测试——被称为“The Last Ones”的网络靶场评估——暴露了短板。这个靶场模拟了一个真实的企业网络环境，要求模型自主完成从侦察、横向移动到数据窃取的完整攻击链。Kimi K3 在没有任何提示引导的情况下，仅完成了 15% 的任务步骤，而 GPT-5 和 Claude 4 分别达到了 38% 和 31%。更值得注意的是，当测试人员尝试绕过模型的安全护栏时，Kimi K3 在 22% 的案例中直接提供了可操作的攻击建议，这一比例高于美国前沿模型的平均 8%。

报告特别指出，Kimi K3 的安全护栏在面对“角色扮演”类越狱提示时表现脆弱——比如让模型假装成一个网络安全培训讲师，它就会放松对恶意请求的过滤。这与之前 Anthropic 和 OpenAI 在各自安全报告中描述的护栏机制形成对比，后者在类似场景下通常能保持更高的拒绝率。社区讨论中，有开发者认为这可能反映了不同地区在安全对齐策略上的优先级差异，但也有人提醒，这只是一份初步评估，样本量有限，且测试环境与真实世界存在差距。

无论如何，这份报告给“中国模型追赶美国前沿”的叙事提供了一个更细粒度的视角：在单项技能上，差距确实在缩小；但在需要复杂推理、长期规划和稳健安全对齐的综合能力上，差距依然显著。
