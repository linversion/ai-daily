今天 The Verge 和 Engadget 等媒体同步爆出，OpenAI 首席执行官 Sam Altman 向特朗普政府抛出了一个史无前例的提议：让美国政府持有 OpenAI 5% 的股份。按当前估值算，这份“见面礼”大约价值 426 亿美元。

但这件事的吊诡之处恰恰在于它的“双赢”表象下藏着巨大的利益冲突。一个监管者同时成为被监管者的股东，谁来保证规则不是为股东利益量身定制的？R Street Institute 的声明直指核心：政府持股会制造“监管捕获”的完美风暴，让监管机构从看门狗变成合伙人。Cato Institute 更是在社交媒体上嘲讽，这相当于“用纳税人的钱为 AI 巨头兜底”。

目前白宫方面尚未正式回应，但据 NOTUS 报道，特朗普政府高级官员确实在认真考虑持有 AI 公司股份的可能性。如果这笔交易成真，它将彻底改写科技公司与政府的关系——从对抗走向共谋，而公众能否真的分到一杯羹，还是只得到一个被收买的监管体系，答案恐怕不乐观。

Kimi K2.7 Code 正式入驻 GitHub Copilot，首个开放权重模型可选

这是什么：月之暗面的 Kimi K2.7 Code 编程模型正式集成进 GitHub Copilot 的模型选择器，成为首个在 Copilot 中可选的开放权重模型。开发者现在可以在 VS Code 等 IDE 中直接切换使用该模型进行代码补全和生成。
🔥 为什么今天值得看：这是 GitHub Copilot 首次纳入开放权重模型，打破了此前只能选择 GPT、Claude 等闭源商业模型的局面。对开发者尤其是企业用户而言，这意味着多了一个低成本、可自部署的选项，降低了供应商锁定风险。

今天，月之暗面的 Kimi K2.7 Code 编程模型正式登陆 GitHub Copilot 的模型选择器。这意味着，全球开发者现在可以直接在 VS Code 等 IDE 里，把 Copilot 的底层模型切换成这个来自中国的开放权重模型，而不用离开熟悉的编码环境。

这件事的分量在于“首个”——Kimi K2.7 Code 是第一个被 GitHub Copilot 纳入模型选择器的开放权重模型。此前，Copilot 用户只能在 GPT、Claude 等闭源商业模型之间切换，现在多了一个低成本、可自部署的选项。对于企业开发者来说，这不仅仅是多一个选择的问题，而是打破了“用 Copilot 就必须绑定某家闭源供应商”的隐性枷锁。你可以先在云端用着，哪天想省成本或者有合规需求，随时可以拉下来自己部署。

回顾一下这个模型的履历：6月13日，月之暗面发布并开源了 Kimi K2.7 Code，当时主打的是解决长上下文指令遵循能力不足、过度思考导致 token 消耗过高的问题，同时提升了 Agent 自主化能力。模型参数规模达到 1T，在编程场景下专门优化了推理效率。有第三方评测指出，它在推理 token 消耗上比同类模型降低了约 30%。现在，这个模型从自家的 Kimi Code 和 API 平台，走到了全球最大开发者社区的心脏地带。

Hacker News 上的讨论热度不低，开发者们最关心的还是实际体验——有人反馈代码补全速度不错，但也有人指出在复杂重构任务上跟 Claude 还有差距。不过，对于“低成本平替”这个定位，社区共识是积极的：不是要打败谁，而是给开发者多一个不被锁定的选择。

日本最高法院终审裁定：AI不能当专利发明人，必须是人

这是什么：日本最高法院做出终审裁定，明确禁止在专利申请中将人工智能（AI）列为发明人。该判决驳回了将AI系统“DABUS”作为发明人的申请，强调专利发明人必须是人类。
🔥 为什么今天值得看：该裁定在司法终审层面解决了AI生成发明权属的法律空白，明确了专利制度激励“人类”创造的核心原则。它巩固了全球主要经济体在此问题上的司法共识，但也为AI生成发明的所有权归属（归开发者还是使用者）留下了新的争议空间。

今天，日本最高法院一锤定音，驳回了将人工智能列为专利申请发明人的诉求。这意味着，在日本，你想让AI当发明家拿专利？法律上此路不通。

这起案件的核心争议点其实很简单：当AI系统在几乎没有人类干预的情况下生成了一项发明，专利申请人一栏能不能填AI的名字？此前，一位名叫斯蒂芬·泰勒的美国研究者就曾以此为由，在日本为其AI系统“DABUS”生成的发明申请专利，但被日本专利局驳回。泰勒不服，一路打官司到知识产权高等法院，再到最高法院。如今，最高法院的裁决为这场拉锯战画上了句号。

为什么这个裁定值得关注？因为它触及了AI时代一个根本性的法律空白：创造的权属问题。现行各国专利法基本都默认发明人是“自然人”，但生成式AI的爆发让“非人类发明”从科幻变成了现实问题。日本最高法院的判决并非在否定AI的创造力，而是在法律层面划清界限——专利制度旨在激励“人类”的创造活动，权利和义务的主体也只能是人。你不能给一台机器授予垄断权，也无法让它承担侵权责任。

值得注意的是，日本并非孤例。美国、英国、欧盟、澳大利亚等地的法院或专利机构此前也做出过类似裁定，均拒绝承认AI的发明人资格。但日本的这次终审，进一步巩固了全球主要经济体在这一问题上的司法共识。当然，裁决也留下了新问题：如果AI生成的发明无法申请专利，那么这些发明的所有权该如何界定？是归AI的开发者，还是使用者？法院并未给出明确答案，这可能会成为未来商业纠纷的新战场。

社区讨论中，有人调侃“AI现在还没学会请律师”，也有人严肃指出，这可能会促使企业将AI的贡献刻意包装成“人类辅助”的成果，以绕过法律限制。但无论如何，至少在专利文书上，发明人那一栏，暂时还得填个会呼吸的碳基生物。

Chrome 官方 MCP 服务器更新：AI 代理可直接操控浏览器进行调试

这是什么：Chrome DevTools 官方 MCP 服务器迎来功能更新，新增 autoConnect 支持（兼容 Chrome 144+）、内存调试和结构化内容输出等实验性功能，让 AI 编码代理能更便捷地控制和检测实时 Chrome 浏览器。该项目已在 GitHub 获得 45.1k Stars，本次因更新登上 Trending。
🔥 为什么今天值得看：AI 编码助手（如 Claude、Cursor）此前无法直接观察代码在浏览器中的实际运行效果，只能依赖文本描述进行“盲写”。Chrome DevTools MCP 通过 MCP 协议将完整的 DevTools 能力（DOM 检查、网络调试、性能分析、内存诊断）暴露给 AI 代理，使其能像人类开发者一样打开浏览器检查问题，大幅提升前端开发与调试的自动化水平。Chrome 官方亲自维护该项目，也标志着浏览器厂商开始将 AI 代理视为重要的工具使用者。

今天 GitHub Trending 上出现了一个熟悉又陌生的项目——Chrome DevTools MCP，一个由 Chrome 官方团队维护的 MCP 服务器，已经积累了 4.5 万颗星。它这次重新进入大众视野，是因为最近一波更新让 AI 编码代理与浏览器的交互方式又往前迈了一步。

简单说，这个工具解决了 AI 编码助手（比如 Claude、Cursor、GitHub Copilot）的一个尴尬：它们能写代码，但没法亲眼看看代码在浏览器里跑起来是什么样。Chrome DevTools MCP 充当了中间人，通过 MCP 协议把 Chrome DevTools 的全部能力——DOM 检查、网络请求分析、性能剖析、内存调试——打包成 AI 代理可以直接调用的工具集。你让 AI 改个 CSS 样式，它不再只能盲猜，而是能打开浏览器看一眼实际渲染效果，再决定下一步怎么调。

这次更新的亮点在于 autoConnect 功能，支持 Chrome 144 及以上版本自动连接，省去了手动配置远程调试端口的麻烦。此外还扩展了客户端配置示例，让接入各种 AI 代理的门槛进一步降低。实验性功能方面，内存调试和结构化内容输出的加入，意味着 AI 代理不仅能“看”页面，还能更精细地诊断性能瓶颈和内存泄漏——这对前端开发者来说，相当于多了个不知疲倦的结对编程搭档。

社区讨论中，有人拿它和 Puppeteer 做对比。Puppeteer 是程序化控制无头浏览器的老牌方案，而 Chrome DevTools MCP 更偏向“AI 原生”的工作流——它不是让你写脚本，而是让 AI 代理自己决定什么时候打开 DevTools、检查哪个面板。不过也有开发者指出，目前这套工具在生产环境中的稳定性还有待观察，尤其是内存调试这类实验性功能，偶尔会出现连接中断的情况。但无论如何，Chrome 官方亲自下场做 MCP 集成，本身就说明浏览器厂商开始认真对待 AI 代理作为“新用户”这件事了。
