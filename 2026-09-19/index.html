Claude Code认了AGENTS.md，符号链接可删了

这是什么：2026 年 9 月 18 日，Anthropic 发布命令行 AI 编程工具 Claude Code 的 v2.1.277 版本，更新日志的第一条新增就是读取 AGENTS.md。规则很简单，项目里没有它自家的 CLAUDE.md 说明文件时，Claude Code 自动改读行业通用的 AGENTS.md。这个行为可以在 /config 设置页的 Project instructions 一栏调整。通过 Bedrock、Vertex、Foundry 三种企业渠道使用 Claude Code 的人暂时用不上。这条消息在 Hacker News 拿到 304 分热度。
🔥 为什么今天值得看：AI 编程工具开工前都会读项目根目录的一份须知文件，拿到规矩再干活，各家工具此前认的文件名不同。AGENTS.md 是 OpenAI Codex、Gemini CLI、Zed 等工具都已支持的开放标准，Claude Code 是坚持自家 CLAUDE.md 的少数派。同时用几家工具的开发者只能维护两份内容一样的文件，或者靠符号链接和同步脚本保持一致，改了一处忘了另一处，给 AI 的指令就会分叉。回退机制上线后，一份 AGENTS.md 通吃，重复维护的成本消失。对行业来说，最后一家抵制的头部工具接入社区标准，后来的工具进入项目时门槛更低。HN 上更多人把这看作竞争压力下 Anthropic 向生态标准妥协的一步，此前 Shopify CEO Tobi Lütke 公开威胁要在公司内禁用 Claude Code。

9 月 18 日，Anthropic 给命令行 AI 编程工具 Claude Code 发布了 v2.1.277 版本，更新日志的第一条新增就是在读文件上的一次让步。从这一版起，项目里如果没有 Claude Code 自家的 CLAUDE.md 说明文件，它会自动改读行业通用的 AGENTS.md。这个行为可以在 /config 设置页的 Project instructions 一栏调整，通过 Bedrock、Vertex、Foundry 三种企业渠道接入的用户暂时享受不到。这条消息在 Hacker News 拿下 304 分热度。

先用大白话解释这份文件是干什么的。用 AI 写代码的人，习惯在项目根目录放一份给 AI 的工作须知，写清楚这个项目用什么命令跑测试、哪些目录不能动。麻烦在于各家工具认的文件名不同。AGENTS.md 是社区推的开放标准，OpenAI 的 Codex、Google 的 Gemini CLI 和编辑器 Zed 都认它，Claude Code 此前只认自家的 CLAUDE.md，是头部工具里坚持到最后的一家。同时用几家工具的开发者，要么维护两份内容相同的文件，要么靠符号链接和同步脚本强行保持一致。HN 用户 aroman 说，他终于可以删掉自己的 sync-agent-docs.sh 了，这个脚本的工作就是把 AGENTS.md 递归地链接成 GEMINI.md 和 CLAUDE.md。

这次更新有前情。Shopify CEO Tobi Lütke 周二在 X 上写道:"我在考虑在 Shopify 禁用 Claude Code,直到他们改变主意,读取 AGENTS.md 和 .agents/skills 等文件。" HN 讨论里，有人用 Anthropic 的口吻调侃自家市场份额在流失，坚持自家文件格式的代价变大了；也有人认为这单纯是市场竞争在起作用，并庆幸这个领域的竞争比想象中多。

同一个版本还有两处开发者该知道的改动。弃用已久的 TaskOutput 工具被正式移除，后台任务的输出改用 Read 工具直接读文件，taskOutputMaxChars 设置和 TASK_MAX_OUTPUT_LENGTH 环境变量随之失效。另一项和安全有关，子代理交回的结果现在会带一个明确标题并整体缩进，子代理输出里的文字再也没法冒充这场会话自身的指令。这类风险叫提示词注入，指外部文本里藏一句话，让 AI 误以为收到了用户命令。

新功能仍有缺口。Claude Code 依旧不识别 .agents/skills 目录，那里存放跨工具通用的技能文件，和 AGENTS.md 同属一套约定。HN 用户 nomel 贴出了自己的土办法，用 git 的 post-checkout 钩子在每次切换分支时自动补建符号链接。用户 verdverm 对此不满，认为这种事不该按仓库逐个解决，Anthropic 可以选择做一个生态里更配合的玩家。

27B 模型压到 5.9GB,16GB 笔记本就能本地跑

这是什么：9 月 18 日,PrismML 发布 Ternary Bonsai 2 27B,把 Qwen3.8 27B 这个原本要占 53.80 GB 的大模型压到 5.93 GB,缩小约 9.1 倍,采用 Apache 2.0 开源许可。官方称一台 16 GB 内存的笔记本或一张 24 GB 显卡就能跑起来,模型支持文字和图片输入,上下文长度 26.2 万 token。这是两个月内该系列的第二代。
🔥 为什么今天值得看：这个量级的模型以前想在本地运行,基本要配大显存的专业显卡,多数人只能调云端接口,数据要出本机,还要按用量付费。压到 5.93 GB 之后,普通笔记本可以离线跑,隐私和成本两笔账都变了。技术上,9.1 倍压缩配 98.2% 的平均保留率,数学、编程这类硬项基本不掉分,而传统方案 IQ2_XXS 平均掉到 75.2 分,三值量化第一次给出完整的多硬件实测对比。因果的另一面也要看清,长程智能体任务只保留约 75%,拿它当全天候编程代理还不够稳。
展开正文

9 月 18 日,PrismML 发布开源模型 Ternary Bonsai 2 27B。它是对 Qwen3.8 27B 做"三值量化"之后的版本,模型文件 5.93 GB,而原版按标准精度存放要 53.80 GB,缩小约 9.1 倍。模型采用 Apache 2.0 许可证,能读文字也能看图片,一次可处理约 26.2 万 token 的内容。官方还放出演示,让它在一张 RTX 5090 显卡上驱动 Cline 编程智能体和操作电脑。

量化意味着把模型里存的数字换成更粗的刻度,用精度换体积。PrismML 的做法是让每个权重只取 -1、0、+1 三种值,每 128 个权重共用一个 16 位精度的缩放系数,平均下来每个权重约 1.72 比特。取整之前先对权重做块大小 1024 的 Hadamard 旋转,相当于换一套坐标存放同一组数字,减少取整带来的失真,这个思路来自 SpinQuant 论文。至于每个权重最终取哪个值,分配方法没有公开。

官方报告的成绩单里,20 项基准平均分 83.9,母模型 85.4,保留率 98.2%,指令遵循这一小项甚至到 101.7%。更能说明问题的是与传统量化的对比。把同一个 Qwen3.8 27B 压到 7.3 GB 的 IQ2_XXS 方案,20 项平均只有 75.2 分,数学题集 AIME26 上得 78.6,新模型得 95.83;编程测试 LiveCodeBench v6 上,两者是 70.05 对 90.07。数学和编程两类的保留率分别为 99.5% 和 99.3%。

速度数据在 2026 年 9 月 16 日实测。RTX 5090 上生成速度达到每秒 142.5 个 token,单个 token 能耗 0.582 毫瓦时;RTX 4090 每秒 96.7,72 瓦的 L4 也有 32.1;苹果笔记本上 M5 Max 为 46.8,M5 Pro 为 27.7。官方给出的最低配置是 16 GB 内存的笔记本或一张 24 GB 显存的显卡,并称整体能效比全精度的 8B 模型高 40%。文件有两种打包,PTQ1_0 是 5.93 GB,PQ2_0 是 7.25 GB,在不同硬件上各有快慢。

短板同样写得清楚。长程智能体任务只保留约 75%,Terminal-Bench 2.1 上 52.8 分,母模型 69.7 分;SWE-bench Verified 上 60.8 对 80.6。低推理强度档位不支持,中档模式下平均 79.3 分,全精度基准是 82.6。所有成绩都出自 PrismML 自己在 H100 上的测试,尚无第三方复现。使用上还有一道坎,GGUF 文件必须用 PrismML 改造的 llama.cpp 分支加载,原版会直接拒绝;Mac 用户走配套的 MLX 运行时,另有一个在浏览器里跑的 WebGPU 演示。

这是该系列的第二代。两个月前的第一代 Bonsai 27B 保留率约 95%,这一代提到 98.2%,并首次披露完整的量化细节和多种硬件的实测数据。母模型总参数 27.36B,由 24.35B 语言骨干、2.54B 嵌入层与输出头、0.47B 视觉塔组成,Bonsai 2 保持这套架构不变,仅 0.0976% 的参数维持高精度。

DeepSeek 把模型阅读笔记压到每 token 890 字节

这是什么：DeepSeek 团队把 DeepSeek-V4.1-Flash 的论文放上了 HuggingFace 论文版（编号 2609.19969），论文把这个骨干参数 5520 亿的多模态混合专家模型的 KV 缓存压到每 token 890 字节，约为上一代 DeepSeek-V4-Flash 的四分之一，经部署优化后约八分之一，模型权重已在 HuggingFace 开源。官方新闻页显示模型更早已经发布，本轮新闻点是论文公开。
🔥 为什么今天值得看：KV 缓存是大模型读长文本时存在显存里的记录，输入越长占用越大，直接决定一块 GPU 能同时服务多少人、上下文能开多长。论文判断，长程 Agent 让模型负载越来越偏向读入大量内容，prefill 计算贵、KV 缓存挤占显存和 SSD，合起来是继续压低部署成本的主要瓶颈。压到每 token 890 字节后，同样一块显卡能装下的长对话变多，长文档问答和连续执行任务的 Agent 应用有了降成本的空间。按该数字粗算，读满 100 万 token 上下文只需约 890 MB 缓存。
展开正文

DeepSeek 团队的论文 DeepSeek-V4.1-Flash 出现在 HuggingFace 的论文版上，编号 2609.19969，主题只有一个，把大模型的 KV 缓存压缩推向极限。模型的权重同步开源在 huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash，谁都可以下载。时间上要交代一句，官方新闻页显示这个模型更早已经发布，这次引起关注的是论文公开，把整套设计细节完整摆了出来。

先弄清 KV 缓存是什么。AI 读你发去的长文档时，每读一个 token 都要在显存里记一笔笔记，生成回答时随时回头翻看，这笔不断增长的笔记就是 KV 缓存。论文开头的判断是，长程 Agent 普及之后，模型负载越来越偏输入，一整份文档、一整个代码库都要读进来，回答常常只有几句，而读题阶段（论文里叫 prefill）计算昂贵，巨大的 KV 缓存又持续挤占显存和 SSD 的容量与传输带宽，合起来构成继续压低部署成本的主要瓶颈。

DeepSeek-V4.1-Flash 本体是一个多模态混合专家模型，骨干参数 5520 亿，读题阶段每读一个 token 只激活其中 160 亿，上下文窗口最长 100 万 token。这一代采用了因果编码器-解码器架构（CED），论文称其显著提升了读题阶段的计算效率。

真正的重头戏在压缩。跨层 KV 缓存复用让相邻的层共用同一份笔记，FP4 KV 缓存用 4 比特的极低精度来存，两者叠加把全局 KV 缓存降到每 token 890 字节，约为上一代 DeepSeek-V4-Flash 的四分之一，再经过名为 SWABoundedReplay 的部署优化，可以进一步压到上一代的约八分之一。按每 token 890 字节粗算，读满 100 万 token 的上下文，这份笔记大约只占 890 MB。

论文称，压缩到这个程度，模型性能仍然显著优于基线。这件事的经济含义相当直接，KV 缓存决定一块 GPU 能同时接待多少请求、能把上下文开多长，缓存降到四分之一乃至八分之一，长上下文服务的显存开销就腾出了大块空间，长文档问答和连续干活的 Agent 应用因此有了把成本往下拉的余地。也要留一句，性能结论目前是论文自述，数字能不能扛住，还要等独立复现。

阿里Qwen发布全模态模型，带着问题看视频，音视频成本降九成

这是什么：2026年9月18日,阿里Qwen团队发布Qwen3.8-Omni-Flash。它能读文字、图片、声音、视频,回答只用文字,一次能装下的材料上限标称为100万token。官方称这是Qwen第一个围绕智能体能力打造的全模态模型,看长视频时先看问题、再自己决定看哪几段,像查案取证。发布时只提供线上API,未开放模型权重。
🔥 为什么今天值得看：长视频理解过去贵在从头读到尾,整段视频都按token计费。这个模型从问题出发多轮取证,官方数字显示token省约45.7%的同时准确率从63.4升到67.8,效果和账单两头同时改善,长视频问答、录音总结这类应用离普及更近一步。音频输入每小时成本较上一代Qwen3.5-Omni-Plus降超98%,直接拉低了相关产品的落地门槛。对行业来说,大厂把多模态理解和智能体工具链装进同一个模型,是个方向信号。代价是发布时只开放云端API,数据要发到阿里的服务器,隐私敏感场景需要自行权衡。
展开正文

2026年9月18日,阿里Qwen团队发布了新模型Qwen3.8-Omni-Flash。官方称这是他们第一个围绕智能体能力打造的全模态模型。全模态的意思是,文字、图片、声音、视频都能作为输入读进去,模型的回复只有文字。发布时它只开放了线上调用接口,能在QwenCloud、阿里云Model Studio和Qwen Studio三处使用,模型权重没有放出来,暂时没法自己部署。

这个模型最值得聊的是它看长视频的方式。多数视频模型会把长视频从头到尾看完,哪怕答案只藏在其中三分钟里。Qwen团队描述的流程是,模型先看你的问题,自己决定该看哪几段、听哪几段,再像查案一样一轮轮收集线索,把算力花在关键片段上。官方公布的数字是,在OmniVideoBench长视频测试上,准确率从63.4升到67.8,消耗的token从145,736降到79,117,省了约45.7%。token是模型计量和计费的单位,大致相当于一个词或几个字。

账单还往下压了一层。和上一代Qwen3.5-Omni-Plus相比,官方口径称音频输入每小时成本降了超过98%,音视频输入降了超过93%,官方X帖给的视频单项降幅约89%。定价为每100万token输入0.15美元、输出0.47美元,重复内容命中缓存时只收0.016美元。按这个价位,拿AI听完几小时录音再写总结,从成本上讲已经进入日常可用的区间。

176 组实验拆开 AI 编程工具的外壳，流行做法缺乏证据

这是什么：一篇 2026 年 9 月挂上 arXiv 的论文 9 月 18 日起在 Hacker News 引发热议，截至抓取拿到 197 分。论文研究的是 AI 编程工具里除大模型以外的那层工程外壳，做法是把它拆成规划、动作空间、上下文管理三个部件，在 4 个模型、176 组对照设置下分别测试，发现多项被社区当作常识的做法其实没有带来收益。
🔥 为什么今天值得看：AI 编程工具的效果和账单由模型和外壳共同决定。外壳决定模型每一步看到什么、能用什么工具、历史记录怎么压缩，直接影响任务成败和花费。过去厂商和开发者往外壳里加规划模式、预定义工具、各种插件，判断价值靠直觉和营销话术。这份研究给出了第一批分部件的量化证据，提示该按模型强弱和预算选设计。对普通用户的意义是，两款编程助手的表现差距未必取决于模型，外壳同样在起作用，功能清单长不等于效果好。
展开正文

一篇 2026 年 9 月挂上 arXiv 的论文《An empirical study of harness design for coding agents》，9 月 18 日起在 Hacker News 引发热议，截至抓取拿到 197 分。它试着回答一个很多人想问却没法验证的问题，AI 编程工具里，除掉大模型本身，剩下那套工程外壳到底哪些部分在起作用。

外壳并不神秘。你常用的 AI 编程助手由两层组成，大模型每次只负责思考一步，另有一套程序负责把文件、命令行和对话历史递到模型眼前，再把模型的决定执行下去。这套程序在行业里叫 harness，可以理解成执行框架。Claude Code、Codex 这类产品的差异，既来自模型，也来自这层框架怎么写。过去的研究总是把整套框架当成一个整体打分，说不清哪个零件立了功，哪些纯属装饰。

这批研究者改用控制变量的办法。执行循环完全固定，只允许三个部件更换。规划部件决定要不要先列计划再动手。动作空间部件决定给模型一套现成工具，还是只给一条命令行。上下文管理部件负责在历史记录太长时删减和压缩。他们在 SWE-Bench Verified 和 Terminal-Bench 2.1 两个测试集上，用 4 个模型跑了 176 组匹配设置，相当于把同一台车换轮胎、换变速箱分别跑圈速。

在测试的这些模型上，结论对日常选型很有参考价值。窗口预算越紧，上下文管理越有价值，收益主要来自防止历史记录塞爆上下文导致任务直接失败。具体策略上，先用固定规则删掉旧内容、再让模型把剩余历史写成摘要的分层做法效率最高；让被删内容可以找回的机制，模型很少使用，也没有换来准确率提升。规划的角色随模型强弱变化，能力弱的模型靠它抬高准确率，能力强的模型用它几乎只剩省钱。动作空间同样因模型而异，bash 能力弱的模型需要预定义工具，bash 熟练的模型只用命令行接口就能把活干好，成本大幅降低，在命令行为主的任务上尤其明显。研究者还分析了执行轨迹，发现上下文管理拉长了轨迹但基本不改变行为，规划改变轨迹在哪里停下，动作空间改变写代码的粒度。

争论同样激烈。HN 用户 vblanco 直言研究用的是 Nemotron 和 Mistral，比当前前沿落后约两代，新一代模型已经在训练中被围绕各家自家框架做过强化学习适配，250k 到 1M 的上下文窗口也让旧式上下文管理失去意义。论文摘要没有点名测试用的模型，Nemotron 和 Mistral 这份名单出自 vblanco 的评论。另一边，shermantanktop 和 Systemerror7A69 反驳，拿不出最新模型存在根本差异的证据，就不该凭直觉否定一项实证研究，何况社区里流行的 skills、MCP 插件本来就几乎没有效果验证。mini-swe-agent 的作者 lieret 也现身，提醒多数基准测试里，复杂框架并未稳定胜过他的极简实现，该项目起步时只有 100 行代码，跟帖有人指出如今算上注释约 190 行。

这是什么：Vercel 的 mcp-handler 库发布 2.2.0 版本，加入了对 WebMCP 的实验性支持。用这个库搭建的网站，只要在页面里加一段脚本标签，就能把已有的 MCP 工具开放给浏览器里的 AI 助手。开发者需要先在配置里声明开放哪些工具，没有声明的工具不会被暴露。
🔥 为什么今天值得看：MCP 工具此前难以被浏览器内的 AI 直接调用，网站想把功能交给网页里的助手，缺少现成的对接方式。这次更新让网站直接复用现有的 MCP 工具，浏览器端的调用以用户在网站上的登录身份代理回服务器，需要登录的功能不用再在浏览器里走一遍第三方授权。对开发者来说少写一套对接，对普通用户来说，网页内的 AI 助手调用网站功能这条路变得更顺。
展开正文

Vercel 的 mcp-handler 库发布了 2.2.0 版本，加入了对 WebMCP 的实验性支持。MCP 可以理解成 AI 程序连接外部工具的通用插口，WebMCP 则是把这套接口延伸到浏览器的提案，想让网站用普通网页技术把工具交给浏览器里的 AI 助手。

具体用法分两步。开发者在配置里添加一个名为 experimental_webMcp 的对象，列出愿意开放的工具，比如官方示例里的掷骰子工具 roll_dice；然后在页面中插入一行脚本标签，从 MCP 接口的 ?webmcp-script 参数加载注册脚本。脚本会把列出的工具注册到页面上，浏览器里的 AI 每次调用时，请求以当前登录用户的身份转回网站自己的 MCP 服务器。因为调用带着登录状态，需要授权的工具不用再走浏览器端的 OAuth 流程，也就是常见的第三方授权登录那一步。

还要留意两点。WebMCP 目前仍处于提案阶段，标准没有定稿；mcp-handler 这次的支持也是实验性功能，开发者主动声明之后工具才会开放，没有声明的工具不会被暴露。

9 月 17 日，Meta 的 AI 助手 Muse 推出 Mac 桌面版，Meta 的 Alexandr Wang 当天在 X 上官宣了这一消息。据 TechCrunch 报道，Muse 在 Mac 上能进入文件、信息、日历、备忘录和邮件这几个系统自带应用，在里面替用户做事。

Jina AI 开源文档解析模型，低端显卡解析速度近翻倍

这是什么：9 月 18 日，隶属 Elastic 的 Jina AI 发布 jina-ocr-v1，一个视觉文档解析模型，能把 PDF、扫描件、表格、图表、发票一次转换成 Markdown，表格用 HTML、公式用 LaTeX。模型总参数 3.4B，采用 MoE 结构，每个 token 激活约 570M，在 DeepSeek-OCR 基础上后训练得到。权重放在 Hugging Face，BF16 下约 6.8 GB，内置的投机解码头让它在低成本显卡上跑得更快。
🔥 为什么今天值得看：很多团队要把堆积如山的文档变成可检索、可喂给大模型的文本，解析速度直接决定这项工作的成本。jina-ocr-v1 瞄准 NVIDIA L4 这类低成本显卡，单卡就能跑，单张 A100 并发 32 时每秒解析 2.57 页，是 Jina AI 实测的 14 个系统里最高的。精度上它居中，OmniDocBench v1.6 得 91.14 分，低于 PaddleOCR-VL-1.6 的 96.34，追求最高识别准确率的场景需要斟酌。
展开正文

9 月 18 日，隶属 Elastic 的 Jina AI 发布了文档解析模型 jina-ocr-v1。它吃进 PDF、扫描件、表格、图表或发票，一遍就吐出干净的 Markdown，表格用 HTML 表达，公式用 LaTeX 书写。模型总参数 3.4B，采用 MoE 设计，每个 token 只激活约 570M，骨架来自 DeepSeek-OCR。

这次发布真正想讲的是速度。Jina AI 在模型里内置了一个叫 FastMTP 的投机解码头，让低成本显卡也跑得动。在 NVIDIA L4 单卡上，解码速度从每秒 42.7 个 token 提到 83.1 个，提速 1.95 倍，输出和不开加速时完全一致，属于无损加速。吞吐测试里，单张 A100 40GB、32 路并发，它每秒解析 2.57 页，是 Jina AI 实测的 14 个系统里的最高值。作为参照，olmOCR-2 每秒 1.22 页，chandra-ocr-2 每秒 0.38 页。

精度方面需要如实讲。OmniDocBench v1.6 它拿 91.14 分，低于 PaddleOCR-VL-1.6 的 96.34 和 HunyuanOCR-1.5 的 94.74；olmOCR-Bench 拿 83.4 分，也低于 chandra-ocr-2 的 85.8 和 dots.mocr 的 83.9。后训练让它比骨干 DeepSeek-OCR 在 olmOCR-Bench 上高 7.4 分，进步是真的，但它没有拿到两个榜单的第一名。选型时应该冲着吞吐和低部署成本来，追求精度榜首的可以看别家。

上手路径有三条。最省事的是 Jina Reader，把 URL 发到 r.jina.ai 并带上指定响应头，返回的就是 Markdown；api.jina.ai 提供 OpenAI 兼容接口；也可以自托管，权重在 Hugging Face，BF16 下约 6.8 GB，FastMTP 需要 vLLM 0.21 及以上版本。许可证是 CC BY-NC 4.0，只覆盖研究和非商业用途，商用需要联系 Jina AI 单独拿授权。
