Google 发布 Gemini 3.8 Live，Extended Thinking 边推理边说话登顶语音评测

这是什么：Google 在 9 月 15 日一次发布两款实时语音对话模型。Gemini 3.8 Live 走量大便宜的路线，负责规模化语音场景；Gemini 3.8 Live Extended Thinking 走聪明路线，专攻高复杂度任务，最大卖点是边推理边说话。以前让语音助手办件复杂的事，它得先安静想半天再开口；新模型收到请求会先说一句「让我查一下…」，任务挪到后台执行，它一边继续跟你聊，一边实时播报任务进度。发布当天开发者就能在 Gemini API 和 Google AI Studio 调用，普通用户在 Search Live 和 Gemini 应用里能体验到。
🔥 为什么今天值得看：语音智能体长期被一道选择题卡住，模型反应快就办不了复杂的事，能办复杂的事对话体验就差。这次官方把升级重点放在并行推理上，让模型在说话的同时处理多步任务，等于把两条路并成一条。对开发者，官方称这是搭建可靠、可投产语音智能体的构件，Agora、LangChain、LiveKit、Vercel 等平台通过 Gemini Live API 支持开发者搭建语音界面，实时媒体流的底层由平台打理；对企业，Salesforce、Genspark、Lumeris 等公司已是合作伙伴，官方引用它们对延迟、流畅度和工具调用能力的正面评价。配合登顶的评测分数，语音智能体上生产环境缺的能力清单又短了一截。

Google DeepMind 在 9 月 15 日发布两款实时语音对话模型，Gemini 3.8 Live 和 Gemini 3.8 Live Extended Thinking。官方称这次的主要升级在智能水平和并行推理。两个模型分工不同，3.8 Live 为规模化场景而生，把对话智能、流畅对话和视觉理解打包在一起，强调成本效率；Extended Thinking 面向高复杂度任务，加强多步推理，用于企业级任务执行。

语音智能体一直有道取舍题，模型埋头做复杂推理时对话容易停顿，专注对话流畅时又难完成多步任务。Extended Thinking 的解法是让推理和说话同时进行。它先用「让我查一下…」这样的语音提示确认收到请求，再对后台执行的多步任务做实时进度播报。官方演示里，它一边保持对话，一边把草图和实时语音反馈变成能运行的 React 界面代码，还协调了多步预订和异步函数调用，对话全程不中断。3.8 Live 的看家本领是近实时视觉输入，官方展示了它用视觉上下文实时指导员工入职、近实时下国际象棋。

评测数字方面，Extended Thinking 在 Artificial Analysis 的语音到语音质量指数拿到 82.6 分，排名第一；智能体任务完成上，τ-Voice 得分 68.6%，Sierra 的 τ-Voice-banking 得分 35.1%；推理基准 Big Bench Audio 得分 97.7%。官方同时强调其价格与其他前沿模型相比保持竞争力。3.8 Live 在 Speech Agent Arena 按用户偏好排名第二，定位是高性价比、可规模化部署。在 ServiceNow 的 EVA-Bench 语音智能体评测中，官方称两款模型在准确率与对话质量之间取得平衡，把复杂工作流表现推到新的帕累托前沿，测试环境是 Gemini Enterprise Agent Platform 上的 Live API。

渠道方面，发布当天开发者即可通过 Gemini API 和 Google AI Studio 调用两款模型；普通用户可在 Search Live 使用 3.8 Live，在 Gemini Live 使用 Extended Thinking；Workspace 里的 Docs Live、Gmail Live、Keep Live 当天上线，其中 Docs 的 Extended Thinking 能力面向 Google AI Pro 和 Ultra 订阅用户，Gmail 与 Keep 面向所有 Google AI 订阅用户。企业版两款模型都在 Gemini Enterprise 私人预览中，Customer Experience 版本和 Workspace 商业版的官方说法是即将推出。公告只提供托管服务渠道，未涉及开源权重。安全方面，Google 称其 AI 产品生成的全部音频都织入 SynthID 不可感知水印，用于检测 AI 生成内容，安全细节见模型卡。

9 月 15 日，Meta 随新公布的 AI 订阅计划一同宣布，企业接入 WhatsApp Business 消息服务时，设置和管理工作可以交给开发者自己选的 AI agent。WhatsApp Business 是企业通过 WhatsApp 对话连接客户的服务，过去开发者完成接入，要在 Developer Console、Meta 的 Business Manager、API 参考文档和自己的编辑器之间来回切换，现在改成用对话向 agent 描述需求，由它代为执行。

支撑这次调整的是新发布的 WhatsApp Business Tools MCP 服务器（MCP 全称 Model Context Protocol，中文常译作模型上下文协议），它把 Claude、Cursor、Codex、ChatGPT 这类 AI 编码 agent 直接连到 WhatsApp Business Platform。Meta 此前的 MCP 服务器覆盖广告管理和应用配置监控等场景，这次新增了一台专门帮企业入驻 WhatsApp 的服务器，属于产品线扩张。配置过程中，Meta 已有的 Meta Social Technologies MCP 也能配合使用，用来发现 API 端点、搜索文档、排查错误。

agent 承接的是入驻流程里的大部分杂务，包括创建企业的 WhatsApp Business 账号、添加并验证电话号码、注册 Cloud API 访问、核对服务条款。入驻之后，企业可以用自然语言描述想要的消息模板让 agent 创建，也可以让它编辑现有模板，还能测试消息和 webhook，并盯住服务条款、支付方式、企业验证这些以往容易悄悄失效的配置项。

放在行业里看，PayPal、Stripe、GitHub、Notion、Slack、Salesforce、Atlassian、X、Google、Microsoft 等公司也都提供 MCP 服务器，让 AI agent 安全地与各自服务交互。Meta 这次为自家商业消息平台的企业入驻新开一台，等于把开放路线从广告等管理场景推进到了开号和运维环节，企业接入 WhatsApp 的体力活第一次可以交给编码 agent 代跑。

编码 agent 界瑞士军刀 Pi，一个仓库攒出 10.6 万 star

这是什么：开源项目 Pi（earendil-works/pi）出现在 GitHub Trending 工具榜上。它是一个给 AI 编码 agent 当底座的工具集仓库，2025 年 8 月创建，一年多积累了约 106k star、13.3k fork 和 6361 次提交。本次上榜对应的增量是 9 月 5 日发布的补丁版本 v0.85.1，以及 9 月 15 日仍在进行的代码推送和 README 更新，属于持续迭代项目的热度体现。
🔥 为什么今天值得看：编码 agent 的竞争不只在成品产品层面，自建派开发者同样需要趁手底座。Pi 的方案是把统一 LLM API、agent 运行时、终端 UI 库和成品编码 CLI 分层装进一个 monorepo，统一 API 让换供应商接近只改配置，分层让开发者可以只取需要的那一层。供应链加固和无权限系统的风险提示被写进 README，社区项目按生产标准自我要求的意图相当明显。约 106k star 的体量也说明这条路线已经聚起一个相当大的开发者盘子。
展开正文

GitHub Trending 工具榜最近出现了 earendil-works/pi 的身影。这个仓库 2025 年 8 月创建，一年多攒下约 106k star、13.3k fork 和 6361 次提交，9 月 5 日刚发布补丁版本 v0.85.1，9 月 15 日仍有代码推送和 README 更新。它自我定位为 agent harness，官方描述里最直接的概括是 AI agent toolkit，也就是一套开发和运行 AI agent 的底座工程。

这个 monorepo（多个软件包放在同一个仓库里维护）装着几件互相配套的东西。最底层是 @earendil-works/pi-ai，把 OpenAI、Anthropic、Google 等多家供应商的大模型接口收拢成统一 API。中间一层放着带工具调用和状态管理的 agent 运行时 pi-agent-core，外加一个差分渲染（只重绘变化部分）的终端 UI 库 pi-tui。面向使用者的是交互式编码 agent 命令行工具 pi-coding-agent，官方强调它可以自我扩展。仓库里还有负责应用组合的 chord 运行时和厂商中立的 pi-telemetry 遥测包，Slack 等聊天自动化则放在独立仓库 pi-chat。

仓库当前把大量篇幅给了工程细节。安全上，README 明确写出 Pi 没有内置权限系统，默认继承启动它的用户和进程的权限，需要更强隔离时官方文档给出三种容器化方案，Gondolin 扩展把工具调用路由进本地 Linux micro-VM，普通 Docker 把整个进程装进容器，OpenShell 提供按策略控制的沙箱。供应链上，直接依赖全部精确锁版，npm 解析时避开当天新发布的依赖，发布的 CLI 用 shrinkwrap 锁死传递依赖，依赖的生命周期脚本要走白名单审核，CI 定时运行 npm audit。社区侧，维护者鼓励使用者把真实的开源编码会话经 pi-share-hf 发到 Hugging Face，用真实任务和真实修复替代玩具基准。

对自建 agent 的开发者，这套布局的价值在于自主和分层。统一 API 作为开源库自己引入、自己运行，换供应商时业务代码基本不动；运行时、界面、成品 CLI 各自独立成包，想借鉴哪一层就直接读哪一层的源码。项目采用 MIT 许可，pi.dev 域名由 exe.dev 捐赠，读文档之外官方还提示可以直接问 agent 本人，让编码 agent 解释自己。

Salesforce 首个推理模型 Koa 发布，基于 Nemotron 后训练专攻销售客服

这是什么：Salesforce 在本周 Dreamforce 大会上发布了公司第一个推理模型 Koa。它基于 Nvidia 的开源权重模型 Nemotron 后训练而成，两家公司合作把训练目标收窄到销售、营销和客服任务。Koa 会作为新选项进入 Salesforce 的 Agentforce 平台，客户在这个平台上搭建处理客服咨询、安排预约这类重复事务的 agent，遇到任务时由 AI 网关自动决定用哪个模型。
🔥 为什么今天值得看：此前 Agentforce 里需要长链条多步推理的任务，一律经 AI 网关送往 Claude 或 ChatGPT，企业按 token 付费，数据也要离开自己的边界。Koa 把这个环节收了回来，数据主权、成本和任务专精三笔账可以一起算。基座选择传递的信号更大，Govindarajan 称此前不存在满足条件的主权美国预训练模型，也不知道 Qwen 用什么数据训练，Nemotron 正好补上这个空位。TechCrunch 的判断是，企业对 AI 的需求正在与前沿实验室的供给分化，Koa 是这种分化的一个样本。

本周 Dreamforce 大会上，Salesforce 发布了公司第一个推理模型 Koa。推理模型指能分步思考、处理长链条多步任务的模型。Koa 基于 Nvidia 的开源权重模型 Nemotron 后训练而成，开源权重指参数文件公开可下载，企业可以自行部署和改造，后训练指在通用基座上做定向加工。两家公司合作把训练目标收窄到销售、营销和客服，模型进入 Agentforce 平台，客户在这个平台上搭建处理重复事务的 agent，比如回答客服咨询、安排预约。

在此之前，Agentforce 里凡是需要长推理的任务，都会经 AI 网关送往 Claude 或 ChatGPT 这类前沿模型，AI 网关就是决定哪个请求交给哪个模型的调度系统。Salesforce AI 的 EVP Jayesh Govindarajan 对 TechCrunch 说：「我们造过很多小型的任务专用语言模型，都在 Agentforce 的组合里。但推理这一块，我们一直依赖前沿模型厂商。到现在为止。」

基座选择是这次发布里信息量最大的部分。Govindarajan 说，公司一直想训练自己的企业级前沿模型，苦于没有合适的预训练起点。「直到 Nemotron 出现，才有可用的主权美国预训练模型，它同时达到最先进水平，数据来源也清晰。我们完全不知道 Qwen 拿什么数据训练。」Qwen 是阿里巴巴推出的流行开源权重模型。这句话把企业挑基座的标准摆上了台面，数据来源能否讲清楚，直接决定过不过得了合规这一关。

后训练环节同样绕开了真实数据。两家公司没有使用任何 Salesforce 客户的数据，转而构造模仿客户行为模式的合成数据。Govindarajan 描述了模拟场景：「我们模拟了一个客服环境，有角色扮演的客服专业人员，包括打进客服中心的愤怒客户，一直到努力成交的销售专业人员。」官方表述是 Koa「没有 ingested 任何真实客户数据」，因此没有可供外泄的东西。

token 是大模型处理文本的计量单位，也是按量计费的基础。Koa 的另一目标就是省 token，把销售客服类任务做得比送往 Claude 或 ChatGPT 更便宜。Nvidia 企业生成式 AI 软件副总裁 Kari Ann Briski 对 TechCrunch 说：「我们有一套独特的推理架构来实现 token 效率。主权 AI、首 token 响应时间、高效推理，这几样合在一起，才撑得起整体的 token 经济账。」首 token 响应时间指用户发出请求到模型吐出第一个字之间的等待。

Koa 在 Agentforce 里与 Claude、ChatGPT 等模型并存，由 AI 网关按任务需要自动路由。它的训练目标是具体的工作任务，那些解不开的数学难题不在清单上，同时它遵循客户的数据要求，安全设置内嵌在 Salesforce 里。TechCrunch 原文的判断是，企业世界对 AI 的需求正在与前沿实验室的供给分化。实验室希望企业把文件、代码、提示词和反馈直接上传进自家模型并为此投入重金，Salesforce 这类厂商给出的是另一条路径，企业按任务把活分给最合适的模型。

Agent 平均分掩盖翻车风险，IBM 开源一致性诊断工具

这是什么：IBM 研究团队 9 月 15 日在 Hugging Face 发文，为开源智能体工具库 ALTK-Evolve 新增了 Consistency Analyzer（一致性分析器）和一种一致性指南。分析器能定位智能体执行轨迹里最容易在下次运行时改主意的决策步骤，生成的指南注入上下文后，让原本时对时错的任务更稳定地做对。文章同时点出一个被普遍忽略的事实，榜单只报平均成功率，用户真正关心的问题它答不了，同一句话再问一遍还行不行。
🔥 为什么今天值得看：生产环境里，用户会反复发来同样的请求，一次成功只够撑过演示，撑不起第二次调用。对账一笔金融交易、核查一份合同的义务条款，这类关键流程失败一次就不可接受，77.4% 与 53.0% 之间的落差正是埋在这里的风险。更大的模型填不平这个坑，作者把能力与一致性定义为互相独立的两条轴，换更强的模型会抬高平均分，一致性差距未必跟着收窄。诊断本身只需要一条历史轨迹，不需要标准答案，也不用把任务对着环境重放一遍，因此可以直接用于生产流量。可靠性由此从体感问题变成了可测量、可修复的工程对象。

同一个智能体，同一个任务，环境什么都没变，这次做成了，下次可能就砸。IBM 研究团队 9 月 15 日在 Hugging Face 博客上发表的工作，把这种演示现场式的事故变成了可以计算的指标。在 AppWorld 基准（一批模拟在常用应用里办事的任务）上，一个基于 GPT-4.1、以 ReAct 方式逐步调用工具的智能体，五次重复运行的平均成功率为 77.4%。而五次全部成功的任务只占 53.0%。两个数字之间 24.4 个百分点的落差被团队命名为一致性差距，在难任务上这个差距会拉大到 30 个百分点。

榜单几乎只报第一个数字。Mean@k 是行业默认口径，把任务跑 k 次取平均通过率，k 常取 3，有时只跑 1 次，宣传里的「77% 准确」就是它。Pass@k 是乐观口径，k 次里至少一次成功就算过，常见于代码生成论文，适合能验证、能重试的场合。Pass^k 问的是最严苛的可能，k 次必须全部成功，用户把同一句话再问一遍时得到的就是这个待遇。三个数永远满足 Pass^k ≤ Mean@k ≤ Pass@k。

翻动的根源藏在概率分布的形状里。模型每做一次决策（调哪个 API、传什么参数、要不要重试），输出都来自对下一个 token 的概率分布。分布尖锐时，概率质量集中在一个选项上，重复运行结果稳定；分布平坦时，几个近并列的选项分走相近的概率，谁胜出接近抛硬币。一条轨迹串着几十个决策，单步很小的翻转概率层层叠加，整条路径分岔的机会随之放大。团队特别说明，实验智能体运行在温度 0.0 上，这些波动与普通采样无关，托管端点上概率本身的微小漂移就足以让近平局今天判向一边、明天判向另一边。

诊断工具叫 Consistency Analyzer，已并入 IBM 此前开源的 ALTK-Evolve（一套把智能体历史轨迹自动提炼成可复用指南、在推理时注入回去的工具库）。它只需要一条录好的执行轨迹，在每个决策点上只额外发一次模型调用，一次带出 k 个补全（默认 k=5），对比这些补全的差异，差异大的决策点被写进记分卡，标出下次运行最容易翻转的位置。整个回放对着已录好的上下文进行，不发起新的工具调用，不与环境交互，全程黑盒，不读 logits、不看模型内部，也不需要真值标签，因此可以直接用在无法重放任务的生产流量上。被标记的步骤随后由 ALTK-Evolve 生成一致性指南，比如数笔记里的复选框标记时，用按行锚定的正则匹配取代朴素的子串计数。指南注入上下文后，演示里此前五次运行三比二分裂的任务做到了五次全部一致。

在 AppWorld test_normal 的 168 个任务上，每个任务只用一条基线轨迹生成指南，再用 5 次全新运行检验。Pass^5 从 53.0% 升至 69.0%，Mean@5 同步从 77.4% 升至 81.0%，一致性差距从 24.4 个百分点收窄到 12.0 个百分点，接近砍半，此前表现摇摆的任务里近三分之一变成次次通过。中等难度任务提升 22.9 个百分点，难任务提升 14.3 个百分点，平均准确率在每个难度档都没有下降。指南也迁移得动，用于同一场景的相似任务时 Pass^5 仍提升 13.0 个百分点，只比同任务低 3 个百分点。换到基线低得多的 gpt-oss-120b 上，相似任务的提升（8.7 个百分点）反超了同任务的 6.0 个百分点。

对准备上线智能体的团队，作者的建议很直接。榜单之外同时报告 Pass^k，即便 k=3 也能暴露此前不知道的差距；预期差距随难度上升，最难档位的单个平均数最有迷惑性；遇到差距先做诊断再谈换模型，能力与一致性是互相独立的两条轴，更强的模型抬高 Mean@k，未必收窄差距。全部代码在 github.com/AgentToolkit/altk-evolve 开放，完整方法论见 arXiv 技术报告。

🔥 为什么今天值得看：传统机器人操作要针对特定任务和环境专门训练，换一个任务就得重新来。AGP 把规划与执行交给通用智能体在运行时现场完成，靠推理和编程直接驱动机器人，论文用积木搭建等多个真实任务验证了这条零训练路线可行，通用智能体的推理与编程能力因此被带进与物理世界的连续交互。

一篇题为 Agent as Policy for Robotic Manipulation 的论文提出了 AGP 框架，把任务规划和执行全部交还给通用智能体本身。给定一个任务和机器人接口，智能体自己解读视觉证据、编写可执行程序、发出运动指令，再根据物理结果修正下一步动作，全程无需针对任何任务或环境做专门训练。研究团队在多类真实操作任务上验证了这条路线，覆盖精度操作、动态动作和可变形物体三类场景，具体包括从人类视频学习组装、依据目标图像搭积木、骰子翻转、定向投掷和双臂毛巾折叠。其中三个积木搭建配置的成功率分别为 100%、100% 和 80%。论文认为，这为通用智能体充当机器人策略建立了一条路径，让运行时推理、编程与物理交互连成一个闭环。

开源编排工具 Ordewell 把编码目标变成可编辑任务计划

这是什么：一个叫 Ordewell 的开源工具在 Hacker News 上首发。它接收一句大白话写的目标，先生成一份排好顺序的任务清单，每个任务指定用哪个编码 agent、用哪个模型来干，清单在动手之前可以随意修改，确认后再交给各 agent 逐项执行并自动验收。项目放在 GitHub 开源，处于早期阶段，目前 88 star、91 次提交。
🔥 为什么今天值得看：编码 agent 接到大目标时，计划通常锁在它自己的内部状态里，人看不见也改不了，方向跑偏只能整轮推倒重来。Ordewell 把计划摊开成一份可编辑的文件，花钱之前就能审查和调整，每个任务还能按轻重配不同价位的模型，贵的留给安全重构，便宜的拿去改文档。验收以输出中的完成标记为证据，退出码只留作诊断参考，避免只凭 agent 的一面之词认定任务完成。想把多个编码 agent 组合起来干大活的人，拿到了一套 npm 就能装的现成骨架。

GitHub 上出现了一个新的开源项目 Ordewell，思路是让使用者先用大白话描述目标，一个只读的规划 agent 研究仓库、追问模糊之处，然后产出一份排好顺序的任务计划。每个任务自带 runner、模型、思考强度与模式，安全重构可以配强模型，README 更新可以换便宜模型。这份计划在花 token 之前可以随意改写，增删任务、重连依赖都不会丢掉已完成的工作。确认之后，Ordewell 为每个任务启动真实的编码 agent 会话，按依赖图执行，独立任务默认三路并行。任务是否完成由 VerdictEngine 依据输出中的完成标记判定，退出码只留作诊断证据。项目以 Show HN 形式首次公开，拿到 47 points，仓库已有 88 star 和 91 次提交。

MIT教授1400万美元下注，宣称自然语言才是企业软件新源码

这是什么：一家名为 G5 Labs 的创业公司走出隐身状态，发布云端平台 G5，同时宣布完成 1400 万美元种子轮融资。创始人是 MIT 教授 Tim Kraska。G5 想把企业用文字写下的需求、决策和规矩整理成一张计算机可读的语义图，再让软件代码从这张图里自动生成，按照官网的说法，改动意图，代码就重写自己。
🔥 为什么今天值得看：企业里写代码的主力正在变成 AI agent，多家 agent 同时改一套系统时，代码合并经常出现无谓冲突，几十万行的变更也让人没法逐行审查，Kraska 举例称其一名工程师一周内就提交了 30 万行代码变更。G5 把审查与合并挪到含义层面来做，一个人要求按钮必须是红色，另一个人对颜色没有表态，系统判定语义兼容后自动合并，两条互相矛盾的认证要求才会触发需要人来裁决的真冲突。如果这条路走得通，产品和合规人员可以直接检查软件该做什么，开发者则转向架构决策，去管理一群虚拟员工。

AI 编码 agent 正在成为企业软件的主要作者，Anthropic 内部已有 80% 的生产代码由它们写成。多家 agent 同时改一套系统时，代码互相冲突的问题随之而来。MIT 教授 Tim Kraska 创办的 G5 Labs 今日走出隐身状态，拿到 1400 万美元种子轮，首款产品 G5 把企业的业务需求、架构决策和合规政策整理成一张结构化语义图，公司称之为 system ontology，代码由这张图派生。Kraska 在采访中的表述是：「自然语言加上一层结构，也就是我们所说的 system ontology，就成为新的源码，Python、Rust 等代码由它派生。」这个思路与 spec-driven development 相似，也与 Palantir Ontology 相近，但 G5 的宣称更激进，语义图要与实现代码持续双向同步，并充当软件反复重新生成的源头。竞争环境并不宽松，Amazon Kiro 和 GitHub Spec Kit 已把规格驱动与代码核对做进产品。疑点也要摆明，G5 网站所称的在多个强监管行业落地、数百万行遗留代码完成转换，均为公司自述，VentureBeat 未能独立核实，早期客户因保密协议全部匿名，约九成集中在金融业。融资只说明资本愿意赌这个方向，语义图与代码在大规模持续变动的企业代码库上能否长期保持一致，仍是最硬的问题。

Agent 长任务失败先别怪模型，Scale AI 用迭代搜索把归因 F1 提升超四成

这是什么：Scale AI 团队 9 月 11 日在 arXiv 发表论文，提出名为 Continual Search 的迭代诊断框架。它把大模型裁判的一次性下结论改成多轮提示，每一轮都催促裁判质疑自己刚给出的失败原因，把尚未查看的证据继续翻出来检查，直到没有未解线索。团队同时发布配套基准 MegaRCA-Mix，用 50 条人工标注的失败试验专门检验超长执行轨迹下的归因能力。
🔥 为什么今天值得看：agent 承接的任务越拉越长，失败日志的体量已经超出人工复盘的承受范围，自动归因判不准，失败信号就无法变成具体的修复动作。这篇论文把准确率低的原因归结为裁判过早下结论，用可迭代的搜索流程换来了实打实的准确率，GPT-5.5 的 F1 从 0.349 升到 0.498。同族低配模型反超高配的结果进一步说明，调试长程 agent 时改进查证方法比堆模型规模更划算。

AI agent 接手的长时程任务会产生海量执行日志，人看不过来，交给大模型当裁判又常常判错。Scale AI 团队 9 月 11 日发布在 arXiv 的论文把病灶定位在裁判的工作方式上。现有自动根因归因方法多靠一次性的 LLM 判断，裁判只读了轨迹的一部分就锁定一个貌似合理的诊断，长轨迹里剩下的关键证据从未被打开。论文提出的 Continual Search 把诊断改成多轮迭代，每一轮都催促裁判质疑自己上一轮的答案，继续搜查尚未审视的证据，直到没有未解的诊断线索。为了检验效果，团队同时发布 MegaRCA-Mix 基准，用 50 条人工标注的失败试验考察超长轨迹下的归因，单条轨迹中位 286K token。在这套基准上，GPT-5.5 的归因 F1（综合衡量诊断准确程度的常用评分）从 0.349 升到 0.498，提升超过 40%，方法在四个既有 RCA 基准和多个模型家族上也取得一致改进。团队还发现，同一模型家族内低配模型借助这套搜索流程能反超高配模型，搜索的有效性压过了模型规模本身。

Google 给 Agent 加装行车记录仪，三项防御搬进运行时

这是什么：Google 开发者博客 9 月 15 日发布零信任 AI Agent 教程的第二篇。第一篇教开发者在写代码和构建的阶段把安全检查写进程序，第二篇换成在 agent 运行的过程中管安全，靠平台提供的三项现成防御，在 Gemini Enterprise Agent Platform 上启用即可。文章用第一篇出现过的退款 Agent 重新演示了运行时的治理效果。
🔥 为什么今天值得看：企业把 agent 放进生产环境后，攻击发生在运行当中。提示注入随时可能出现，一次工具调用在语法上挑不出毛病，放到业务规则下就是越权操作，恶意指令还能拆成多轮对话慢慢喂进来，这类形态在构建时检查里根本遇不到。只做上线前检查，相当于汽车只做年检，路上发生什么没人管。运行时治理把判断时机挪到每次调用发生的当下，按业务规则决定放行与否，攻击才有机会在造成损失前被拦下。策略由安全管理员在平台层统一调整，业务规则变化时不用等开发者改代码重新发版。

9 月 15 日，Google Developers Blog 更新零信任 AI Agent 系列第二篇，作者为 Eric Dong 与 Shubham Saboo。第一篇在构建阶段做静态安全检查，这一篇把治理搬到 agent 运行的过程中，核心主张是安全判断要看意图，只核对语法挡不住真实攻击。整套方案落在 Gemini Enterprise Agent Platform 上，由三项平台托管防御组成。Model Armor 在边缘筛查进入的提示词；工具调用发生时，Semantic Governance Policies 依据业务规则评估这次调用的意图该不该放行；Agent Anomaly Detection 盯住多轮对话，捕捉跨多轮组合而成的攻击。三项运行时控制与第一篇的构建时控制一一对应，合成构建时加运行时的纵深防御。演示沿用第一篇的退款 Agent，展示同一场景进入运行时后的治理过程。安全策略改由安全管理员在平台层动态执行，开发者无需在代码里硬编码。
