Anthropic未发布模型推进黎曼猜想，60个子代理协作

这是什么：TechCrunch 报道，Anthropic 一款尚未发布的模型在黎曼猜想上取得边界进展，把已知满足猜想的解的下界显著推高。模型协调 60 个子代理，测试 650 种思路，消耗约 3100 万个输出 token。黎曼猜想仍未被解决。
🔥 为什么今天值得看：这次结果展示了研究代理如何把一个数学问题拆成多条探索路线，再由不同代理负责提出想法、检查论证和整理论文。结果还经过 Lean 形式化验证与两名 Anthropic 内部数学家确认，说明 AI 数学研究开始出现可追踪、可检查的协作链条，但离独立数学审查完成还有距离。

黎曼猜想已经悬而未决超过 150 年，它试图解释素数如何分布，也是数学界最著名的未解问题之一。TechCrunch 报道，Anthropic 宣布一款尚未发布的模型在这个问题上取得了进展，把目前已知满足猜想的解的下界显著推高。这个结果距离完整证明仍然很远，数学界为通用证明设置的 100 万美元奖金也仍未有人领取。

这次报道最有信息量的部分，在于模型怎样组织探索。一名数学训练并不深的 Anthropic 员工提示模型认真尝试证明黎曼猜想，随后让它连续运行了约一天半。模型没有只给出一段答案，它测试了 650 种不同思路，协调 60 个子代理，总共消耗约 3100 万个输出 token。对普通读者来说，可以把这些子代理理解成同时尝试不同路线的一组研究助手，模型负责分配任务，再把想法收回来检查。

论文脚注给出了这 60 个角色的分工。2 个子代理提出关键数学想法，13 个为它们补充思路，30 个尝试提出新想法但没有成功，13 个负责检查论证是否正确，最后 2 个协助撰写论文初稿。这个安排让一次探索留下了可追踪的过程，读者能看到哪些代理提出了想法，哪些代理承担了验证工作。

验证也分成了两道关。Anthropic 的两名内部数学家确认了这一发现，研究结果随后用开源证明助手 Lean 做了形式化验证。Lean 可以把数学论证写成机器能够检查的形式，减少只凭一段自然语言说明来判断正确性的风险。它仍然不能替代数学共同体的审查，尤其不能把公司内部数学家的确认直接等同于独立复核。

这条消息展示了一种新的研究代理形态。模型承担的不只是回答问题，还会提出多条候选思路，调度其他代理，再让专门的角色检查论证并整理成论文。今年，AI 模型已经参与解决一些 Erdős 问题，OpenAI 的 Astra 模型公布过 10 项内部证明结果，Anthropic 的另一项工作也曾给 Jacobian 猜想找到反例。黎曼猜想这次仍是边界推进，价值在于它把多代理探索、形式化工具和人工确认放进了同一条链条。

数学界对这条路并没有形成统一看法。TechCrunch 提到，6 月一份由多位知名数学家签署的公开声明担心 AI 会削弱数学研究中由具体作者署名、承担发现责任并对正确性负责的传统标准。菲尔兹奖得主 Timothy Gowers 则提出，未来定理与数学家之间的联系或许会变得更复杂，也可能带来积极变化。眼下更稳妥的判断是把这项成果看作一条经过初步验证的新线索，等独立数学家完成审查后，再决定它在数学上究竟站得多稳。

加密推理痕迹也会泄密，研究重建704个隐私工件

这是什么：一项针对专有大模型 API 的安全研究展示了加密推理块的解码方法。研究者从 GitHub 和 Hugging Face 的 6708 条公开 agent 轨迹中重建出 315320 个推理块，并在 OpenAI、Anthropic 和 Google 模型的材料中恢复出 704 个隐私工件。
🔥 为什么今天值得看：隐藏推理块可能携带最终答案没有显示的凭据和个人信息。研究中有 64 个隐私工件只出现在推理块里，说明只检查用户可见输出，可能无法发现模型处理过的敏感内容。加密形式本身也不足以单独证明这些内容不会被重新解码。

模型 API 返回给用户的答案之外，还可能保留一段用户看不见的推理痕迹。它通常以加密块的形式存在，外部读者无法直接阅读。最近一项名为《Stealing Reasoning Traces from Proprietary LLM APIs》的研究展示了一种解码方法，研究对象包括 OpenAI、Anthropic 和 Google 的前沿模型。研究者没有声称所有生产 API 都已经失守，演示的材料来自公开可取得的 agent 轨迹，重点是检验这些加密推理块能否被还原，以及还原后会暴露什么。

研究者从 GitHub 和 Hugging Face 收集了 6708 条公开的 agent 轨迹。这些轨迹由 Claude、GPT 和 Gemini 模型产生，里面仍然保留着经过签名的加密推理块。研究团队把解码流程应用到这些块上，一共重建出 315320 个推理块。在 OpenAI、Anthropic 和 Google 模型的演示中，解码出的推理内容数量与 API 报告的隐藏思考 token 数量高度吻合。这个对应关系让研究者能够把攻击从单个示例推进到大规模公开材料。

隐私泄露的数字更直接。研究者排除了基准测试，查看真实用户会话后，恢复出 704 个不同的隐私工件。这里的工件可以理解为会话中出现过的敏感信息，包括 62 个 API 密钥、33 个密码、24 个访问令牌和 30 个个人邮箱地址，也包括姓名、邮寄地址、内部 URL 以及其他技术标识符。704 个工件里，有 64 个只出现在隐藏推理块中，用户可见的会话输出里完全没有它们。

这组结果把安全边界从“用户能不能看到答案”推向了“模型在生成答案时还保存了什么”。如果凭据或个人信息只出现在隐藏过程里，常规的可见输出检查就可能漏掉它。加密外观也不能单独证明数据已经安全，系统还要考虑推理块如何生成、签名、保存、分享，以及不同模型或用户之间能否重新处理这些内容。研究没有交代所有专有 API 的生产配置，也没有证明每一种接口都存在同样的缺陷，所以这些数字应当被理解为公开轨迹上的实证结果和风险演示。

Hacker News 上的争论集中在“stealing”这个词是否准确。有人认为，研究者只是从模型输出中提取了信息，把它称为偷窃带有道德化色彩；有人则认为，未经授权取得隐藏数据，至少可以讨论侵权或未授权访问。评论中还有人指出，自己按 token 付费，模型的思考过程本来就是服务的一部分。这个争论没有改变研究报告列出的技术事实，但它提醒读者分开看两件事。研究展示的是加密推理块可以被解码，并且其中包含凭据与个人信息。至于这种行为应当使用什么法律或道德称呼，HN 讨论并没有形成安全共识。对 API 使用者来说，优先级更实际，任何会被模型读到的密钥、密码和个人资料，都不应因为最终回答没有显示它们，就被当成已经脱离风险。

Google的Gemini独立应用，月活跃用户已经超过10亿。Google CEO Sundar Pichai在X上宣布，这款应用成为公司增长最快的产品之一，也是Google第14个达到10亿用户规模的产品。这个数字很大，但真正需要先看清的是统计对象。

这也解释了为什么不能只拿一个10亿去做简单的公司排名。OpenAI的ChatGPT在6月达到10亿月活，Google这次披露的是Gemini应用最近超过10亿月活，两个数字的发布时间不同，产品渠道和披露口径也需要分别理解。把它们并列看，可以看到头部AI助手正在接近同一个用户规模；把它们当成同一时点、同一统计体系下的严格名次，就超出了材料能支持的范围。

这条消息最有价值的部分，是Google同时披露了规模和行为。十亿月活能说明Gemini已经进入大规模消费产品行列，63%的语音使用率、每天超过1.5亿张图像以及超过1亿的iOS活跃用户，则提供了产品形态和平台分布的线索。材料没有给出留存时长、付费转化或这些数字的外部审计结果，所以它更适合被读作Google对产品使用情况的公开披露，而不是一张完整的竞争成绩单。

Metals v2开源，2600万行JVM代码快速导航

这是什么：Databricks 开源了 Metals v2，这是面向大型 Java 和 Scala 代码库的语言服务器，可接入 Cursor、VS Code 和 Neovim。它针对约 2600 万行的 monorepo 重做了启动、索引、编译器管道和构建集成，让轻量编辑器在构建同步前也能开始做工作区导航和搜索。
🔥 为什么今天值得看：大型 JVM 仓库的编辑器体验常被启动和构建同步拖慢。Metals v2 把工作区索引与交互式编译器放到编辑器的早期路径，把依赖、生成源文件、测试发现和调试启动器等信息留给按需的 BSP 查询。对使用 AI 代理编写代码的团队，工程师仍要快速定位代码和检查修改影响，这类低延迟的代码理解能力会直接影响轻量编辑器是否能承担日常 JVM 开发。

Databricks 开源了 Metals v2，一款面向大型 Java 和 Scala 代码库的语言服务器。它可以接入 Cursor、VS Code 和 Neovim，目标是在轻量编辑器里提供跨仓库的代码导航、符号搜索和诊断能力。Databricks 用一个约 2600 万行的 monorepo 来检验这套方案。

这件事和 AI 编码的关系很直接。Databricks 在文章中说，公司大部分代码现在由代理编写。工程师仍然需要打开代码、理解调用关系、确认修改影响，只是编辑器首先要解决的任务变了。启动成本、反馈速度和对代码库的定位能力，成为代理参与开发时的基础条件。Databricks 从 2025 年 5 月开始把日常编辑器流程向 Cursor 集中，Metals v2 负责补上 Scala 和 Java 大型仓库的能力缺口。

Metals v2 的第一层改造是 build-free 的 mbt 索引。它用 git ls-files --stage 发现工作区文件，再用 Git blob OID 判断哪些索引条目可以复用。每个条目只描述一个源文件，记录包声明、定义位置，以及用于筛选引用关系的紧凑 Bloom filter。这样，编辑器在等待构建同步前，就能回答一批最先需要的问题，包括工作区符号搜索、跨仓库跳转到定义，以及部分引用和实现查找。这个索引只覆盖工作区代码，跳转到外部依赖或生成代码不在它的范围内。

第二层是编译器管道。Scala 使用 presentation compiler，把 2400 万行代码放进一个编译器实例中，并用 fallback 和 precise 两种模式处理不同阶段的信息。打开的文件可以得到更精确的诊断，未打开的源文件会被裁剪成保留类型签名的 outline，减少方法体带来的检查成本。Java 则直接基于 javac API 实现语言服务器功能，并用改造后的 Turbine 头编译器生成适合编辑器的类路径。

第三层是 metadata-first 的 BSP 构建集成。BSP 仍然存在，但主要用来查询依赖、生成源文件、测试发现和调试启动器等构建元数据。日常诊断不再把构建服务器放在编辑器的关键路径上，Bazel 也不会在后台自动启动。用户明确请求后，系统才按文件或目录同步需要的目标，避免大型仓库的后台同步抢占构建锁。

Databricks 给出的内部数据说明了这套设计的目标。生产环境中，TTII，也就是语言服务器启动后编辑器变得可用所需的时间，p50 为 8.7 秒，p90 为 36.7 秒。覆盖 290 万个工作区符号的模糊搜索，p50 为 10 毫秒，p90 为 95 毫秒。Scala 诊断在 2400 万行代码上达到 p50 0.9 秒、p90 8.9 秒，跨整个仓库的跳转到定义达到 p50 7 毫秒、p90 575 毫秒。文章还给出 Java 管道的基准，Turbine 单线程每秒处理接近 100 万行 Java，javac 的分析阶段在测试中接近每秒 10 万行。

这些数字来自 Databricks 的生产环境和基准测试，不能直接当成所有仓库的承诺。开源版本也不包含 Databricks 内部为自家 Bazel 规则编写的 BSP 服务器。Metals v2 当前更适合被理解为一套针对超大型 Java 和 Scala 仓库重新划分启动路径的基础设施方案。它把最常用的工作区理解能力提前交给索引和编译器，再把依赖与构建细节留给按需同步。对 AI 编码时代的编辑器来说，这种取舍比堆叠更多补全按钮更接近底层需求。

Anthropic将为Claude生成文本和文件加入水印

这是什么：Anthropic确认，Claude等模型生成的文本和文件将加入水印。8月2日之后发布的新模型会从发布时自动支持，旧模型也会逐步补齐。文本水印会随复制粘贴传播，文件则采用C2PA开放标准。
🔥 为什么今天值得看：AI内容标识被放到了模型输出层，其他系统有机会识别内容是否由AI生成或编辑，这为欧盟透明度要求提供了技术入口。水印仍可能被编辑移除，Anthropic也没有说明需要多少编辑才能清除，所以它不能单独证明内容一定来自AI。

Anthropic确认，Claude等模型生成的文本和文件将加入水印，以符合欧盟相关规定。公司是在更新后的帮助页面中说明这项安排的。欧盟人工智能法案的透明度代码已于8月2日生效，要求人工智能公司以其他系统能够识别的方式标记人工智能生成或编辑的内容。

按Anthropic的说法，8月2日之后发布的所有模型，从发布时就会自动具备文本和文件水印能力。已经发布的旧模型也会逐步获得支持。这个表述很关键，它描述的是一项正在扩展的计划，并不等于所有Claude产品已经同时完成部署。水印会在模型层面加入，所以无论文本来自Claude平台API、Claude、Claude Code、Claude Cowork还是Claude Tag，原则上都适用。

文本水印和文件标记不是同一件事。文本水印直接成为文本的一部分，用户复制粘贴到其他位置时，水印会随文字一起传播，经过部分编辑后也可能保留。文件则采用C2PA开放标准。对普通用户来说，可以把它理解成两条不同的标记路径：一条跟着可复制的文字走，另一条附着在文件使用的标准里。原文没有给出C2PA的具体实现细节，也没有说明每种文件的展示方式。

这项变化的价值在于，内容来源标识开始被放进模型输出环节，而不只是交给发布平台事后判断。其他系统如果能够识别这些标记，就有机会在内容流转时知道它曾由AI生成或编辑。对新闻发布、企业文档和公共平台来说，这可能为透明度要求提供一个技术入口。

水印也不是一张不可撕下的标签。Anthropic承认，目前还不清楚用户需要进行多少编辑才能移除文本水印，公司已经被要求进一步澄清。复制粘贴可以让标记继续传播，但编辑操作会不会削弱或清除它，取决于具体处理方式。它能帮助系统识别一部分来源，却不能单独证明一段文字一定来自AI。

Anthropic之外，Black Forest Labs、Google、Meta、Microsoft、OpenAI和Synthesia也承诺遵守欧盟这套代码。原文还提到，Suno上周宣布将标记平台生成的音乐，Substack上个月与Pangram合作标记AI生成内容。平台开始密集部署标识功能，监管要求是一条推动力，用户对AI内容的反弹也是另一条推动力。接下来真正要看的，不只是模型是否加上水印，还包括标记在复制、编辑和跨平台传播后还能保留多少。

LTX-2.5开放权重上线，本地GPU降低视频试错成本

这是什么：LTX发布了LTX-2.5，一款面向视频生成、实时应用和物理AI的开放权重模型。它针对NVIDIA RTX GPU和DGX Spark做了本地推理优化，提供Hugging Face权重、GitHub代码、文档、ComfyUI原生集成和LTX API。
🔥 为什么今天值得看：开放权重和本地GPU让创作者可以把视频生成放到自己的机器上，减少对云端按次计费或额度的依赖。原文还把原生多镜头、角色和场景一致性、LoRA快速微调列为使用路径，创作者可以围绕一个需求批量试多个版本。不过显卡、显存和实际配置仍决定本地运行是否可行。

LTX发布了LTX-2.5，一款面向视频生成、实时应用和物理AI的开放权重模型。MarkTechPost的报道把重点放在本地运行上：LTX-2.5针对NVIDIA RTX GPU和DGX Spark做了优化，目标是降低显存需求，让创作者可以把生成环节放到自己的机器上。模型同时提供Hugging Face开放权重、GitHub代码、文档、ComfyUI原生集成和LTX API，使用路径从本地部署到托管生成都有对应入口。

对视频创作者来说，变化不只是多了一个模型名称。原文把LTX-2.5的原生多镜头生成列为主要更新，它可以把一段完整序列作为一次输出处理，并尝试保持角色、场景和声音在不同镜头之间一致。LTX还称，新扩散视频解码器会减少高速运动画面中的视觉伪影，Gemma 4语言骨干和提示增强器则用于处理更复杂的多主体描述。这些能力如果在实际使用中成立，创作者就可以先在ComfyUI里生成多组方向，再用LoRA做快速微调，固定某个角色或视觉风格，减少每次从头试错的成本。这里的“成立”仍需要独立样本验证，当前材料主要是发布方信息的转述。

本地运行带来的实际价值，在于视频生成可以从按次付费的云服务转成一次性占用本地算力。原文称，额外生成不会产生按片计费或额度消耗，创作者可以围绕同一个需求批量尝试不同版本。对短视频和广告团队，这种方式可能让小团队更容易连续测试多个开头、不同市场的本地化版本和一周内的素材更新。不过，机器本身的显卡、显存和运行配置仍是门槛。LTX的材料说它降低了VRAM需求，也提到从数据中心GPU到Mac的运行范围，但没有给出完整的最低显存、具体RTX型号或不同设备上的生成速度，不能把“本地可用”直接理解成任何电脑都能顺畅运行。

速度数据也要按来源看。LTX公布的图像转视频基准显示，在2块NVIDIA GB200上生成10秒视频需要6.8秒，通过LTX API需要23.7秒；MarkTechPost转述的对照表中，所列封闭模型耗时为52至398秒。报道据此给出了比最近封闭替代品快7.6倍、比最慢者快约58倍的说法。这组数字来自LTX发布的基准和单篇MarkTechPost报道，测试硬件、提示词和比较条件并不构成对所有消费级RTX设备的性能承诺，也没有独立评测来确认画面质量和一致性。

许可证同样需要留出边界。原文称，年经常性收入低于1000万美元的组织可以免费使用这些权重，同时模型也通过Hugging Face、ComfyUI和API提供。报道没有进一步解释高于这一收入门槛的授权费用，也没有把所有商业使用条件逐项列出。开放权重给了团队自选硬件和定制的空间，实际部署前仍应按自己的组织收入、用途和许可证条款核对。

MarkTechPost的标题和正文使用了“整套视频制作栈放在一张桌子上”等宣传性表达，原文也把输出描述为接近制作完成。当前没有评论区讨论或独立用户反馈，报道来源只有MarkTechPost。更稳妥的读法是把LTX-2.5看作一条值得试用的本地视频生成路径，重点观察自己的显卡能否承受、ComfyUI接入是否顺手，以及多镜头和LoRA效果是否符合实际项目要求。
