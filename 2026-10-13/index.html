Meta发布首批前沿模型Muse Wonder，最强版锁进订阅墙

这是什么：10 月 12 日，Meta 超级智能实验室发布公司首批前沿模型 Muse Wonder 与 Muse Wonder Full：Wonder 经 Meta Model API 商用，定价 $4/$20 每百万输入/输出 token；更强的 Wonder Full 不上 API，仅向 Muse Code 订阅用户开放（$50/$200 月）。主打长时程智能体的 active memory 能力，第三方 Artificial Analysis 智能指数 56 与 Claude Sonnet 5.5 持平。两款模型均不开放权重。
🔥 为什么今天值得看：其一，Meta 在重组约 14 个月后重回前沿竞争的边缘位置，且这次有独立评测而非仅厂商自宣背书；其二，分发策略是真正的新东西——把最强模型做成订阅护城河而非 API 商品，直接改变企业买家的采购与部署决策；其三，Llama 曾定义开放权重时代，如今两款旗舰闭源，意味着 Meta 不再是开源阵营的前沿模型供给方，开放生态的前沿供给进一步集中于其他厂商。

10 月 12 日，Meta 超级智能实验室（MSL）发布公司第一批真正意义上的前沿模型：Muse Wonder 与 Muse Wonder Full。扎克伯格 2025 年 8 月重组 Meta AI 部门、设立超级智能实验室并请来 Alexandr Wang 领导，约 14 个月后，Meta 第一次真正回到前沿模型牌桌——此前它只拿出过轻量级的 Muse Spark 和 Muse agent，一直避开 OpenAI、Anthropic 式的旗舰级发布。

两款模型定位拉开档次：Wonder 走商业 API，模型标识 muse-wonder-1.0；更强的 Wonder Full 不上 API，只向 Muse Code 编程助手的付费订阅用户开放。两者也都用于驱动 Muse agent。

基准：第三方给 56 分，与 Sonnet 5.5 打平

第三方评测机构 Artificial Analysis 给 Wonder Full 的智能指数为 56，与 Anthropic Claude Sonnet 5.5 持平，高于 GPT-6 Astra、Gemini 4 Argon 和 Claude Fable 5.1（三者均为 53），仅低于 Claude Opus 5.5 的 58；标准版 Wonder 为 52，比 GPT-6 Astra 低 1 分。这是独立评测结果，不是 Meta 自家合成分数。

Meta 模型卡（10 月 12 日，最大推理力度）给出的细分图景互有胜负：长时程编码 SWE-Marathon 上 Wonder Full 拿 57.5，明显领先 Opus 5.5 的 46.3 和 GPT-6 Astra 的 42.5；法律任务 Harvey LAB-AA 上 13.1 对 8.6/4.2 领先；但 Terminal-Bench 4.0-AA（57.1 对 59.1/59.6）和 HealthBench Pro（62.3 对 65.3/65.6）落后于两个对手。模型卡混合了自测、厂商提供与第三方结果，部分软件工程对比使用了不同编码工具，方法学需要打折看待。

定价与分发：$4/$20，旗舰锁进订阅

Wonder 定价为每百万输入 token 4 美元、输出 20 美元，缓存输入 0.20 美元，与 Claude Opus 5.5 完全相同；约为 GPT-6 Sol、Sonnet 5.5、Gemini 4 Argon 介绍价合计的两倍，低于 $10/$50 档的 GPT-6 Astra 与 Fable 5.1。API 兼容 OpenAI/Anthropic 接口，限流为每分钟 3000 请求、400 万 token，上下文窗口约 100 万，联网搜索另收每千次 2.50 美元。

Wonder Full 未公布按量付费价格，只能通过 Muse Code 订阅获得：Power Usage 档每月 50 美元（用量为 Everyday 档的 20 倍），Maximum Usage 档每月 200 美元（80 倍），均有用量上限。想在自有生产系统里部署最强版本，目前做不到。

active memory：差异化主张

模型面向长时程智能体场景，Meta 提出两个核心能力：active memory（跨对话保留、检索并整合用户的个人与工作上下文）和 active focus（遇到障碍时修正计划、探索替代路径、在重大动作前请求许可）。Meta 自测在 MemoryBench 记忆基准上超过 Fable、Opus 与 Astra。研究科学家 Kavya Kopparapu 在发布视频中介绍，团队花了大量精力让模型能在数天、数周、数月乃至更长时间里记住对用户重要的事。

值得注意的是，这套能力依赖跨工作流持续留存信息，而 Meta 的数据政策分为 Standard 模式（内容不用于训练，按量付费 API 仅提供此模式）与 Contributor 模式（默认用于训练，可关闭但仅对未来提交生效，且条款禁止提交机密、敏感或个人信息）。记忆能力与隐私配置能否兼容，是企业买家要自己算的账。

战略信号：告别开放权重

更具符号意义的是分发方式。Llama 系列曾让"可下载权重、自建基础设施运行"成为 Meta 的标签，而两款 Wonder 均不提供公开可下载权重，不能自托管或私有部署——对比之下，较小的 Muse Glimmer 反而以 Apache 2.0 开源。从开放旗帜到闭源 API 加订阅墙，Meta 这次的商业转身相当彻底。Meta 在博客中称这两款模型是"扩展阶梯上的下一步，迈向个人超级智能的一大步"；扎克伯格则在 X 上称 Wonder 是比 Muse Spark 大得多、先进得多的一类模型。

阿里 QwenGyre：超长时程智能体 RL 训练最高提速 1.85 倍

这是什么：阿里巴巴 Qwen 团队 10 月 12 日发布 QwenGyre，一个面向超长时程（XLong-horizon）智能体的弹性在线强化学习训练框架。定位是训练框架而非模型，配套 arXiv 论文，但论文未附公开代码。它通过未经修改的黑盒 harness 训练编码智能体（基准全部使用 Claude Code 2.1.220），针对运行数小时、token 量接近百万（实测约 70 万）的 rollout，在相同评测分数下取得对 Async 1.38-1.78 倍、对 Colocate 1.21-1.85 倍的加速。
🔥 为什么今天值得看：长时程智能体的 RL 训练有一笔算力账：Colocate 模式下训练要等最慢的 rollout，GPU 在长尾里空转；Async 模式下 rollout 与训练各占固定 GPU 池，忙闲不均时无法互借。当单次 rollout 以小时计，浪费被成倍放大。QwenGyre 把 GPU 变成可在两种角色间动态切换的弹性 cell，又把分支式执行历史压成有界训练样本——它展示的是训练基础设施如何跟上智能体任务的时长爆炸，这是各家模型发布背后少有人算的隐形成本。

发生了什么

阿里巴巴 Qwen 团队发布 QwenGyre，一个面向超长时程（XLong-horizon）智能体的弹性在线强化学习训练框架。关键定位：它是训练框架，不是模型，配套 arXiv 论文，但论文未附公开代码。

它训练的是运行数小时、token 量接近百万（实测约 70 万）的智能体 rollout，通过未经修改的黑盒 harness 进行——全部基准使用 Claude Code 2.1.220，GPU 预算相等、staleness 匹配。整体架构上 Megatron 负责训练，SGLang 服务 rollout，GPU 型号未披露。

为什么重要

长时程智能体的 RL 训练有一笔没人爱算的账。Colocate 模式下，训练要等最慢的 rollout 结束，GPU 在长尾里空转；Async 模式下，rollout 和训练各占固定 GPU 池，忙闲不均时无法互借。单次 rollout 以小时计时，这些浪费被成倍放大。

QwenGyre 的回答是两个机制：让 GPU 在 rollout 和训练之间弹性切换，以及把分支式的智能体执行历史压成有界训练样本。在相同评测分数下，它对 Async 提速 1.38-1.78 倍，对 Colocate 提速 1.21-1.85 倍。

弹性调度器

GPU 被划分为共享训练布局的 cell。核心 cell 持有权威权重和优化器状态，卫星 cell 后加入训练。调度器跟踪 rollout 水位线（排队与运行中的执行数）：随着执行完成，cell 在“剩余 cell 仍能服务所有在跑任务”的前提下切换去训练；模型调用经代理重定向，harness 继续运行无感知。

工程细节上，KV-cache 块在重路由时经 RDMA 迁移以减少前缀重算；卫星 cell 通过 Mooncake Transfer Engine 拉取核心权重、加入进行中的批次；流式训练让 cell 在数据就绪时认领微步。角色切换平均耗时 8.52 秒（rollout→训练）和 3.46 秒（训练→rollout）。

轨迹处理器

Claude Code 这类 harness 会压缩上下文、派生子智能体、重试，一次执行是分支树而非单条轨迹，展开每条路径会重复共享前缀、推高训练成本。QwenGyre 的代理用 TITO（token-in, token-out）记录精确 token ID 与行为 log 概率，把调用存为前缀共享轨迹树，再做四件事：

  • 有界采样：每次执行最多保留 5 条轨迹，按主轨迹 > 主摘要 > 子智能体 > 子智能体摘要排序；5 条上限在匹配未封顶训练分数的同时，削减 25.2% 前向-反向耗时
  • 部分计分：超时执行仍按其保留的工作区计分；评估器失败被排除，绝不计为零奖励
  • 去重：共享目标只算一次，只训练策略生成的 token
  • 公平加权：损失在每次执行内取平均，多分支不给这次执行灌水

训练算法是改造版 GSPO，每组 16 个 rollout。

实测数字

Qwen 3.6 122B（24-32 节点）：

  • NL2RepoBench（48 步）：对 Async 1.42-1.53 倍，对 Colocate 1.36-1.47 倍
  • DeepSWE（24 步）：对 Async 1.569-1.572 倍，对 Colocate 1.610-1.824 倍
  • TerminalBench（24 步）：对 Async 1.383-1.430 倍，对 Colocate 1.809-1.849 倍

Qwen 3.8 2.4T（192 节点，4 个 cell 各 48）：NL2RepoBench 48 步，对 Async 1.78 倍、对 Colocate 1.21 倍；总耗时 75.42 小时，对照 Async 134.55 小时、Colocate 91.47 小时；通过率从 52.48% 升至 58.54%。

限制与同行对照

论文明示了下限：2.4T 模型上对 Colocate 只有 1.21 倍，因为该设定下许多查询接近超时。更大的现实门槛是可得性——论文未附公开代码，许可证未披露。对照之下，veRL（字节跳动 Seed + 社区，Apache-2.0）、AReaL（清华 IIIS + 蚂蚁，Apache-2.0）、Agent Lightning（微软，MIT）均已开源；AReaL 自报对同步训练 2.77 倍加速，但原文提醒各家数字来自各自 setup，不可直接比较。

微软发布 Maia 300：自研芯片瞄准主要 AI 推理系统

这是什么：微软今天官宣第三代自研 AI 芯片 Maia 300，定位“主要 AI 推理系统”，2027 年投产并自 2027 年起扩展至多吉瓦级 Azure 部署。官方首次给出量化指标：每兆瓦 token 产出比领先 GPU 系统高 40%、96 加速器满配机架吞吐最高为 Maia 200 的 7 倍；并披露 chiplet 架构与台积电 N2P 工艺。这是继任者的首次对外发布，不是旧闻更新。

今天微软发布第三代自研 AI 芯片 Maia 300，并把它定位为微软产品与服务的“主要 AI 推理系统”（primary AI inference system）——不只是外部 GPU 之外的补充算力，而是要当主力。芯片计划 2027 年进入生产环境。

两个官方量化指标是这次发布的核心。微软云部门执行副总裁 Scott Guthrie 给出的预期是：与领先的 GPU 系统相比，Maia 300 每兆瓦产出的 token 多 40%；在 96 颗加速器满配的机架里，token 吞吐量最高可达前代 Maia 200 的 7 倍。前者是能效账，后者是机架级算力密度账，两者都直接对应推理成本。

效率提升的战略含义写在 Guthrie 的另一句话里：从 2027 年起，Azure 的 Maia 家族将扩展到“多吉瓦级”部署，使 Maia 成为微软产品与服务的主要 AI 推理系统。换言之，这些改进将让微软不久后主要依靠自研芯片，而不是 Nvidia 和 AMD 的 GPU。

架构层面，Maia 300 换用 chiplet（芯粒）设计，基于台积电 N2P 工艺节点，把计算、内存控制器和 I/O 三类功能拆开。Azure 硬件与基础设施团队解释：这能把更多硅片面积留给计算性能，并让每种功能选用最适合自身角色的制程技术——这是“每兆瓦多 40% token”在芯片设计上的来路。

负载画像也变了。Guthrie 称 Maia 300 是为“今天正在出现的新型 AI 负载”设计的完整 AI 系统：长上下文推理、延迟敏感的对话体验、持续多步的智能体任务——恰好是当前推理开销增长最快的几类场景。

背景值得记一笔：前代 Maia 200 今年 1 月才发布，目前已在 Microsoft Copilot、GitHub Copilot、Microsoft Foundry 以及微软自有模型上承载生产负载。Guthrie 称按真实世界的 AI 服务指标衡量，Maia 200 是微软机队里表现最好的 AI 基础设施。

还有一层意图指向模型侧。微软 AI CEO Mustafa Suleyman 说，微软必须在整个技术栈上工作，“一路下沉到硅片”：在这个规模上需要一个自己拥有、并与模型协同设计的平台，因此“把微软自有模型跑在 Maia 芯片上”是其团队的关键重点。The Verge 将此解读为微软追赶 Google DeepMind、OpenAI 和 Anthropic 的路径之一。

需要保留的限定：40% 与 7 倍都是微软自己的预期口径（原文用的是 “we expect”），7 倍还带“最高可达”（up to）前缀，目前没有第三方基准验证；减依赖也不会立刻发生——投产要到 2027 年，过渡期内 Nvidia 与 AMD 仍是主要供应商。

哈佛研究：AI 编码代理让代码多三成，软件交付没变多

这是什么：哈佛研究者 Fiona Chen 与 James Stratton 基于 Jellyfish 平台 3 亿个工作事件（700 余家企业、70 万+ 员工、2021–2026.03）的汇总数据，用差分之差分回归测量 AI 编码代理的真实影响：代码行数 +30%、提交 +20%、PR +23%，但 Jira 追踪的 Issue/Epic 解决率无统计显著变化；评审时长 +49%、要求修改的 PR 占比近乎翻倍、每 PR 评论 +35%。
🔥 为什么今天值得看：这是目前对"AI 让软件交付变快"叙事规模最大的实证检验之一，且把瓶颈定位到代码评审这个具体环节而非泛泛争论。注意它的结论边界：测的是"编码收益被下游约束吸收"，不是"AI 编码无用"。对正在采购或推广编码智能体的团队，直接含义是：度量交付（Issue/Epic 解决率）而不是产出（代码行数），并把评审容量纳入容量规划。
展开正文

哈佛大学的 Fiona Chen 与 James Stratton 做了一件少见的事：不给 AI 编码智能体跑基准，而是去查企业真实工程系统的流水账。他们从工程分析平台 Jellyfish 拿到汇总数据——3 亿个"工作事件"（提交、PR 等），覆盖 700 余家软件开发企业的 70 万多名员工，时间跨度为 2021 年至 2026 年 3 月。Ars Technica 对结论的概括就是标题那句话：AI 编码代理产生更多代码，但没有产生更多软件。

方法。研究者结合直接测得的 AI 使用情况与 GitHub 活动分析，判断每家公司何时引入 AI 编码助手（以补全人类代码为主）与 AI 编码代理（按提示自主写码并提交），再对不同时点引入工具的组织做关键变量的"差分之差分"（difference of differences）回归。

写代码的一侧，数字很清楚。引入 AI 编码代理后，企业总代码行数平均增长 30%，提交数增长 20%，PR 数增长 23%。

交付的一侧，数字同样清楚。Jira 等工具追踪的 Issue 与 Epic——即完整的软件功能——解决率，在引入 AI 工具后没有统计显著变化。研究者同时确认这些问题在规模与复杂度上没有"组成性偏移"：不是问题变难了，就是解决率没动。

差额出现在评审环节。PR 从提交到合并的平均评审时长增加 49%；被要求修改的 PR 占比近乎翻倍；每条 PR 的评论数增加 35%；执行代码评审的员工占比增加 14%。研究者的表述是：编码阶段的效率提升被"生产流程的下游约束"吸收——评审流程显著变长，PR 更可能被要求返工，评审者留下更多评论。

AI 自己评审了吗？还很少。截至 2026 年 3 月，80% 的受测企业使用了某种形式的 AI 代码评审，但 AI 代理只贡献了全部评审评论的 23.3% 和全部 PR 的 10.8%——绝大多数评审工作仍由人类完成。

就业问题要按原话转述。研究者交叉比对 Jellyfish 与 LinkedIn 数据后写道，他们"无法将显著的就业变化归因于 AI"。注意这句话的边界：它既不支持"AI 导致裁员"，也不支持"AI 没有影响就业"，而是当前数据下归因做不到。

证据的边界。到 2026 年 3 月，研究中 95% 的企业已部署 AI 编码代理；数据截止之后模型能力又有重大升级；研究者也提示，"编码时间与评审时间"的权衡可能随团队经验积累而改善。换句话说，这份研究测的是当前真实工程流程的一次快照：编码收益被评审成本吃掉，而不是 AI 编码没有价值。它把瓶颈定位到一个具体、可优化的环节上。

HN 怎么看。这条讨论在 Hacker News 拿到 284 分。最有分量的一线证言来自用户 bunderbunder：今年处理的每一起严重到要走正式 RCA 流程的缺陷，"AI 生成的测试断言缺陷行为是正确的"都是促成因素之一。反方同样具体：用户 svachalek 让 AI 全量审计约 10 万行测试、判定约 6 万行近乎无用，删除后重写为覆盖更广的场景测试，途中还发现并修了一批 bug，总耗时约 2 小时——他认为人类该评审的是需求、规格与测试场景。用户 staminade 则判断，评审文化的真正变化会先出现在从第一天就执行"无人工评审"并坚持下来的初创公司，只是这类实践目前对研究不可见。围绕"该不该回到重规格开发"的老争论也在重新上演，ipsi 把这层争论概括成一句话：变更的主要成本正越来越多地变成反馈延迟，而不是开发工作量。

Codex CLI 默认后台守护进程引发争议,官方已提交回退

这是什么：GitHub issue #48195 在 HN 重新发酵(398 分):Codex CLI 自 0.157.0 起打开交互式会话就自动启动持久守护进程 codex app-server --managed-daemon,无 TTY、关窗后 reparent 到 PID 1 仍存活。9 月 28 日 breakds 已提交「默认禁用 daemon 自动启动」commit,官方开始回撤;但截至 10 月 12 日 issue 仍未关闭,#40969 也开着。
🔥 为什么今天值得看：守护进程同时打破 CLI 的三条默认契约(进程随窗口生灭、运行用户安装的二进制、不后台自更新),且官方配置参考查不到 daemon_auto_start 开关。更实质的是执行身份错位:自我复制+自我更新之后,真正执行任务的进程未必是用户安装的版本,这对接入 CI、多目录工作流与合规环境的团队是信任边界问题。
展开正文

发生了什么

OpenAI Codex CLI 的 GitHub issue #48195 在 Hacker News 重新发酵(398 分)。这份 9 月 25 日由用户 Yihua-Liu-1997 提交的 issue 指出:自 0.157.0 起,只要打开一个交互式会话,CLI 就会自动启动持久后台守护进程 codex app-server --managed-daemon——它运行在独立会话、没有 TTY,关闭所有 Codex 窗口后仍被 reparent 到 PID 1 继续存活,直到手动执行 codex app-server daemon stop 或重启机器。issue 的诉求是把 daemon_auto_start 改为 opt-in(默认关闭)。

9 月 28 日,breakds 提交了关联该 issue 的 commit「codex: disable daemon auto-start by default」,默认行为开始回撤。但截至 10 月 12 日,issue 仍处于打开状态,强杀活跃任务的关联问题 #40969 也未关闭。

为什么重要

这踩中了命令行工具的三条默认契约:后端进程随窗口生灭、运行用户亲手安装的二进制、不在后台自行更新。守护进程同时打破了三条,而官方配置参考里查不到 daemon_auto_start 这个开关——用户只能在 issue 区互相传授关闭方法。

更实质的是「执行身份」错位:当 CLI 把自己复制进受管目录、再由后台更新器随时替换,真正执行任务的进程未必是你安装的那个版本。对把编码 agent 接入 CI、多目录工作流或企业合规环境的团队,这是信任边界的实质问题。issue 下 aetherxeg-source 提出的「执行回执」提案(向客户端报告 CLI 版本、守护进程二进制摘要、代次、更新器状态、继承环境代次)正是针对这个缺口。

背景

Codex CLI 本体用 Rust 编写(HN 评论者指出),但以 npm 作为二进制分发渠道,静态链接堆出了可观体积。0.157.0 的发布说明只用一句话带过这次变更——为符合条件的交互式会话启用自动后台服务器启动、设置不兼容时提供恢复选项——没有提及常驻进程、约 374 MB 的受管包副本和每小时更新器。

关键细节

• 守护进程把整个平台包(约 374 MB,含 codex、codex-code-mode-host 及捆绑的 bwrap/zsh/rg)字节级复制到 ~/.codex/packages/app-server-daemon/releases/<版本>/ 并从副本运行,后端版本从此与 npm/brew/pacman 安装的 CLI 脱钩;Arch Linux 打包版不加 --no-daemon 直接无法启动(#48050)。

• 附带独立更新器 pid-update-loop:启动 5 分钟后首次检查、此后每小时一次,自动下载新版并重启后端;重启前只给 60 秒 drain 预算,超时对活跃任务 SIGKILL 强杀,且无法禁用(#40969)。执行 daemon stop 后更新器仍会残留——报告者观察到 70 秒后它还活着,只能手动 kill。

• 环境变量被「钉住」:守护进程继承首个启动它的会话的环境。issue 作者按次用 wrapper 设置 HTTPS_PROXY,结果后续所有出站流量都走第一个会话的代理;10 月 12 日 alexklibisz 新报告跨目录泄漏——direnv 注入的 GH_TOKEN 等变量,在第二个目录启动的会话里仍取第一个目录的值,直接打断依赖同名环境变量的工作流。

• Windows 受损最重:两位用户先后报告 CLI 不可用,其中一位称完全无法输入(felipeelopes、zdd);tagorr 在 Windows 10 LTSC 上复现,并确认在 config.toml 写 daemon_auto_start = false 可解。

• 临时关闭组合拳:codex features disable daemon_auto_start,再 codex app-server daemon stop,pkill -f 'app-server daemon pid-update-loop',最后删除 ~/.codex/packages/app-server-daemon 目录。HN 用户 whimblepop 给出更极端的加固:把 ~/.codex 下的 pid/lock 文件替换为指向 /dev/null 的符号链接并 chattr +i。

• 官方响应与文档缺口:9 月 28 日的默认禁用 commit 已关联进 issue;但 10 月 12 日 foma-agent 核查发现,官方配置参考至今没有 daemon_auto_start 的任何条目(同类开关 check_for_update_on_startup 却有记载)。发行版侧也在自救:10 月 7 日、10 月 10 日先后出现为 nix-user-chroot 打沙箱补丁升级到 0.160.1、改从官方 release 二进制打包 Codex CLI 的打包者 commit。

社区怎么说

愤怒是主色调。laurynas-karvelis 的评论「Basically - a trait of malware」(并称不认为这是意外)拿到 12 个赞,tagorr 回应说感觉正是如此——动机判断无从证实,但社区对「常驻+自更新+强杀任务」这个组合的反感是真实的。

也有冷静的技术判断。pilooch 认同应默认关闭,但指出守护进程本身有用:在 daemon server 之上构建 pi 这类自定义 harness 时,共享后端是合理架构,问题只在默认值。st396gt 提供了对照数据点:上周的 v0.160.0 在他机器上已看不到守护进程。讨论还横向蔓延成行业吐槽:sroussey 清理了 20 GB Cursor 缓存,InsideOutSanta 抱怨 Claude Code 留下的临时文件与未清理的 worktree;「Codex 体积大是因为没编译」的说法被纠正——它是 Rust 写的,只是经 npm 分发。觉得两头都糟的 rfgplk 结论是干脆自己写 harness;也有用户指出 hax 可零配置替换 codex-cli(复用已认证的 codex token)。
