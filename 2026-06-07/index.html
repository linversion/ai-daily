OpenAI 正式上线锁定模式，限制 ChatGPT 联网能力防数据外泄

这是什么：OpenAI 正式向 ChatGPT 用户推出“锁定模式”（Lockdown Mode），这是一项通过限制模型联网能力来防止提示注入攻击导致数据外泄的安全功能。开启后，ChatGPT 将无法访问实时网页、不能检索和显示网页图像、无法使用深度研究和代理模式。该功能于 2026 年 6 月 5 日开始向免费、Go、Plus、Pro 及自助 ChatGPT Business 账户滚动推出。
🔥 为什么今天值得看：提示注入攻击是 LLM 应用面临的核心安全威胁之一，攻击者可通过隐藏指令诱导模型将用户敏感数据发送至外部服务器。锁定模式采用“断网”策略，不试图识别恶意指令，而是直接限制模型的行为能力，为处理敏感数据提供了一种简单但有效的防护思路。不过 OpenAI 也承认该模式无法完全免疫提示注入，且技术细节未公开，外界难以评估其真实防护边界。

OpenAI 本周正式向 ChatGPT 用户推出了一项名为“锁定模式”（Lockdown Mode）的安全功能，专门用来应对提示注入攻击中敏感数据被窃取的风险。Simon Willison 和 Hacker News 等社区对此进行了讨论和实测。

这个功能的逻辑很直接——当攻击者试图通过提示注入让 ChatGPT 把对话内容发送到外部服务器时，锁定模式会直接切断数据传输的通道。具体来说，开启后 ChatGPT 将无法访问实时网页，只能读取缓存内容；网页图像检索和显示功能会被禁用，但模型仍然可以生成新图像；深度研究和代理模式也会被关闭。相当于给 ChatGPT 套上了一层网络隔离罩，即使攻击者成功注入了恶意指令，模型也无法执行需要联网的操作。

提示注入攻击一直是 LLM 应用面临的老大难问题。攻击者可以在网页内容、上传文件甚至邮件中埋下隐藏指令，诱导模型将用户的敏感对话内容打包发送到指定地址。传统的防御思路是在输入输出端加护栏检测，但锁定模式走的是另一条路——不试图识别恶意指令，而是直接限制模型的行为能力。这种“断网”策略虽然简单粗暴，但在处理敏感数据时确实能大幅降低泄露风险。

不过 Simon Willison 在测试后也指出了几个关键限制。首先，OpenAI 没有公开锁定模式的具体技术实现细节，外界无法判断它的防护边界到底在哪里——是纯粹的前端限制，还是模型层面也做了约束？其次，官方在说明中也承认，锁定模式并不能完全免疫提示注入攻击，只是降低了数据外泄的风险。另外，这个功能目前仅向 ChatGPT Business 账户和部分符合条件的个人账户开放，覆盖范围有限。

社区讨论中，有开发者认为这种“功能降级”式的安全策略虽然有效，但用户体验牺牲较大——不能联网意味着很多实用场景直接失效。也有人提到，像 Guardrails AI、LangChain 的提示注入检测模块以及开源工具 Rebuff 等替代方案，可以在不牺牲功能的前提下提供更灵活的安全防护。

特朗普政府或入股OpenAI，AI红利能否分给普通美国人

这是什么：特朗普政府正在与OpenAI进行谈判，探讨政府直接持有OpenAI股权的可能性。核心构想是，政府作为股东获得的分红将注入公共财富基金，让美国公民分享AI产业增长带来的经济红利。这是首次有具体报道披露双方就股权入股进行实质性讨论。
🔥 为什么今天值得看：AI创造的财富正快速集中到少数科技公司手中，普通公众难以直接受益。政府入股模式试图在税收和监管之外开辟第三条路径——通过所有权分享实现财富再分配。如果落地，这将开创政府参与私营AI公司利润分配的先例，影响全球AI治理和产业政策的走向。

特朗普政府正在与OpenAI进行谈判，可能通过持有这家AI公司股权的方式，让美国公众从人工智能的经济增长中分得一杯羹。TechCrunch今天独家报道了这一消息，称双方正在探讨一种前所未有的公私合作模式。

这个想法听起来有些激进——政府直接入股一家私营AI公司，但背后的逻辑并不复杂。AI带来的财富正在快速集中到少数科技巨头手中，而普通美国人除了使用产品外，很难直接分享到产业爆发的红利。特朗普政府的思路是，如果OpenAI未来创造巨额利润，政府作为股东获得的分红可以注入一个类似阿拉斯加永久基金的公共财富池，最终以现金分红或公共服务的形式返还给公民。

不过，这个计划目前还停留在非常早期的讨论阶段。OpenAI复杂的公司结构本身就是一大障碍——它由一个非营利母公司控制着营利性子公司，股权设计上对利润分配有严格的上限。政府入股意味着需要重新设计这套架构，而这可能触动现有投资者和员工的利益。

政治层面的阻力同样不可忽视。佛蒙特州参议员伯尼·桑德斯已经提出了一项针对AI公司超额利润的税收提案，主张用征税而非持股的方式来重新分配AI财富。批评者担心，政府直接持有AI公司股权可能引发利益冲突——当监管者同时是被监管者的股东时，如何在产业政策和公共利益之间保持平衡将成为一个棘手的问题。

值得注意的是，这并非美国政府首次尝试以公共资源形式介入AI发展。此前推出的国家AI研究资源计划（NAIRR）旨在为学术界提供共享的AI算力基础设施，但规模远不及直接入股一家估值数千亿美元的行业龙头。放眼全球，欧盟和中国也在以不同形式推动AI发展的公共参与，但美国政府直接持股头部AI公司的做法尚无先例。

目前OpenAI和特朗普政府方面都未对谈判细节作出正式回应。考虑到2026年中期选举临近，这项提案能否从谈判桌走向立法程序，还存在巨大的不确定性。

今天 Hacker News 上一条关于标普 500 指数委员会拒绝 SpaceX、OpenAI 和 Anthropic 快速纳入指数的讨论引发了广泛关注。这三家公司虽然估值惊人、市场影响力巨大，但都因为不满足指数现行的盈利和上市时间要求，被挡在了全球最受追踪的股指门外。

目前这条讨论还停留在社区层面，标普道琼斯指数公司并未发布官方声明。但话题本身触及了指数基金、公司治理和公开市场功能的深层问题，在被动投资规模持续膨胀的背景下，类似的争议只会越来越多。

Simon Willison 发布 MicroPython-WASM 沙箱，可在 Python 应用中安全执行不受信代码

这是什么：Simon Willison 发布 micropython-wasm 项目（alpha 版本），将 MicroPython 解释器编译为 WebAssembly 模块，让开发者能在 Python 应用中安全执行不受信任的代码。配套的 datasette-agent-micropython 插件展示了在 AI Agent 场景下的用法。
🔥 为什么今天值得看：Python 生态长期缺乏轻量级的代码安全执行方案。现有替代品各有短板：Pyodide 体积大、RestrictedPython 只能做静态限制、Docker 级别的隔离太重。micropython-wasm 通过 WASM 沙箱提供了内存/CPU 硬限制、文件网络访问控制、以及宿主函数调用机制，在安全性和可用性之间找到了一个新平衡点，特别适合 AI Agent 需要动态执行 LLM 生成代码的场景。

知名开发者 Simon Willison 今天发布了一个实验性项目——micropython-wasm，它把 MicroPython 解释器编译成了 WebAssembly 模块，让开发者能在自己的 Python 应用里安全地运行不受信任的代码。配套的 datasette-agent-micropython 插件则展示了它在 AI Agent 场景下的用法：让 LLM 生成的代码在一个受限环境里执行，不用担心把服务器搞崩。

这个项目的核心思路很直接——用 WebAssembly 的沙箱隔离能力，加上 MicroPython 本身对系统资源的精简控制，给 Python 生态补上了一块“安全执行”的拼图。它通过 wasmtime 这个 Python 库来加载 WASM 模块，可以限制内存上限和 CPU 指令数，还能控制文件系统和网络访问的开关。更巧妙的是，它支持“宿主函数调用”——沙箱里的代码可以反过来请求宿主 Python 程序执行特定操作，比如读写数据库或调用 API，但全程受宿主控制，不是让沙箱直接碰这些资源。

目前项目处于 alpha 阶段，功能已经包括持久化解释器状态（多次调用间保留变量和导入的模块）、队列驱动的会话管理（避免并发冲突），以及从 PyPI 直接安装依赖的便利性。不过 Willison 本人也坦承，MicroPython 是 CPython 的子集，很多标准库和第三方包跑不了；WASM 沙箱也不是绝对安全的堡垒，像 Spectre 这类侧信道攻击理论上仍可能突破隔离。社区里有人拿它跟 Pyodide 对比——后者是把完整的 CPython 编译到 WASM，兼容性好得多，但体积和启动速度也大不少。micropython-wasm 更像一个轻量级、可控的折中方案，适合对安全性和资源限制有明确需求的场景。

如果你在折腾 AI Agent 或者需要给用户提供在线 Python 执行环境，这个项目值得关注——它解决的不是“能不能跑 Python”的问题，而是“跑坏了怎么办”的问题。

CopilotKit 新增自学习与聊天平台集成，AI 代理能跨 Slack 和 Teams 运行了

这是什么：CopilotKit 发布了两项早期访问功能：基于人类反馈的自学习能力（CLHF），让 AI 代理能在实际使用中持续优化行为；以及 Slack 和 Microsoft Teams 集成，使代理的运行范围从浏览器扩展到聊天平台。同时更新了自有 AG-UI 协议的采用方名单，包括 Google、LangChain、AWS、Microsoft、Mastra、PydanticAI 等。
🔥 为什么今天值得看：这次更新解决了 AI 代理的“平台孤岛”问题——同一个代理现在可以同时驱动 Web 应用、移动端和聊天工具，状态实时同步。自学习能力则让代理不再是静态部署，而是能根据用户反馈动态进化。对于需要跨平台部署 AI 应用的团队，这减少了为每个平台单独开发集成层的重复工作。但 AG-UI 协议仍为私有协议，采用方名单虽亮眼，实际生态影响力有待验证。

前端 AI 框架 CopilotKit 今天放出了一波重要更新——新增了基于人类反馈的自学习功能，同时把代理的运行范围从浏览器扩展到了 Slack 和 Microsoft Teams。这两项能力目前都处于早期访问阶段，但方向很明确：让同一个 AI 代理同时驱动 Web 应用、移动端和聊天平台。

CopilotKit 本身是一个全栈前端框架，专门解决开发者在多平台上集成 AI 代理和生成式 UI 时的碎片化问题。它支持 React、Angular、Vue、React Native 等主流前端技术栈，核心卖点是通过统一的 SDK 和自有的 AG-UI 协议，让代理的状态和界面在不同平台间实时同步。这次新增的自学习能力，官方称为 CLHF（基于人类反馈的持续学习），意味着代理可以在实际使用中根据用户行为不断调整策略，而不是上线后就一成不变。Slack 和 Teams 的集成则进一步打破了代理只能在应用内运行的局限——想象一下，同一个客服代理，用户在网页上提问时它在侧边栏弹出生成式 UI，切换到 Slack 后它还能接着刚才的对话继续处理。

不过，这次更新也伴随着一些需要冷静看待的信号。AG-UI 协议虽然是 CopilotKit 的核心差异化武器，官方列出的采用方名单也颇为亮眼——Google、LangChain、AWS、Microsoft、Mastra、PydanticAI 等都在列——但该协议目前仍是 CopilotKit 团队主导的私有协议，尚未成为行业标准。此外，Slack 和 Teams 集成的实际效果缺乏第三方验证，平台支持的声明可能存在过度包装的风险。在开源社区，CopilotKit 面临的竞争也不小：LangChain 在代理构建领域根基深厚，Vercel AI SDK 在生成式 UI 和流式渲染方面更轻量且与 Next.js 生态深度绑定。CopilotKit 的优势在于提供了一站式多平台方案，但这也意味着更高的集成成本和协议锁定风险。
